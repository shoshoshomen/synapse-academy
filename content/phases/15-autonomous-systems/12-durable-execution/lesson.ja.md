# 長時間実行バックグラウンドエージェント：永続的実行

> 本番のロングホライズンエージェントは`while True`では実行されない。すべてのLLM呼び出しはチェックポイント、リトライ、リプレイを持つアクティビティになる。TemporalのOpenAI Agents SDK統合は2026年3月にGAになった。Claude Code Routines（Anthropic）は永続的なローカルプロセスなしでスケジュールされたClaude Code呼び出しを実行する。セッションは人間入力で一時停止し、デプロイを生き延び、`thread_id`でキーされた最新のチェックポイントから再開する。新しいエルゴノミクスの背後には古いパターン——ワークフローオーケストレーション——が1つの新しい入力と共にある：LLM呼び出しは回復時に決定論的にリプレイされなければならない非決定論的なアクティビティとして。


## 問題

4時間実行するエージェントを考える。3つのツールを呼び出し、ユーザーに2回確認し、40回のLLM呼び出しを行う。途中で実行しているホストが再起動する。何が起きるか？

- 素朴な`while True`ループの場合：すべてが失われる。実行はゼロから再開する。3つのツール呼び出し（本物の副作用を伴う）が再び実行される。ユーザーはすでに承認したことのために再度確認される。40回のLLM呼び出しが再請求される。
- 永続的実行の場合：実行は最も最近のチェックポイントから再開する。すでに完了したアクティビティは再実行されない；その結果は永続ログからリプレイされる。ユーザーはすでに承認したことを再承認しない。すでに行われたLLM呼び出しは再請求されない。

これはワークフローエンジンが10年間出荷してきたのと同じパターンだ（Temporal、Cadence、UberのCherami）。新しいのはLLM呼び出しが今やアクティビティの一種——非決定論的で、高価で、副作用を持つ——であり、このパターンにすっきり収まることだ。

レッスンの一貫したテーマ：ロングホライズンの信頼性が低下する（METRは「35分の劣化」を観察する——成功率はホライズンと約2乗で低下する）。永続的実行は信頼性プロファイルがサポートするよりも長い実行を可能にする。設計が正しければ安全に、間違っていれば安全でなく失敗する新しい方法だ。

## コンセプト

### アクティビティ、ワークフロー、リプレイ

- **ワークフロー**：決定論的なオーケストレーションコード。アクティビティのシーケンス、ブランチ、待機を定義する。驚くべき分岐なしにイベントログからリプレイできるよう決定論的でなければならない。
- **アクティビティ**：非決定論的で、失敗する可能性のある作業単位。LLM呼び出し、ツール呼び出し、ファイル書き込み、HTTPリクエスト。各アクティビティはその入力と（完了したら）その出力でログに記録される。
- **イベントログ**：永続的なバッキングストア。すべてのアクティビティの開始、完了、失敗、リトライ、そしてすべてのワークフロー決定が記録される。
- **リプレイ**：回復時に、ワークフローコードが最初から再実行する；すでに完了したすべてのアクティビティは再実行せずにログに記録された結果を返す。まだ完了していないアクティビティのみが実際に実行される。

これはReactが仮想DOMに対してレンダリングするか、Gitがコミットから作業ツリーを再構築するのと同じ形だ。オーケストレーターの決定論が永続性を安価にするものだ。

### LLM呼び出しがパターンに収まる理由

LLM呼び出しは：
- 非決定論的（温度 > 0；温度0でもモデルバージョン間でドリフトする）。
- 高価（お金とレイテンシ）。
- 失敗する可能性がある（レート制限、タイムアウト）。
- 副作用を持つ（ツールを呼び出す場合）。

これはまさにアクティビティプロファイルだ。すべてのLLM呼び出しをアクティビティとしてラップすることで、指数バックオフ付きのリトライ、再起動をまたいだチェックポイント、デバッグのための再生可能なトレースが得られる。

### `thread_id`でキーされたチェックポイント

LangGraph、Microsoft Agent Framework、Cloudflare Durable Objects、Claude Code Routinesはすべて同じAPIの形に収束した：`thread_id`（または同等のもの）がセッションを識別し；各状態遷移はバックエンドに永続する（デフォルトはPostgreSQL、開発はSQLite、キャッシュはRedis）；再開は最新のチェックポイントを読む。

バックエンドの選択が重要だ：

- **PostgreSQL**：耐久性があり、クエリ可能で、デプロイを生き延びる。LangGraphのデフォルト。
- **SQLite**：ローカル開発のみ；ホストをまたいでデータが失われる。
- **Redis**：AOF/スナップショットが設定されていない限り速いがエフェメラル。
- **Cloudflare Durable Objects**：透過的に分散；ユニークキーでスコープされ；時間から週にわたって生き残る。

### 人間入力を第一級の状態として

提案-コミット（レッスン15）は永続的な「人間を待つ」状態が必要だ。ワークフローは一時停止し、外部キューは保留中のリクエストを保持し、承認がその正確なポイントから再開する。永続性なしでこれはベストエフォートだ；それがあれば、一夜の承認が届いて翌朝ワークフローが続く。

### 35分の劣化

METRは、測定されたすべてのエージェントクラスが連続操作の約35分を超えると信頼性の低下を示すことを観察した。タスク期間を倍にすることで失敗率が約4倍になる。永続的実行はこれを修正しない；信頼性プロファイルがサポートするよりも長く実行することを可能にする。安全なパターンは永続性を、再入時に新鮮なHITLを必要とするチェックポイントと、総コンピューティングをウォールクロック時間に関わらずキャップするバジェットキルスイッチ（レッスン13）と組み合わせることだ。

### 永続的実行が間違った答えのとき

- 人間入力なしで数分より短い実行。オーバーヘッドが利益を上回る。
- 厳密に読み取り専用の情報検索。
- 正確さが1つのコンテキストウィンドウ内でエンドツーエンドを必要とするタスク（いくつかの推論タスク；いくつかのワンショット生成）。

## 使ってみる

`code/main.py`はstdlib Pythonで最小限の永続的実行エンジンを実装する。サポート：

- 入力と出力をJSONイベントログに記録する`@activity`デコレーター。
- アクティビティをシーケンスするワークフロー関数。
- 再実行せずに完了したアクティビティをリプレイする`run_or_replay(workflow, event_log)`関数。

ドライバーは3アクティビティのワークフローをシミュレートし、途中でクラッシュし、（a）素朴なリトライがすべてを再実行するのと（b）リプレイが欠けているアクティビティのみを実行するのを示す。

## 成果物を出す

`outputs/skill-durable-execution-review.md`は提案されたロングランニングエージェント展開の正しい永続的実行の形をレビューする：アクティビティ、決定論、チェックポイントバックエンド、人間入力状態、HITL-on-resumeポリシー。

## 演習

1. `code/main.py`を実行する。素朴なリトライとリプレイの間のアクティビティ実行カウントの違いを観察する。クラッシュポイントを変えてリプレイカウントがそれに応じて変わることを示す。

2. おもちゃのエンジンを`thread_id`を明示的に使用するよう変換する。エンジンを共有する2つの並列セッションをシミュレートし、そのイベントログが衝突しないことを確認する。

3. おもちゃのエンジンの1つのアクティビティを取る。非決定論（ワークフロー決定内のウォールクロックタイムスタンプ）を導入する。リプレイでの分岐を示す。実際のエンジンがこれをどのように処理するかを説明する（副作用登録、`Workflow.now()`API）。

4. LangChainの「本番のディープエージェントの背後のランタイム」の投稿を読む。ランタイムが永続するすべての状態をリストアップし、各状態がカバーする失敗モードに名前をつける。

5. 6時間の自律コーディングタスクのチェックポイントポリシーを設計する。どこでチェックポイントを設定するか？クラッシュ後の再開はどのように見えるか？新鮮なHITLが必要なものは何か？

## キーワード

| 用語 | よく言われること | 実際の意味 |
|---|---|---|
| ワークフロー | 「エージェントのスクリプト」 | 決定論的なオーケストレーションコード；イベントログからリプレイ可能 |
| アクティビティ | 「ステップ」 | 非決定論的な単位（LLM呼び出し、ツール呼び出し）；前後にログ記録 |
| イベントログ | 「バッキングストア」 | すべての状態遷移の永続的な記録 |
| リプレイ | 「再開」 | ワークフローを再実行；完了したアクティビティは再実行せずにログに記録された結果を返す |
| チェックポイント | 「セーブポイント」 | thread_idでキーされた永続状態；再開時は最新が勝つ |
| thread_id | 「セッションキー」 | 永続状態をスコープする識別子 |
| 35分の劣化 | 「信頼性の低下」 | METR：成功率はホライズンと約2乗で低下する |
| 非決定論 | 「リプレイ時のドリフト」 | ウォールクロック、ランダム、LLM出力；副作用として登録されなければならない |
