# Batch API — 業界標準となった50%割引

> 主要プロバイダーはすべて、50%割引と約24時間のターンアラウンドを持つ非同期バッチAPIを提供している。OpenAI・Anthropic・Google、そしてほとんどの推論プラットフォーム（Fireworksのバッチティア、Togetherのバッチ）も同じパターンを実装している。バッチとプロンプトキャッシュを組み合わせれば、夜間パイプラインのコストは同期・非キャッシュの約10%まで下がる。ルールはシンプルだ：インタラクティブでないものはバッチに回せ。コンテンツ生成パイプライン、ドキュメント分類、データ抽出、レポート生成、大量ラベリング、カタログタグ付け——24時間のレイテンシを許容できるものはすべて、バッチに移さない限りコストを無駄にしている。2026年の本番パターンは、すべての新しいLLMワークロードを3つのレーンに振り分けることだ：インタラクティブ（キャッシュ付き同期）、セミインタラクティブ（フォールバック付き非同期キュー）、バッチ（夜間・キャッシュ入力スタック）。インタラクティブのふりをしているが数分のレイテンシを許容できるワークロードは大部分を無駄にしている。


## 学習目標

- 3つのプロバイダーバッチAPI（OpenAI、Anthropic、Google）と、共通の50%割引＋24時間ターンアラウンド保証を挙げる。
- 夜間分類ワークロードにおけるバッチ＋キャッシュ入力のスタックコストを計算し、同期・非キャッシュのベースラインと比較する。
- ワークロードをインタラクティブ／セミインタラクティブ／バッチに振り分けて根拠を説明する。
- 2つの落とし穴を挙げる：部分的インタラクティブ性（ユーザーが24時間より早い応答を期待）と出力スキーマのずれ（バッチファイル形式がプロバイダーごとに異なる）。

## 問題の背景

チームは夜間のレポート生成パイプラインをリリースした。50,000件のドキュメントを各自要約し、要約をクラスタリングし、エグゼクティブブリーフを作成する。同期で実行すると1晩4時間かかり、コストは$2,000/夜。バッチAPIの話を聞いた。

バッチで50%オフになる。さらに全50,000件の呼び出しで共有するシステムプロンプト（4Kトークン）のプロンプトキャッシュを有効にする。スタックすると請求は$180/夜——ベースラインの約9%。同じパイプラインで設定変更3つだけ。

バッチはLLMコストのツールキットの中で最も安いレバーだが、誰も引かない。理由は主に組織的なものだ：SLAが実際には「朝までに」なのに、チームは「リアルタイム」と考えてしまう。このレッスンは、請求の90%をそのままにしないためのものだ。

## コンセプト

### 3つのバッチAPI

**OpenAI Batch API**: リクエストのリストを含むJSONLファイルをアップロード。24時間ターンアラウンドを保証（実際は約2〜8時間）。入出力トークンで50%割引。`/v1/batches`エンドポイント。キャッシュ対象の入力にはキャッシュ入力価格も上乗せされる。

**Anthropic Message Batches**: JSONLアップロード。24時間ターンアラウンド。50%割引。`cache_control`をサポート——キャッシュの書き込みは明示的、読み取りはバッチ内で自動的に行われる。

**Google Vertex AI Batch Prediction**: BigQueryまたはGCS入力。Geminiに対して同様の50%割引。Vertexパイプラインと統合。

### セマンティクス：非同期であって遅いのではない

バッチとは「24時間以内に返す約束」であり、「24時間かかる」という意味ではない。典型的なP50は2〜6時間。プロバイダーはGPUインベントリが低稼働のオフピーク時間帯にバッチをスケジュールする。

### キャッシュとスタックする

同じ4Kトークンのシステムプロンプトを持つ50,000件のドキュメント要約の場合：

- 同期・非キャッシュ：50000 × ($input × 4000 + $output × 200)をフルレートで。
- 同期・キャッシュ：システムプロンプトは最初の書き込み後にキャッシュされ、残り49,999件は入力が10倍安くなる。
- バッチ・キャッシュ：上記すべてに加えて読み書き両方で50%割引。

スタック：バッチ＋キャッシュ = 同期・非キャッシュの請求の約10%。夜間に実行し共有システムプロンプトがあるワークロードはこれを使うべきだ。

### ワークロードの振り分け

**インタラクティブ** — ユーザーが応答を待つ。TTFTが重要。プロンプトキャッシュ付き同期呼び出し。バッチにはできない。

**セミインタラクティブ** — ユーザーがタスクを送信し、数分後に確認する。バッチが利用できない場合の同期フォールバック付き非同期キュー。中程度のボリュームのRAGインデックスなど。

**バッチ** — ユーザーが「朝までに」または「次の時間までに」結果を期待する。コンテンツパイプライン、大規模分類、オフライン分析。常にバッチ、常にキャッシュをスタックする。

よくある間違い：パイプラインが本番だからといってすべてをインタラクティブに分類してしまうこと。本番はレイテンシ仕様ではない——SLAがそれだ。

### 部分的インタラクティブ性の落とし穴

一部の機能はインタラクティブに見えるが5〜10分は許容できる。例：「更新」ボタン付きの夜間顧客ヘルスレポート。ユーザーが更新をクリック；10分待つのは問題ない。チームはそれを同期でリリースした。50件の同時更新は、バッチ送信してメール配信するコストの10倍かかる。

問うべき質問：「このユーザーにとって24時間はどういう意味か？」答えが「気づかないだろう」なら、バッチにしろ。

### 出力スキーマの落とし穴

バッチファイル形式はプロバイダーごとに異なる：

- OpenAI：JSONL、1行に1リクエスト。
- Anthropic：JSONL、1行に1メッセージ；レスポンス形式が埋め込まれる。
- Vertex：BigQueryテーブルまたはTFRecord付きGCSプレフィックス。

プロバイダー間で「1つのバッチクライアント」を書くということは、プロバイダーごとのアダプタコードを意味する。マルチプロバイダーバッチを宣伝するゲートウェイ（Portkey、LiteLLMの一部ティア）でも、生のフォーマットをそのままラップしているに過ぎない。

### 覚えておくべき数値

- プロバイダー全体のバッチ割引：入出力ともに一律50%。
- ターンアラウンドSLA：24時間保証、典型的なP50は2〜6時間。
- バッチ＋キャッシュ入力をスタック：同期・非キャッシュコストの約10%。
- ワークロードの振り分けルール：24時間のレイテンシが許容できる場合は常にバッチ。

## キーワード

| 用語 | よく言われる表現 | 実際の意味 |
|------|----------------|------------|
| Batch API | 「非同期割引」 | 24時間ターンアラウンドで50%オフ |
| JSONL | 「バッチフォーマット」 | 1行に1つのJSONリクエスト；OpenAI/Anthropicの標準 |
| Message Batches | 「Anthropicバッチ」 | AnthropicのバッチAPI製品名 |
| Batch prediction | 「Vertexバッチ」 | Vertex AIのバッチAPI製品 |
| Turnaround SLA | 「24時間の約束」 | 保証であり典型値ではない；典型値は2〜6時間 |
| Workload triage | 「インタラクティブ性の判断」 | インタラクティブ／セミ／バッチのルーティング判断 |
| Output schema | 「レスポンスフォーマット」 | プロバイダーごとのJSONLレイアウト；可搬性なし |
| Stacked discount | 「バッチ＋キャッシュ」 | 両方適用時に非キャッシュ同期の請求の約10% |
