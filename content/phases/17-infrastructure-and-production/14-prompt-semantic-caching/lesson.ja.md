# プロンプトキャッシングとセマンティックキャッシングの経済学

> **価格スナップショットは2026年4月時点。** 以下の数値はこのレッスン公開時点でのベンダーレートカードを反映している；引用する前にリンク先のドキュメントで確認すること。

> キャッシングは2つの層で発生する。L2（プロバイダーレベル）のプロンプト/プレフィックスキャッシングは繰り返されるプレフィックスのアテンションKVを再利用する — Anthropicのプロンプトキャッシングドキュメントは長いプロンプトでコスト最大90%削減、レイテンシ85%削減を謳っている；Claude 3.5 Sonnetのキャッシュ読み込みは$0.30/M対フレッシュ$3.00/M、5分TTLで2x書き込みプレミアム、1時間TTLオプション（docs.anthropic.com、2026年4月）。OpenAIのプロンプトキャッシングは1024トークン以上のプロンプトに自動適用され、キャッシュ済み入力をフレッシュの約90%割引で価格設定する（platform.openai.com、2026年4月）；正確なモデルごとのキャッシュ済みレートはライブレートカードによる。L1（アプリレベル）のセマンティックキャッシングは埋め込み類似度ヒット時にLLMを完全にスキップする。ベンダーの「95%精度」はマッチ正確性を指し、ヒット率ではない — 報告されている本番ヒット率は10%（オープンエンドチャット）から70%（構造化FAQ）の範囲；どのプロバイダーも公式ベースラインを公開していないため、コミュニティテレメトリーとして扱うこと。本番の落とし穴：並列化はキャッシングを壊す（最初のキャッシュ書き込みの前にN件の並列リクエストを発行すると支出が数倍に膨らむことがある）、プレフィックス内の動的コンテンツはキャッシュヒットを完全に妨げる。ProjectDiscoveryは動的テキストをキャッシュ可能なプレフィックスから移動することでヒット率を7%から74%に改善したと報告した（2025年11月）。


## 学習目標

- L2プロンプト/プレフィックスキャッシング（プロバイダーでのKV再利用）とL1セマンティックキャッシング（類似プロンプトでのLLMバイパス）を区別する。
- Anthropicの`cache_control`明示マーキングと2つのTTLオプション（5分対1時間）とその価格乗数を説明する。
- ヒット率、プロンプト/レスポンスミックス、トークン価格を考慮して期待される月次節約を計算する。
- 請求を5〜10倍に膨らませる並列化アンチパターンとヒット率を崩壊させる動的コンテンツアンチパターンを挙げる。

## 問題

RAGサービスにプロンプトキャッシングを追加する。請求は横ばいのまま。ヒット率を測定すると7%。プロンプトは静的に見えるが実はそうではない — システムプロンプトには分単位にフォーマットされた現在日時、リクエストID、多様性のためのランダム化されたサンプル順序が含まれている。すべてのリクエストが新しいキャッシュエントリを書き込み、ゼロを読み込む。

別途、エージェントはユーザーの質問ごとに10件の並列ツール呼び出しを行う。すべて10件が最初のキャッシュ書き込みが完了する前にプロバイダーに到着する。10件の書き込み、ゼロの読み込み。「キャッシュ使用時」で想定していたコストの5〜10倍の請求になっている。

キャッシングはプロトコルであり、フラグではない。2つの層、2つの異なる失敗モード。

## コンセプト

### L2 — プロバイダープロンプト/プレフィックスキャッシング

プロバイダーはキャッシュ可能なプレフィックスのアテンションKVを保存し、プレフィックスにマッチする次のリクエストで再利用する。書き込みコストを一度払い、読み込みはほぼ無料。

**Anthropic（Claude 3.5 / 3.7 / 4シリーズ）**：リクエストに明示的な`cache_control`マーカー。どのブロックがキャッシュ可能かをタグ付けする。TTL：5分（書き込みコストは基本料金の1.25倍）または1時間（書き込みコストは2倍）。キャッシュ読み込み：Claude 3.5 Sonnetで$0.30/M対フレッシュ$3.00/M — 10倍安価（docs.anthropic.com、2026年4月時点）。レートはモデルごとに異なる（Opus/Haikuは別途公開）；常にライブ価格ページでクロスチェックすること。

**OpenAI**：1024トークン以上のプロンプトに自動キャッシング（platform.openai.com、2026年4月）。明示的なフラグなし。キャッシュ済み入力は現在のgpt-4o/gpt-5レートカードでフレッシュより約10倍安価。ドキュメントもリリースノートも公式ヒット率ベースラインを公開していない；コミュニティレポートは慎重なプロンプト設計で30〜60%周辺に集まる。`usage.cached_tokens`を監視して自分のヒット率を計測する。

**Google（Gemini）**：明示的なAPI経由のコンテキストキャッシング；100万トークンコンテキストはキャッシングをさらに有利にする。

**セルフホスト（vLLM、SGLang）**：フェーズ17·06でRadixAttentionをカバー — 自分のコンピュートで同じパターン。

### L1 — アプリレベルセマンティックキャッシング

LLMを呼び出す前に、プロンプトをハッシュし、埋め込み、類似のキャッシュ済みリクエストを探す（コサイン類似度が通常0.95以上のしきい値以上）。ヒットすればキャッシュ済みレスポンスを返す。ミスすればLLMを呼び出して結果をキャッシュする。

オープンソース：Redis Vector Similarity、GPTCache、Qdrant。商用：Portkey Cache、Helicone Cache。

ベンダーの精度主張は返されたキャッシュ済みレスポンスが意味的に適切だった頻度を指す — ヒットした頻度ではない。本番ヒット率：

- オープンエンドチャット：10〜15%。
- 構造化FAQ/サポート：40〜70%。
- コード質問：20〜30%（小さなバリアントがヒットを壊す）。
- プロンプトを繰り返す音声エージェント：50〜80%（音声正規化された固定セット）。

### 並列化アンチパターン

エージェントが10件のツール呼び出しを並列で行う。すべて10件に同じ4Kトークンのシステムプロンプトがある。Anthropicのキャッシュ書き込みはリクエストごと；最初のキャッシュ書き込みはプロバイダーがプロンプトを見てから約300ms後に完了する。リクエスト2〜10は同じミリ秒ウィンドウに到着し、それぞれキャッシュミスを見る。書き込みプレミアムを10件分払い、読み込み割引はゼロ。

修正：シーケンシャルファーストでバッチ処理 — リクエスト1を単独で行い、1のキャッシュが準備できたら2〜10を発火する。最初のツール呼び出しに300msが加わる；請求を5〜10倍節約する。

### 動的コンテンツアンチパターン

システムプロンプトはこのように見える：

```
You are a helpful assistant. The current time is 14:32:17.
User ID: abc123. Today is Tuesday...
```

すべてのリクエストが一意。すべてのリクエストが書き込む。ヒットはゼロ。

修正：完全に静的なものをキャッシュ可能なプレフィックスに移動し、動的コンテンツをキャッシュ境界の後に追加する：

```
[cacheable]
You are a helpful assistant. [rules, examples, instructions]
[/cacheable]
[dynamic, not cached]
Current time: 14:32:17. User: abc123.
```

ProjectDiscoveryはこの方法でキャッシュヒット率を7%から74%に改善し、その仕組みを公開した。

### 夜間ワークロードのためにバッチ+キャッシュを積み重ねる

バッチAPI（フェーズ17·15）は24時間ターンアラウンドで50%割引を提供する。その上にキャッシュ済み入力を重ねると約10倍の追加割引になる。夜間分類、ラベリング、レポート生成ワークロードは積み重ねることで同期・未キャッシュコストの約10%まで削減できる。

### 覚えておくべき数値

価格ポイントはリンク先のベンダードキュメントから2026年4月に取得したもので数ヶ月ごとに変動する — 依拠する前に再確認すること。

- Anthropicのキャッシュ読み込み：Claude 3.5 Sonnetで$0.30/M、フレッシュ入力より約10倍安価（docs.anthropic.com）。
- Anthropicのキャッシュ書き込みプレミアム：1.25倍（5分TTL）または2倍（1時間TTL）。
- OpenAI自動キャッシュ：1024トークン以上のプロンプトに適用；キャッシュ済み入力は現在のレートカードでフレッシュ入力の約10%の価格（platform.openai.com）。
- セマンティックキャッシュヒット率（コミュニティ報告）：オープンチャットで約10%；構造化FAQで最大約70%。ベンダーが文書化したベースラインではない。
- ProjectDiscovery：プレフィックスから動的を移動することで7%→74%ヒット率（プロジェクトブログ、2025年11月）。
- 並列化アンチパターン：N件の並列リクエストが最初のキャッシュ書き込みを見逃す場合の請求5〜10倍膨張の典型的な報告。

## 使ってみる

`code/main.py`は混合ワークロードでL1+L2キャッシングをシミュレートする。ヒット率、請求を報告し、並列化ペナルティを示す。

## 成果物を出す

このレッスンは`outputs/skill-cache-auditor.md`を作成する。プロンプトテンプレートとトラフィックを与えるとキャッシュ可能性を監査し再構築を推奨する。

## 演習

1. `code/main.py`を実行する。並列化フラグを切り替える。請求はどれくらい変わるか？
2. システムプロンプトに日付がある。移動する。ヒット率の変化を数式で示す。
3. リクエスト到着率を考慮して、1時間TTL（2倍書き込み）対5分TTL（1.25倍書き込み）の損益分岐点を計算する。
4. セマンティックキャッシュを0.95しきい値では20%ヒットする。0.85では50%ヒットするが誤ったキャッシュ済みレスポンスが見られる。正しいしきい値を選んで理由を述べる。
5. ユーザーの質問ごとに10件の並列サブクエリをバッチ処理する。エンドツーエンドレイテンシを増やさずにキャッシュフレンドリーに書き直す。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------|
| L2プロンプトキャッシュ | 「プレフィックスキャッシュ」 | プロバイダーが繰り返されるプレフィックスのKVを保存する |
| `cache_control` | 「Anthropicキャッシュマーカー」 | キャッシュ可能なブロックをマーキングする明示的な属性 |
| キャッシュ書き込みプレミアム | 「書き込み税」 | 最初のミスからキャッシュへの追加コスト（1.25倍または2倍） |
| L1セマンティックキャッシュ | 「埋め込みキャッシュ」 | LLMを呼び出す前のアプリレベルのハッシュ＆埋め込み |
| GPTCache | 「LLMキャッシングライブラリ」 | 人気のあるOSS L1キャッシュライブラリ |
| キャッシュヒット率 | 「ヒット/合計」 | キャッシュから提供されたリクエストの割合 |
| 並列化アンチパターン | 「N書き込みトラップ」 | N件の並列リクエストがキャッシュをN回ミスする |
| 動的コンテンツトラップ | 「プロンプト内時刻トラップ」 | プレフィックス内の動的バイトがヒット率を壊す |
| RadixAttention | 「レプリカ内キャッシュ」 | SGLangのプレフィックスキャッシュ実装 |
