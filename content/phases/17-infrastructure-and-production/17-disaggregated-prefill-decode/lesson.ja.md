# 分離型プリフィル／デコード — NVIDIA DynamoとLLm-d

> プリフィルはコンピュート律速；デコードはメモリ律速。両方を同じGPUで実行するとどちらかのリソースが無駄になる。分離化はそれらを別々のプールに分割し、NIXL（RDMA/InfiniBandまたはTCPフォールバック）経由でKVキャッシュを転送する。NVIDIA Dynamo（GTC 2025発表、1.0 GA）はvLLM/SGLang/TRT-LLMの上位に位置する——そのPlanner Profiler＋SLA PlannerはSLOを満たすようにプリフィル:デコード比を自動レートマッチする。NVIDIAは中レイテンシ領域でのGB200 NVL72＋Dynamo上のDeepSeek-R1 MoEで約6倍の改善（developer.nvidia.com、2025年6月）を公表しており、Dynamoの製品ページ（developer.nvidia.com、日付なし）ではGB300 NVL72＋DynamoのHopperと比較して最大50倍のMoEスループットを宣伝している。「30倍」という数字はBlackwell全スタック＋Dynamo＋DeepSeek-R1レポートのコミュニティ集計であり、正確に30倍と述べた単一の一次情報源は見つかっていないため、方向性を示す主張として扱う。llm-d（Red Hat＋AWS）はKubernetesネイティブ：プリフィル／デコード／ルーターを独立したServicesとしてロールごとのHPAで実装。llm-d 0.5は階層的KVオフロード、キャッシュ認識LoRAルーティング、UCCLネットワーキング、スケールtoゼロを追加。経済性：複数の顧客開示の内部集計によると、一定のSLAでコロケーションサービングから分離化＋Dynamoに切り替えた際、$200万規模の推論費用で30〜40%の節約（すなわち年間$60〜80万）が示されており、この$200万→$60〜80万という数字は1つの公開事例研究ではなく内部複合値——大まかな目安として使い、参照引用としては使わないこと。短いプロンプト（512トークン未満、短い出力）は転送コストが割に合わない。


## 学習目標

- プリフィルとデコードが異なる最適なGPU割り当てを必要とする理由を説明し、コロケーション下での無駄を定量化する。
- 分離化アーキテクチャを図示する：プリフィルプール、デコードプール、NIXL経由のKV転送、ルーター。
- 分離化が割に合わない条件を挙げる（短いプロンプト、短い出力）。
- NVIDIA Dynamo（スタックアバブ）とllm-d（Kubernetesネイティブ）を区別し、それぞれを運用コンテキストにマッチさせる。

## 問題の背景

8台のH100でLlama 3.3 70Bを実行している。混合ワークロード（長いプロンプト＋短い出力）では、ほとんどのコンピュートがプリフィルに費やされるためデコード中にGPUがアイドルになる。異なるワークロード（短いプロンプト＋長い出力）では逆のことが起きる。コロケーションされたプリフィル＋デコードは両方に対してオーバープロビジョニングを強いる。

予算への影響：GPUタイムの20〜40%が間違ったリソースで無駄になる。H100コンピュートを買ってメモリ律速のデコードを実行したり、H100 HBM帯域幅を買ってコンピュート律速のプリフィルを実行したりしている。どちらも高価な無駄だ。

分離化はプリフィルとデコードをそれぞれのボトルネックに合わせたサイズの別々のプールに分割する。KVキャッシュはプリフィルプールからデコードプールへ高帯域幅インターコネクト経由で転送される。

## コンセプト

### ボトルネックが異なる理由

**プリフィル** — 1回のフォワードで入力プロンプト全体にトランスフォーマーを実行する。行列積が支配的；コンピュート律速。H100 FP8は有用なスループット約2000 TFLOPSを提供。バッチ効率は良好——1回のフォワードで多くのトークンを処理。

**デコード** — 各イテレーションで完全な重みを読み込みながら1トークンずつ生成。メモリ帯域幅律速。HBM3は約3 TB/sを提供。バッチ効率は高並列時のみ良好——重みの読み込みがバッチ全体に償却される。

コロケーション：両方に最適化されたGPUを購入する。H100は両方に優れているがどちらの方法でも同じコストがかかる。規模では、プリフィルプールにH100／コンピューティングヘビー；デコードプールにH200／メモリヘビー、または積極的な量子化を使用したい。

### アーキテクチャ

```
            ┌──────────────┐
  Request → │    Router    │ ───────────────────────┐
            └──────┬───────┘                        │
                   │                                │
                   ▼ (prompt only)                  │
            ┌──────────────┐    KV cache    ┌───────▼──────┐
            │ Prefill pool │ ─── NIXL ────► │ Decode pool  │
            │  (compute)   │                │  (memory)    │
            └──────────────┘                └──────┬───────┘
                                                   │ tokens
                                                   ▼
                                                 Client
```

NIXLはNVIDIAのノード間トランスポートだ。利用可能な場合はRDMA/InfiniBand、それ以外はTCPフォールバックを使用。転送レイテンシは実際に存在する——70B FP8の4Kトークンプロンプトのためのプリフィルプールから70B FP8へのKVキャッシュは通常20〜80 ms。これが短いプロンプトで分離化が割に合わない理由だ：転送コストが節約を上回る。

### DynamoとLLm-dの比較

**NVIDIA Dynamo**（GTC 2025発表、1.0 GA）：
- vLLM、SGLang、TRT-LLMの上位オーケストレーターとして位置する。
- Planner ProfilerがワークロードをはかりSLA Plannerがプリフィル:デコード比を自動設定。
- Rustコア、Python拡張性。
- スループット向上：NVIDIAはGB200 NVL72＋Dynamoでの中レイテンシ領域のDeepSeek-R1 MoEで6倍を報告（developer.nvidia.com、2025年6月）；フルBlackwell＋Dynamo＋DeepSeek-R1スタックの「最大30倍」というコミュニティレポートには単一の一次情報源がなく、方向性として扱うべき。
- GB300 NVL72＋Dynamo：Dynamoの製品ページによるとHopperと比較して最大50倍のMoEスループット（developer.nvidia.com、日付なし）。

**llm-d**（Red Hat＋AWS、Kubernetesネイティブ）：
- プリフィル／デコード／ルーターを独立したKubernetes Servicesとして実装。
- キュー深さ（プリフィル）／KV利用率（デコード）シグナルによるロールごとのHPA。
- `topologyConstraint packDomain: rack`でプリフィル＋デコードのクリークを同一ラック内にパックして高帯域KV転送を実現。
- llm-d 0.5（2026年）：階層的KVオフロード、キャッシュ認識LoRAルーティング、UCCLネットワーキング、スケールtoゼロ。

管理されたスタックアバブオーケストレーターを望む場合はDynamoを選択。KubernetesネイティブプリミティブでCNCFエコシステムにコミットしている場合はllm-dを選択。

### 経済性

内部複合値（1つの公開事例研究ではない——大まかな目安）：

- コロケーションサービングでの年間$200万の推論費用。
- 分離化＋Dynamoに切り替え。
- 同じリクエストボリューム、同じP99レイテンシSLA。
- 報告された節約：年間$60万〜$80万（30〜40%削減）。
- 新しいハードウェアなし。

この数字は1つの引用可能な事例研究ではなく複数の顧客開示を統合したもの；最も近い公開データポイントはBasetenの2倍速いTTFT/61%高スループット（baseten.co、2025年10月）と、VAST＋CoreWeaveの40〜60%KVヒット率で40〜60%多いトークン/$という予測（vastdata.com、2025年12月）。節約は各プールの適正サイズから生まれる；RAGの8K+プレフィックスなどプリフィルヘビーなワークロードはバランス型よりも多く恩恵を受ける。

### 分離化が割に合わない場合

- プロンプト512トークン未満で出力200トークン未満：転送コストが利益を上回る。
- 小規模クラスター（4 GPU未満）：プールの多様性が足りない。
- ロールごとのスケーリングで2つのGPUプールを運用できないチーム：Dynamoが助けになるが自明ではない。
- RDMAファブリックなし：TCPの転送コストが重くなる。

### ルーターはフェーズ17・11と統合

分離化されたルーターはKVキャッシュ認識（フェーズ17・11）。リクエストはそのプレフィックスを保持するデコードプールにランドする——一致しない場合はプリフィル→デコードに流れる。ヒット率と分離化は複合する——キャッシュ認識ルーターが新しいプリフィルが必要かどうかを判断する。

### MoE on Blackwellで実際の数字が出る

GB300 NVL72＋DynamoはHopperベースラインと比較して50倍のMoEスループットを示す。MoEのエキスパートルーティングはプリフィルではコンピューティングヘビーだがデコードではメモリヘビー（エキスパートキャッシュ）なので、分離化は二重の恩恵をもたらす。2026年のフロンティアモデルサービングはMoE支配的だ（DeepSeek-V3、将来のGPT-5バリアント）。

### 覚えておくべき数値

ベンチマーク数値はドリフトする——NVIDIAと推論スタックは四半期ごとに更新された結果を投稿する。引用する前に再確認すること。

- GB200 NVL72＋DynamoでのDeepSeek-R1：中レイテンシ領域でベースラインに対して約6倍のスループット（developer.nvidia.com、2025年6月）；フルBlackwell＋Dynamoスタックのコミュニティ「最大30倍」の主張は単一の一次情報源のない方向性集計。
- GB300 NVL72＋Dynamo：Hopperと比較して最大50倍のMoEスループット（developer.nvidia.com、日付なし）。
- 節約の目安（内部複合値、単一事例研究ではない）：一定のSLAで$200万の年間費用に対して年間$60〜80万。
- 分離化の閾値：512トークン超のプロンプト＋200トークン超の出力。
- NIXL経由のKV転送：70B FP8の4Kプロンプトのため20〜80 ms。

## 演習

1. `code/main.py`を実行する。どのプロンプト長で分離化がコロケーションに勝るか？
2. P99プレフィックス長8K、出力300のRAGサービスのプリフィルプールとデコードプールを設計する。
3. DynamoとLLm-d：Pythonランタイムへの好みがない純粋なKubernetesショップにはどちらを選ぶか。
4. KV転送コストを計算する：70B FP8の4Kプリフィル = 約500 MB KV。RDMA 100 GB/sで転送 = 5 ms。TCP 10 GB/sで = 50 ms。SLAに対してどちらが重要か？
5. MoEのエキスパートルーティングはKVアクセスパターンを変える。トークンごとに異なるエキスパートをアクティベートするMoEで分離化はどう動作するか？

## キーワード

| 用語 | よく言われる表現 | 実際の意味 |
|------|----------------|------------|
| Disaggregated serving | 「プリフィル/デコード分割」 | 各フェーズに別々のGPUプール |
| NIXL | 「NVIDIAトランスポート」 | DynamoのノードKV転送（RDMA/TCP） |
| NVIDIA Dynamo | 「オーケストレーター」 | vLLM/SGLang/TRT-LLMのスタックアバブコーディネーター |
| llm-d | 「Kubernetesネイティブ」 | Red Hat＋AWS K8s分離化スタック |
| Planner Profiler | 「Dynamo自動設定」 | ワークロードを測定しプール比率を設定 |
| SLA Planner | 「Dynamoポリシー」 | SLOを満たすようにプリフィル:デコードを自動レートマッチ |
| `packDomain: rack` | 「llm-dトポロジー」 | 高速KVのためにプリフィル＋デコードを同一ラックにパック |
| UCCL | 「統合集合通信」 | スケールtoゼロのためのllm-d 0.5ネットワーキング層 |
| MoE expert routing | 「トークンごとのエキスパート」 | DeepSeek-V3パターン；分離化が効果的 |
