# プレフィックス重いワークロードのためのSGLangとRadixAttention

> SGLangはKVキャッシュをradixツリーに格納するファーストクラスの再利用可能なリソースとして扱う。vLLMがFCFS（先着順）でリクエストをスケジュールするのに対して、SGLangのキャッシュ対応スケジューラーはより長い共有プレフィックスを持つリクエストを優先する — ホットブランチをHBMに常駐させるための深さ優先radixトラバーサルが実質的な動作だ。ShareGPTライクな1Kプロンプトを使ったLlama 3.1 8Bでは、SGLangは約16,200 tok/sを達成し、vLLMの約12,500に対して約29%の優位を示す。プレフィックス重いRAGワークロードではその優位が6.4倍に達する。音声クローニング形状のワークロードではキャッシュヒット率が86%を超えた。xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWSで400,000以上のGPUに2026年にデプロイ済み。落とし穴は6.4倍の数値がプレフィックスの順序が一貫していない場合に消えること — 順序付けはエンジニアのレバーだ。


## 学習目標

- RadixAttentionを図示する：プレフィックスがradixツリーにどのように格納され、同じブランチを根とするシーケンス間でKVブロックがどのように共有されるか。
- キャッシュ対応スケジューリングと、FCFSがプレフィックス重いトラフィックに対してなぜ誤りかを説明する。
- プレフィックスキャッシュヒット率とプロンプト長分布に基づいて、ワークロードの期待スピードアップを計算する。
- 6.4倍の数値を現実にするプロンプト順序付けの規律と、失われた利益を挙げる。

## 問題

クラシックな配信は各リクエストのプロンプトを不透明として扱う。5,000のRAGリクエストすべてが同じ2,000トークンのシステムプロンプトと同じ検索プリアンブルから始まる場合でも、vLLMはその2,000トークンのプレフィックスを5,000回プリフィルする。GPUは何度も同じ作業をする。

観察：エージェンティックとRAGのワークロードではプロンプトはほぼ常に長いプレフィックスを共有する。システムプロンプト、ツールスキーマ、Few-shotの例、検索ヘッダー、会話履歴 — すべてがリクエスト間で繰り返される。そのプレフィックスのKVキャッシュを一度格納して再利用できれば、再びプリフィルしなくてよい。

RadixAttentionはまさにそれを行う。トークンはradixツリーにインデックスされ、各ノードはルートからのパス上のトークンシーケンスのKVブロックを所有する。新しいリクエストはツリーをウォークする：一致するノードはそのKVブロックを再利用する。プリフィルコストは完全なプロンプトではなく「新しい」サフィックスに比例する。

課題はスケジューリングだ。2つのリクエストが2,000トークンのプレフィックスを共有し、3つ目が同じプレフィックスの200トークンしか共有しない場合、長い共有プレフィックスを持つ2つのリクエストを一緒に提供したい。FCFSはその逆をする — 最初に到着した順に提供し、次の長いプレフィックスリクエストが来る前にホットブランチを退去させる可能性がある。

## コンセプト

### KVインデックスとしてのradixツリー

radixツリー（コンパクトなトライ）はトークンシーケンスを格納する。各ノードはトークン範囲とその範囲のために計算されたKVブロックを所有する。子ノードはシーケンスを1つ以上のトークン延長する。

```
root
 |- "You are a helpful assistant..."  (2,000トークン、124 KVブロック)
      |- "Context: <doc A>..."        (500トークン、31ブロック)
           |- "Question: Alice..."    (80トークン、5ブロック)
           |- "Question: Bob..."      (95トークン、6ブロック)
      |- "Context: <doc B>..."        (520トークン、33ブロック)
```

システムプロンプト + "Context: <doc A>" + "Question: Carol"を含む新しいリクエストが来る。スケジューラーがウォーク：システムプレフィックスが一致（124ブロック再利用）、doc-Aブランチが一致（31ブロック再利用）、その後"Question: Carol"のみに新しいブロックを割り当て（4ブロック）。プリフィルコスト：新しいトークンの4ブロック。ツリーなし：160ブロック。プリフィルで約40倍の節約。

### キャッシュ対応スケジューリング

radixツリーバックのキャッシュがチャーンするなら再利用は意味がない。2つの主要なポリシー：

1. **深さ優先ディスパッチ**。キューから次のリクエストを選ぶとき、現在実行中のセットと同じブランチを根とするリクエストを優先する。これによってホットブランチがピン留めされる。
2. **ブランチレベルのLRU、ブロックレベルではない**。全ブランチを退去させる（最も短く使われたリーフから始めて）、個別のブロックではなく。キャッシュシェイプがradixシェイプと一致する。

FCFSは両方に違反する。2,000トークンを共有するリクエストが50トークンしか共有しないリクエストの後ろに並び、2,000トークンのブランチが50トークンのリクエストを受け入れるために退去される。

### 記憶すべきベンチマーク数値

- Llama 3.1 8B、H100、ShareGPT 1Kプロンプト：SGLang約16,200 tok/s vs vLLM約12,500（約29%の優位）
- プレフィックス重いRAG（同じシステム + 同じドキュメント、異なる質問）：SGLangで最大6.4倍
- 音声クローニングワークロード：86.4%のプレフィックスキャッシュヒット率
- SGLang顧客全体の本番ヒット率：プロンプトの規律に応じて50〜99%
- 2026年に400,000以上のGPUにデプロイ

### 順序付けの落とし穴

6.4倍の数値は一貫したプロンプトテンプレート順序に依存する。クライアントが一部のリクエストで`[system, tools, context, history, question]`、他では`[system, context, tools, history, question]`としてプロンプトを構成する場合、ツリーは共有プレフィックスを見つけられない。人間には共有プレフィックスに見えるものが、radixツリーには2つの別個のシーケンスだ。

エンジニアのレバー：プロンプトテンプレートはキャッシュキーだ。順序を固定する。不変なもの（システム、ツール、スキーマ）を最初に置く。次に検索コンテキスト。最後にユーザーの質問を置く。動的なコンテンツをプレフィックスに差し込まない。

研究からの実例：あるデプロイメントでキャッシュ可能なプレフィックスから動的コンテンツを移動させたところ、1回の変更でヒット率が7%から74%に上がった。

### RadixAttentionが勝つ場面と負ける場面

勝つ場面：
- RAG（同じ検索プリアンブル、異なる質問）
- エージェント（同じツールスキーマ、異なるクエリ）
- 長いシステムプロンプトを持つチャット
- 繰り返しプリアンブルを持つ音声/ビジョンワークロード

負ける場面（vLLMレベルのスループットに戻る）：
- 固有のプロンプトを持つシングルショット生成（システムプロンプトなしのコード補完、オープンエンドチャット）
- 各リクエストがプレフィックスに固有のコンテンツを挿入する動的プロンプト

### これがスケジューラーの問題であり、カーネルの問題だけでない理由

KVの再利用をカーネルトリックとして実装できる。SGLangの洞察は、スケジューラーがホットブランチを常駐させておく場合のみ再利用が報われるということだ。ナイーブな「利用可能なら再利用」ポリシーは混合負荷下でキャッシュをチャーンさせる。radixツリーインデックスのスケジューラーが、カーネルトリックを29%の本番優位に変えるものだ。

### vLLMとの相互作用

2つのシステムは厳密な競合ではない。2026年にvLLMはプレフィックスキャッシング（`--enable-prefix-caching`）とキャッシュ対応ルーター（Rust製vLLM Router）を追加した。差は縮まったが完全になくならなかった — SGLangのスタック全体がradixファースト。vLLMはそれを後から接ぎ木した。プレフィックス再利用に支配されるワークロードでは、SGLangがデフォルトのまま。強いプレフィックスパターンのない一般目的の配信では、vLLMは同等かそれ以上だ。

## 使ってみる

`code/main.py`はおもちゃのradixツリーKVキャッシュと2つのポリシーを持つスケジューラーを実装する：FCFSとキャッシュ対応。同じワークロードを両方で実行し、プレフィックスキャッシュヒット率とスループットデルタを報告する。次に「スクランブルされた順序付け」ワークロードを実行して6.4倍の崩壊を示す。

## 成果物を出す

このレッスンでは`outputs/skill-radix-scheduler-advisor.md`を作成する。ワークロードの説明（プロンプトテンプレートシェイプ、検索パターン、同時テナント数）に基づいて、プロンプト順序付けの処方箋とSGLang採用のgo/no-goを提供する。

## 演習

1. `code/main.py`を実行する。同じワークロードでFCFSとキャッシュ対応を比較する。デルタはプリフィル節約、デコード節約、キュー遅延のどこから来るか？
2. プロンプトが`[system, tools, context]`をランダムに並べ替えるようにワークロードを変更する。再実行する。ヒット率はどうなるか？なぜか？
3. Llama 3.1 8Bで2,000トークンのシステムプロンプトを1つのradixブランチとして常駐させるためのHBMコストを計算する。プレフィックス再利用なしの16シーケンスバッチのコストと比較する。
4. SGLang RadixAttentionペーパーを読む。プレフィックス重い負荷においてツリー形状のLRU退去がブロック形状のLRUに勝る理由を3文で説明する。
5. 顧客がキャッシュヒット率8%しか報告しない。3つの可能性のある原因と各診断を挙げる。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------|
| RadixAttention | 「SGLangのもの」 | 共有プレフィックスがブロックを再利用できるようにradixツリーとしてインデックスされたKVキャッシュ |
| Radixツリー | 「コンパクトなトライ」 | 各ノードがトークン範囲とそのKVブロックを所有するツリー |
| キャッシュ対応スケジューラー | 「ホットブランチファースト」 | 常駐ブランチを共有するリクエストを優先するスケジューラー |
| プレフィックスキャッシュヒット率 | 「プロンプトの何割がタダだったか」 | 再利用されたKVブロックから提供されたプロンプトトークンの割合 |
| FCFS | 「先着順」 | プレフィックスの局所性を壊すデフォルトスケジューリング |
| ブランチレベルのLRU | 「リーフを退去させる」 | Radixシェイプに合った退去ポリシー |
| プロンプトテンプレート順序付け | 「キャッシュキー」 | プロンプトのコンポーネント順序がツリーが共有できるものを決定する |
| システムプロンプトのピン留め | 「常駐プレフィックス」 | 退去スラッシングを避けるために不変のシステム部分をピン留めする |
