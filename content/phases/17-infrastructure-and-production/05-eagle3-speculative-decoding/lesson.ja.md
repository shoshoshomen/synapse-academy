# 本番環境でのEAGLE-3投機的デコード

> 投機的デコードは高速なドラフトモデルとターゲットモデルをペアにする。ドラフトがKトークンを提案し、ターゲットが1回のフォワードで検証し、受け入れられたトークンはタダになる。2026年においてEAGLE-3は本番グレードのバリアントだ — ターゲットモデルの隠れ状態でドラフトヘッドをトレーニングすることで、一般的なチャットで受け入れ率alphaを0.6〜0.8のバンドに押し込む。正しい問いは「ドラフトはどれくらい速いか」ではなく「自分のトラフィックでalphaはいくつか」だ。alphaが約0.55を下回ると、拒否されたドラフトはすべて2回目のターゲットフォワードパスを消費するため、高並行では投機的デコードはネガティブになる。このレッスンでは最初にalphaを測定し、その後フラグを有効にすることを教える。


## 学習目標

- 投機的デコードの3世代を挙げ、EAGLE-3がEAGLE-2とクラシックドラフトモデルから何を変えたかを説明する。
- 受け入れ率alpha、alphaとK（ドラフト長）からの期待スピードアップを計算し、ターゲット並行数に対する損益分岐alphaを特定する。
- 2026年のvLLMで投機的デコードがオプトイン（デフォルトでない）の理由と、alphaを測定せずにオンにすることが本番のアンチパターンである理由を説明する。
- 測定計画を書く：どのベンチマーク、どのプロンプト分布、どの並行点、どのメトリクスでゲートするか。

## 問題

デコードはメモリバウンドだ。H100上のLlama 3.3 70B FP8では、各デコードトークンがウェイトの約140 GB/sを読み込み、1トークンを出力する。GPUコンピュートはデコード中ほぼアイドル — ボトルネックはHBM帯域幅であり、行列乗算スループットではない。

投機的デコードはこのギャップを利用する。安価なドラフトモデルでK個の候補トークンを生成し、ターゲットモデルに1回のフォワードパスですべてKを検証させる。検証された各トークンは実質的にタダだ（ターゲットがいずれにしろ行わなければならないK個のバッチフォワードに償却される）。

クラシックドラフトモデルアプローチは同じファミリーの小さなモデルを使う（Llama 3.3 70B用のドラフトとしてLlama 3.2 1B）。機能するが受け入れ率は平凡 — 小さなモデルの分布がターゲットから乖離する。EAGLE、次にEAGLE-2、次にEAGLE-3はターゲットモデルの内部状態でドラフトヘッドを直接トレーニングするため、ドラフトの分布はターゲットをはるかによく追跡する。それがalphaがドラフトモデルの0.4からEAGLE-3の0.6〜0.8に上がる理由だ。

落とし穴：EAGLE-3は2026年のvLLMでオプトインだ。`speculative_config`を明示的に設定しなければならない。フラグなし、加速なし。実際のトラフィックのalphaを測定せずにオンにするチームは、レイテンシが改善するどころか悪化するのをよく見る。

## コンセプト

### 投機的デコードが実際に何をもたらすか

投機的デコードなしでは、トークンあたりのコストは1回のターゲットフォワードだ。ドラフト長Kと受け入れ率alphaで投機的デコードを使うと、ターゲットフォワードあたりの期待トークンは`1 + K * alpha`だ。スピードアップは`(1 + K * alpha) / (1 + epsilon)`で、epsilonはドラフト＋検証オーバーヘッドだ。K=5、alpha=0.7の場合：`(1 + 5*0.7) / (1 + 0.1) = 4.5 / 1.1 = 4.1倍`。実世界の数値は2〜3倍前後に集まる。本番トラフィックでalphaがそれほど高くなく、epsilonが高いバッチサイズで成長するためだ。

### alphaだけが重要なメトリクスである理由

拒否されたトークンは消えない — 最初の拒否されたトークンに対して2回目のターゲットフォワードを強制する。alphaが0.4まで下がるワークロードでは、ドラフトオーバーヘッド + 検証 + 再ロールを払う。高並行（例えば256同時）では、デコードバッチはすでに十分大きく、「ターゲット単独」と「検証付きターゲット」のメモリ帯域幅ギャップが縮む。ほとんどの2026ハードウェアではalphaが0.55を下回ると、投機的デコードはネガティブになる。

Alphaはワークロードによって異なる。ShareGPT系の一般チャットでは、ShareGPTでトレーニングされたEAGLE-3は0.6〜0.8を達成する。ドメイン固有のトラフィック（コード、医療、法律）では、一般データでトレーニングされたドラフトヘッドは0.4〜0.6に下がる。ドメイン固有のドラフトヘッドをトレーニングするとalphaが回復する — ターゲットのファインチューニングと比較して軽くて素早いトレーニングジョブだ。

### EAGLE世代の概要

- **クラシックドラフトモデル**：同じファミリーの小さなモデル。Alpha 0.3〜0.5。インフラシンプル — 2つのモデルをロード、ドラフトはターゲットフォワードごとにK回フォワード。
- **EAGLE-1（2024）**：ターゲット隠れ状態（最終層）でトレーニングされた単一ドラフトヘッド。Alpha 約0.5〜0.6。ターゲットの上に小さなパラメータオーバーヘッド。
- **EAGLE-2（2025）**：適応ドラフト長とツリーベースドラフト（1回のターゲットパスで複数のブランチを検証）。Alpha 約0.6〜0.7。より複雑なドラフトスケジューラー。
- **EAGLE-3（2025〜2026）**：複数のターゲット層（最終層だけでなく）でトレーニングされたドラフトヘッド、より良いアライメント。Alpha 一般チャットで約0.6〜0.8。

### 2026年の本番レシピ

1. ターゲットモデルをそのままデプロイする。目標並行でのベースラインTTFT、ITL、スループットを測定する。
2. vLLM `speculative_config`でEAGLE-3ドラフトを有効にする。ベンチマークを再実行する。
3. 受け入れ率alphaをログに記録する。vLLM V1はこれを`spec_decode_metrics.accepted_tokens_per_request`として報告する。要求されたドラフト長で割ってalphaを得る。
4. 本番トラフィック分布でalphaが0.55未満の場合、投機的デコードを無効にするかドメイン固有のEAGLE-3ドラフトをトレーニングする。
5. 本番並行数で再実行する。P99 ITLが悪化していないことを確認する。

### 本番の落とし穴：P99テール

投機的デコードで平均ITLは下がる。チューニングしないとP99が悪化することがある。拒否されたドラフトは2パスシーケンスをトリガーする（ドラフト + 検証失敗 + 再ロール）。フルバッチでは、この2パスがシリアライズする。P50ではなくP99 ITLを見ること。

### EAGLE-3がすでにデプロイされている場所

GoogleはAI Overviewsに2025年に投機的デコードをデプロイした（同じ品質、より速いレスポンス）。vLLM V1は`speculative_config`をドキュメント化されたインターフェースとして提供。V1のNグラムGPU投機的デコードはチャンクプリフィルと互換性があるバリアントだ。SGLangはプレフィックス重いワークロードに推奨されるドラフトパスとしてEAGLE-3をサポートする。

### 1行での損益分岐数学

期待スピードアップ：`S(alpha, K) = (1 + K*alpha) / (1 + verify_overhead)`。`S = 1`に設定するとalphaを解ける：`alpha_breakeven = verify_overhead / K`。典型的なverify_overhead約0.15とK=5の場合：`alpha_breakeven = 0.03`。しかしそれは純粋なデコードの数学だ。高並行ではverifyオーバーヘッドが上昇し、デコードバッチがすでにシーケンス間でメモリ読み込みを償却するため、有効なalpha_breakevenは実際には約0.45〜0.55まで上昇する。

### 投機的デコードを使わない場面

- レイテンシが重要でないバッチ1のオフライン生成。シンプルなターゲットを使う。
- 非常に短い出力（50トークン未満）。ドラフトオーバーヘッドと検証コストが支配する。
- ドメイン固有のドラフトヘッドなしの専門ドメイン。Alphaが低すぎる。
- vLLM v0.18.0 + ドラフトモデル投機的デコード + `--enable-chunked-prefill`。この組み合わせはコンパイルできない。ドキュメント化された例外はV1のNグラムGPU投機的デコードだ。

## 使ってみる

`code/main.py`は、さまざまなalpha値とドラフト長Kにわたって投機的デコードありとなしのデコードループをシミュレートする。損益分岐alpha、測定されたスピードアップ、テール動作を出力する。投機的デコードが報われなくなる正確な場所を見るために、複数の（alpha、K）の組み合わせで実行する。

## 成果物を出す

このレッスンでは`outputs/skill-eagle3-rollout.md`を作成する。ターゲットモデル、トラフィック分布の説明、並行数ターゲットに基づいて、段階的なEAGLE-3ロールアウト計画を提供する — ベースラインのベンチマーク、設定の有効化、alphaの測定、alpha >= 0.55でのゲート、P99 ITLの監視。

## 演習

1. `code/main.py`を実行する。K=5で2倍のスピードアップに必要なalphaはいくつか？3倍では？verify_overheadに対してどれくらい感度があるか？
2. 本番トラフィックが一般チャット70%、コード30%に分割されているとする。ShareGPTでトレーニングされたEAGLE-3で一般チャットはalpha 0.7、コードはalpha 0.4を達成する。ブレンドalphaはいくつで、投機的デコードはネットプラスか？
3. vLLMの`speculative_config`ドキュメントを読む。3つのモード（ドラフトモデル、EAGLE、Nグラム）を挙げ、どれがチャンクプリフィルと互換性があるか答える。
4. EAGLE-3を有効にした後、平均ITLが25%下がるがP99 ITLが15%上がるのを見る。診断して緩和策を提案する。
5. Llama 3.3 70BのEAGLE-3ドラフトヘッドのメモリコストを計算する。クラシックドラフトとしてLlama 3.2 1Bを実行する場合と比較する。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------|
| 投機的デコード | 「ドラフト＋検証」 | 安価なモデルでKトークンを提案し、1回のターゲットフォワードですべてKを検証 |
| 受け入れ率alpha | 「投機受け入れ率」 | ターゲットに受け入れられたドラフトトークンの割合。唯一重要なメトリクス |
| ドラフト長K | 「投機k」 | ドラフトがターゲットフォワードごとに提案するトークン数。通常4〜8 |
| 検証オーバーヘッドepsilon | 「投機オーバーヘッド」 | 検証・再ロール対シンプルなターゲットフォワードの追加コスト。バッチで成長 |
| EAGLE-3 | 「最新のEAGLE」 | 2025〜2026バリアント。複数のターゲット層でドラフトヘッドをトレーニング。一般チャットでalpha 0.6〜0.8 |
| `speculative_config` | 「vLLM投機設定」 | vLLM V1での明示的オプトイン。デフォルトなし = 加速なし |
| Nグラム投機的デコード | 「Nグラムドラフト」 | プロンプト内のNグラムルックアップを使用するGPU側ドラフト。チャンクプリフィル互換 |
| 損益分岐alpha | 「無効化alpha」 | 投機的デコードがゼロスピードアップを与えるalpha。本番並行で監視する |
| 拒否ドラフト2パス | 「再ロールコスト」 | ドラフト拒否時の2回のターゲットフォワード。P99テールを駆動する |
