# LMCacheのKVオフロードを使ったvLLMプロダクションスタック

> vLLMのproduction-stackはKubernetesの参照デプロイメントだ——ルーター、エンジン、オブザーバビリティが連携している。LMCacheはKVキャッシュをGPUメモリから取り出し、クエリとエンジン間で再利用するKVオフロード層だ（CPU DRAM、続いてディスク/Ceph）。vLLM 0.11.0のKVオフロードコネクター（2026年1月）はコネクターAPI（v0.9.0+）経由でこれを非同期かつプラガブルにする。オフロードのレイテンシはユーザー向けではない。LMCacheは共有プレフィックスがない場合でも価値がある——GPUのKVスロットが枯渇したとき、プリエンプトされたリクエストはプリフィルを再計算するのではなくCPUから復元できる。16台のH100（80GB HBM）上で4台のa3-highgpu-4gにわたる公開済みベンチマーク：KVキャッシュがHBMを超えると、ネイティブCPUオフロードとLMCacheの両方がスループットを大幅に改善する；KVフットプリントが小さい場合、すべての設定がベースラインと一致し、オーバーヘッドはわずかだ。


## 学習目標

- vLLMプロダクションスタックの層を図示する：ルーター、エンジン、KVオフロード、オブザーバビリティ。
- KVオフロードコネクターAPI（v0.9.0+）と0.11.0の非同期パスがオフロードレイテンシを隠す方法を説明する。
- LMCacheのCPU-DRAMが役立つ場合（KV > HBM）と追加オーバーヘッドになる場合（KVがHBMに収まるほど小さい場合）を定量化する。
- デプロイメント制約を考慮してvLLMネイティブCPUオフロードとLMCacheコネクターを選択する。

## 問題の背景

vLLMサービングでは、並列処理が増えるたびにプリエンプションイベントでGPUがHBM 100%になっている。リクエストがエビクト、再キューイングされ、同じ2Kトークンプロンプトを1分間に4回プリフィルし直している。GPUコンピュートが冗長なプリフィルに費やされ、グッドプットは生スループットをはるかに下回っている。

GPUを追加するとコストが線形に増加する。HBMを追加することはできない。しかしCPU DRAMは安価だ——1ソケットが512 GB以上あり、HBMよりはるかに悪いレイテンシだが「一時的にウォーム」なKVキャッシュには十分だ。

LMCacheはKVキャッシュをCPU DRAMに取り出してプリエンプトされたリクエストが速く復元できるようにし、エンジン間で繰り返されるプレフィックスを各エンジンが再プリフィルすることなく共有する。

## コンセプト

### vLLMプロダクションスタック

`github.com/vllm-project/production-stack`は参照Kubernetesデプロイメントだ：

- **ルーター** — キャッシュ認識（フェーズ17・11）。KVイベントを消費。
- **エンジン** — vLLMワーカー。GPUごとまたはTP/PPグループごとに1つ。
- **KVキャッシュオフロード** — LMCacheデプロイメントまたはネイティブコネクター。
- **オブザーバビリティ** — Prometheusスクレイプ、Grafanaダッシュボード、OTelトレース。
- **コントロールプレーン** — サービスディスカバリー、設定、ローリングアップデート。

HelmチャートとオペレーターとしてShipped。

### KVオフロードコネクターAPI（v0.9.0+）

vLLM 0.9.0でプラガブルなKVキャッシュバックエンドのコネクターAPIが導入された。エンジンがブロックをコネクターにオフロードし、コネクターがそれを保存する（RAM、ディスク、オブジェクトストレージ、LMCache）。リクエストがブロックを必要とすると、コネクターがそれをロードバックする。

vLLM 0.11.0（2026年1月）は非同期オフロードパスを追加した——一般的なケースではエンジンがそこでブロックしないようにオフロードをバックグラウンドで実行できる。エンドツーエンドのレイテンシとスループットは依然としてワークロードの形状、KVキャッシュのヒット率、システムプレッシャーによって異なる；vLLMの独自ノートでは、カスタムカーネルオフロードが低ヒット率でスループットを低下させる可能性があること、非同期スケジューリングに投機的デコードとの既知の相互作用問題があることを指摘している。

### ネイティブCPUオフロード対LMCache

**ネイティブvLLM CPUオフロード**：エンジンローカル。ホストRAMにKVブロックを保存。実装が速く、ネットワークホップなし。エンジンをまたがない。

**LMCacheコネクター**：クラスタースケール。ブロックを共有LMCacheサーバー（CPU DRAM + Ceph/S3ティア）に保存。すべてのエンジンからブロックにアクセス可能。16台のH100ベンチマーク済み。

単一エンジンにHBMプレッシャーがある場合はネイティブを選択。複数エンジンがプレフィックスを共有する場合（共通システムプロンプトのRAG、共有テンプレートのマルチテナント）はLMCacheを選択。

### ベンチマーク動作

4台のa3-highgpu-4gに分散した16台のH100（80 GB HBM）テスト：

- 低KVフットプリント（短いプロンプト、低並列性）：すべての設定がベースラインと一致し、LMCacheは約3〜5%のオーバーヘッドを追加。
- 中程度のフットプリント：LMCacheがエンジン間のプレフィックス再利用で効果を発揮し始める。
- KVがHBMを超える：ネイティブCPUオフロードとLMCacheの両方がスループットを大幅に改善；LMCacheはクロスエンジン共有のため大きな利益。

### LMCacheが決定的な場合

- テナント間でシステムプロンプトが共有されるマルチテナントサービング。
- ドキュメントチャンクがクエリ間で繰り返されるRAG。
- 同じベースモデルのファインチューンバリアント（LoRA）でベースモデルKV再利用が冗長な作業を削減する場合。
- プリエンプションヘビーなワークロード：CPUからの復元が再プリフィルより安価。

### 有効にしてはいけない場合

- HBMプレッシャーが小さい——利益なしにオーバーヘッドを払う。
- 短いコンテキスト（1Kトークン未満）——転送時間 > 再プリフィル。
- シングルテナントのシングルプロンプトワークロード——再利用するものがない。

### 分離型サービングとの統合

フェーズ17・17の分離型サービング＋LMCacheは複合する：プリフィルプールからデコードプールへのKV転送は未使用の場合LMCacheにランドし、後続のクエリがLMCacheから取得する。フェーズ17・11のキャッシュ認識ルーターは、ローカルまたはLMCache共有キャッシュが一致するエンジンにルーティングできる。

### 覚えておくべき数値

- vLLM 0.9.0：コネクターAPIがShipped。
- vLLM 0.11.0（2026年1月）：非同期オフロードパス；エンドツーエンドのレイテンシ影響はワークロード、KVヒット率、システムプレッシャーによって異なる（絶対保証ではない）。
- 16台のH100ベンチマーク：KVフットプリントがHBMを超えるとLMCacheが効果を発揮。
- HBMプレッシャーが小さい場合：利益なしに3〜5%のオーバーヘッド。

## 演習

1. `code/main.py`を実行する。どのHBM利用率でLMCacheが効果を発揮し始めるか？
2. テナントが200クエリ/時間にわたって6Kトークンのシステムプロンプトを共有する。テナントあたりの期待されるLMCache節約を計算する。
3. LMCacheサーバーは単一障害点だ。HA戦略を設計する（レプリカ、ネイティブへのフォールバック）。
4. LMCacheがCephのスピニングディスクに保存する。70B FP8の4KトークンKV（500 MB）の読み取り時間と再プリフィルを比較するとどうなるか？
5. vLLM 0.11.0の非同期パスが「無料」かどうかを議論する——どこにオーバーヘッドが隠れているか？

## キーワード

| 用語 | よく言われる表現 | 実際の意味 |
|------|----------------|------------|
| Production-stack | 「参照デプロイメント」 | vLLMのKubernetes Helmチャート＋オペレーター |
| Connector API | 「KVバックエンドインターフェース」 | vLLM 0.9.0+のプラガブルKVストアインターフェース |
| Native CPU offload | 「エンジンローカルスピル」 | 同じエンジンのホストRAMにKVを保存 |
| LMCache | 「クラスターKVキャッシュ」 | CPU DRAM＋ディスク上のクロスエンジンKVキャッシュサーバー |
| 0.11.0 async | 「ノンブロッキングオフロード」 | エンジンストリームの背後に隠されたオフロード |
| Preemption | 「空きを作るためにエビクト」 | HBMが満杯のときのKVキャッシュシャッフル |
| Prefix reuse | 「同じシステムプロンプト」 | 複数のクエリが先頭を共有；キャッシュヒット |
| Ceph tier | 「ディスクティア」 | キャッシュ階層でDRAMの下の永続ストレージ |
