# vLLM配信の内部：PagedAttention、連続バッチング、チャンクプリフィル

> 2026年のvLLMの優位性は3つの相互補完するデフォルトにあり、単一のトリックではない。PagedAttentionは常にオンだ。連続バッチングはデコードイテレーション間にアクティブバッチに新しいリクエストを注入する。チャンクプリフィルは長いプロンプトをスライスして、デコードトークンが飢餓状態にならないようにする。3つすべてをオンにすると、1台のH100 SXM5上のLlama 3.3 70B FP8は128並行で2,200〜2,400 tok/sを達成 — vLLM自身のデフォルトより約25%上で、ナイーブなPyTorchループの3〜4倍だ。このレッスンではスケジューラーとアテンションカーネルを図示できるレベルで読み解き、`code/main.py`の簡易連続バッチャーでvLLMと同様にプリフィルとデコードをスケジュールする実装で終わる。


## 学習目標

- PagedAttentionをKVキャッシュアロケーターとして説明する：ブロック、ブロックテーブル、本番負荷で断片化が4%未満に収まる理由。
- イテレーションレベルでの連続バッチングを図示する：終了したシーケンスがバッチを去り、新しいシーケンスがドレインせずに参加する方法。
- チャンクプリフィルを1文で説明し、それが保護するレイテンシメトリクスを挙げる（ヒント：平均スループットではなくTTFTテールだ）。
- 2026年のvLLM v0.18.0で、すべての最適化を一度に有効にしようとするチームを困らせる落とし穴を挙げる。

## 問題

ナイーブなPyTorchサーブループは1度に1リクエストを実行する：トークン化、プリフィル、EOSまでデコード、返却。1ユーザーではうまく機能する。100ユーザーでは忍耐強い人々のキューだ。明らかな解決策 — 静的バッチング — はウィンドウ内で最も長いプロンプトにすべてのリクエストをパディングし、最も長い期待出力にすべてのデコードをパディングし、バッチ全体を最も遅いシーケンスで停止させる。使われないパディングに支払い、高速なリクエストが遅いものを待つ。

vLLMは3つの問題を同時に解決する。PagedAttentionはクラシックな連続割り当てが行う60〜80%のようにKVキャッシュ断片化がGPUメモリを食い尽くすのを防ぐ。連続バッチングによりリクエストはデコードイテレーションごとにバッチに参加・離脱でき、バッチは常に実際の作業で満たされる。チャンクプリフィルは32kトークンのプロンプトを約512トークンのスライスに分割してデコードと交互に実行するため、長いプロンプトがGPU上の他のすべてのデコードトークンをフリーズさせない。

2026年の本番デフォルトは3つすべてオンだ。各機能が何をするかを理解する必要がある。失敗モードはすべてスケジューラーにあり、モデルにはない。

## コンセプト

### 仮想メモリシステムとしてのPagedAttention

KVキャッシュはシーケンスごとに`num_layers × 2 × num_heads × head_dim × seq_len × bytes_per_element`だ。BF16でLlama 3.3 70Bの8192トークンでは、シーケンスごとに約1.25 GBだ。すべてのリクエストに8192スロットを事前予約するが平均リクエストが1500トークンしか使わない場合、予約したHBMの約82%を無駄にしている。クラシックバッチングはこの無駄を払う。

PagedAttentionはOSの仮想メモリからアイデアを借りている。KVキャッシュはシーケンスごとに連続していない。固定サイズブロック（デフォルト16トークン）で割り当てられる。各シーケンスは論理トークン位置を物理ブロックIDにマッピングするブロックテーブルを持つ。シーケンスが割り当てられたブロックを超えると、さらに1ブロックが追加される。シーケンスが終了すると、そのブロックはプールに戻る。

断片化は60〜80%（クラシック）から4%未満（PagedAttention）に下がる。フラグでPagedAttentionを有効にする必要はない — vLLMが出荷する唯一のアロケーターだ。ノブは`--gpu-memory-utilization`（デフォルト0.9）で、ウェイトとアクティベーションをロードした後にKVブロック用に予約するHBMの割合を伝える。

### イテレーションレベルでの連続バッチング

古い「動的バッチング」はウィンドウ（例えば10ms）を待ってバッチを満たし、その後すべてのシーケンスが終了するまでプリフィル + デコード + デコード + デコードを実行した。高速なシーケンスが早く終わり、GPUが遅いシーケンスを終わらせる間アイドルになった。

連続バッチングは各デコードステップ間で操作する。実行中のシーケンスのセットを`RUNNING`リストと呼ぶ。各イテレーションで：

1. `RUNNING`内でEOSまたはmax_tokensに達したシーケンスを削除する。
2. スケジューラーは待機キューを見る。KVブロックに空きがあれば新しいシーケンスを受け入れる（プリフィルまたは再開）。
3. フォワードパスが`RUNNING`にある何でも実行し、シーケンスごとに1つの新しいトークンを出力する。

バッチサイズは固定数にパディングされない。異なる出力位置のシーケンスが1つの融合フォワードを共有する。2026年のvLLMではこれを`V1スケジューラー`と呼ぶ。主要な不変条件：スケジューラーはリクエストごとではなくデコードイテレーションごとに1回実行される。

### チャンクプリフィルはTTFTテールを保護する

プリフィルはコンピュートバウンドだ。H100上のLlama 3.3 70Bの32kトークンプロンプトは純粋なプリフィルに約800msかかる。プリフィルが実行されている間、バッチ内の他のすべてのシーケンスのデコードトークンが待つ。配信ループでは、1つの長いプロンプトのファーストトークンレイテンシ（TTFT）が、他の数十ユーザーのインタートークンレイテンシ（ITL）のブリップになる。

チャンクプリフィルはプリフィルを固定サイズチャンク（デフォルト512トークン）に分割し、各チャンクを1単位としてスケジュールする。チャンク間でスケジューラーはデコードシーケンスを1トークン進めることができる。チャンクごとにわずかなプリフィルレイテンシのヒット（数ms）を払う代わりに、デコード時のジッターが大幅に低下する。公開されたベンチマークでは混合負荷下のP99 ITLが約50msから約15msに下がる。

### 3つのデフォルトの相互作用

3つの機能はすべてお互いを前提としている。PagedAttentionはスケジューラーに細粒度のKVリソースを取引させる。連続バッチングはそのリソースを必要とし、新しいシーケンスを受け入れてもグローバルな再シャッフルを強制しない。チャンクプリフィルはスケジューラーが同じ`RUNNING`リスト上で行う決定 — 別のシステムではなく1つのスケジューラーポリシーだ。

すべてのフラグを知る必要はない。スケジューラーが最適化するものを知る必要がある：チャンクプリフィルスライシングに従いつつKVブロック予算下のグッドプット。

### 2026年のv0.18.0の落とし穴

vLLM v0.18.0では`--enable-chunked-prefill`とドラフトモデル投機的デコード（`--speculative-model`）を組み合わせることができない。ドキュメントに記載された例外はV1スケジューラーのNグラムGPU投機的デコードだ。リリースノートを読まずにすべてのフラグをオンにするチームは、サイレントなリグレッションではなく起動時のランタイムエラーを受け取る。チャンクプリフィルを有効にするために投機的なゲインが価値あると思うなら、選択を再検討する — 2026年の正解はチャンクプリフィルなしのEAGLE-3で、コンパイルできないドラフトモデルとチャンクプリフィルの組み合わせではない。

### 覚えておくべき数値

- Llama 3.3 70B FP8、H100 SXM5、128並行、3つすべてオン：2,200〜2,400 tok/s
- 同じモデル、デフォルトvLLM（チャンクプリフィルなし）：約1,800 tok/s
- 同じモデル、ナイーブなPyTorchフォワードループ：約600 tok/s
- 本番負荷でPagedAttentionによるKV断片化の無駄：4%未満
- 混合負荷下のP99 ITL：チャンクプリフィルありで約15ms、なしで約50ms

### スケジューラーの動作

```
while True:
    finished = [s for s in RUNNING if s.is_done()]
    for s in finished: release_blocks(s); RUNNING.remove(s)

    while WAITING and have_free_blocks_for(WAITING[0]):
        s = WAITING.pop(0)
        allocate_initial_blocks(s)
        RUNNING.append(s)

    # プリフィルチャンクとデコードを1バッチでスケジュール
    batch = []
    for s in RUNNING:
        if s.in_prefill:
            batch.append(next_prefill_chunk(s))   # 例: 512トークン
        else:
            batch.append(decode_one_token(s))     # 1トークン

    run_forward(batch)                            # 1つの融合GPU呼び出し
```

`code/main.py`はstdlib Pythonで偽のトークン数と偽のフォワードレイテンシを使ったまさにこのループだ。実行すると、長いプリフィル中にチャンクプリフィルがデコードシーケンスを生かしておく様子が分かる。

## 使ってみる

`code/main.py`はトグル可能な機能を持つvLLMスタイルのスケジューラーをシミュレートする。実行すると：

- `NAIVE`モード：一度に1リクエスト、バッチなし
- `STATIC`モード：パディングして待つ、クラシックバッチング
- `CONTINUOUS`モード：イテレーションレベルの受け入れと解放
- `CONTINUOUS + CHUNKED`モード：デコードと交互のプリフィルスライス

出力は仮想秒あたりの総スループット（トークン数）、TTFTの平均、P99 ITLを表示する。`CONTINUOUS + CHUNKED`行は混合トラフィックで支配的なはずだ。

## 演習

1. `code/main.py`を実行する。混合の短いリクエストと長いリクエストのワークロードで`STATIC`と`CONTINUOUS`を比較する。スループット差はプリフィル効率、デコード効率、テールレイテンシのどこから来るか？
2. おもちゃのスケジューラーを改変して`--max-num-batched-tokens`を追加する。Llama 3.3 70B FP8を実行するH100の正しい値は？（ヒント：KVブロックサイズと空きブロック数の関数で、生のHBMではない）
3. vLLM v0.18.0のリリースノートを再読する。互いに排他的なフラグの組み合わせはどれか？列挙する。
4. 平均出力1,500トークン、標準偏差600トークンの1,000リクエストのトレースで、（a）8192最大での連続リクエスト割り当て、（b）16トークンブロックのPagedAttentionでKVキャッシュ断片化の無駄を計算する。
5. チャンクプリフィルが単独ではスループットではなくP99 ITLを助ける理由を1段落で説明する。実際のスループット勝利はどこから来るか？

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------|
| PagedAttention | 「KVトリック」 | KVキャッシュ用の固定サイズブロックアロケーター。断片化4%未満 |
| ブロックテーブル | 「ページテーブル」 | シーケンスごとの論理トークン位置から物理KVブロックへのマップ |
| 連続バッチング | 「動的バッチング、ただし正しい」 | 受け入れ/解放の判断をデコードイテレーションごとに行う |
| チャンクプリフィル | 「プリフィル分割」 | 長いプリフィルをデコードと交互の512トークンスライスに分割 |
| TTFT | 「ファーストトークン時間」 | プリフィル + キュー + ネットワーク。長いプロンプトではプリフィルが支配 |
| ITL | 「インタートークンレイテンシ」 | 連続デコードトークン間の時間。バッチサイズが支配 |
| グッドプット | 「SLOを満たすスループット」 | すべてのリクエストがTTFTとITLターゲットを満たしているトークン/秒 |
| V1スケジューラー | 「新しいスケジューラー」 | vLLMの2026スケジューラー。Nグラム投機的デコードがチャンクプリフィル互換パス |
| `--gpu-memory-utilization` | 「メモリノブ」 | ウェイトとアクティベーション後にKVブロック用に予約するHBMの割合 |
