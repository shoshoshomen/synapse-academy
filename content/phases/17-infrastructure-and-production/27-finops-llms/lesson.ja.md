# LLMのFinOps — ユニットエコノミクスとマルチテナント帰属

> 従来のFinOpsはLLMの支出では機能しない。コストはトークントランザクションであり、リソースの稼働時間ではない。タグはマッピングされない——APIコールはトランザクションであり、アセットではない。エンジニアリングの決定（プロンプト設計、コンテキストウィンドウ、出力長）は財務的な決定だ。2026年のプレイブックには初日からインストゥルメント化すべき3つの帰属ディメンションがある：シートプライシングと拡張のためのユーザーごと（`user_id`）、製品サーフェスコストと優先順位付けのためのタスクごと（`task_id` + `route`）、ユニットエコノミクスと更新のためのテナントごと（`tenant_id`）。4つのトークン層——プロンプト、ツール、メモリ、レスポンス——を1つのバケツにまとめると支出が隠れる。マルチテナント製品のエンフォースメントラダー：テナントごとのレートリミット（予想ピークの2〜3倍、明確な429＋retry-after）；日次支出上限（契約上限の1.5〜3倍；レートを締め付けてアラートをトリガー）；支出のzスコアが4を超えたらキルスイッチ（自動停止＋オンコール呼び出し）。帰属パターン：タグアンドアグリゲート、テレメトリジョイナー（トレースID→請求；最高精度）、サンプリングと外挿、モデルベースアロケーション、イベントソース、リアルタイムストリーミング。ユニットメトリクス：解決されたクエリごとのコスト、生成された成果物ごとのコスト——$/Mトークンではない。遡及的なタグ付けは常に漏れがある；リクエスト作成時にインストゥルメント化する。


## 学習目標

- 従来のFinOps（タグ＋ティア）がLLMの支出で機能しない理由を説明し、3つの新しい帰属ディメンションを挙げる。
- 4つのトークン層（プロンプト、ツール、メモリ、レスポンス）と単一バケツ課金がコストを隠す理由を列挙する。
- マルチテナント製品のエンフォースメントラダー（レート→支出上限→キルスイッチ）を設計する。
- $/Mトークンの代わりにユニットメトリクス（解決されたクエリごとのコスト/成果物）を選ぶ。

## 問題の背景

請求書には$40,000と書かれている。以下がわからない：
- どのテナントが使ったか。
- どの製品機能が引き起こしたか。
- 個々のユーザーが乱用していたかどうか。
- プロンプトの膨張、ツールコール、メモリの増幅が原因かどうか。

プロバイダー側のタグアンドアグリゲートはタグが行アイテムに伝播するクラウドリソース（EC2、S3）では機能する。LLM APIコールは自動タグ付けされない——コールサイトでuser/task/tenantをスタンプして通し続けなければならない。遡及的な帰属は常にエッジケースを見逃す。

## コンセプト

### 3つの帰属ディメンション

**ユーザーごと**（`user_id`）：誰がいくら使っているか。シートプライシング、拡張の会話、パワーユーザーの特定に使う。

**タスクごと**（`task_id` + `route`）：どの製品サーフェスがいくらかかるか。機能の優先順位付け、高コスト機能の廃止決定に使う。

**テナントごと**（`tenant_id`）：どの顧客が利益をもたらすか。ユニットエコノミクス、更新時の価格設定、ティア閾値に使う。

初日からコールサイトで3つすべてをインストゥルメント化する。遡及的は常に精度が落ちる。

### 4つのトークン層

| 層 | 例 | 典型的な割合 |
|----|-----|------------|
| プロンプト | システム＋ユーザー入力 | 40〜60% |
| ツール | ツールコール結果のフィードバック | 20〜40%（エージェントワークロード） |
| メモリ | 過去の会話/取得したドキュメント | 10〜30% |
| レスポンス | モデル出力 | 10〜30% |

4つをまとめると最適化が盲目になる。帰属スキーマで分解する。

### エンフォースメントラダー

1. **レートリミット** テナントごと。予想ピークの2〜3倍。`Retry-After`付きで429を返す。テナントは摩擦を感じるが請求が膨らまない。

2. **日次支出上限** テナントごと。契約上限の1.5〜3倍。トリガー：レートリミットを締め付けてカスタマーサクセスにアラート。

3. **キルスイッチ** テナントベースラインに対する支出のzスコアが4を超えたとき。テナントを自動停止；オンコールに呼び出し；Ops＋CSにエスカレーション。

### 帰属パターン

- **タグアンドアグリゲート**：メタデータヘッダーをスタンプして後でアグリゲート。シンプルだが粗い。
- **テレメトリジョイナー**：トレースIDでトレースと請求を結合。最高精度。成熟したチームがやること。
- **サンプリングと外挿**：5〜10%をサンプリングして乗算。概算支出にはコスト効率が良い；テールを見逃す。
- **モデルベースアロケーション**：回帰でコストドライバーを推測。タグのないレガシーデータ向け。
- **イベントソース**：ストリーム（Kafka/Kinesis）のイベントとしてのコスト。リアルタイム。
- **リアルタイムストリーミング**：ダッシュボードがサブ秒で更新。

### コストXはユニットメトリクス

$/Mトークンはベンダー用語だ。製品メトリクス：

- サポートチケット1件解決あたりのコスト。
- 記事1本生成あたりのコスト。
- エージェントタスク成功1件あたりのコスト。
- ユーザーセッション1分あたりのコスト。

コストを製品のアウトカムに結びつける。そうしないと最適化の基準がなくなる。

### コスト帰属トレースの形

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

全てのコールで発行する。データレイクに保存する。ディメンションごとにアグリゲートする。フェーズ17・13のオブザーバビリティスタックがここに住む。

### コンパウンドされた節約スタック

スタック：キャッシュ＋バッチ＋ルート＋ゲートウェイ。4つすべてで：
- キャッシュL2（フェーズ17・14）：入力が約10倍安い。
- バッチ（フェーズ17・15）：50%オフ。
- 安価なモデルへのルーティング（フェーズ17・16）：60%コスト削減。
- ゲートウェイ効率（フェーズ17・19）：冗長性＋リトライ。

最良のケースでスタック：単純なベースラインの約5〜10%。ほとんどのチームは2〜3つのレバーを使っている；4つすべてをスタックするチームは少ない。

### 覚えておくべき数値

- 帰属ディメンション：ユーザーごと、タスクごと、テナントごと。
- 4つのトークン層：プロンプト、ツール、メモリ、レスポンス。
- キルスイッチ：支出のzスコアが4を超えたとき。
- ユニットメトリクス：解決されたクエリごとのコスト、$/Mトークンではない。
- スタックされた最適化：ベースラインの約5〜10%が可能。

## 使ってみる

`code/main.py`は3層エンフォースメントラダーを持つマルチテナントLLMサービスをシミュレートする。悪意のあるテナントを注入し、キルスイッチが発動するデモを見せる。

## 成果物を出す

このレッスンでは`outputs/skill-finops-plan.md`を生成する。製品とスケールを考慮して、帰属スキーマとエンフォースメントラダーを設計する。

## 演習

1. `code/main.py`を実行する。キルスイッチはどのzスコアで発動するか？閾値をどう選ぶか？
2. テナントごと、タスクごとのコストダッシュボードを設計する。最初に構築する5つのビューは何か？
3. 最大のテナントがユニットエコノミクス的に赤字だ。顧客インパクト順に3つの介入を提案する。
4. サポート製品のチケット1件解決あたりのコストを計算する：チケットあたり3Mトークン、1日約800件、GPT-5キャッシュレート。
5. 遡及的なタグ付けが機能するかどうかを議論する。それが許容される場合はいつか？

## キーワード

| 用語 | よく言われる表現 | 実際の意味 |
|------|----------------|------------|
| ユーザーごとの帰属 | 「ユーザーレベルコスト」 | 全てのコールにスタンプされた`user_id` |
| タスクごとの帰属 | 「機能コスト」 | 製品サーフェスを特定する`task_id`＋`route` |
| テナントごとの帰属 | 「顧客コスト」 | `tenant_id`；ユニットエコノミクスを駆動 |
| 4つのトークン層 | 「コスト層」 | プロンプト＋ツール＋メモリ＋レスポンス |
| レートリミット | 「429ガード」 | ゲートウェイで適用されるテナントごとの上限 |
| 日次支出上限 | 「日次上限」 | アラート付きのテナントスコープの予算 |
| キルスイッチ | 「自動停止」 | 支出のzスコアが4を超えると自動停止がトリガー |
| 解決あたりのコスト | 「製品ユニットメトリクス」 | トークンではなく製品のアウトカムに結びついたコスト |
| テレメトリジョイナー | 「トレースから請求へ」 | 最高精度の帰属パターン |
| スタックされた最適化 | 「キャッシュ＋バッチ＋ルート＋ゲートウェイ」 | ベースラインの約5〜10%まで節約を複利化 |
