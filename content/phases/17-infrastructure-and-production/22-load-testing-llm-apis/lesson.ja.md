# LLM APIの負荷テスト — k6とLocustが嘘をつく理由

> 従来の負荷テスターはストリーミングレスポンス、可変出力長、トークンレベルのメトリクス、GPU飽和のために設計されていなかった。ほとんどのチームに2つの落とし穴が噛みつく。GILの落とし穴：Locustのトークンレベルの測定はPython GILの下でトークン化を実行し、高並列性下でリクエスト生成と競合する；その後トークン化のバックログが報告されたインタートークンレイテンシを膨らませる——クライアントがボトルネックであり、サーバーではない。プロンプト一様性の落とし穴：ループ内の同一プロンプトはトークン分布上の1点をテストする；実際のトラフィックは可変長と多様なプレフィックスマッチを持つ。LLMPerfは`--mean-input-tokens`＋`--stddev-input-tokens`でこれを修正する。2026年のツールマッピング：トークンレベルの精度にはLLM専門ツール（GenAI-Perf、LLMPerf、LLM-Locust、guidellm）；**k6 v2026.1.0**＋**k6 Operator 1.0 GA（2025年9月）** — ストリーミング認識、TestRun/PrivateLoadZone CRD経由のKubernetesネイティブ分散、CI/CDゲートに最適；Go定常レート飽和にはVegeta；ストリーミング用にはLLM-Locust拡張付きのLocust 2.43.3のみ。負荷パターン：定常状態、ランプ、スパイク（オートスケーリングテスト）、ソーク（メモリリーク）。


## 学習目標

- LLM APIで汎用的な負荷テスターが嘘をつく2つのアンチパターン（GILの落とし穴、プロンプト一様性の落とし穴）を説明する。
- 目的に応じたツールを選択する：LLMPerf（ベンチマーク実行）、k6＋ストリーミング拡張（CIゲート）、guidellm（大規模合成）、GenAI-Perf（NVIDIAリファレンス）。
- 4つの負荷パターン（定常、ランプ、スパイク、ソーク）を設計し、それぞれが検出する障害モードを挙げる。
- 固定長ではなく入力トークンの平均＋標準偏差を使ってリアルなプロンプト分布を構築する。

## 問題の背景

LLMエンドポイントを500同時ユーザーでk6テストした。持ちこたえた。リリースした。実際の200ユーザーで本番サービスが崩壊——P99 TTFTが爆発し、GPUが固まった。

2つのことが起きた。まず、k6が500件の同一プロンプトを送ったため——リクエストのコアレッシングとプレフィックスキャッシュで、実際には1件の同時デコードを処理していたのに500件を処理しているように見えた。次に、k6はストリーミングレスポンスのインタートークンレイテンシを目で見るような方法で追跡しない；1つのHTTP接続を見るが、様々な間隔で到着する500トークンではない。

LLMの負荷テストはそれ自体が独立した規律だ。

## コンセプト

### GILの落とし穴（Locust）

LocustはPythonを使い、GILの下でクライアント側でトークン化を実行する。高並列性下でトークナイザーがリクエスト生成の後ろに並ぶ。報告されたインタートークンレイテンシにはクライアント側のトークン化バックログが含まれる。サーバーが遅いと思うが、テストハーネスが原因だ。

修正：LLM-Locust拡張がトークン化を別プロセスに移動する、またはコンパイル言語ハーネス（k6、tokenizers.rsを使うLLMPerf）を使う。

### プロンプト一様性の落とし穴

既知の負荷テスターはすべて1つのプロンプトを設定できる。10,000回のループテストで正確に同じプロンプトが毎回送られる。サーバーは毎回同じプレフィックスを見る——プレフィックスキャッシュのヒット率が100%に近づき、スループットが素晴らしく見える。

修正：プロンプト分布からサンプリングする。LLMPerfは`--mean-input-tokens 500 --stddev-input-tokens 150`を使う——多様な長さ、多様なコンテンツ。

### 4つの負荷パターン

1. **定常状態** — 30〜60分間の一定RPS。検出：ベースラインのパフォーマンス後退。
2. **ランプ** — 15分間でRPSを0から目標まで線形に増加。検出：容量ブレークポイント、ウォームアップ異常。
3. **スパイク** — 2分間のRPSの3〜10倍の急増後に元に戻す。検出：オートスケーリングのレイテンシ、キュー飽和、コールドスタートの影響。
4. **ソーク** — 4〜8時間の定常状態。検出：メモリリーク、コネクションプールドリフト、オブザーバビリティのオーバーフロー。

### 2026年のツールマッピング

**LLMPerf**（Anyscale）— PythonだがRustバックドのトークン化。平均/標準偏差プロンプト。ストリーミング認識。パフォーマンス実行のデフォルトとして最適。

**NVIDIA GenAI-Perf** — NVIDIAのリファレンス。Tritonクライアントを使用；包括的なメトリクスカバレッジ。そのITLはTTFTを除外することに注意；LLMPerfのは含む。2つのツールが同じサーバーに対して異なるTPOTを生成する。

**LLM-Locust**（TrueFoundry）— GILの落とし穴を修正するLocust拡張。使い慣れたLocust DSL＋ストリーミングメトリクス。

**guidellm** — 大規模合成ベンチマーキング。

**k6 v2026.1.0**＋**k6 Operator 1.0 GA（2025年9月）**：
- k6自体（Go、コンパイル済み、GILなし）がストリーミング認識メトリクスを追加した。
- k6 OperatorはTestRun / PrivateLoadZone CRDを使ってKubernetesネイティブの分散テストを実施。
- CI/CDゲートとSLAテストに最適。

**Vegeta** — Go、k6よりシンプル。一定レートHTTP飽和。LLM認識ではないが、ゲートウェイ/レート制限テストに良い。

**Locust 2.43.3ストック** — LLMにはGILの落とし穴がある。LLM-Locust拡張付きのみ。

### CIのSLAゲート

PRでk6を実行する：

- ベースラインRPSで各30〜50回反復。
- ゲート：P50/P95 TTFT、5xx < 5%、閾値未満のTPOT。
- 違反時はビルドを壊す。

### リアルなプロンプト分布

実際のトラフィックサンプルから構築する（持っている場合）、または公開された分布から構築する（チャット用のShareGPTプロンプト、コード用のHumanEval）。平均＋標準偏差をLLMPerfに渡す。1つのプロンプトでのループはどんな代償を払ってでも避ける。

### 覚えておくべき数値

- k6 Operator 1.0 GA：2025年9月。
- k6 v2026.1.0：ストリーミング認識メトリクス。
- 典型的なLLMPerf実行：並列性Xで100〜1,000リクエスト。
- 典型的なCIゲート：PRごとに30〜50回反復。
- 4つのパターン：定常、ランプ、スパイク、ソーク。

## キーワード

| 用語 | よく言われる表現 | 実際の意味 |
|------|----------------|------------|
| LLMPerf | 「LLMハーネス」 | Anyscaleのベンチマークツール、ストリーミング認識 |
| GenAI-Perf | 「NVIDIAツール」 | NVIDIAのリファレンスハーネス |
| LLM-Locust | 「LLM用Locust」 | GILの落とし穴を修正するLocust拡張 |
| guidellm | 「合成ベンチマーク」 | 大規模合成ツール |
| k6 Operator | 「K8s k6」 | CRDベースの分散k6 |
| GIL trap | 「Pythonクライアントのオーバーヘッド」 | トークン化バックログが報告レイテンシを膨らませる |
| Prompt-uniformity trap | 「シングルプロンプトの嘘」 | 同じプロンプトのループがキャッシュにヒットしてスループットを膨らませる |
| Steady-state | 「一定負荷」 | N分間の平坦なRPS |
| Ramp | 「線形増加」 | 0から目標まで期間をかけて |
| Spike | 「バーストテスト」 | 急激な乗数後に元に戻す |
| Soak | 「長時間テスト」 | リーク検出のための数時間 |
