# LLMのためのシャドウトラフィック、カナリーロールアウト、プログレッシブデプロイメント

> LLMのロールアウトはソフトウェアデプロイメントの最も難しい部分を組み合わせる：ユニットテストなし、拡散した障害モード、遅延したシグナル。シーケンスは次の通り：(1) シャドウモード——プロダクションリクエストを候補モデルに複製してログを取り、ユーザーへの影響ゼロで比較する；明らかな分布問題を検出するが品質保証ではない；(2) カナリーロールアウト——各ステップでゲートを設けながらトラフィックを10% → 25% → 50% → 75% → 100%と段階的にシフトする；レイテンシパーセンタイル、リクエストあたりのコスト、エラー/拒否率、出力長分布、ユーザーフィードバック率を追跡する；(3) 安定性確認後の明確な代替案に対するA/Bテスト。非決定性は不可逆だ——GPU FPの非結合性とバッチサイズの分散により、同一入力での実行間で最大15%の精度変動がある。コストは定数ではなく変数だ——20%優れたモデルがコール1回あたり3倍高価になり得る。ロールバック速度が決定的だ：ロールバックに再デプロイが必要なら遅すぎる。ポリシーは設定/フラグで管理し、モデルはピン固定されたダイジェストでレジストリに保管する；ロールバック = ポリシーを変更 + 閾値を元に戻す + 数秒で古いモデルをピン固定。


## 学習目標

- シャドウモード（ゼロインパクト比較）、カナリー（ライブトラフィックのプログレッシブ）、A/B（安定性確認後の比較）を区別する。
- LLM固有の5つのカナリーメトリクスを列挙する（レイテンシ、リクエストあたりのコスト、エラー/拒否、出力長分布、ユーザーフィードバック）。
- LLMの非決定性（最大15%）がロールアウトで「安定」の意味をどう変えるかを説明する。
- 時間（再デプロイ）ではなく秒単位のロールバックパス（ポリシーフリップ）を設計する。

## 問題の背景

新しいモデルをリリースした。オフライン評価で3%の精度向上が示されている。本番で有効にした。24時間以内に、コストが40%増加し、ユーザーのサムズダウンが8%増加し、3件の顧客チケットが「奇妙な回答」を報告した。ロールバックした。再デプロイに3時間かかった。週末が台無しになった。

これはすべて防げた。シャドウモードはどのユーザーも見る前に40%のコストスパイクを検出していた。カナリーはサムズダウンが動いた10%の段階で止まっていた。ポリシーフラグのロールバックは30秒かかった。この規律は「オフライン評価が良好に見える」と「実際のユーザーが満足している」の間のギャップを埋めるものだ。

## コンセプト

### シャドウモード

候補がプロダクションと同じリクエストを受け取り、出力がログに記録されてユーザーに返されない。ユーザーへの影響はゼロ。ログ：

- 出力内容（プロダクションとの差分）。
- トークン数（コストデルタ）。
- レイテンシ。
- 拒否とエラー。

検出できるもの：コスト爆発、長さの後退、明らかな拒否変化、ハードエラー。検出できないもの：ユーザーが感じる品質デルタ。シャドウはスモークテストであり、品質テストではない。

### カナリーロールアウト

ゲート付きのプログレッシブトラフィックシフト。典型的な進行：1% → 10% → 25% → 50% → 75% → 100%。各ステップで5つのメトリクスをゲートする：

1. **レイテンシパーセンタイル** — P50、P95、P99。違反：カナリーのP99がベースラインの1.5倍超。
2. **リクエストあたりのコスト** — ブレンド$。違反：ベースライン比20%超。
3. **エラー/拒否率** — 5xxと明示的な拒否。違反：ベースラインの2倍。
4. **出力長分布** — 平均＋P99。違反：分布シフト。
5. **ユーザーフィードバック率** — サムズダウン/チケット提出。違反：ベースラインの1.5倍。

### 非決定性が新しい分散だ

同一入力が同一でない出力を生む。理由：

- GPU FP非結合性（浮動小数点の削減順序がバッチによって異なる）。
- バッチサイズの分散（128のバッチ対16のバッチで同じプロンプト）。
- サンプリング（temperature > 0）。

測定値：同一評価セットでの実行間で最大15%の精度変動。ロールアウトでの「安定」とは、メトリクスが期待される分散の範囲内であること——ベースラインと同一ではない。ノイズフロアよりも高いゲートを設定する。

### コストが変数だ

20%優れたモデルがコール1回あたり3倍高価になり得る。リクエストあたりのコストが5つのゲートの1つだ。「より良い」モデルをリリースしてユニット経済を壊すのはロールバックケースだ。

### ロールバックが武器だ

- ポリシーフラグ（フィーチャーフラグシステム）：設定でパーセンテージをフリップ；数秒かかる。
- モデルピン固定（レジストリダイジェスト）：ピン固定されたモデルは自動アップグレードしない。
- ロールバック = フラグを元に戻す + ピン固定されたダイジェストを以前に設定する。時間ではなく秒。

ロールバックに再デプロイが必要なスタックは、ローリング前にそれを修正すること。

### ツール

**Argo Rollouts** / **Flagger** — Kubernetesプログレッシブデリバリーコントローラー。Istio/Linkerdの重み付きルーティングと統合。

**Istio重み付きルーティング** — サービスメッシュレベルのトラフィック分割。

**KServe / Seldon Core** — カナリー機能を内蔵したモデルサービング。

**フィーチャーフラグ** — LaunchDarkly、Flagsmith、Unleash。ポリシーレベルのフリップ、再デプロイ不要。

### メトリクスのケイデンス

カナリーゲートはトラフィックボリュームによって5〜15分ごとにチェックする。1%のトラフィックで10 req/minなら、ウィンドウごとに50〜150データポイント——レイテンシには十分だがユーザーフィードバックにはノイジー。10%なら約10倍多い。各ステップで十分なサンプルを蓄積するのに十分なほど長く進行を一時停止すべきだ。

### A/Bステップはオプション

新しいモデルが明確に異なる場合（異なる動作、異なるコストカーブ、異なるトーン）、カナリー通過後に50%でA/Bテストする。単に改善されたバージョンならカナリーゲートを通過したら100%に進む。

### 覚えておくべき数値

- カナリー進行：1% → 10% → 25% → 50% → 75% → 100%。
- 非決定性の上限：同一入力での実行間で最大15%の分散。
- 5つのカナリーメトリクス：レイテンシ、コスト、エラー/拒否、出力長、ユーザーフィードバック。
- コストゲート：ベースライン比20%超は違反。
- ロールバック：時間ではなく秒。

## 使ってみる

`code/main.py`は、注入された後退でカナリーロールアウトをシミュレートする。どのステージでロールアウトが止まり、どのゲートがトリガーされたかをレポートする。

## 成果物を出す

このレッスンでは`outputs/skill-rollout-runbook.md`を生成する。候補モデル、ベースライン、リスク許容度を考慮して、シャドウ→カナリー→100%プランを設計する。

## 演習

1. `code/main.py`を実行する。25%のコスト後退を注入する。どのステージでカナリーが止まるか？
2. 新しいモデルがオフラインで3%の精度向上を持つが、リクエストあたりのコストが+18%。リリースするか？ポリシーによる——両方のパスを書く。
3. エンドツーエンドで60秒未満でロールバックできる設計を作る。必要なインフラを列挙する。
4. 非決定性が評価で±7%を示す。誤アラートが出ないようにカナリーゲートを設定する。どの乗数を使うか？
5. シャドウモードがカナリー前に40%のコストスパイクを検出する。シャドウで発火するアラートルールを書く。

## キーワード

| 用語 | よく言われる表現 | 実際の意味 |
|------|----------------|------------|
| Shadow mode | 「新しいものに複製」 | ログのためにゼロインパクトで候補に送信 |
| Canary | 「プログレッシブトラフィック」 | ゲート付きのユーザー向け段階的ロールアウト |
| Gates | 「ロールアウトチェック」 | 進行をブロックするメトリクス閾値 |
| Non-determinism | 「LLMの分散」 | 不可逆な実行間の差異 |
| Policy flag | 「フラグフリップのロールバック」 | 設定レベルのロールバック、時間ではなく秒 |
| Model pin | 「レジストリダイジェスト」 | モデルバージョンへの不変参照 |
| Argo Rollouts | 「K8sプログレッシブ」 | Kubernetesネイティブのカナリー/ロールバックコントローラー |
| KServe | 「推論K8s」 | カナリープリミティブを持つモデルサービング |
| Istio weighted | 「メッシュスプリット」 | サービスメッシュのトラフィックスプリッター |
