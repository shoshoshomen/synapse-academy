# AIのためのSRE — マルチエージェントのインシデント対応、ランブック、予測検知

> AI SREはインフラデータ（ログ、ランブック、サービストポロジー）によってグラウンディングされたLLMをRAG経由で使い、調査・文書化・調整フェーズを自動化する。2026年のアーキテクチャパターンはマルチエージェントオーケストレーション——専門エージェント（ログ、メトリクス、ランブック）がスーパーバイザーによって調整される；AIが仮説とクエリを提案し、人間が判断の呼び出しを承認する。Datadog Bits AIとAzure SRE Agentはこれをマネージド製品としてリリースしている。ランブックが進化中だ：NeuBird Hawkeyeは対立的評価（2つのモデルが同じインシデントを分析；合意 = 信頼度、不一致 = 不確実性）を使い；運用メモリはチームの変更を超えて持続する。自動修復は慎重なまま：AIが提案し、人間が承認する。完全な自律的アクションは狭く（ポッドの再起動、特定のデプロイのロールバック）厳格なガードレール付き——「設定して忘れろ」を売る人は売りすぎだ。新興のフロンティア：インシデント前の予測。MITの研究では、過去のログ＋GPU温度＋APIエラーパターンで訓練されたLLMが障害の89%を10〜15分前に予測したと報告している。予測：2026年末までにエンタープライズLLMの95%が自動フェイルオーバーを持つ。


## 学習目標

- マルチエージェントAI SREアーキテクチャを図示する：スーパーバイザー＋専門エージェント（ログ、メトリクス、ランブック）＋人間承認ゲート。
- 自動修復が（サービスの再アーキテクトではなく）ポッドの再起動やデプロイの元に戻しなど狭い理由を説明する。
- 対立的評価パターン（NeuBird Hawkeye）を挙げる：2つのモデルが合意 = 信頼度；不一致 = エスカレート。
- MITの89%早期検知の結果と運用上の制約を引用する：予測と実行がなければダッシュボードに過ぎない。

## 問題の背景

オンコールエンジニアが午前3時にページを受ける。「チェックアウトで高エラー率」。DatadogをチェックしLokiを確認し3つのランブックとデプロイログを調べる。30分後にKVキャッシュスパイクによるvLLM OOMが根本原因だとわかる。ポッドを再起動し、エラーが解消する。

2026年ではその調査の最初の20分は自動化可能だ。サービスごとのログのグループ化、最近のデプロイとの相関、ランブックとのマッチング——これらすべてがRAG＋ツール使用だ。監督されたエージェントは人間がDatadogを開く前に最初のトリアージを行い仮説を提示できる。

完全な自律的修復は別の問題だ。ポッドの再起動：安全。GPUプールのスケール：ポリシーが許可する場合は安全。サービスの再アーキテクト：絶対にない。規律は狭い線を引くことだ。

## コンセプト

### マルチエージェントアーキテクチャ

```
          Incident
             │
             ▼
        Supervisor
        /    |    \
       ▼     ▼     ▼
  Log agent  Metric agent  Runbook agent
       │     │     │
       └─────┴─────┘
             │
             ▼
        Hypothesis + evidence
             │
             ▼
        Human approval
             │
             ▼
        Action (narrow set)
```

スーパーバイザーがインシデントをサブクエリに分解する。専門エージェントはツールアクセスを持つ（ログ検索、PromQL、ドキュメント検索）。スーパーバイザーが統合し、仮説＋証拠を人間に提示する。人間が承認するかリダイレクトする。

### 自動修復のスコープ

**安全（狭い）**：ポッドの再起動、特定のデプロイの元に戻し、事前承認された範囲内でのプールのスケール、事前承認されたフィーチャーフラグの有効化。

**安全でない（広い）**：サービストポロジーの変更、リソース制限の変更、新しいコードのデプロイ、IAMの変更、データベースの変更。

「設定して忘れろ」を売る人は売りすぎだ。AI SREが成熟するにつれて安全なセットは成長するが、境界は実在する。

### 対立的評価（NeuBird Hawkeye）

2つのモデルが同じインシデントを独立して分析する。根本原因で合意する場合は信頼度が高い。不一致の場合は両方の仮説を見えた状態で人間にエスカレートする。シンプルなパターンで幻覚的な根本原因に対する効果的なフィルターだ。

### 運用メモリ

チームの入れ替わりは従来のSREのサイレントキルだ——部族的知識が去る。AI SREはランブック＋ポストモーテムをベクトルDBに保存し；エージェントが新しいインシデントごとに検索する。新しいエンジニアが参加したとき、AIは完全な履歴を持っている。

### インシデント前の予測

MIT 2025年研究：過去のログ、GPU温度、APIエラーパターンで訓練されたLLMがテストセットで障害の89%を発生10〜15分前に予測した。

現実チェック：実行のない予測はダッシュボードだ。運用上の問いは「予測したとき、何をするか？」だ。予防的ドレイン？ページャー？オートスケール？答えはポリシー固有だ。

### 2026年の製品

- **Datadog Bits AI** — Datadog内のマネージドSREコパイロット。
- **Azure SRE Agent** — Azureネイティブ。
- **NeuBird Hawkeye** — 対立的評価＋運用メモリ。
- **PagerDuty AIOps** — トリアージ＋重複排除。
- **Incident.io Autopilot** — インシデントコマンダー＋調整。

### コードとしてのランブック

ランブックはConfluenceページから構造化セクション付きのバージョン管理されたmarkdownに進化する（症状、仮説、検証、行動）。構造化されたランブックはよりよいRAG検索を提供する。AI-SREのロールアウトはまず非構造化ランブックを構造化に変換することから始める。

### 覚えておくべき数値

- MITの早期検知：障害の89%、10〜15分のリードタイム。
- マルチエージェントトリアージ：スーパーバイザー＋（ログ、メトリクス、ランブック）＋人間。
- 安全な自動修復セット：ポッドの再起動、デプロイの元に戻し、範囲内でのスケール。
- 対立的評価：2つのモデルが独立；合意 = 信頼度。

## 使ってみる

`code/main.py`はマルチエージェントトリアージをシミュレートする：ログエージェントがエラーを見つけ、メトリクスエージェントがCPUスパイクを見つけ、ランブックエージェントが既知の問題とマッチさせる。スーパーバイザーが仮説をランク付けする。

## 成果物を出す

このレッスンでは`outputs/skill-ai-sre-plan.md`を生成する。現在のオンコール、インシデントボリューム、チームの成熟度を考慮して、AI SREのロールアウトを設計する。

## 演習

1. `code/main.py`を実行する。ログとメトリクスエージェントが不一致の場合はどうなるか？スーパーバイザーはどう解決するか？
2. サービスに対して3つの「安全な」自動修復アクションを定義する。それぞれを正当化する。
3. 構造化ランブックテンプレートを書く：セクション、必須フィールド、検証コマンド。
4. 予測検知が12分のリードタイムで発火する。ポリシーは何か——ページャー、予防的ドレイン、または両方？
5. 3人チームが2026年にAI SREを採用すべきか、待つべきかを議論する。成熟度、ボリューム、リスクを考慮する。
