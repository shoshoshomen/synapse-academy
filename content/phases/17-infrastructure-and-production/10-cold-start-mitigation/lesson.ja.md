# サーバーレスLLMのコールドスタート軽減

> 20GBのモデルイメージは、コールドから配信まで5〜10分（7B）から20分以上（70B）かかる。真のサーバーレス世界では、それはウォームアップではなく障害だ。軽減策は5つの層で操作する：事前シードされたノードイメージ（AWS上のBottlerocket、デュアルボリュームアーキテクチャ）、モデルストリーミング（NVIDIA Run:ai Model Streamer、vLLMにネイティブ）、GPUメモリスナップショット（Modalチェックポイント、最大10倍高速な再起動）、ウォームプール（`min_workers=1`）、階層型ロード（ServerlessLLMのNVMe→DRAM→HBMパイプライン、レイテンシ10〜200倍削減）、およびKVキャッシュ（GB）ではなく入力トークン（KB）を移動するライブマイグレーション。Modalは2〜4sのコールドスタートをフロアとして公開。BasetenはデフォルトとしてGreetings5〜10s、事前ウォームアップで1秒未満。このレッスンでは5つの層を測定、予算化、積み重ねることを教える。


## 学習目標

- コールドスタート軽減の5つの層を列挙し、各層での1つのツールまたはパターンを挙げる。
- 70Bモデルの合計コールドスタート時間を（ノードプロビジョニング）+（ウェイトダウンロード）+（HBMへのウェイトロード）+（エンジン初期化）の合計として計算する。
- ライブマイグレーションがKVキャッシュ（GB）ではなく入力トークン（KB）を転送する理由と、そのペナルティ（再計算）が何かを説明する。
- ウォームプールのトレードオフ（アイドルGPUの費用を払うかコールドスタートのテールを受け入れるか）と、`min_workers > 0`が必須になるSLAしきい値を挙げる。

## 問題

サーバーレスLLMエンドポイントが夜間にゼロにスケールする。午前8時にトラフィックが急増する。最初のリクエストが待つ：

1. Karpenterがノードをプロビジョニング：45〜60秒
2. コンテナがウェイト付きの30GBイメージをプル：120〜300秒
3. エンジンがウェイトをHBMにロード：モデルサイズとストレージ速度によって45〜120秒
4. vLLMまたはTRT-LLMがCUDAグラフ、KVキャッシュプール、トークナイザーを初期化：10〜30秒

合計：220〜510秒（おおよそ3〜8分）、1トークンが戻る前。SLAは2秒だ。ウォームプール（`min_workers=1`）を出荷すると問題が消えたように見えるが — 今は24時間365日1台のアイドルGPUに支払っている。サービスに5つのプロダクトがあり各ウォームレプリカが1つなら、単一ユーザーが呼ばなくても5 × 24 × 30 = 3,600 GPU時間/月だ。

コールドスタート軽減は、サーバーレス経済を維持しながら常時オンのレイテンシに近づける方法だ。

## コンセプト

### 第1層 — 事前シードされたノードイメージ（Bottlerocket）

AWSでは、BottlerocketのデュアルボリュームアーキテクチャがOSとデータを分離する。コンテナイメージが事前プルされたデータボリュームのスナップショットを取り、`EC2NodeClass`でスナップショットIDを参照する。新しいノードはウェイトがすでにローカルNVMeにある状態でブートする — ステップ2とステップ3の一部が消える。KarpenterとネイティブGに動作する。典型的な節約：大規模モデルのコールドスタートごとに2〜4分。

GCPの同等品：事前ベイクされたコンテナレイヤー付きのカスタムVMイメージ。Azure：同じパターンでマネージドディスクスナップショット。

### 第2層 — モデルストリーミング（Run:ai Model Streamer）

最初のリクエストに応答する前にフルファイルをロードする代わりに、ウェイトをGPUメモリにレイヤーごとにストリームし、最初のトランスフォーマーブロックが常駐したらすぐに処理を開始する。NVIDIA Run:ai Model Streamerは2026年のvLLMにネイティブで搭載されている。S3、GCS、ローカルNVMeと動作する。I/OとコンピュートセットアップをオーバーラップすることでRamaの大規模モデルのウェイトロード時間をおよそ半分に削減する。

### 第3層 — GPUメモリスナップショット（Modal）

Modalは最初のロード後のGPU状態（ウェイト、CUDAグラフ、KVキャッシュ領域）のチェックポイントを取る。後続の再起動はHBMに直接デシリアライズする — 再初期化より10倍速い。これは「2秒でウォームGPUをブート」に最も近いものだ。トレードオフ：スナップショットはGPUトポロジーごとなので、Karpenterが異なるSKUに移行すると再チェックポイントが必要だ。

### 第4層 — ウォームプール（min_workers=1）

最もシンプルな軽減：常に1つのレプリカを準備しておく。コストは24時間365日のGPUの時間当たりレート。計算は小さなモデルには厳しく（30秒のコールドスタートを避けるために0.85〜1.50ドル/時払う）、大きなモデルには親切だ（5分のコールドスタートを避けるために4ドル/時払う）。ウォームプールが必須になるSLAしきい値：70B以上のモデルでTTFT P99 < 60秒が典型。

### 第5層 — 階層型ロード（ServerlessLLM）

ServerlessLLMはストレージを階層として扱う：NVMe（速いが大きい）、DRAM（中程度だが階層化）、HBM（小さいが瞬時）。ウェイトはDRAMに事前ロードされ、HBMにオンデマンドでロードされる。論文はナイーブなディスクからHBMと比較してコールドロードで10〜200倍のレイテンシ削減を報告。本番採用は初期段階だがvLLMとの統合が存在する。

### 第6層 — ライブマイグレーション（ボーナスパターン）

ノードが利用できなくなった場合（スポット退去、ノードドレイン）、従来のパターンは別のレプリカをコールドスタートしてリクエストキューをドレインすることだ。ライブマイグレーションは入力トークン（キロバイト）をモデルがロードされている宛先に移動し、宛先でKVキャッシュを再計算する。再計算はネットワーク経由でGBのKVキャッシュを転送するより安い。分散デプロイメントに適用可能。

### ウォームプールの計算

P99 TTFT SLA 2秒のサービスでは、問いは「ウォームプールはい/いいえ」ではなく「ウォームレプリカをいくつ、どのパスが受け取るか」だ。

- 価値の高いインタラクティブパス（ライブチャット、音声エージェント）：`min_workers=1〜2`
- バックグラウンドバッチパス（夜間分類）：ゼロへのスケールを受け入れ、5〜10分のコールドスタートは許容
- プレミアムティア：専用キャパシティでテナントごとの`min_workers`

### 最適化する前に測定する

新しいノード上の70Bモデルのコールドスタートの構造（例示的）：

| フェーズ | 時間 | 軽減 |
|---------|------|------|
| ノードプロビジョニング | 50秒 | Bottlerocket + 事前シードイメージ、ウォームプール |
| イメージプル | 180秒 | 事前シードデータボリューム（排除） |
| HBMへのウェイト | 75秒 | モデルストリーマー（半分に）、GPUスナップショット（排除） |
| エンジン初期化 | 20秒 | 永続CUDAグラフキャッシュ |
| 最初のフォワード | 3秒 | 固有の最小レイテンシ |
| **合計コールド** | **328秒** | |
| **軽減後合計** | **約15秒** | 22倍削減 |

### 覚えておくべき数値

- Modalのコールドスタート：2〜4秒（GPUスナップショット付き）
- Basetenのデフォルトコールドスタート：5〜10秒。事前ウォームアップで1秒未満
- 生の70Bコールドスタート：3〜8分
- Run:ai Model Streamer：ウェイトロード約2倍スピードアップ
- ServerlessLLM階層型ロード：10〜200倍レイテンシ削減（論文数値）

## 使ってみる

`code/main.py`は各軽減ありとなしのコールドスタートパスをモデル化する。合計コールドスタート時間、ウォームプールコスト、ウォームプールが自身のコストを正当化するための損益分岐リクエストレートを報告する。

## 成果物を出す

このレッスンでは`outputs/skill-cold-start-planner.md`を作成する。SLA、モデルサイズ、トラフィックシェイプに基づいてどの軽減を積み重ねるかを選択する。

## 演習

1. `code/main.py`を実行する。ウォームレプリカがSLO上のコールドスタート税による追加リクエストドロップを払うより安くなる損益分岐リクエストレートを計算する。
2. P99 TTFT SLA 3秒の13Bモデルをデプロイする。それを達成する最小軽減スタック（最少の層）を選ぶ。
3. Bottlerocket事前シードはイメージプルを排除するが、スナップショットされたNVMeからHBMへのウェイトロードは残る。NVMeが7 GB/sで読む場合の70Bモデルの壁時間を計算する。
4. サーバーレスプロバイダーがGPUスナップショット（Modal）を提供するが、チームが「スナップショットはPIIをリークする」として拒否する。両方の立場を論じる — 現実的なリスクは何か、軽減策は何か（エフェメラルスナップショット、暗号化、名前空間分離）？
5. 階層型ウォームプールポリシーを設計する：有料ユーザー、トライアルユーザー、バッチワークロードにいくつのウォームレプリカか？計算を示す。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------|
| コールドスタート | 「大きな休止」 | 新しいレプリカでリクエストから最初のトークンまでの時間 |
| ウォームプール | 「常時オンの最小値」 | 少なくとも1つのレプリカを準備しておく`min_workers >= 1` |
| 事前シードイメージ | 「ベイクされたAMI」 | コンテナウェイトが事前常駐しているノードイメージ |
| Bottlerocket | 「AWSノードOS」 | デュアルボリュームスナップショットサポート付きのAWSコンテナ最適化OS |
| モデルストリーマー | 「ストリーミングロード」 | ウェイトI/Oとコンピュートセットアップをオーバーラップ |
| GPUスナップショット | 「HBMへのチェックポイント」 | ポストロードGPU状態をシリアライズ。再起動時にデシリアライズ |
| 階層型ロード | 「NVMe + DRAM + HBM」 | ストレージ層の階層。オンデマンドでロード |
| ライブマイグレーション | 「トークンを移動」 | 入力（KB）を転送し、宛先でKVを再計算 |
| `min_workers` | 「ウォームレプリカ」 | サーバーレスの最小キープアライブカウント |
| ゼロスケール | 「フルサーバーレス」 | アイドル時のコストゼロ。フルコールドスタート税を受け入れる |
