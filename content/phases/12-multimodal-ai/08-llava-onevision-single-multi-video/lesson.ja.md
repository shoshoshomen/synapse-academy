# LLaVA-OneVision：シングル画像、マルチ画像、ビデオを1つのモデルに

> LLaVA-OneVision（Liら、2024年8月）以前、オープンVLMの世界は分かれた系統を持っていた：シングル画像にはLLaVA-1.5、マルチ画像モデルにはMantisとVILA、ビデオモデルにはVideo-LLaVAとVideo-LLaMA。それぞれ自身のベンチマークで勝ち、他では失敗した。LLaVA-OneVisionは単一のカリキュラムが1つのモデルを3つすべてのシナリオで支配するよう学習でき、創発的なタスク転移効果（シングル画像スキルがビデオに輸出、マルチ画像推論がシングル画像に輸出）が専門家の合計を上回ることを論じた。レシピは欺くほどシンプル：シナリオをまたがって一定のビジュアルトークンバジェット、さらにシングル画像からOneVision（マルチ画像）、ビデオへと移行する明示的なカリキュラム。このレッスンではバジェット、カリキュラム、創発的な挙動を読み解く。


## 学習目標

- シングル画像、マルチ画像、ビデオ入力をまたがって一定のビジュアルトークンバジェットを設計する。
- 壊滅的忘却なしにスキルをシングル画像からビデオへ転移させる学習カリキュラムを順序付ける。
- カリキュラムが正しく行われた場合に単一モデルが同じパラメータ数で専門家を上回る理由を説明する。
- LLaVA-OneVisionが報告した3つの創発的能力を挙げる：マルチカメラ推論、set-of-mark プロンプティング、iPhoneスクリーンショットエージェント。

## 問題

画像、マルチ画像、ビデオはそれぞれモデルに異なる負荷をかける。

シングル画像は、OCRや細かいディテールを捉えるために高解像度トークン（AnyRes、約2880ビジュアルトークン）が欲しい。1サンプルあたりのバジェット：1画像、2880トークン。

マルチ画像は、コンテキスト内での画像間推論が収まるよう中程度解像度（それぞれ約576トークン）の複数画像が欲しい。1サンプルあたりのバジェット：4〜8画像、576ずつ、2300〜4600トークン。

ビデオは時間的ダイナミクスを捉えるためにプーリング後の低解像度（フレームあたり約196トークン）の多くのフレームが欲しい。1サンプルあたりのバジェット：8〜32フレーム、196ずつ、1600〜6200トークン。

別々のモデルを学習させると、1つのバジェットを選ぶことになる。1つのモデルを学習させると、コンテキストを吹き飛ばすことなくシナリオをまたがってバジェットがうまくスケールする必要がある。

OneVision以前のデフォルトの答えは「1つのシナリオを学習し、他は無視」だった。Video-LLaVAは追加学習ステージで画像モデルにビデオを後付けした。LLaVA-NeXTはタイリングでマルチ画像サポートを追加した。どれも3つ全部をきれいに処理しなかった。

## 概念

### OneVisionトークンバジェット

LLaVA-OneVisionは統合ビジュアルトークンバジェットを1サンプルあたり約3000〜4000トークンに選び、シナリオごとに異なる配分を行う：

- シングル画像：AnyRes-9（3×3タイル + サムネイル）、各タイルは384で729パッチ、積極的なバイリニアプーリング2×2 → タイルあたり182。合計：9 × 182 + 182 = 1820トークン。またはAnyRes-4でタイルあたり729 = 2916 + 729。
- マルチ画像：各画像を中程度解像度（384、タイリングなし）で、プーリングなしの729トークン。バジェット6画像 → 4374トークン。
- ビデオ：積極的な3×3バイリニアプールで384解像度の32フレーム → フレームあたり81トークン。合計：32 × 81 = 2592トークン。

配分はほぼ一定の総トークン数を維持する。LLMはコンテキストを吹き飛ばすバッチを決して見ない。エンコーダーはシナリオごとに異なるジオメトリを生成するが、LLMは同じバジェットを消費する。

### 3段階カリキュラム

LLaVA-OneVisionは3段階で学習する：

1. シングル画像SFT（ステージSI）。すべてのデータはシングル画像 + テキスト。高解像度AnyRes入力で学習。知覚、OCR、細粒度の理解を教える。LLaVA-NeXTデータとOneVision固有のシングル画像データを使用。
2. OneVision SFT（ステージOV）。シングル画像 + マルチ画像 + ビデオを混合（均一サンプリングフレーム）。統合トークンバジェットで学習。モデルに不均一なバッチ形状を処理させる。ウェイトリセットなし――ステージSIから継続。
3. タスク転移（ステージTT）。ターゲットタスクミックスで継続、通常は製品によってマルチ画像またはビデオで重め。デプロイ用の任意のファインチューニング。

重要：カリキュラムの順序が重要だ。ビデオ優先またはマルチ画像優先で学習すると、同じデータでもシングル画像のパフォーマンスが劣る。論文はこれを明示的にアブレーションしている。

### カリキュラムが機能する理由

シングル画像学習が知覚ベースを構築する。パッチトークンが細粒度の視覚特徴を保持し；LLMがテキストとの統合を学習する。マルチ画像とビデオは構造的な課題（どの画像が何か、何が最初に起きたか）を導入するが、強い知覚ベースなしに学習するのは難しい。

すべてのシナリオを最初からまとめて学習すると、モデルは知覚をアンダーフィット（バッチあたりのシングル画像データが限定的）し、構造をオーバーフィット（多くのマルチ画像/ビデオデータ）する。結果：クロス画像推論パターンに従うが視覚的に浅いモデル。

カリキュラムの順序付けによって、ステージSIから知覚の強さを、ステージOVから構成的/時間的推論を得られる、どちらも失うことなく。

### 創発的なクロスシナリオスキル

LLaVA-OneVision論文は3つの創発的能力を報告する：

1. マルチカメラ推論。マルチ画像 + ビデオを別々に学習；推論時に、マルチカメラ運転シーンについて推論するよう尋ねられる。モデルはその正確な形式を学習データで見たことがないにもかかわらず視点を正しく統合する。
2. Set-of-mark プロンプティング。ユーザーが番号付きのマークで画像内のオブジェクトを注釈する；モデルが「マーク3はマーク7に対して何をしているか」について推論する。マークも注釈も学習していない；空間的グラウンディング + マルチ画像参照の組み合わせから学習。
3. iPhoneスクリーンショットエージェント。ユーザーがiPhoneスクリーンのスクリーンショットを提供して次のクリックを計画するよう尋ねる。UIスクリーンショット、ユーザーワークフローのビデオ、マルチ画像の前後ペアで学習。エージェントユースケースに汎化。

これらは学習されたタスクではない；カリキュラムの構成的な構造から創発する。

### ビジュアルトークンプーリング

トークンバジェットにはプーリングが必要だ。OneVisionは2Dパッチグリッドでのバイリニア補間を使用する：24×24 = 576パッチが12×12 = 144（2倍因数）または8×8 = 64（3倍因数）になる。プーリングは局所性を保持するためにトークン空間ではなくパッチグリッド空間で行われる。

シナリオごとのプーリング因数の選択それ自体がハイパーパラメータだ。プーリングが少ない = より多いトークン = より豊かな表現。プーリングが多い = より少ないトークン = より多くのフレーム/画像が収まる。

### LLaVA-OneVision-1.5

2025年のフォローアップ（LLaVA-OneVision-1.5、arXiv 2509.23661）は学習データ、モデルウェイト、コードで「完全オープン」だ。いくつかのベンチマークで専有のギャップに匹敵し、レシピを民主化する。同じカリキュラム、より多くのデータ、より良いベースLLM。アーキテクチャ変更なし。

### Qwen2.5-VLとの対比

Qwen2.5-VL（レッスン12.09）は異なる選択をする。固定プーリングの代わりにM-ROPEと動的FPSを使用する。バジェットが入力でスケールする――1分のビデオは5秒のビデオより多くのトークンを使用する。LLaVA-OneVisionはバジェットを固定してプーリングをスケールする。どちらも機能；構成可能性と予測可能性をトレードオフする。

## 使ってみる

`code/main.py`はOneVisionスタイルVLMのカリキュラムとバジェットプランナーだ。1サンプルあたりのトークンバジェットとターゲットシナリオミックス（例えば40%シングル画像、30%マルチ画像、30%ビデオ）が与えられた場合：

- シナリオごとに解像度、プーリング因数、フレームを配分する。
- すべてのシナリオが共有バジェット内に収まることを確認する。
- 期待されるトークン数、LLM FLOPs、どのシナリオがトークン不足かを報告する。
- 段階ごとの学習スケジュールを印刷する。

OneVisionファインチューンを計画する時やVLMデプロイのリクエストごとのコストを確認するために使おう。

## 成果物を出す

このレッスンは`outputs/skill-onevision-budget-planner.md`を生成する。ターゲットタスク分布と1サンプルあたりのバジェットが与えられた場合、AnyRes因数、フレームごとのプーリング、ビデオフレーム数、カリキュラムステージ重みを出力する。統合シナリオVLMを学習またはファインチューニングするときはいつでも使う。

## 演習

1. あなたの製品は80%シングル画像、10%マルチ画像（2〜4枚）、10%ビデオ（8〜16フレーム）をサポートする。トークンバジェットを設計せよ。大量のマルチ画像をしないことで節約した追加バジェットはどこに置くか？

2. LLaVA-OneVision Section 4.3（創発的能力）を読め。カリキュラムがおそらく解除するが論文が報告しなかった4番目の創発的スキルを提案せよ。

3. カリキュラムの順序を入れ替えよ――マルチ画像を最初に、次にシングル画像、次にビデオ。どのベンチマークが低下するか、そしてなぜかを予測せよ。

4. 論文はサンプルあたり8フレームのビデオで学習したビデオベンチマークを報告する。それは推論時に30秒のビデオに汎化するか？最初に何が壊れるか――トークンバジェットか時間的推論か？

5. 24×24パッチのバイリニアプーリングを12×12にすると次元あたり4倍の削減だ。stdlib Pythonでプーリングを実装し、各2×2ブロックの平均がバイリニア出力と一致することを確認せよ。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|-----------------|------------------------|
| OneVisionシナリオ | "シングル画像、マルチ画像、またはビデオ" | 統合VLMが処理する3つの入力形状のうちの1つ；バジェットはまたがって一定 |
| トークンバジェット | "1サンプルあたりのトークン数" | LLMが1学習/推論サンプルあたり見る総ビジュアルトークン数、通常3000〜4000 |
| カリキュラム | "学習順序" | 創発的転移のために選ばれたステージ順序（シングル画像 → マルチ画像 → ビデオ） |
| バイリニアプーリング | "トークン縮小" | バイリニア補間をパッチグリッド（2D）に適用してトークン数を局所性を保ちながら削減 |
| 創発的スキル | "学習していないのに機能する" | 一致する学習データなしに推論時に現れる能力、カリキュラムの構成によって |
| AnyRes-k | "kタイル設定" | 固定解像度のkサブタイルと1つのサムネイル、典型的なkは4または9 |
| タスク転移 | "クロスシナリオ汎化" | シングル画像で学習したスキルが（その逆も）共有バックボーンを介してビデオに適用される |
