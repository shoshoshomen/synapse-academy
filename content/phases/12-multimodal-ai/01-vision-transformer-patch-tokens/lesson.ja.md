# Vision TransformerとPatchトークンの基本

> マルチモーダル処理の前に、まず画像をTransformerが処理できるトークンの列に変換する必要がある。2020年のViT論文はこれを16×16ピクセルのパッチ、線形射影、位置埋め込みで実現した。5年後の2026年フロンティアモデル（Claude Opus 4.7の2576px ネイティブ対応、Gemini 3.1 Pro、Qwen3.5-Omni）でも依然として同じ基本方式を採用している。エンコーダーはViTからDINOv2、SigLIP 2へと進化し、レジスタトークンが追加され、位置スキームが2D-RoPEになったが、基本のプリミティブは変わっていない。このレッスンではパッチ→トークンのパイプラインを端から端まで読み解き、フェーズ12の残りの部分が「ビジュアルトークン」について具体的なメンタルモデルを持てるようにstdlib Pythonで実装する。


## 学習目標

- HxWx3の画像を正しい位置エンコーディングを持つパッチトークンの列に変換する。
- 与えられた（パッチサイズ、解像度、隠れ次元、深さ）のViTの列長、パラメータ数、FLOPsを計算する。
- ViTを2020年の研究から2026年のプロダクションへ引き上げた3つの改善点を挙げる：自己教師あり事前学習（DINO / MAE）、レジスタトークン、ネイティブ解像度パッキング。
- CLS pooling、mean pooling、レジスタトークンのいずれかをダウンストリームタスクに応じて選択する。

## 問題

Transformerはベクトルの列を処理する。テキストはすでに列になっている（バイトまたはトークン）。画像は3色チャンネルを持つ2Dグリッドのピクセルであり、列ではない。すべてのピクセルを展開すると、224×224のRGB画像は150,528トークンになり、その長さでの自己注意計算は（長さの2乗スケール）現実的でない。

2020年以前のアプローチはCNNの特徴抽出器を前段に接続していた。ResNetが7×7の特徴マップ（2048次元のベクトル）を生成し、それら49トークンをTransformerに渡す。機能はするが、CNNのバイアス（平行移動等変性、局所的受容野）を引き継ぎ、Transformerのスケール伸長能力を失う。

Dosovitskiyら（2020年）は直球な問いを立てた：CNNを省略したらどうなるか？画像を固定サイズのパッチ（例えば16×16ピクセル）に分割し、各パッチをベクトルに線形射影し、位置埋め込みを加えて、そのままvanilla Transformerに渡す。当時これは異端だった――畳み込みなしのビジョン。十分なデータ（JFT-300M、その後LAION）があれば、ImageNetでResNetを上回り、さらに改善し続けた。

2026年時点でViTのプリミティブは揺るぎない基盤となっている。すべてのオープンウェイトVLMのビジョンタワーは何らかの派生形（DINOv2、SigLIP 2、CLIP、EVA、InternViT）だ。問いは「パッチを使うべきか？」ではなく「どのパッチサイズ、どの解像度スケジュール、どの事前学習目標、どの位置エンコーディングを使うか」に変わっている。

## 概念

### トークンとしてのパッチ

形状`(H, W, 3)`の画像`x`とパッチサイズ`P`が与えられた場合、画像を`(H/P) × (W/P)`の重複しないパッチのグリッドに分割する。各パッチは`P × P × 3`ピクセルの立体だ。各立体を`3P^2`のベクトルに展開する。共有線形射影`W_E`（形状`(3P^2, D)`）を適用して各パッチをモデルの隠れ次元`D`にマッピングする。

ViT-B/16の標準設定：
- 解像度224、パッチサイズ16 → グリッド14×14 → 196パッチトークン。
- 各パッチは`16 × 16 × 3 = 768`ピクセル値で、`D = 768`に射影。
- 学習可能な`[CLS]`トークンを追加 → 列長197。

パッチ射影は数学的に、カーネルサイズ`P`、ストライド`P`、`D`出力チャンネルの2D畳み込みと同等だ。プロダクションコードでは実際に`nn.Conv2d(3, D, kernel_size=P, stride=P)`として実装される。「線形射影」という表現は概念的なもので、カーネルとしての表現が効率的だ。

### 位置埋め込み

パッチには固有の順序がない――Transformerはそれらをバッグとして見る。初期のViTは学習可能な1D位置埋め込みを追加していた（位置あたり1つの768次元ベクトル、計197個）。機能するが、モデルを学習解像度に結びつける：グリッドを変更すると推論時に位置テーブルを補間する必要がある。

現代のビジョンバックボーンは2D-RoPE（Qwen2-VLのM-RoPE、SigLIP 2のデフォルト）またはファクタライズされた2D位置を使用する。2D-RoPEはパッチの（行、列）インデックスに基づいてクエリとキーベクトルを回転させるため、モデルは回転角から相対的な2D位置を推論する。位置テーブルなし。任意のグリッドサイズを推論時に処理できる。

### CLSトークン、プーリング出力、レジスタトークン

画像レベルの表現とは何か？3つの選択肢が共存する：

1. `[CLS]`トークン。学習可能なベクトルをパッチ列の先頭に追加する。すべてのTransformerブロックを通過した後、CLSトークンの隠れ状態が画像表現となる。BERTから継承。元々のViT、CLIPで使用。
2. Mean pool。パッチトークンの出力隠れ状態を平均化する。SigLIP、DINOv2、ほとんどの現代VLMで使用。
3. レジスタトークン。Darcetら（2023年）は、明示的なシンクトークンなしに学習されたViTが高ノルムの「アーティファクト」パッチを開発し、自己注意を乗っ取ることを観察した。4〜16個の学習可能なレジスタトークンを追加するとこの負荷を吸収し、密な予測品質（セグメンテーション、深度）が向上する。DINOv2とSigLIP 2はどちらもレジスタを搭載。

選択肢はダウンストリームタスクに重要だ。CLSは分類に適している。パッチトークンをLLMに渡すVLMでは、poolingを完全にスキップする――すべてのパッチがLLMの入力トークンになる。レジスタはハンドオフ前に破棄される（足場であり、コンテンツではない）。

### 事前学習：教師あり、コントラスティブ、マスク、自己蒸留

2020年のViTはJFT-300Mでの教師あり分類で事前学習された。すぐに置き換えられた：

- CLIP（2021年）：400Mペアでのコントラスティブ画像テキスト。レッスン12.02。
- MAE（2021年、Heら）：パッチの75%をマスクしてピクセルを再構築。純粋な画像での自己教師あり学習。
- DINO（2021年）/ DINOv2（2023年）：学生教師による自己蒸留、ラベルなし、キャプションなし。2023年のDINOv2 ViT-g/14は最も強力な純視覚バックボーンで、「密な特徴」ユースケースのデフォルト。
- SigLIP / SigLIP 2（2023年、2025年）：シグモイド損失とNaFlexによるネイティブアスペクト比対応のCLIP。2026年のオープンVLM（Qwen、Idefics2、LLaVA-OneVision）で支配的なビジョンタワー。

事前学習の選択によってバックボーンの強みが決まる：テキストとのセマンティックマッチングにはCLIP/SigLIP、密な視覚特徴にはDINOv2、ダウンストリームファインチューニングの出発点にはMAE。

### スケーリング則

ViTのスケーリング（Zhaiら、2022年）はViTの品質がモデルサイズ、データサイズ、計算量において予測可能な法則に従うことを確立した。一定の計算量では：
- 大きなモデル + 多くのデータ → 高品質。
- パッチサイズは列長と忠実度のトレードオフのレバーだ。パッチ14（DINOv2/SigLIP SO400m の典型）はパッチ16よりも1画像あたりのトークンが多い；OCRや密なタスクに優れているが速度は遅い。
- 解像度も重要なレバーだ。224から384、512への変更はほぼ常に効果があるが、FLOPsの2乗コストがかかる。

ViT-g/14（10億パラメータ、パッチ14、解像度224→256トークン）とSigLIP SO400m/14（4億パラメータ、パッチ14）が2026年のオープンVLMの2つの主力エンコーダーだ。

### ViTのパラメータ数

完全な計算は`code/main.py`にある。ViT-B/16（解像度224）の場合：

```
patch_embed = 3 * 16 * 16 * 768 + 768  =  591k
cls + pos    = 768 + 197 * 768          =  152k
block        = 4 * 768^2 (QKVO) + 2 * 4 * 768^2 (MLP) + 2 * 2*768 (LN)
             = 12 * 768^2 + 3k          =  7.1M
12 blocks    = 85M
final LN    = 1.5k
total       ≈ 86M
```

ダウンストリームVLMにロードする前に、このようにViTの規模を概算しよう。バックボーンサイズがVRAMの下限を設定する。

### 2026年のプロダクション設定

2026年にほとんどのオープンVLMが採用しているエンコーダーはSigLIP 2 SO400m/14（ネイティブ解像度対応のNaFlex）だ：
- 4億パラメータ。
- パッチサイズ14、デフォルト解像度384 → 1画像あたり729パッチトークン。
- 画像レベルタスクにはmean pool；VQAのためにすべて729パッチがLLMに渡される。
- 4個のレジスタトークン、LLMハンドオフ前に破棄。
- ネイティブアスペクト比対応の画像レベルスケーリング付き2D-RoPE。

その設定の各決定は、読むことができる論文に遡ることができる。

## 使ってみる

`code/main.py`はパッチトークナイザーとジオメトリ計算機だ。（画像H, W、パッチP、隠れ次元D、深さL）を受け取り以下を報告する：

- パッチ処理後のグリッド形状と列長。
- 合成8×8ピクセルのトイ画像のトークン列（展開 + 射影パスを追いかける）。
- パッチ埋め込み、位置埋め込み、Transformerブロック、ヘッドごとのパラメータ数内訳。
- 対象解像度でのフォワードパスあたりのFLOPs。
- ViT-B/16@224、ViT-L/14@336、DINOv2 ViT-g/14@224、SigLIP SO400m/14@384の比較表。

実行して、パラメータ数を公表数値と照合しよう。パッチサイズと解像度を変えてトークン数コストを体感しよう。

## 成果物を出す

このレッスンは`outputs/skill-patch-geometry-reader.md`を生成する。ViTの設定（パッチサイズ、解像度、隠れ次元、深さ）から、トークン数、パラメータ数、VRAM推定値を根拠付きで計算する。VLM用のビジョンバックボーンを選ぶたびにこのスキルを使うこと――「トークンが爆発してLLMのコンテキストが埋まった」という驚きを防ぐ。

## 演習

1. パッチサイズ14でネイティブ1280×720入力のQwen2.5-VLのパッチトークン列長を計算せよ。CLS専用表現と比べてどうか？

2. パッチ14で1080p（1920×1080）フレームはいくつのトークンを生成するか？30FPSで5分間のビデオでは合計何個のビジュアルトークンになるか？pooling、フレームサンプリング、トークンマージングのどれが最もコスト削減に効果的か？

3. pure Pythonでパッチトークンに対するmean poolingを実装せよ。DINOv2出力の196トークンのmean-poolが、pooled embeddingを要求した時にモデルの`forward`が返すものと一致することを確認せよ。

4. 「Vision Transformers Need Registers」（arXiv:2309.16588）のSection 3を読め。レジスタが吸収するアーティファクトが何であり、それがダウンストリームの密な予測にとってなぜ重要かを2文で説明せよ。

5. `code/main.py`を修正してpatch-n'-packをサポートせよ：異なる解像度の画像リストが与えられた場合に、1つのパックされた列とブロック対角注意マスクを生成する。レッスン12.06に達した時にそこで確認せよ。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| パッチ | "16×16ピクセルの正方形" | 入力画像の固定サイズの重複しない領域；1つのトークンになる |
| パッチ埋め込み | "線形射影" | 展開されたパッチピクセルをD次元ベクトルにマッピングする共有学習行列（またはstride=PのConv2d） |
| CLSトークン | "クラストークン" | その最終隠れ状態が画像全体を表す、先頭に追加する学習可能なベクトル；2026年では任意 |
| レジスタトークン | "シンクトークン" | 事前学習中にViTが発展させる高ノルムの注意アーティファクトを吸収する追加学習可能トークン |
| 位置埋め込み | "位置情報" | 列が順序を認識できるようにする位置ごとのベクトルまたは回転；2D-RoPEが現代のデフォルト |
| グリッド | "パッチグリッド" | 与えられた解像度とパッチサイズのパッチの(H/P) × (W/P) 2D配列 |
| NaFlex | "ネイティブ柔軟解像度" | SigLIP 2の機能：再学習なしで複数のアスペクト比と解像度を1つのモデルで提供 |
| バックボーン | "ビジョンタワー" | VLMのLLMにパッチトークン出力を渡す事前学習済み画像エンコーダー |
| Pooling | "画像レベルの要約" | パッチトークンを1つのベクトルに変換する戦略：CLS、mean、attention pool、またはregisterベース |
| パッチ14 vs 16 | "細かいvs粗いグリッド" | パッチ14は1画像あたりのトークンが多く、OCRの忠実度が高いが遅い；パッチ16は従来のデフォルト |
