# 任意解像度ビジョン：Patch-n'-PackとNaFlex

> 実世界の画像は224×224の正方形ではない。レシートは9:16、チャートは16:9、医療スキャンは4096×4096、モバイルスクリーンショットは9:19.5かもしれない。VLMの2024年以前の答え――すべてを固定正方形にリサイズする――は、OCR、文書理解、高解像度シーン解析を機能させるシグナルを捨てていた。NaViT（Google、2023年）はブロック対角マスキングで可変解像度のパッチを単一のTransformerバッチに詰め込めることを示した。Qwen2-VLのM-RoPE（2024年）は絶対位置テーブルを完全に廃止した。LLaVA-NeXTのAnyResは高解像度画像をベース + サブ画像にタイリングした。SigLIP 2のNaFlex変形（2025年）は今や任意のアスペクト比を1つのチェックポイントで提供したいオープンVLMのデフォルトエンコーダーだ。このレッスンではpatch-n'-packをエンドツーエンドで実装する。


## 学習目標

- 可変解像度画像のバッチからパッチを1つの列にパックし、ブロック対角注意マスクを構築する。
- 与えられたタスクに対してAnyResタイリング（LLaVA-NeXT）、NaFlex（SigLIP 2）、M-RoPE（Qwen2-VL）から選択する。
- リサイズなしでOCR、チャート、写真のトークンバジェットを計算する。
- 正方形リサイズの3つの失敗モードを挙げる：つぶれたテキスト、切り取られたコンテンツ、パディングによる無駄なトークン。

## 問題

Transformerは列を期待する。バッチは同じ長さの列のスタックだ。画像がすべて224×224なら、常に196個のパッチトークンが得られ、パディング不要で問題なし。224で学習し、224で推論し、解像度について二度と考えなくていい。

しかし実世界は協力しない。文書は縦向き（8.5×11インチ、約2:3）。チャートスクリーンショットは横向き（16:9）。レシートは縦長で細い（1:3）。医療画像は2048×2048以上。モバイルデバイスのスクリーンショットは1170×2532（0.46:1）。

2024年以前の3つの選択肢とそれぞれが失敗する理由：

1. 固定正方形にリサイズ（224×224または336×336）。圧縮でテキストと顔がゆがむ。ダウンスケールでチャートラベルとOCRコンテンツが破壊される。LLaVA-1.5まで標準的な実践。
2. 固定アスペクト比にトリミング。画像のほとんどを捨て、トリミング場所の選択自体がビジョン問題になる。
3. 最長辺にパディング。ゆがみは修正されるが、縦向き画像のパディングで50%以上のトークンが無駄になる。それらのパッドトークンに対する2次コストの自己注意。

2024〜2025年の答え：Transformerに画像のネイティブ解像度でパッチを食べさせ、計算の無駄なしに不均一なバッチを1つの列にパックする方法を考え出す。

## 概念

### NaViTとpatch-n'-pack

NaViT（Dehghaniら、2023年）はこれが大規模に機能することを示した論文だ。アイデアは機械的だ：

1. バッチ内の各画像について、選んだパッチサイズ（例えば14）でネイティブパッチグリッドを計算する。
2. 各画像のパッチを自身の可変長列に展開する。
3. すべての画像のパッチをバッチのための1つの長い列に連結する。
4. 画像Aのパッチが画像Aの中でのみ注意を向けるようにブロック対角注意マスクを構築する。
5. パッチごとの位置情報（2D RoPEまたは分数位置埋め込み）を保持する。

336×336（576トークン）、224×224（256トークン）、448×336（768トークン）の3つの画像のバッチは、1600×1600のブロック対角マスクを持つ1600トークンの1つの列になる。パディングなし。無駄な計算なし。Transformerが任意のアスペクト比を処理する。

NaViTはまた学習中のフラクショナルパッチドロッピングも導入した――バッチ全体でランダムに50%のパッチをドロップする――これは正則化と学習速度向上の両方に機能する。SigLIP 2はこれを継承した。

### AnyRes（LLaVA-NeXT）

LLaVA-NeXTのAnyResは実用的な代替策だ。高解像度画像と固定エンコーダー（336のCLIPまたはSigLIP）が与えられたとき、タイリングする：

1. 画像のアスペクト比に最も合う定義済みのグリッドレイアウトセット――(1×1)、(1×2)、(2×1)、(1×3)、(3×1)、(2×2)など――から選ぶ。
2. 画像全体をグリッドにタイリングし、各タイルが336×336クロップになる。
3. サムネイルも生成：グローバルコンテキストトークンとして画像全体を336×336にリサイズ。
4. フリーズした336エンコーダーですべてのタイルをエンコードする。タイルトークン + サムネイルトークンを連結する。

2×2グリッド + サムネイル付きの672×672画像：4 × 576 + 576 = 2880ビジュアルトークン。高コストだが効果的――LLMはローカルな詳細とグローバルコンテキストの両方を見る。

AnyResはエンコーダーがフリーズしていて1つの解像度のみをサポートする場合の選択肢だ。大きな画像ではトークン数が爆発する（4×4グリッドの1344×1344画像は9216 + 576 ≈ 9800トークンで、ほとんどの8k LLMコンテキストを埋める）。

### M-RoPE（Qwen2-VL）

Qwen2-VLはMultimodal Rotary Position Embeddingを導入した。NaViTの分数位置やAnyResのタイルアンドサムネイルの代わりに、各パッチが3D位置（時間、高さ、幅）を保持する。クエリ/キーの回転が任意のH、W、時間長を処理する。

M-ROPEはネイティブ動的解像度を再学習なしで提供する。推論時に任意のHxW画像を渡すと、パッチエンベッダーがH/14 × W/14トークンを生成し、各トークンが(t=0, r=行, c=列)の位置を得て、RoPEが適切な周波数で注意を回転させる、完了。Qwen2.5-VLとQwen3-VLがこれを継続する。InternVL3のV2PEはモダリティごとの可変エンコーディングで同じアイデアだ。

AnyResとは異なり、M-ROPEはネイティブ解像度でO(H × W / P^2)トークン――乗算的なタイルオーバーヘッドなし。NaViTとは異なり、1フォワードあたりまだ1枚の画像を期待する。解像度をまたぐバッチングではpatch-n'-packが必要。

### NaFlex（SigLIP 2）

NaFlexはSigLIP 2チェックポイントのネイティブフレックスモードだ。1つのモデルが推論時に複数の列長（256、729、1024トークン）を提供する。内部的には学習中にNaViTスタイルのpatch-n'-packを使用し、パッチごとの絶対分数位置を持つ。セールスポイント：1つのチェックポイントで、タスクに応じてトークンバジェットを推論時に選べる。

セマンティックタスク（分類、検索）には256トークン。OCRやチャート理解には1024トークン。再学習なし。

### パッキングマスク

ブロック対角マスクはほとんどの実装がつまずく場所だ。長さ`n_i`を持つ画像`i=0..B-1`をカバーする合計長`N_total`のパックされた列に対して、形状`(N_total, N_total)`のマスク`M`は、両方のインデックスが同じ画像のブロックに属する場合は1、それ以外は0だ。累積長リストから構築できる：

```
offsets = [0, n_0, n_0+n_1, ..., N_total]
M[i, j] = 1 iff there exists b where offsets[b] <= i < offsets[b+1] and offsets[b] <= j < offsets[b+1]
```

これはPyTorchで`torch.block_diag`または明示的なgatherを使って1行で書ける。FlashAttentionの可変長パス（`cu_seqlens`）は密なマスクを完全にスキップして、累積長テンソルを使って列内で直接注意を向ける――典型的なバッチで密なマスクより約10倍速い。

### トークンバジェット

タスクによって戦略を選べ：

- OCR / 文書：1024〜4096トークン。SigLIP 2 NaFlex at 1024、またはAnyRes 3×3 + サムネイル。
- チャートとUI：384〜448ネイティブで729〜1024トークン。Qwen2.5-VLの最大ピクセルキャップ付き動的解像度。
- 自然写真：256〜576トークンで十分。ダウンストリームLLMには十分見える。コンテンツ密度が高い場所でトークンに課金する。
- ビデオ：空間プーリング後にフレームあたり64〜128トークン、2〜8FPS。レッスン12.17で詳しく説明。

2026年のプロダクションルール：タスクごとの最大ピクセルキャップを選び、そのキャップ以内でネイティブアスペクト比でエンコードし、バッチをパックして、パディングをスキップする。Qwen2.5-VLはこのノブのために`min_pixels`と`max_pixels`を公開している。

## 使ってみる

`code/main.py`は整数ピクセル座標を持つ不均一な画像バッチのpatch-n'-packを実装する：

- (H, W)画像サイズのリストを受け取る。
- パッチサイズ14で各画像のパッチ列長を計算する。
- それらを合計長`sum(n_i)`の1つの列にパックする。
- ブロック対角注意マスクを構築する（明確さのために密で）。
- パックコスト vs 正方形リサイズとAnyResタイリングを比較する。
- 混合バッチ（レシート、チャート、スクリーンショット、写真）のトークンバジェット表を印刷する。

実行しよう。出てくる数字が2026年のすべてのオープンVLMがpatch-n'-packを使う理由だ。

## 成果物を出す

このレッスンは`outputs/skill-resolution-budget-planner.md`を生成する。混合アスペクト比のワークロード（OCR、チャート、写真、ビデオフレーム）と総トークンバジェットが与えられた場合、適切な戦略（NaFlex、AnyRes、M-RoPE、または固定正方形）を選択してリクエストごとの設定を出力する。VLMを製品向けにサイジングするときにこのスキルを使う――レイテンシバジェットを壊すサイレントな10倍トークン爆発を防ぐ。

## 演習

1. レシートは600×1500（1:2.5）だ。パッチサイズ14でネイティブ解像度のトークンはいくつか？336への正方形リサイズ後は？実際にどちらがOCR精度をより多く失うか？

2. 長さ256、576、729、1024の4枚の画像のバッチのブロック対角マスクを構築せよ。注意行列が2585×2585で正確に`256^2 + 576^2 + 729^2 + 1024^2`個の非ゼロエントリを持つことを確認せよ。

3. パッチ14での1792×896の画像を比較せよ：(a)336に正方形リサイズしてエンコード、(b)AnyRes 2×1 + サムネイル、(c)M-ROPEでネイティブ。どれが最も少ないトークンを使うか？どれが最も詳細を保持するか？

4. フラクショナルパッチドロッピングを実装せよ：パックされた列が与えられた場合、ランダムに一様に50%のトークンをドロップし、ブロック対角マスクを適宜更新する。マスクのスパース性の変化を測定せよ。

5. Qwen2-VL論文（arXiv:2409.12191）のSection 3.2を読め。`min_pixels`と`max_pixels`が何を制御するか、そしてなぜ両方の境界が重要かを2文で説明せよ。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|-----------------|------------------------|
| Patch-n'-pack | "NaViTスタイルパッキング" | 異なる画像からの可変長パッチ列を1つのバッチ次元に連結 |
| ブロック対角マスク | "パッキングマスク" | 各画像のパッチが隣接するパックに対してではなく自分自身の中でのみ注意を向けるよう制限する注意マスク |
| AnyRes | "LLaVA-NeXTタイリング" | 高解像度画像をグローバルサムネイルを加えた固定サイズタイルのグリッドに分割；すべてのタイルを固定エンコーダーでエンコード |
| NaFlex | "SigLIP 2ネイティブフレックス" | 再学習なしで推論時に256/729/1024トークンバジェットを提供するSigLIP 2チェックポイント |
| M-RoPE | "マルチモーダルRoPE" | 位置テーブルなしで任意のH、W、Tを処理する3次元回転位置エンコーディング（時間、行、列） |
| cu_seqlens | "FlashAttentionパッキング" | FlashAttentionの可変長パスが密なブロック対角マスクの代わりに使用する累積長テンソル |
| min_pixels / max_pixels | "解像度境界" | 非常に小さいまたは非常に大きい入力でのトークン数をキャップするQwen2.5-VLのリクエストごとのノブ |
| ビジュアルトークンバジェット | "1画像あたりのトークン数" | 1画像あたりに出力されるパッチトークンのおおよその数；LLMのプロンプトバジェットと注意コストを設定 |
