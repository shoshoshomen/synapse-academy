# エージェントオブザーバビリティ: Langfuse、Phoenix、Opik

> 3つのオープンソースエージェントオブザーバビリティプラットフォームが 2026 年を支配しています。Langfuse（MIT）— 月間 600 万以上のインストール、トレーシング + プロンプト管理 + エバル + セッションリプレイ。Arize Phoenix（Elastic 2.0）— 深いエージェント固有のエバル、RAG 関連性、OpenInference 自動インストルメンテーション。Comet Opik（Apache 2.0）— 自動化されたプロンプト最適化、ガードレール、LLM ジャッジによる幻覚検出。


## 学習目標

- トップ3のオープンソースエージェントオブザーバビリティプラットフォームとそのライセンスを説明できる。
- 各プラットフォームの強みを区別できる: Langfuse（プロンプト管理 + セッション）、Phoenix（RAG + 自動インストルメンテーション）、Opik（最適化 + ガードレール）。
- 2026 年までに 89% の組織がエージェントオブザーバビリティを導入している理由を説明できる。
- LLM ジャッジ評価を持つ標準ライブラリのトレース→ダッシュボードパイプラインを実装できる。

## 問題設定

OTel GenAI（レッスン23）はスキーマを提供します。スパンを取り込み、評価を実行し、プロンプトのバージョンを保存し、リグレッションを表面化させるプラットフォームがまだ必要です。3つの競合製品はそれぞれライフサイクルの異なる部分を重視しています。

## コンセプト

### Langfuse（MIT）

- 月間 SDK インストール 600 万以上、GitHub スター 1.9 万以上。
- 機能: トレーシング、バージョン管理 + プレイグラウンドを持つプロンプト管理、評価（LLM-as-judge、ユーザーフィードバック、カスタム）、セッションリプレイ。
- 2025年6月: 以前は商用だったモジュール（LLM-as-a-judge、アノテーションキュー、プロンプト実験、プレイグラウンド）が MIT でオープンソース化。
- 強み: 緊密なプロンプト管理ループを持つエンドツーエンドのオブザーバビリティ。

### Arize Phoenix（Elastic License 2.0）

- 深いエージェント固有の評価: トレースクラスタリング、異常検出、RAG の検索関連性。
- ネイティブの OpenInference 自動インストルメンテーション。
- 本番向けのマネージドな Arize AX とペアリング。
- プロンプトバージョン管理なし — より広いプラットフォームの隣でドリフト/動作リグレッションツールとして位置付け。
- 強み: RAG 関連性、動作ドリフト、異常検出。

### Comet Opik（Apache 2.0）

- A/B 実験による自動化されたプロンプト最適化。
- ガードレール（PII 編集、トピカルな制約）。
- LLM ジャッジによる幻覚検出。
- Comet 自身の計測によるベンチマーク: Opik がログ + エバルを 23.44 秒 vs Langfuse 327.15 秒（約 14 倍のギャップ）— ベンダーベンチマークは方向性として扱う。
- 強み: 最適化ループ、自動化された実験、ガードレール施行。

### 業界データ

Maxim（2026 年のフィールド分析）によると: 89% の組織がエージェントオブザーバビリティを導入済み。品質の問題がトップの本番バリアです（回答者の 32% が引用）。

### どれを選ぶか

| ニーズ | 選択 |
|--------|------|
| プロンプト管理付きオールインワン | Langfuse |
| 深い RAG 評価 + ドリフト | Phoenix |
| 自動化された最適化 + ガードレール | Opik |
| ELv2 なしのオープンライセンス | Langfuse（MIT）または Opik（Apache 2.0） |
| Datadog / New Relic 統合 | どれでも — すべて OTel をエクスポート |

### このパターンが失敗するケース

- **エバル戦略なし.** エバルなしのトレーシングは高価なロギングにすぎません。
- **グラウンディングなしのセルフロールド LLM ジャッジ.** CRITIC パターン（レッスン05）が適用されます — ジャッジは事実確認のために外部ツールが必要です。
- **トレースに紐付けられないプロンプトバージョン.** 本番でリグレッションが起きたとき、その原因となったプロンプトを特定できません。

## 実装する

`code/main.py` は標準ライブラリのトレースコレクター + LLM ジャッジ評価器を実装しています:

- GenAI 形状のスパンを取り込み。
- セッションでグループ化し、失敗した実行にタグ付け（ガードレールトリップ、低信頼度エバル）。
- ルーブリックに対してエージェントレスポンスをスコアリングするスクリプト化された LLM ジャッジ。
- ダッシュボード風のサマリー: 失敗率、トップの失敗理由、エバルスコアの分布。

実行:

```
python3 code/main.py
```

出力: Langfuse/Phoenix/Opik が表示するものに合わせたセッションごとのエバルスコアと失敗の分類。

## 使ってみる

- **Langfuse** はセルフホストまたはクラウド。OTel または彼らの SDK 経由で接続。
- **Arize Phoenix** はセルフホスト。OpenInference を自動インストルメント。
- **Comet Opik** はセルフホストまたはクラウド。自動化された最適化ループ。
- **Datadog LLM Observability** は Datadog をすでに実行している混合 ops+ML チームに。

## 成果物を出す

`outputs/skill-obs-platform-wiring.md` はプラットフォームを選択して、既存エージェントにトレース + エバル + プロンプトバージョンを組み込みます。

## 演習

1. OTel トレースを1週間 Langfuse クラウド（無料ティア）にエクスポートします。どのセッションが失敗しましたか？なぜ？
2. 自分のドメイン向けの LLM ジャッジルーブリックを書きます（事実の正確さ、トーン、スコープ遵守）。50 のトレースでテストします。
3. Langfuse のプロンプトバージョン管理と Phoenix のトレースクラスタリングを比較します。何が壊れたかをどちらがより速く教えてくれますか？
4. Opik のガードレールドキュメントを読みます。エージェント実行の1つに PII 編集ガードレールを組み込みます。
5. 3つのプラットフォームを自分のコーパスでベンチマークします。ベンダーが公開している数字は無視して、自分で計測してください。

## キーワード

| 用語 | 一般的な言い方 | 実際の意味 |
|------|----------------|------------|
| トレーシング | "スパンコレクター" | OTel / SDK スパンを取り込んでセッションでインデックス |
| プロンプト管理 | "プロンプト CMS" | トレースに紐付けられたバージョン管理されたプロンプト |
| LLM-as-judge | "自動化されたエバル" | 別の LLM がルーブリックに対してエージェントの出力をスコアリング |
| セッションリプレイ | "トレースの再生" | デバッグのために過去の実行をステップ実行 |
| RAG 関連性 | "検索品質" | 取得されたコンテキストがクエリに一致するか |
| トレースクラスタリング | "動作グルーピング" | ドリフト検出のために類似した実行をクラスタリング |
| ガードレール施行 | "ログ時のポリシー" | ログに記録されたコンテンツに対する PII/毒性/スコープチェック |
