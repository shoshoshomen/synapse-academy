# プロダクション・ランタイム：キュー、イベント、クーロン

> プロダクションエージェントは6種類のランタイム形状で動作する：リクエスト＆レスポンス、ストリーミング、デュラブル実行、キューベースのバックグラウンド、イベント駆動、スケジュール実行。フレームワークを選ぶ前に形状を選ぶこと。オブザーバビリティはどの形状でも重要なコンポーネントである。


## 学習目標

- 6種類のプロダクションランタイム形状を挙げ、それぞれをフレームワーク/プロダクトパターンに対応づける。
- デュラブル実行（LangGraph）が長期タスクに重要な理由を説明する。
- イベント駆動ランタイムと、Claude Managed Agentsが適している場面を説明する。
- マルチステップエージェントにおける「オブザーバビリティは重要なコンポーネント」という主張を説明する。

## 問題

プロダクション環境のエージェントはJupyterノートブックでは再現できない方法で失敗する：ステップ37でのネットワークタイムアウト、音声通話の途中でのユーザー切断、マシン再起動時のクーロンジョブ死亡、バックグラウンドワーカーのメモリ不足。ランタイムの形状が、どの失敗から回復できるかを決める。

## コンセプト

### リクエスト＆レスポンス

- 同期HTTP。ユーザーが完了を待つ。
- 短いタスク（30秒未満）にのみ有効。
- スタック：Agno（Python + FastAPI）、Mastra（TypeScript + Express/Hono/Fastify/Koa）。
- オブザーバビリティ：標準HTTPアクセスログ + OTelスパン。

### ストリーミング

- プログレッシブ出力のためのSSEまたはWebSocket。
- LiveKitはこれをWebRTCに拡張し、音声/ビデオに対応（レッスン22）。
- スタック：ストリーミングサポートのある任意のフレームワーク + SSE/WSを処理するフロントエンド。
- オブザーバビリティ：チャンクごとのタイミング、最初のトークンレイテンシ、テールレイテンシ。

### デュラブル実行

- すべてのステップ後にステートがチェックポイントされ、失敗時に自動再開される。
- AutoGen v0.4のアクターモデルが1つのエージェントへの失敗を分離する（レッスン14）。
- LangGraphのコアな差別化機能（レッスン13）。
- ステップ数が不明で復旧コストが高い場合に必須。

### キューベース / バックグラウンド

- ジョブがキューに入り、ワーカーが取り出し、結果がWebhookまたはpub/subで返される。
- 長期エージェントに必須（タスクあたり数十〜数百ステップ、Anthropicのコンピューターユース発表より）。
- スタック：Celery（Python）、BullMQ（Node）、SQS + Lambda（AWS）、カスタム。
- オブザーバビリティ：キュー深度、ジョブごとのレイテンシ分布、DLQサイズ。

### イベント駆動

- エージェントがトリガーをサブスクライブする：新規メール、PR開設、クーロン実行。
- Claude Managed Agentsがこれをすぐに対応している（レッスン17）。
- CrewAI Flows（レッスン15）がイベント駆動の決定論的ワークフローを構造化する。
- オブザーバビリティ：トリガーソース、イベント開始レイテンシ、エージェントレイテンシ。

### スケジュール実行

- 定期的に実行されるクーロン形状のエージェント。
- デュラブル実行と組み合わせることで、失敗した夜間実行が次のティックで再開される。
- スタック：Kubernetes CronJob + デュラブルフレームワーク；ホスティング型（Render cron、Vercel cron）。

### 2026年のデプロイメントパターン

- **CrewAI Flows**：イベント駆動のプロダクション向け。
- **Agno**：PythonマイクロサービスのためのステートレスFastAPI。
- **Mastra**：埋め込み用サーバーアダプター（Express、Hono、Fastify、Koa）。
- **Pipecat Cloud / LiveKit Cloud**：マネージド音声（レッスン22）。
- **Claude Managed Agents**：ホスティング型の長時間実行非同期処理。

### オブザーバビリティは重要なコンポーネント

OpenTelemetry GenAIスパン（レッスン23）とLangfuse/Phoenix/Opikバックエンド（レッスン24）なしでは、ステップ40で失敗したマルチステップエージェントをデバッグできない。これはプロダクションにおいてオプションではない。「素早くデバッグできる」と「ログを増やしてゼロから再実行する」の違いである。

### プロダクションランタイムが失敗する場所

- **形状の選択ミス。** 5分かかるタスクにリクエスト＆レスポンスを選ぶ。ユーザーが切断し、ワーカーが積み上がり、リトライが複合する。
- **DLQなし。** デッドレターなしのキューワーカー。失敗したジョブが消える。
- **不透明なバックグラウンド処理。** バックグラウンドエージェントがトレースエクスポートなしで実行される。ユーザーから報告されるまで失敗が見えない。
- **デュラブルステートのスキップ。** 再起動を許容できない30秒超の実行にはデュラブル実行が必要。

## 実装する

`code/main.py` は標準ライブラリによるマルチ形状デモ：

- リクエスト＆レスポンスエンドポイント（プレーン関数）。
- ストリーミングハンドラー（ジェネレーター）。
- DLQ付きキューベースワーカー。
- イベントトリガーレジストリ。
- クーロン形状スケジューラー。

実行：

```bash
python3 code/main.py
```

出力：同じタスクに対する各形状の動作を示す5つのトレース。同じエージェントロジック、異なる外殻。デュラブル実行（6番目の形状）はレッスン13でLangGraphチェックポイントと一緒に意図的に扱われる。

## 使ってみる

- **リクエスト＆レスポンス**：チャットスタイルのUX向け。
- **ストリーミング**：プログレッシブレスポンス向け。
- **デュラブル**：長期タスク向け。
- **キュー**：バッチ / 非同期 / 長時間実行向け。
- **イベント**：エージェントの反応性向け。
- **クーロン**：ハウスキーピング（メモリ統合、評価、コストレポート）向け。

## 成果物を出す

`outputs/skill-runtime-shape.md` がタスクのランタイム形状を選択し、オブザーバビリティ要件を組み合わせる。

## 演習

1. レッスン01のReActループを自分のスタックの6つの形状すべてに移植する。どの形状がどのプロダクト表面に合うか？
2. キューベースデモにDLQを追加する。10%のジョブ失敗をシミュレートし、DLQサイズを表面化させる。
3. 毎晩上位20件のトレースに対して実行するクーロントリガー付き評価エージェントを作成する。
4. バックプレッシャー付きストリーミングを実装する：クライアントが遅い場合、エージェントを一時停止する。これはターンバジェットとどう相互作用するか？
5. Claude Managed Agentsのドキュメントを読む。自己ホスト型の長期エージェントをいつマネージドに移行するか？

## キーワード

| 用語 | 一般的な言い方 | 実際の意味 |
|------|----------------|------------|
| リクエスト＆レスポンス | 「同期」 | ユーザーが待つ；短いタスクのみ |
| ストリーミング | 「SSE / WS」 | プログレッシブ出力；より良いUX；チャンクごとにレイテンシが観測可能 |
| デュラブル実行 | 「失敗からの再開」 | チェックポイントされたステート；最後のステップから再起動 |
| キューベース | 「バックグラウンドジョブ」 | プロデューサー / ワーカープール / DLQ |
| イベント駆動 | 「トリガーベース」 | エージェントが外部イベントに反応する |
| DLQ | 「デッドレターキュー」 | 失敗したジョブの保留場所 |
| Claude Managed Agents | 「ホスティング型ハーネス」 | Anthropicホスティングの長時間実行非同期処理（キャッシュ + コンパクション付き） |
