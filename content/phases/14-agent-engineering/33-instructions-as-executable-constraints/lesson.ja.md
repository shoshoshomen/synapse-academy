# 実行可能制約としてのエージェント指示

> 散文で書かれた指示は願い事だ。制約として書かれた指示はテストだ。ワークベンチは各ルールをエージェントがランタイムでチェックでき、レビュアーが事後に検証できるものに変える。


## 学習目標

- ルーティング散文と運用ルールを分離する。
- 起動ルール、禁止アクション、完了の定義、不確実性の処理、承認境界を機械チェック可能な制約として表現する。
- 実行に対してルールセットをスコアリングするルールチェッカーを実装する。
- ルールセットをdiffフレンドリーにして、レビューで何が変わったかを見られるようにする。

## 問題

典型的な`AGENTS.md`はオンボーディングドキュメントのように読める。エージェントに「注意して」「徹底的にテストして」「不明なら聞いて」と伝える。3日後、エージェントはテストなしで変更を出荷し、禁止されたディレクトリに書き込み、どこが境界線かを知らなかったため決して聞かない。

指示は運用可能な時に強力で、願望的な時に弱い。修正はワークベンチが解釈できレビュアーがスコアリングできるルールを書くことだ。

## コンセプト

ルールは短いルートルーターから離れて`docs/agent-rules.md`に属する。各ルールには名前、カテゴリー、チェックがある。

```mermaid
flowchart LR
  Router[AGENTS.md] --> Rules[docs/agent-rules.md]
  Rules --> Checker[rule_checker.py]
  Checker --> Report[rule_report.json]
  Report --> Reviewer[レビュアー]
```

### ほとんどのルールをカバーする5つのカテゴリー

| カテゴリー | ルールが答える質問 | 例 |
|----------|-----------------|---|
| 起動 | 作業開始前に何が真である必要があるか？ | 「ステートファイルが存在し、新鮮である」 |
| 禁止 | 決して起こってはならないことは？ | 「`scripts/release.sh`を編集しない」 |
| 完了の定義 | タスクが完了している証拠は何か？ | 「pytestがゼロで終了し、受け入れ行が合格する」 |
| 不確実性 | 不明な時にエージェントは何をするか？ | 「推測する代わりに質問ノートを開く」 |
| 承認 | 人間の承認が必要なものは？ | 「新しい依存関係、プロドライト」 |

これら5つのいずれかに収まらないルールは通常、2つのルールにしたい。分割を強制する。

### ルールは機械可読

各ルールにはスラッグ、カテゴリー、1行説明、`rule_checker.py`の関数を名前付けする`check`フィールドがある。ルールを追加することはチェックを追加することを意味する；チェッカーがワークベンチと一緒に成長する。

### ルールはdiffフレンドリー

ルールは単一のmarkdownファイルの見出しごとに1つ存在する。名前変更がdiffで見える。新しいルールがカテゴリーのトップに座る。古いルールは削除され、コメントアウトされない。なぜならワークベンチが記録のシステムであり、チームが昨年何を感じていたかのチャットログではないから。

### ルール対フレームワークガードレール

フレームワークガードレール（OpenAI Agents SDKガードレール、LangGraphインタラプト）はランタイムレベルでルールを強制する。このレッスンのルールセットは、それらのガードレールが実装する人間可読で、レビュー可能なコントラクトだ。両方が必要だ：ランタイムがターン中に違反をキャッチし、ルールセットがランタイムが正しいことをしていることを証明する。

### プログレッシブ開示：百科事典ではなく地図

`AGENTS.md`が成長し続ける理由は、すべてのインシデントがルールを追加し、どのインシデントもルールを削除しないからだ。1年後にファイルは2000行になり、エージェントは最初の画面を読み、注意バジェットを使い切り、伝えられたことの一部に対して行動する。巨大な指示ファイルが40ページのオンボーディングドキュメントと同じ理由で失敗する：読者が一度ざっと読んで重要な部分に戻らない。

修正は短いファイルではない。階層化されたファイルだ。ルートルーターはすべてのセッションで読めるほど小さく保たれ、ポインターだけを持つ。深さはエージェントがタスクがそれらに触れる時だけロードするトピックファイルに存在する。エージェントに百科事典全体ではなく地図を与えて、必要なページに歩かせる。

```
AGENTS.md                  # ルーター、< 50行：このリポジトリが何か、どこを見るか、5つのハードルール
docs/
  agent-rules.md           # 完全なルールセット（このレッスン）
  architecture.md          # タスクがモジュール境界に触れる時にロードされる
  testing.md               # タスクがテストを書くか実行する時にロードされる
  deploy.md                # リリース作業のみ、承認ルールでゲートされる
feature_list.json          # バックログ（フェーズ14・36）
```

| 層 | 存在する場所 | 読まれる時 | サイズバジェット |
|---|----------|-----------|---------------|
| ルーター | `AGENTS.md` | すべてのセッション、常に | 約50行以内 |
| ルール | `docs/agent-rules.md` | すべてのセッション、起動時 | カテゴリーごとに1画面 |
| トピックドキュメント | `docs/<topic>.md` | タスクがそのトピックに触れる時のみ | 必要な深さ |

2つのテストが階層化を誠実に保つ。到達可能性テスト：エージェントはルーターから最大2ホップで任意のルールに到達できるべきだ。そのためルーターはすべてのトピックドキュメントをパスでリンクし、散文で説明しないこと。鮮度テスト：ルーターはすべてのPRでレビュアーが再読するほど短いこと、これがそれを黙って百科事典に戻すことを止める唯一のものだ。解決しないリンクはルールの欠落より悪い失敗なので、ルーターの壊れたリンクはそれ自体が起動チェック違反だ。

## 実装する

`code/main.py` が出荷するもの：

- ルールをデータクラスにロードする`agent-rules.md`パーサー。
- `check`参照ごとに1つ、`rule_checker.py`スタイルのチェッカー関数。
- 2つのルールに違反するデモエージェント実行と、それをキャッチするチェックパス。

実行：

```
python3 code/main.py
```

出力：解析されたルールセット、実行トレース、ルールごとの合格/不合格、スクリプトの横に保存された`rule_report.json`。

## 実際の本番パターン

3つのパターンが、1四半期続くルールセットと1週間で崩壊するルールセットを分ける。

**書き込み時の重大度タグ付け。** すべてのルールが`severity`：`block`、`warn`、または`info`を持つ。チェッカーが3つすべてを報告する；ランタイムは`block`のみを拒否する。ほとんどのチームが早期に重大度を誇張してから締め切りプレッシャーの下で静かに弱める；書き込み時のタグ付けが最初からキャリブレーションを強制する。検証ゲートとペアにする（フェーズ14・38）、それが`block`ルールのオーバーライドを`overrides.jsonl`監査ログに署名する。

**強制機能としてのルール有効期限。** すべてのルールが`expires_at`日付（デフォルト：作成から90日）を持つ。チェッカーは未期限のルールが60連続日間でゼロ違反だった時に警告を出す；次の四半期レビューでそれを保持するか、`info`に弱めるか、削除するかを正当化する。Cloudflareのプロダクション AIコードレビューデータ（2026年4月、30日で5,169リポジトリにわたる131,246レビュー実行）は、明示的な有効期限を持つルールセットがリポジトリあたり30ルール以内に収まることを示した；なしのものは80以上に成長し、ほとんどが発火しなかった。

**ソースとしてのMarkdown、キャッシュとしてのJSON。** `agent-rules.md`が作成ファイル；`agent-rules.lock.json`がホットパスでチェッカーが読むキャッシュ。ロックはpre-commitフックで再生成される。Markdownのdiffがレビュー可能；JSON解析がすべてのターンの外に保たれる。`package.json` / `package-lock.json`と`Cargo.toml` / `Cargo.lock`と同じ形状。

## 使ってみる

プロダクションでは：

- Claude Code、Codex、Cursorがセッション開始時にルールを読み、アクションを拒否する時にそれらを引用する。チェッカーがCIで再実行してサイレントドリフトをキャッチする。
- OpenAI Agents SDKガードレールが同じチェックを入力と出力ガードレールとして登録する。Markdownがドキュメント表面；SDKがランタイム表面。
- LangGraphインタラプトがインフライトのノードがルールに違反した時に発火する。インタラプトハンドラーがルールを読み、人間に聞き、再開する。

ルールセットはMarkdownと関数名だけなのですべて3つで移植可能だ。

## 成果物を出す

`outputs/skill-rule-set-builder.md` がプロジェクトオーナーにインタビューし、既存の散文指示を5つのカテゴリーに分類し、バージョン管理された`agent-rules.md`とチェッカースタブを出力する。

## 演習

1. 自分の製品が本当に必要とする場合は6番目のカテゴリーを追加する。5つのいずれかに崩壊しない理由を擁護する。
2. ルールが重大度（`block`、`warn`、`info`）を持てるようにチェッカーを拡張し、レポートがそれに応じて集計する。
3. チェッカーをCIに組み込む：最新のエージェント実行でブロック重大度のルールが失敗した場合、ビルドを失敗させる。
4. ルールごとに「有効期限」フィールドを追加する。90日間チェック失敗なしの後、ルールはレビュー対象となる。
5. 実際の`AGENTS.md`を見つけて5カテゴリールールとして書き直す。運用的なものは何行あったか？願望的なものは？

## キーワード

| 用語 | 一般的な言い方 | 実際の意味 |
|------|----------------|------------|
| 運用ルール | 「本当の指示」 | ワークベンチがランタイムでチェックできるルール |
| 願望ルール | 「注意して」 | チェックのないルール；削除するかアップグレードする |
| 完了の定義 | 「受け入れ」 | タスクが完了している客観的なファイルバックの証明 |
| ブロック重大度 | 「ハードルール」 | 違反が実行を停止する；オペレーターなしでは黙らせることができない |
| ルール有効期限 | 「古いルール掃除」 | N日間失敗のないルールは廃止候補 |
