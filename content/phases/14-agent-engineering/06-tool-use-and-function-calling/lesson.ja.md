# ツール使用とファンクションコーリング

> Toolformer（Schick et al.、2023）が自己教師ありツールアノテーションを始めた。Berkeley Function Calling Leaderboard V4（Patil et al.、2025）が2026年のバーを設定する: 40%エージェント型、30%マルチターン、10%ライブ、10%非ライブ、10%幻覚。シングルターンは解決済みだ。メモリ、動的意思決定、長期ツールチェーンは未解決だ。


## 学習目標

- Toolformerの自己教師ありトレーニングシグナルを説明できる: 実行が次トークンの損失を削減する場合のみツールアノテーションを保持する。
- BFCL V4の5つの評価カテゴリとそれぞれが何を測定するかに名前を付けられる。
- スキーマ検証、引数強制、実行サンドボックスを持つstdlibツールレジストリを実装できる。
- 2026年の3つのオープン問題を診断できる: 長期ツールチェーニング、動的意思決定、メモリ。

## 課題

初期のツール使用は「モデルは正しいファンクションコールを予測できるか？」と尋ねた。現代のツール使用は「モデルは40ステップ間ツールをチェーンでき、メモリがあり、部分的な可観測性があり、ツールの失敗から回復でき、存在しないツールを幻覚せずにできるか？」と尋ねる。

Toolformerはベースラインを確立した: モデルは自己教師ありでツールを呼び出すタイミングを学習できる。BFCL V4は2026年の評価ターゲットを定義する。それらの間のギャップが本番エージェントが生きている空間だ。

## コンセプト

### Toolformer（Schick et al.、NeurIPS 2023）

アイデア: モデルに自分の事前学習コーパスを候補APIコールでアノテートさせる。各候補に対して実行する。アノテーションは次のトークンの損失を削減する場合のみ保持する。フィルタリングされたコーパスでファインチューンする。

カバーするツール: 電卓、QAシステム、検索エンジン、翻訳機、カレンダー。自己教師ありシグナルは純粋にツールがテキストを予測するのに役立つかどうかについて—人間ラベルなし。

スケール結果: ツール使用はスケールとともに出現する。より小さいモデルはツールアノテーションから損害を受け; より大きいモデルは利益を得る。これが2026年のフロンティアモデルが強いツール使用を組み込んでいる一方で、ほとんどの7Bモデルが信頼性のためには明示的なツール使用ファインチューニングを必要とする理由だ。

### Berkeley Function Calling Leaderboard V4（Patil et al.、ICML 2025）

BFCLは2026年のデファクト評価だ。V4の構成:

- **エージェント型（40%）** — 完全なエージェントトラジェクトリ: メモリ、マルチターン、動的決定。
- **マルチターン（30%）** — ツールチェーンを持つインタラクティブな会話。
- **ライブ（10%）** — ユーザーが提出した実際のプロンプト（より難しい分布）。
- **非ライブ（10%）** — 合成テストケース。
- **幻覚（10%）** — ツールを呼び出すべきでない場合を検出する。

V3はステートベース評価を導入した: ツールシーケンス後、ツール呼び出しのASTをマッチングするのではなく、APIの実際の状態（例: 「ファイルが作成されたか？」）をチェックする。V4はウェブ検索、メモリ、フォーマット感度カテゴリを追加した。

2026年の主要な発見: シングルターンのファンクションコーリングはほぼ解決済みだ。失敗はメモリ（ターン間のコンテキストの運搬）、動的意思決定（以前の結果に基づいてツールを選ぶ）、長期チェーン（20ステップ以降のドリフト）、幻覚検出（ツールが合わない場合に呼び出しを拒否する）に集中している。

### ツールスキーマ

すべてのプロバイダーにスキーマがある。詳細は異なるが、同じ形状を共有する:

```
name: string
description: string （何をするか、いつ使うか）
input_schema: JSON Schema （properties、required、types、enums）
```

Anthropicは`input_schema`を直接使用する。OpenAIは`function.parameters`を使用する。両方ともJSON Schemaを受け入れる。説明は重要だ—モデルはそれを読んで正しいツールを選ぶ。悪いツール説明は間違ったツール選択失敗の#1根本原因だ。

### 引数検証

ツール呼び出しを信頼しない。以下を検証:

1. **型強制。** モデルはスキーマがintと言っているのに文字列"5"を返すかもしれない。明確な場合は強制する; そうでない場合は拒否する。
2. **Enum検証。** スキーマが `status in {"open", "closed"}` と言っているのにモデルが `"in_progress"` を出力した場合、説明的なエラーで拒否する。
3. **必須フィールド。** 必須フィールドが欠けている -> クラッシュではなくモデルへの即時エラー観察。
4. **フォーマット検証。** 日付、メール、URL—regexではなく具体的なパーサーで検証する。

すべての検証失敗は、モデルが正しい形状でリトライできるよう構造化された観察を返すべきだ。

### 並列ツール呼び出し

現代のプロバイダーは1つのアシスタントターンで並列ツール呼び出しをサポートする。ループ:

1. モデルが異なる `tool_use_id` を持つ3つのツール呼び出しを出力する。
2. ランタイムがそれらを（独立している場合は並列で）実行する。
3. 各結果は `tool_use_id` で相関付けられた `tool_result` ブロックとして戻る。

エンジニアリングルール: 相関IDを重要なものとして扱う。それらを交換すると、間違ったツールに間違った結果がルーティングされる。

### サンドボックス

ツール実行はサンドボックス境界だ。詳細はレッスン09を参照。短版: すべてのツールは読み取り/書き込み表面、ネットワークアクセス、タイムアウト、メモリキャップを指定すべきだ。汎用 `run_shell(cmd)` はレッドフラグ; 特定の `git_status()` の方が安全だ。

## 実装する

`code/main.py` は本番形状のツールレジストリを実装している:

- JSON Schemaサブセットバリデーター（stdlibのみ）。
- 説明、入力スキーマ、タイムアウト、エグゼキューターを持つツール登録。
- 引数強制とenum検証。
- 相関IDを持つ並列ツールディスパッチ。
- 構造化された文字列としてのエラー観察。

実行:

```
python3 code/main.py
```

トレースは1つのターンで3つのツールを呼び出すミニエージェントを示し、1つは意図的に不正な形式で、モデルが対応できる説明的なエラーで拒否される。

## 使ってみる

すべてのプロバイダーには独自のツールスキーマがある—Anthropic、OpenAI、Gemini、Bedrock。マルチプロバイダーが必要な場合は変換レイヤー（OpenAI Agents SDK、Vercel AI SDK、LangChainツールアダプター）を使用する。BFCLがリファレンスベンチマークだ—ツール使用が製品の中心の場合、出荷前にエージェントに対して実行する。

## 成果物を出す

`outputs/skill-tool-registry.md` は特定のタスクドメインのツールカタログ、スキーマ、レジストリを生成する。説明の品質チェックを含む（各ツールの説明はモデルにいつ使うかを伝えているか？）。

## 演習

1. モデルが明示的に他のツールを使用することを拒否できる「何もしない」ツールを追加する。BFCLライクな幻覚テストで計測する。
2. int-as-stringとfloat-as-stringの引数強制を実装する。強制はどこで実際のバグを隠し始めるか？
3. ツールごとのタイムアウトとサーキットブレーカー（3回連続失敗後60秒ツールを拒否する）を追加する。これはモデルの回復方法に何を変えるか？
4. BFCL V4の説明を読む。1つのカテゴリ（例: 「マルチターン」）を選び、エージェントを通じて10個のプロンプトの例を実行する。パスレートを報告する。
5. stdlibバリデーターをPydanticまたはZodにポートする。Pydantic/Zodがトイが見逃したものを何を検出したか？

## キーワード

| 用語 | よく聞く言い方 | 実際の意味 |
|------|----------------|------------|
| Function calling（ファンクションコーリング） | "ツール使用" | 検証されたスキーマを持つ構造化出力ツール呼び出し |
| Toolformer | "自己教師ありツールアノテーション" | Schick 2023 — 結果が次トークン損失を削減するツール呼び出しを保持 |
| BFCL | "Berkeley Function Calling Leaderboard" | 2026年ベンチマーク: 40%エージェント型、30%マルチターン、10%ライブ、10%非ライブ、10%幻覚 |
| Tool schema（ツールスキーマ） | "モデル向けの関数シグネチャ" | 名前、説明、引数のJSON Schema |
| tool_use_id | "相関ID" | ツール呼び出しをその結果に結び付ける; 並列ディスパッチに不可欠 |
| Hallucination detection（幻覚検出） | "呼び出さない場合を知る" | V4カテゴリ: ツールが合わない場合に呼び出しを拒否する |

| Sandboxing（サンドボックス） | "ツール実行境界" | ツールごとの読み取り/書き込み表面、ネットワーク、タイムアウト、メモリキャップ |
