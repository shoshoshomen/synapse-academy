# 失敗モード: エージェントが壊れる理由

> MASFT（Berkeley、2025年）は3つのカテゴリに14のマルチエージェント失敗モードを分類しています。Microsoft のタクソノミーは既存の AI の失敗がエージェント設定でどのように増幅するかを文書化しています。業界のフィールドデータは5つの繰り返しモードに収束しています: 幻覚アクション、スコープクリープ、連鎖エラー、コンテキスト喪失、ツールの誤用。


## 学習目標

- MASFT の3つの失敗カテゴリと各カテゴリの少なくとも4つの具体的なモードを説明できる。
- エージェント的な失敗が既存の AI 失敗モード（バイアス、幻覚）を増幅させる理由を説明できる。
- 5つの業界繰り返しモードとその軽減策を説明できる。
- エージェントトレースに失敗モードラベルをタグ付けする標準ライブラリ検出器を実装できる。

## 問題設定

チームはトレースの 90% で機能するエージェントを出荷します。10% の失敗はランダムノイズではありません — 少数の繰り返しカテゴリに収まります。それらに名前を付けられれば、監視して修正できます。

## コンセプト

### MASFT（Berkeley、arXiv:2503.13657）

マルチエージェントシステム失敗タクソノミー。3つのカテゴリに14の失敗モード。アノテーター間の Cohen's Kappa 0.88 — カテゴリは確実に区別可能です。

中心的な主張: 失敗はマルチエージェントシステムの基本的な設計上の欠陥であり、より良いベースモデルで修正されるべき LLM の制限ではありません。

### Microsoft のエージェント AI システムの失敗モードのタクソノミー

- 既存の AI の失敗（バイアス、幻覚、データ漏洩）はエージェント設定で増幅します。
- 自律性から新しい失敗が生まれます: 大規模での意図しないアクション、ツールの誤用、ミッションドリフト。
- このホワイトペーパーはエージェント製品のリスクレジスターです。

### エージェント AI における障害の特性評価（arXiv:2603.06847）

- 失敗はオーケストレーション、内部状態の進化、環境との相互作用から生じます。
- 単純な「バッドコード」や「バッドモデル出力」ではありません。

### LLM エージェント幻覚サーベイ（arXiv:2509.18970）

2つの主要な現れ方:

1. **指示遵守からの逸脱** — エージェントがシステムプロンプトに従わない。
2. **長距離コンテキストの誤用** — エージェントが前のターンからのコンテキストを忘れたり誤って適用する。

サブインテンションエラー: 省略（見逃したステップ）、冗長（繰り返しステップ）、無秩序（順序外のステップ）。

### 5つの業界繰り返しモード

Arize、Galileo、NimbleBrain の 2024〜2026 年のフィールド分析は以下に収束:

1. **幻覚アクション.** エージェントが存在しないツールを呼び出すか、引数を捏造する。
2. **スコープクリープ.** エージェントがユーザーの依頼を超えてタスクを拡張する（余分な PR を作成、余分なメールを送信）。
3. **連鎖エラー.** 1つの間違った呼び出しが下流の影響を引き起こす。幻想のSKUの幻覚が4回の API 呼び出しをトリガーします — マルチシステムのインシデント。
4. **コンテキスト喪失.** 長期タスクが初期ターンの制約を忘れる。
5. **ツールの誤用.** 間違った引数で正しいツールを呼び出すか、完全に間違ったツールを呼び出す。

連鎖が最も致命的です。エージェントは「失敗した」と「タスクが不可能」の区別ができず、ループを閉じるために 400 エラーで成功メッセージを幻覚することがよくあります。

### 軽減策: すべてのステップでゲート

推論チェーンのすべてのステップでの自動検証ゲート。環境状態に対して事実的なグラウンディングをチェックします。具体的には:

- ステップごとの安全分類器（レッスン21）。
- ツール呼び出し引数の検証（レッスン06）。
- 取得されたコンテンツを既知の事実とクロスチェック（レッスン05、CRITIC）。
- 状態を再プローブして成功幻覚を検出（ファイルは実際に作成されましたか？）。

### 失敗監視が失敗するケース

- **クラッシュのみのタグ付け.** ほとんどのエージェント失敗は有効に見える出力を生成します。コンテキストレベルのチェックが必要です。
- **ベースラインなし.** ドリフト検出には最後の既知の良好な状態が必要です。それがなければ「悪化している」と言えません。
- **過剰アラート.** すべての失敗がページを生成する。クラスタリングとレートリミットをしてください。

## 実装する

`code/main.py` は標準ライブラリの失敗モードタガーを実装しています:

- 5つのモードをカバーする合成トレースデータセット。
- モードごとの検出関数（ツール呼び出し、出力、繰り返しアクションのシグネチャパターン）。
- 各トレースにラベルを付けてモード分布を報告するタガー。

実行:

```
python3 code/main.py
```

出力: トレースごとのラベル + 集計分布。Phoenix のトレースクラスタリングが表面化するものの安価な再現。

## 使ってみる

- **Phoenix** は本番のドリフトクラスタリングに（レッスン24）。
- **Langfuse** はセッションリプレイ + アノテーションに。
- **カスタム** はオブザーバビリティプラットフォームが検出できないドメイン固有のシグネチャに。

## 成果物を出す

`outputs/skill-failure-detector.md` はトレースストアに組み込まれた、自分のドメインに合わせた失敗モード検出器を生成します。

## 演習

1. 「成功幻覚」の検出器を追加します: エージェントが成功を返すがターゲットの状態は変わっていない。
2. 自分が構築したプロダクトから 100 件の実際のトレースにタグを付けます。どのモードが支配的ですか？修正のコストは？
3. 「連鎖半径」メトリクスを実装します: ステップ N での失敗が与えられた場合、何個の下流ステップが影響を受けましたか？
4. MASFT の 14 の失敗モードを読みます。自分のプロダクトに適用される3つを選びます。検出器を書きます。
5. 1つの検出器を CI ジョブに組み込みます: トレースの 5% 以上がモードにタグ付けされたらビルドを失敗させます。

## キーワード

| 用語 | 一般的な言い方 | 実際の意味 |
|------|----------------|------------|
| MASFT | "マルチエージェント失敗タクソノミー" | Berkeley の 14 モード分類 |
| 連鎖エラー | "リプル失敗" | 1つの早期の間違いが N ステップにわたって伝播する |
| コンテキスト喪失 | "制約を忘れた" | 長期ターンが初期ターンの事実を落とす |
| ツールの誤用 | "間違ったツール / 間違った引数" | 有効な呼び出し、間違った呼び出し方 |
| 成功幻覚 | "偽完了" | エージェントが 400 で成功を主張。状態は変わらず |
| スコープクリープ | "過剰行動" | エージェントが依頼より多くを行う |
| 指示遵守からの逸脱 | "不服従" | システムプロンプトまたはユーザー制約を無視 |
| サブインテンションエラー | "計画バグ" | 計画実行における省略、冗長、無秩序 |
