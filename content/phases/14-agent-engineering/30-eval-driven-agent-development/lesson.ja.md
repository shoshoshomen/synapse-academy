# 評価駆動エージェント開発

> Anthropicのガイダンス：「シンプルなプロンプトから始め、包括的な評価でそれを最適化し、必要な時にのみマルチステップのエージェントシステムを追加する」。評価は最後のステップではない。フェーズ14のあらゆる選択を駆動する外側のループである。


## 学習目標

- 3つの評価層——静的ベンチマーク、カスタムオフライン、オンラインプロダクション——とそれぞれの用途を挙げる。
- 評価者・最適化者の緊密なループを説明する。
- 2026年のベストプラクティスを説明する：評価はコードのそばに置き、CIで実行し、PRをゲートする。
- フェーズ14の各レッスンを、それが生成する評価ケースと結びつける。

## 問題

エージェントはデモに合格する。デモが予測できない方法でプロダクションで失敗する。ベンチマークは「このモデルは広く有能か？」に答えるが、「このエージェントは自分の製品に正しいパッチを出荷しているか？」には答えない。答えは：3つの層で継続的に実行される評価であり、すべてのガードレールと学習済みルールが評価ケースに対応づけられている。

## コンセプト

### 3つの評価層

1. **静的ベンチマーク** — コード用のSWE-bench Verified（レッスン19）、ブラウジング/デスクトップ用のWebArena/OSWorld（レッスン20）、汎用のGAIA（レッスン19）、ツール使用のBFCL V4（レッスン06）。クロスモデル比較とリグレッションゲートに使用。汚染は実在する：SWE-bench+では32.67%のソリューション漏洩が見つかった。常にVerified / +-監査済みスコアを報告すること。

2. **カスタムオフライン評価** — 製品の形状に応じて：
   - LLM-as-judge（Langfuse、Phoenix、Opik — レッスン24）。
   - 実行ベース（パッチを実行してテストを確認）。
   - 軌跡ベース（アクションシーケンスをゴールドと比較；OSWorld-Humanではトップエージェントがゴールドの1.4〜2.7倍）。

3. **オンライン評価** — プロダクション：
   - セッションリプレイ（Langfuse）。
   - ガードレールトリガーアラート（レッスン16、21）。
   - ステップごとのコスト/レイテンシ追跡（レッスン23 OTelスパン）。

### 評価者・最適化者（Anthropic）

緊密なループ：

1. プロポーザーが出力を生成する。
2. 評価者が判定する。
3. 評価者が合格するまで改善する。

これはSelf-Refine（レッスン05）を一般化したものだ。関心のあるエージェントフローはすべて、評価者・最適化者でラップして信頼性を高めることができる。

### 2026年のベストプラクティス

- 評価はコードのそばに置く。
- すべてのPRでCIで実行する。
- 評価スコアでマージをゲートする（例：「mainに対して5%以上のリグレッションなし」）。
- すべてのガードレールが評価ケースに対応している。
- すべての学習済みルール（Reflexion、proワークフローlearn-rule）が失敗ケースに対応している。

### フェーズ14のまとめ

フェーズ14の各レッスンが評価ケースを生成する：

| レッスン | 生成される評価ケース |
|--------|----------------------|
| 01 エージェントループ | バジェット枯渇、無限ループガード |
| 02 ReWOO | ツール失敗時にプランナーが正しく再計画する |
| 03 Reflexion | 再試行時に学習済みリフレクションが適用される |
| 05 Self-Refine/CRITIC | ジャッジが改善された出力を合格とする |
| 06 ツール使用 | 引数の変換が機能する；未知のツールが拒否される |
| 07-10 メモリ | 検索の引用がソースと一致する；古い事実が無効化される |
| 12 ワークフローパターン | 各パターンが正しい出力を生成する |
| 13 LangGraph | 再開がステートを正確に再現する |
| 14 AutoGen アクター | DLQがクラッシュしたハンドラーをキャッチする |
| 16 OpenAI Agents SDK | ガードレールが正しい入力でトリップする |
| 17 Claude Agent SDK | サブエージェントの結果がオーケストレーターに返る |
| 19-20 ベンチマーク | SWE-bench Verifiedスコア、WebArena成功率、OSWorld効率 |
| 21 コンピューターユース | ステップごとの安全性がインジェクトされたDOMをキャッチする |
| 23 OTel | スパンが必要な属性を出力する |
| 26 失敗モード | 検出器が既知の失敗をタグ付けする |
| 27 プロンプトインジェクション | PVEが汚染された検索を拒否する |
| 28 オーケストレーション | スーパーバイザーが正しい専門家にルーティングする |
| 29 ランタイム形状 | DLQがN%の失敗を処理する |

評価スイートにこれらすべてのケースがあれば、フェーズ14をカバーしている。

### 評価駆動開発が失敗する場所

- **ベースラインなし。** ベースラインのない評価は読み取れない。ベースラインを保存する。
- **グラウンディングなしのLLMジャッジ。** ジャッジもハルシネーションする。CRITICパターン（レッスン05）——ジャッジは外部ツールでグラウンディングする。
- **評価への過学習。** 評価に最適化することでプロダクションの有用性から乖離する。ケースをローテーションする。
- **不安定な評価。** 非決定論的なケースが誤アラームを引き起こす。シードを固定し、ステートをスナップショットする。

## 実装する

`code/main.py` は標準ライブラリの評価ハーネス：

- カテゴリ付きケースレジストリ（ベンチマーク、カスタム、オンライン）。
- テスト対象のスクリプト済みエージェント。
- 評価者・最適化者ループ：提案、判定、合格またはmax ラウンドまで改善。
- CIゲート：集計合格率 + ベースラインに対するリグレッション。

実行：

```
python3 code/main.py
```

出力：ケースごとの合格/不合格、リグレッションフラグ、CIゲート判定。

## 使ってみる

- エージェントコードと同じリポジトリに評価ケースを書く。
- すべてのPRでCIを通じて実行する。
- リグレッションでビルドを失敗させる。
- 経時的に合格率を追跡する。
- すべてのプロダクション失敗を新しいケースに結びつける。

## 成果物を出す

`outputs/skill-eval-suite.md` がCIゲートとリグレッション追跡を持つエージェント製品の3層評価スイートを構築する。

## 演習

1. プロダクション失敗の1つを取り上げる。それを再現する評価ケースを書く。エージェントは今それに合格するか？
2. 3次元（事実性、トーン、スコープ）を持つドメイン用LLMジャッジルーブリックを構築する。50セッションをスコアリングする。
3. 評価スイートをCIに組み込む。5%以上のリグレッションでビルドを失敗させる。
4. 軌跡効率メトリクスを追加する：エージェントはゴールド軌跡と比較して何ステップかかったか？
5. フェーズ14の各レッスンをスイートの評価ケースにマッピングする。欠けているものは？それが埋めるべきギャップだ。

## キーワード

| 用語 | 一般的な言い方 | 実際の意味 |
|------|----------------|------------|
| 静的ベンチマーク | 「既製評価」 | SWE-bench、GAIA、AgentBench、WebArena、OSWorld |
| カスタムオフライン評価 | 「ドメイン評価」 | 製品形状に合わせたLLM-as-judge / 実行 / 軌跡 |
| オンライン評価 | 「プロダクション評価」 | セッションリプレイ、ガードレールアラート、コスト/レイテンシ追跡 |
| 評価者・最適化者 | 「提案・判定・改善」 | ジャッジが合格するまで繰り返す |
| CIゲート | 「マージブロッカー」 | 評価リグレッションでビルドを失敗させる |
| ベースライン | 「最後の既知良好」 | リグレッションを検出するための基準スコア |
| 軌跡効率 | 「ゴールドに対するステップ数」 | エージェントのステップ数を人間専門家の最小値で割ったもの |
