# Self-RefineとCRITIC: 反復的な出力改善

> Self-Refine（Madaan et al.、2023）は1つのLLMを3つの役割で使用する—生成、フィードバック、精製—をループ内で。7つのタスクで平均+20絶対的改善。CRITIC（Gou et al.、2023）はフィードバックステップを外部ツールを通じて検証することで強化する。2026年にこのパターンはすべてのフレームワークで「評価器-オプティマイザー」（Anthropic）またはガードレールループ（OpenAI Agents SDK）として出荷されている。


## 学習目標

- Self-Refineの3つのプロンプト（生成、フィードバック、精製）を説明し、精製プロンプトに履歴が重要な理由を説明できる。
- CRITICの重要な洞察を説明できる: LLMは外部の根拠なしでは自己検証が信頼できない。
- 履歴とオプションの外部検証器を持つstdlib Self-Refineループを実装できる。
- このパターンをAnthropicの「評価器-オプティマイザー」ワークフローとOpenAI Agents SDKの出力ガードレールにマッピングできる。

## 課題

エージェントがほぼ正しい答えを生成する。おそらくコードの行に構文エラーがある。おそらくサマリーが長すぎる。おそらくプランにエッジケースが欠けている。必要なのは: エージェントが自分の出力を批判し、それを修正することだ。

Self-Refineは、これが単一モデル、トレーニングデータなし、RLなしで機能することを示す。しかしキャッチがある: LLMは難しい事実の自己検証が苦手だ。CRITICは修正を命名する—外部ツール（検索、コードインタープリター、電卓、テストランナー）を通じて検証ステップをルーティングする。

これらの2つの論文が2026年の反復的改善のデフォルトを定義している: 生成、（可能な場合は外部で）検証、精製、検証器が通過するまで停止。

## コンセプト

### Self-Refine（Madaan et al.、NeurIPS 2023）

1つのLLM、3つの役割:

```
generate(task)            -> output_0
feedback(task, output_0)  -> critique_0
refine(task, output_0, critique_0, history) -> output_1
feedback(task, output_1)  -> critique_1
refine(task, output_1, critique_1, history) -> output_2
...
フィードバックが「問題なし」と言うかバジェットが枯渇するまで停止。
```

重要な詳細: `refine` は完全な履歴—以前のすべての出力と批判—を見るため、ミスを繰り返さない。論文はこれをアブレーションする: 履歴を削除すると品質が急落する。

ヘッドライン: GPT-4を含む7つのタスク（数学、コード、頭字語、ダイアログ）で平均+20絶対的改善。トレーニングなし、外部ツールなし、単一モデル。

### CRITIC（Gou et al.、arXiv:2305.11738、v4 2024年2月）

Self-Refineの弱点: フィードバックステップはLLMが自分をスコアリングしている。事実の主張ではこれは信頼できない（幻覚は、それを生成したモデルにとってしばしば説得力があるように見える）。CRITICは `feedback(task, output)` を `verify(task, output, tools)` に置き換える。`tools` には以下が含まれる:

- 事実の主張のための検索エンジン。
- コードの正確性のためのコードインタープリター。
- 算術のための電卓。
- ドメイン固有の検証器（ユニットテスト、型チェッカー、リンター）。

検証器はツール結果に根拠を置いた構造化された批判を生成する。精製器はその批判を条件付けにする。

ヘッドライン: CRITICは批判が根拠付けられているため、事実タスクでSelf-Refineを上回る。外部検証器のないタスク（創造的な文章、フォーマット）ではCRITICはSelf-Refineに劣化する。

### 停止条件

2つの一般的な形状:

1. **検証器が通過する。** 外部テストが成功を返す。利用可能な場合に好ましい（ユニットテスト、型チェッカー、ガードレールアサーション）。
2. **フィードバックが出ない。** モデルが「出力は問題ない」と言う。安いが信頼できない; 最大イテレーションキャップと組み合わせる。

2026年のデフォルト: 両方を組み合わせる。「検証器が通過するか、モデルが問題ないと言い、イテレーション >= 2、またはイテレーション >= max_iterations の場合に停止する。」

### 評価器-オプティマイザー（Anthropic、2024年）

Anthropicの2024年12月の投稿はこれを5つのワークフローパターンの1つとして名付けている。2つの役割:

- 評価器: 出力をスコアリングし、批判を生成する。
- オプティマイザー: 批判に基づいて出力を修正する。

評価器が通過するまでループする。これはAnthropicのフレーミングでのSelf-Refine/CRITICだ。Anthropicが追加する重要なエンジニアリングの詳細: 評価器とオプティマイザーのプロンプトは実質的に異なるべきであり、モデルが単にゴム判子にしないようにする。

### OpenAI Agents SDKの出力ガードレール

OpenAI Agents SDKはこのパターンを「出力ガードレール」として出荷する。ガードレールはエージェントの最終出力で実行される検証器だ。ガードレールが作動する（`OutputGuardrailTripwireTriggered` を発生させる）と、出力は拒否され、エージェントはリトライできる。ガードレールはツールを呼び出せる（CRITICスタイル）または純粋関数にできる（Self-Refineスタイル）。

### 2026年の落とし穴

- **ゴム判子ループ。** 同じプロンプトスタイルで生成と批判を行う同じモデルは「良さそうだ」に収束する。構造的に異なるプロンプトを使うか、批判には安い小さいモデルを使う。
- **過剰精製。** 各精製パスはレイテンシとトークンを追加する。1〜3パスに予算を設定する; その後は人間のレビューにエスカレートする。
- **些細なタスクでのCRITIC。** 外部検証器がない場合、CRITICはSelf-Refineに劣化する; スタブ検証器のレイテンシを払わない。

## 実装する

`code/main.py` はトイタスクでSelf-RefineとCRITICを実装している: トピックを与えられた短い箇条書きリストを生成する。検証器はフォーマットをチェックする（3つの箇条書き、それぞれ60文字未満）。CRITICは既知の幻覚にペナルティを与える外部「事実検証器」を追加する。

コンポーネント:

- `generate` — スクリプト化プロデューサー。
- `feedback` — LLMスタイルの自己批判。
- `verify_external` — CRITICスタイルの根拠付き検証器。
- `refine` — 履歴を与えて出力を書き直す。
- 停止条件 — 検証器が通過するか最大4イテレーション。

実行:

```
python3 code/main.py
```

Self-Refine vs CRITIC実行を比較する。CRITICは外部検証器がSelf-Criticにはない根拠を持っているため、Self-Refineが見逃した事実エラーを検出する。

## 使ってみる

Anthropicの評価器-オプティマイザーはClaudeフレンドリーな言語でのこのパターンだ。OpenAI Agents SDKの出力ガードレールはCRITIC形状だ（ガードレールはツールを呼び出せる）。LangGraphはSelf-Refineのように読めるリフレクションノードを出荷する。GoogleのGemini 2.5 Computer Useは、CRITICのバリアントであるステップごとの安全性評価器を追加する: すべてのアクションはコミット前に検証される。

## 成果物を出す

`outputs/skill-refine-loop.md` は、タスク形状、検証器の利用可能性、イテレーション予算に基づいて評価器-オプティマイザーループを設定する。ジェネレーター、評価器/検証器、オプティマイザーのプロンプト、および停止ポリシーを出力する。

## 演習

1. max_iterations=1でトイを実行する。CRITICはまだ役立つか？
2. 外部検証器をノイジーなもの（30%のランダム偽陽性）に置き換える。ループは何をするか？これは2026年のほとんどのガードレールスタックの現実だ。
3. 「異なるモデルによる生成器-批判者」バリアントを実装する: 大きいモデルが生成し、小さいモデルが批判する。同じモデルに勝るか？
4. CRITIC セクション3（arXiv:2305.11738 v4）を読む。3つの検証ツールカテゴリに名前を付け、それぞれの例を挙げる。
5. OpenAI Agents SDKの`output_guardrails`をCRITICの検証器の役割にマッピングする。SDKが間違っていることと正しいことは何か？

## キーワード

| 用語 | よく聞く言い方 | 実際の意味 |
|------|----------------|------------|
| Self-Refine | "自分を修正するLLM" | 1つのモデルで履歴を持つGenerate -> feedback -> refineループ |
| CRITIC | "ツール根拠の検証" | フィードバックを外部検証器（検索、コード、電卓、テスト）に置き換える |
| Evaluator-Optimizer（評価器-オプティマイザー） | "Anthropicワークフローパターン" | 2つの役割—評価器がスコアリング、オプティマイザーが修正—収束までループ |
| Output guardrail（出力ガードレール） | "後処理チェック" | OpenAI Agents SDK検証器がエージェントの出力生成後に実行される |
| Verify step（検証ステップ） | "批判フェーズ" | 重要な決定: 根拠付きまたは自己評価 |
| Refine history（精製履歴） | "モデルが既に試したこと" | 精製プロンプトに先付けされた以前の出力 + 批判; 削除すると品質が崩壊 |
| Rubber-stamp loop（ゴム判子ループ） | "自己合意の失敗" | 同じプロンプトの批判が「良さそうだ」を返す; 構造的に異なるプロンプトで修正 |
| Stop condition（停止条件） | "収束テスト" | 検証器が通過するか、フィードバックなし、かつイテレーションキャップ; 単一条件は決してしない |
