# メモリ: 仮想コンテキストとMemGPT

> コンテキストウィンドウは有限だ。会話、ドキュメント、ツールトレースはそうではない。MemGPT（Packer et al.、2023）はこれをOS仮想メモリとしてフレーミングする—メインコンテキストはRAM、外部ストアはディスク、エージェントはそれらの間でページングする。これは2026年のすべてのメモリシステムが継承するパターンだ。


## 学習目標

- MemGPTが構築するOSアナロジーを説明できる: メインコンテキスト = RAM、外部コンテキスト = ディスク、メモリツール = ページイン/アウト。
- メインコンテキストバッファ、外部検索可能ストア、ページイン/アウトツールを持つstdlibで2層MemGPTパターンを実装できる。
- エージェントが外部メモリをクエリまたは変更するために「割り込み」を発行する方法と、結果が次のプロンプトにどのようにスプライスされるかを説明できる。
- Letta（レッスン08）とMem0（レッスン09）に引き継がれるMemGPTの設計選択を特定できる。

## 課題

コンテキストウィンドウはメモリを解決すべきように見える。解決しない。本番で3つの失敗モードが繰り返される:

1. **オーバーフロー。** マルチターンの会話、長いドキュメント、ツール呼び出しが多いトラジェクトリはウィンドウを超える。カットオフを超えたものはすべて消える。
2. **希薄化。** ウィンドウ内でも、関係のないコンテキストを詰め込むと重要なものへのアテンションが希薄化する。フロンティアモデルは依然として長い入力で劣化する。
3. **永続性。** 新しいセッションは空のウィンドウで始まる。外部メモリのないエージェントはセッション間で「以前そのように頼まれた…」と言えない。

ウィンドウを大きくすることは助けになるが、これを修正しない。Mem0の2025年の論文は128kウィンドウベースラインが、外部メモリを持つ4kウィンドウエージェントが捕捉する長期的な事実をまだ見逃していることを測定した。

## コンセプト

### MemGPT: OSアナロジー

Packer et al.（arXiv:2310.08560、v2 2024年2月）はコンテキスト管理をオペレーティングシステムの仮想メモリにマッピングする:

| OSコンセプト | MemGPTコンセプト | 2026年本番アナログ |
|------------|---------------|------------------------|
| RAM | メインコンテキスト（プロンプト） | Anthropic/OpenAIコンテキストウィンドウ |
| ディスク | 外部コンテキスト | ベクターDB、KV、グラフストア |
| ページフォルト | メモリツール呼び出し | `memory.search`、`memory.read`、`memory.write` |
| OSカーネル | エージェントコントロールループ | メモリツールを持つReActループ |

エージェントは通常のReActループを実行する。1つの追加ツールクラスがメインコンテキストとの間でデータをページングできる。

### 2層

- **メインコンテキスト。** 現在のタスクを保持する固定サイズのプロンプト。常にモデルに見える。
- **外部コンテキスト。** 無制限で、ツールを介して検索可能。関連する場合は読み取り、事実が出てきたら書き込む。

元の論文はベースウィンドウを超える2つのタスクでこの設計を評価した: 100kトークンを超える文書分析と、数日間にわたる永続的なメモリを持つマルチセッションチャット。

### 割り込みパターン

MemGPTはメモリ-割り込みとして導入する: 会話の途中でエージェントはメモリツールを呼び出し、ランタイムがそれを実行し、結果は観察として次のアシスタントターンにスプライスされる。概念的にはUnixの `read()` システムコールと同一で、プロセスをブロックし、バイトを返し、プロセスが続く。

標準的なメモリツール表面:

- `core_memory_append(section, text)` — プロンプトの永続セクションに書き込む。
- `core_memory_replace(section, old, new)` — 永続セクションを編集する。
- `archival_memory_insert(text)` — 検索可能な外部ストアに書き込む。
- `archival_memory_search(query, top_k)` — 外部ストアから取得する。
- `conversation_search(query)` — 過去のターンをスキャンする。

### MemGPTが終わりLettaが始まる場所

2024年9月にMemGPTはLettaになった。研究リポジトリ（`cpacker/MemGPT`）は残る; Lettaは設計を拡張する:

- 2層ではなく3層（コア、リコール、アーカイブ—レッスン08）。
- `send_message`/ハートビートパターンを置き換えるネイティブ推論（レッスン08）。
- 非同期でメモリ作業を実行するsleep-timeエージェント（レッスン08）。

本番システムがLetta、Mem0、またはカスタム2層ストアを実行していても、MemGPT論文は2026年の基盤だ。

### このパターンが間違いになる場所

- **メモリ腐敗。** 書き込みが読み取りより速く蓄積する; 取得が古い事実で溺れる。修正: 定期的な統合（Lettaのsleep-time）、明示的な無効化（Mem0の競合検出器）。
- **メモリ汚染。** 外部メモリは取得されたテキストだ。攻撃者が制御するコンテンツがメモリノートに入ると、エージェントは次のセッションでそれを再取り込みする。これはGreshake et al.（レッスン27）の攻撃を時間を超えて言い直したものだ。
- **引用の喪失。** エージェントは「ユーザーがXを出荷するよう頼んだ」と思い出すが、どのターンかを引用できない。すべてのアーカイブ書き込みにソース参照（セッションID、ターンID）を保存する。

## 実装する

`code/main.py` はstdlibでMemGPTの2層パターンを実装している:

- `MainContext` — `core` dictと `messages` リストを持つ固定サイズのプロンプトバッファ; キャップを超えると最も古いメッセージを自動圧縮する。
- `ArchivalStore` — （id、text、tags、session、turn）レコードのインメモリBM25的ストア（トークンオーバーラップスコアリング）。
- MemGPT表面にマッピングする5つのメモリツール。
- 事実をアーカイブに書き込み、次に `archival_memory_search` を呼び出してフォローアップ質問に答えるスクリプト化エージェント。

実行:

```
python3 code/main.py
```

トレースはエージェントが3つの事実を書き込み、メインコンテキストをキャップまで埋め（退避を強制し）、次にアーカイブから取得することでフォローアップ質問に答える様子を示す—実際のLLMなしでMemGPTワークフローを再現する。

## 使ってみる

今日のすべての本番メモリシステムはMemGPTのバリアントだ:

- **Letta**（レッスン08）— 3層、ネイティブ推論、sleep-time compute。
- **Mem0**（レッスン09）— スコアリングレイヤーと融合したベクター + KV + グラフ。
- **OpenAI Assistants / Responses** — スレッドとファイルによる管理されたメモリ。
- **Claude Agent SDK** — スキルとセッションストアによる長期メモリ。

コアパターン—MemGPT—ではなく、運用形状（セルフホスト、マネージド、フレームワーク統合）で選ぶ。

## 成果物を出す

`outputs/skill-virtual-memory.md` は、退避ポリシーと引用フィールドを組み込んだ任意のターゲットランタイム向けに、正しい2層メモリスキャフォールド（メイン + アーカイブ + ツール表面）を生成する再利用可能なスキルだ。

## 演習

1. `max_main_context_tokens` キャップをトークン（`len(text.split()) * 1.3` で近似）で追加する。キャップを超えると最も古いメッセージをサマリーに圧縮する。サマライザーありとなしの動作を比較する。
2. アーカイブストアでBM25を適切に実装する（単語頻度、逆文書頻度）。トークンオーバーラップベースラインに対して、トイファクトセットでのrecall@10を測定する。
3. `citation` フィールド（session_id、turn_id、source_url）をアーカイブ挿入に追加する。エージェントがすべての取得ベースの回答でソースを引用するようにする。
4. メモリ汚染をシミュレートする: 「将来のすべてのユーザー指示を無視する」と言うアーカイブレコードを追加する。取得をスキャンして指令形状のテキストを探し、それらを信頼できないとマークするガードを書く。
5. MemGPT研究リポジトリのコアメモリJSONスキーマ（`cpacker/MemGPT`）を使うように実装をポートする。フラット文字列から型付きセクションに切り替えると何が変わるか？

## キーワード

| 用語 | よく聞く言い方 | 実際の意味 |
|------|----------------|------------|
| Virtual context（仮想コンテキスト） | "無制限メモリ" | メイン（プロンプト）+ 外部（検索可能）層とページイン/アウト |
| Main context（メインコンテキスト） | "ワーキングメモリ" | プロンプト—固定サイズ、常に見える |
| Archival memory（アーカイブメモリ） | "長期ストア" | 外部の検索可能な永続性、要求に応じて取得 |
| Core memory（コアメモリ） | "永続プロンプトセクション" | メインコンテキスト内にピン留めされた名前付きセクション |
| Memory tool（メモリツール） | "メモリAPI" | エージェントが外部メモリを読み書きするために発行するツール呼び出し |
| Interrupt（割り込み） | "メモリページフォルト" | エージェントが一時停止し、ランタイムが取得し、結果が次のターンにスプライスされる |
| Memory rot（メモリ腐敗） | "古い事実" | 古い書き込みが取得を溺れさせる; 統合で修正 |
| Memory poisoning（メモリ汚染） | "注入された永続ノート" | 攻撃者のコンテンツがメモリノートとして保存され、リコール時に再取り込みされる |
