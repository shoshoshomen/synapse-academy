# HTNと進化的探索によるプランニング

> シンボリックプランニングはプランが証明可能に正しい場合を扱う。進化的コード探索はフィットネス関数が機械チェック可能な場合を扱う。ChatHTN（2025年）とAlphaEvolve（2025年）は、LLMと組み合わせた場合にそれぞれが何を解放するかを示す。


## 学習目標

- 階層的タスクネットワークを説明できる: タスク、メソッド、オペレーター、前提条件、効果。
- ChatHTNのハイブリッドループを説明できる—LLMフォールバック分解を持つシンボリック探索。
- AlphaEvolveの進化的ループとなぜプログラム的評価器でのみ機能するかを説明できる。
- stdlibでトイHTNプランナーとトイ進化的探索を実装できる。

## 課題

ReWOO（レッスン02）、Plan-and-Execute、ReActはほとんどのエージェントプランニングをカバーする。2つのケースがうまくカバーされていない:

1. **証明可能な正確性を持つプラン。** スケジューリング、フライトパス、コンプライアンスワークフロー—プランは構造的に健全でなければならない。ステップを時々幻覚する流暢なLLMプランは受け入れられない。
2. **機械チェック可能なフィットネス関数を持つ最適化。** 行列乗算、スケジューリングヒューリスティック、コンパイラパス—目標は「正しいプラン」ではなく「最良のプラン」だ。

HTNプランニングとAlphaEvolveは2つの異なる問題を解決する。両方ともLLMを増幅器として使い、置き換えとしてではない。

## コンセプト

### 階層的タスクネットワーク

HTNは:

- **タスク** — 複合（分解する）とプリミティブ（直接実行可能）。
- **メソッド** — 複合タスクをサブタスクに分解する方法、前提条件を持つ。
- **オペレーター** — 前提条件と効果を持つプリミティブアクション。
- **状態** — 事実のセット。

プランニング: ゴールタスクと初期状態が与えられた場合、前提条件が順番に満たされるプリミティブオペレーターへの分解を見つける。

HTNはLLMよりも古く、証明可能に正しいプランのリファレンスだ。

### ChatHTN（Gopalakrishnan et al.、2025年）

ChatHTN（arXiv:2505.11814）はシンボリックHTNとLLMクエリをインターリーブする:

1. 既存のメソッドで現在の複合タスクを分解しようとする。
2. メソッドが適用されない場合、LLMに尋ねる: 「状態 `s` でどのように `task` を分解するか？」
3. LLMの応答を候補サブタスクに変換する。
4. オペレータースキーマに対して検証する; 無効な分解を拒否する。
5. 再帰する。

論文の核心の主張: LLMの提案が候補分解としてのみ入り、直接プランの編集としてではないため、すべての生成されたプランは証明可能に健全だ。シンボリック層が正確性を所有する; LLMはメソッドライブラリを拡張する。

オンラインメソッド学習（OpenReview `gwYEDY9j2x`、2025年のフォローアップ）は、LLMが生成した分解を回帰によって一般化する学習者を追加し、LLMクエリ頻度を最大75%削減する。

### AlphaEvolve（Novikov et al.、2025年）

AlphaEvolve（arXiv:2506.13131、DeepMind、2025年6月）は別物だ: Gemini 2.0 Flash/Proアンサンブルによってオーケストレーションされる進化的コード探索。

ループ:

1. シードプログラム + プログラム的評価器（フィットネススコアを返す）で始める。
2. LLMのアンサンブルが変異を提案する。
3. 評価器を通じて変異を実行する。
4. 最良のものを保持; 再び変異させる。

発表された成果:

- 56年ぶりの4x4複素数行列乗算でのStrassenに対する初めての改善（48スカラー乗算）。
- BorgスケジューリングヒューリスティックによるGoogleコンピューティングの0.7%回復。
- フロンティアワークロードでのFlashAttentionの32%スピードアップ。

ハードな制約: フィットネス関数は機械チェック可能でなければならない。散文の回答に対する進化的探索は収束しない。

### いつどれを使うか

| 問題クラス | 使う | 理由 |
|---------------|-----|-----|
| ハードな制約を持つスケジューリング | HTN + ChatHTN | 証明可能な健全性 |
| コンパイラの最適化 | AlphaEvolve | 機械チェック可能なフィットネス |
| マルチステップタスク実行 | ReAct / ReWOO | ループ内のLLM、正式な保証なし |
| テストを持つコード改善 | AlphaEvolve | テストが評価器 |
| ポリシー制限の自動化 | HTN | 前提条件がポリシーをエンコード |

### このパターンが間違いになる場所

- **オペレーターなしのHTN。** 前提条件/効果スキーマなしでは健全性の主張が崩壊する。ChatHTNの「LLMが分解を提案する」はスキーマが無効なムーブを拒否する必要がある。
- **実際の評価器なしのAlphaEvolve。** 「コードがより良いかどうかをLLMに尋ねる」はフィットネス関数ではない。評価器は決定論的で高速でなければならない。
- **過剰エンジニアリング。** ほとんどのエージェントタスクはどちらも必要としない。まずReActまたはReWOOを使う。

## 実装する

`code/main.py` は2つのトイを実装している:

- オペレーター、メソッド、前提条件、効果、複合タスクにメソッドが一致しない場合にキックインする `LLMFallback` を持つstdlib HTNプランナー。「LLM」はスクリプト化された分解器なので、プランナーはオフラインで実行する。
- 算術プログラムに対するstdlib進化的探索: テストセットに対して `|f(x) - target|` を最小化する出力の式を成長させる。評価器は決定論的。

実行:

```
python3 code/main.py
```

トレースはHTNプランナーが複合タスクを分解する（ミッドプランのLLMフォールバックを持つ）と、進化的ループがターゲット式に収束する様子を示す。

## 使ってみる

- **HTNプランナー** — `pyhop`、`SHOP3`、またはドメイン固有のポリシー施行のために自分でビルドする。
- **ChatHTN** — 研究コード; パターン（シンボリック + LLMフォールバック）は任意のHTNプランナーに綺麗にポートする。
- **AlphaEvolve** — DeepMind論文; パターン（アンサンブル + 評価器）は再現可能。OpenEvolveと同様のオープンソースフォークが出現している。
- **エージェントフレームワーク** — まだどれもファーストクラスのHTNまたはAlphaEvolveを出荷していない。サブエージェントまたはバックグラウンドワーカーとして構築する。

## 成果物を出す

`outputs/skill-hybrid-planner.md` は、LLMの役割が明示的にスコープされたハイブリッドプランナースキャフォールド（HTNまたは進化的）を生成する。

## 演習

1. HTNプランナーにバックトラッキングを追加する: オペレーターの事後条件が実行時に失敗した場合、ロールバックして次のメソッドを試す。
2. ChatHTNにLLMメソッドキャッシュを追加する: LLMが状態パターン `P` でタスク `T` を分解した場合、結果を保存する。次の呼び出しで先にメソッドライブラリを再チェックする。
3. 進化的探索評価器を実際のテストスイートに交換する。20のテストケースに通過するソート関数を進化させる; 収束するまでの世代数を報告する。
4. AlphaEvolveの評価器設計ノートを読む。興味のあるドメインの評価器を設計する（SQLクエリ最適化、テストスイートの最小化、デプロイメントYAML）。
5. 組み合わせる: HTNを使って複合タスクをサブタスクに分解し、次に各サブタスクのプリミティブオペレーターで進化的探索を使う。どこで輝き、どこで過剰エンジニアリングになるか？

## キーワード

| 用語 | よく聞く言い方 | 実際の意味 |
|------|----------------|------------|
| HTN | "階層的プランナー" | オペレーター、前提条件、効果を持つタスク分解 |
| Method（メソッド） | "分解ルール" | 複合タスクをサブタスクに分解する方法 |
| Operator（オペレーター） | "プリミティブアクション" | 前提条件と効果を持つ具体的なステップ |
| ChatHTN | "LLM + HTN" | シンボリックプランナーがメソッドが一致しない場合にLLMに尋ねる |
| AlphaEvolve | "進化的コード探索" | アンサンブルLLMがコードを変異させる; 決定論的評価器が選択 |
| Fitness function（フィットネス関数） | "評価器" | 出力に対する決定論的、機械チェック可能なスコア |
| Online method learning（オンラインメソッド学習） | "キャッシュされたLLM分解" | LLMプランを保存 + 一般化してクエリコストを削減 |
