# Anthropicのワークフローパターン: シンプルさを優先する

> Schluntzとチャン（Anthropic、2024年12月）はワークフロー（事前定義されたパス）とエージェント（動的なツール使用）を区別する。5つのワークフローパターンがほとんどのケースをカバーする。直接APIコールから始める。ステップを予測できない場合のみエージェントを追加する。


## 学習目標

- Anthropicの5つのワークフローパターンに名前を付けられる: プロンプトチェーニング、ルーティング、並列化、オーケストレーター-ワーカー、評価器-オプティマイザー。
- エージェントとワークフローの区別とそれぞれのエンジニアリングコストを説明できる。
- ワークフローよりエージェントを選ぶ場合（とその逆）を特定できる。
- stdlibでスクリプト化されたLLMに対してすべての5つのパターンを実装できる。

## 課題

チームは単一の関数呼び出しを望む問題にマルチエージェントフレームワークを使う。コストは現実だ: フレームワークはプロンプトを不明確にし、制御フローを隠し、時期尚早な複雑さを招く層を追加する。Schluntzとチャンの2024年12月の投稿が最も引用されている業界の反論だ: シンプルから始め、コストに見合う場合のみ複雑さを追加する。

## コンセプト

### ワークフロー vs エージェント

- **ワークフロー。** 事前定義されたコードパスを通じてオーケストレーションされたLLMとツール。エンジニアがグラフを所有する。
- **エージェント。** LLMが動的に自分のツールを指示し、自分のステップを踏む。モデルがグラフを所有する。

両方に場所がある。ワークフローはより安く、より速く、デバッグしやすい。エージェントはオープンエンドな問題を解放するが、失敗モードを推論しにくくする。

### 拡張されたLLM

すべての5つのパターンの基盤: 3つの能力が組み込まれた1つのLLM—検索（取得）、ツール（アクション）、メモリ（永続性）。すべてのAPIコールはこれらを使用できる。

### 5つのパターン

1. **プロンプトチェーニング。** 呼び出し1の出力は呼び出し2の入力だ。タスクにきれいな線形分解がある場合に使う。ステップ間のオプションのプログラム的ゲート。

2. **ルーティング。** 分類器LLMがどの下流LLMまたはツールを呼び出すかを選ぶ。カテゴリ的に異なる入力が異なる処理を必要とする場合に使う（ティア1サポート vs 返金 vs バグ vs 営業）。

3. **並列化。** N個のLLM呼び出しを同時に実行し、結果を集約する。2つの形状: セクショニング（異なるチャンク）と投票（同じプロンプト、N回実行、多数決/合成）。

4. **オーケストレーター-ワーカー。** オーケストレーターLLMがどのワーカー（LLMも）を実行するかを動的に決定し、出力を合成する。エージェントループに似ているが、オーケストレーターは無限にループしない。

5. **評価器-オプティマイザー。** 1つのLLMが回答を提案し、別のLLMがそれを評価する。評価器が通過するまでイテレートする。これはSelf-Refine（レッスン05）を一般化したものだ。

### ワークフローがエージェントに勝る場所

- **予測可能なタスク。** ステップを列挙できる場合、そうすべきだ。
- **コスト制約のタスク。** ワークフローは制約されたステップ数を持つ; エージェントは螺旋になりえる。
- **コンプライアンス制約のタスク。** 監査人はグラフを読みたい、トラジェクトリから推論したくない。

### エージェントがワークフローに勝る場所

- **オープンエンドなリサーチ。** 次のステップが最後のステップが返したものに依存する場合。
- **可変長タスク。** ステップ数が不明な数分から数時間の作業。
- **新しいドメイン。** 適切なワークフローがまだわかっていない場合—まず探索し、後でコード化する。

### コンテキストエンジニアリングの仲間

「AIエージェントのための効果的なコンテキストエンジニアリング」（Anthropic 2025年）は隣接する規律を形式化する: 200kウィンドウは予算であり、コンテナではない。何を含めるか、いつコンパクトにするか、コンテキストをいつ成長させるか。フェーズ14の以前のレッスン（コンテキスト圧縮）で詳細にカバーされている。

## 実装する

`code/main.py` は `ScriptedLLM` に対してすべての5つのワークフローパターンを実装している:

- `prompt_chain(input, steps)` — 順次。
- `route(input, classifier, handlers)` — 分類 + ディスパッチ。
- `parallel_vote(prompt, n, aggregator)` — N回実行、集約。
- `orchestrator_workers(task, workers)` — オーケストレーターがワーカーを選ぶ。
- `evaluator_optimizer(task, proposer, evaluator, max_iter)` — 通過するまでループ。

実行:

```
python3 code/main.py
```

各パターンはそのトレースを印刷する。パターンごとのコード行数は約10〜15行; フレームワークのコストは何千行もある。

## 使ってみる

- ほとんどのタスクには直接APIコール。
- パターンが本当に耐久性のある状態（LangGraph）、アクターモデルの並行性（AutoGen v0.4）、またはロールテンプレート（CrewAI）を必要とする場合のみフレームワーク。
- Claude Code ハーネス形状を再構築せずに望む場合はClaude Agent SDKを使う。

## 成果物を出す

`outputs/skill-workflow-picker.md` は、タスクの説明に対して正しいパターンを選択し、決定の根拠とワークフローが不十分な場合のエージェントへのリファクタリングパスを含む。

## 演習

1. 信頼度閾値を持つルーティングを実装する。閾値未満 -> 人間にエスカレート。ティア1サポートのユースケースで閾値はどこに落ちるか？
2. `parallel_vote` にタイムアウトを追加する。1つの呼び出しがハングしたときどうなるか？欠けている投票で集約をどうするか？
3. `evaluator_optimizer` をバンディットにする: イテレーション間でトップ2の出力を保持し、後の良い結果が後の悪い結果に上書きされないようにする。
4. プロンプトチェーニングとルーティングを組み合わせる: ルーターが3つのチェーンのうちの1つを選ぶ。単一の大きいプロンプトの代替に対してトークンコストを測定する。
5. 本番の機能の1つを選ぶ。ワークフローグラフを描く。ステップを数える。ここでエージェントが実際により良いか？

## キーワード

| 用語 | よく聞く言い方 | 実際の意味 |
|------|----------------|------------|
| Workflow（ワークフロー） | "事前定義されたフロー" | エンジニアが所有するLLMとツール呼び出しのグラフ |
| Agent（エージェント） | "自律型AI" | モデルが所有するグラフ; 動的なツール指示 |
| Augmented LLM（拡張LLM） | "ツールを持つLLM" | LLM + 検索 + ツール + メモリ; 原子単位 |
| Prompt chaining（プロンプトチェーニング） | "順次呼び出し" | 呼び出しNの出力は呼び出しN+1の入力 |
| Routing（ルーティング） | "分類器ディスパッチ" | どのチェーン/モデルが入力を処理するかを選ぶ |
| Parallelization（並列化） | "ファンアウト" | N並列呼び出し; セクショニングまたは投票で集約 |
| Orchestrator-workers（オーケストレーター-ワーカー） | "ディスパッチャーエージェント" | オーケストレーターLLMが専門LLMを動的に選ぶ |
| Evaluator-optimizer（評価器-オプティマイザー） | "提案者 + ジャッジ" | 評価器が通過するまでイテレート; Self-Refineの一般化 |
