# CrewAI: ロールベースのクルーとフロー

> CrewAI は 2026 年のロールベース・マルチエージェントフレームワークです。4つのプリミティブ: Agent, Task, Crew, Process。2つの最上位形式: Crews（自律的なロールベース協調）と Flows（イベント駆動、決定論的）。公式ドキュメントでは「本番運用アプリケーションには必ず Flow から始めること」と明記されています。


## 学習目標

- CrewAI の4つのプリミティブ（Agent, Task, Crew, Process）と各要素の役割を説明できる。
- Sequential、Hierarchical、および計画中の Consensus の各プロセスを区別し、ワークロードに応じて選択できる。
- Crews（自律的なロールベース）と Flows（イベント駆動、決定論的）の違いを説明し、公式ドキュメントの本番推奨を解説できる。
- `@tool` デコレーターと `BaseTool` サブクラスでツールを接続し、構造化出力と自由テキストを使い分けられる。
- CrewAI の4種類のメモリタイプと、各タイプが効果を発揮する場面を説明できる。
- 標準ライブラリのみで researcher, writer, editor の3エージェント・クルーを実装してブリーフを生成できる。
- CrewAI の3つの失敗パターン（プロンプト肥大化、マネージャー LLM コスト、脆弱なハンドオフ）を特定できる。

## 問題設定

マルチエージェントフレームワークを採用するチームは同じ壁に当たります。「自律的な協調」はデモでは素晴らしく聞こえます。ところが顧客からバグ報告が来て、決定論的な再現が必要になります。あるいは財務部門が LLM ルーティングのクルーでの実行コストを尋ねてきます。あるいはオンコール担当が深夜3時にどのエージェントが止まったかを把握しようとします。

自由形式の LLM ルーティング・クルーはこれらのどれにもきれいに答えられません。純粋な DAG は全て答えられますが、ブレインストーミング・エージェントが必要とする探索的な形を失います。

CrewAI の分割はトレードオフを正直に示しています。協調的・ロールベース・探索的な作業には Crews。イベント駆動・コード所有・監査可能な本番には Flows。同じフレームワーク、2つの形式、用途に応じて選択します。

## コンセプト

### 4つのプリミティブ

CrewAI のインターフェースは小さいです。これを暗記すれば、残りは設定です。

- **Agent.** `role + goal + backstory + tools + (optional) llm`。backstory は重要な役割を持ちます。トーン、判断、エージェントが停止するタイミングを形成します。Tools はエージェントが呼び出せる関数です（後述）。
- **Task.** `description + expected_output + agent + (optional) context + (optional) output_pydantic`。再利用可能な作業単位。`expected_output` はコントラクトです。`context` は出力を渡す上流タスクを列挙します。`output_pydantic` は構造化された形式を強制します。
- **Crew.** コンテナ。`agents` のリスト、`tasks` のリスト、`process`、およびオプションの `memory` + `verbose` + `manager_llm` 設定を所有します。
- **Process.** 実行戦略。Sequential、Hierarchical、Consensus（計画中）。実行の形を決定します。

エージェントは互いを直接見ることはありません。Tasks はエージェントを参照します。Crew はタスクを順序付けます。Process が次のタスクを誰が選ぶかを決めます。これがメンタルモデル全体です。

> **検証:** CrewAI 0.86 (2026-05) で確認済み。新バージョンではプロセスタイプの名称変更や統合が行われる可能性があります。特定の形に依存する前に [CrewAI Processes ドキュメント](https://docs.crewai.com/concepts/processes)を確認してください。

### Sequential vs Hierarchical vs Consensus

- **Sequential.** タスクは宣言順に実行されます。タスク N の出力はタスク N+1 に `context` として渡されます。コスト最小。最も予測可能。順序が固定の場合に使用します。
- **Hierarchical.** マネージャー Agent（別の LLM 呼び出し）がスペシャリスト間のルーティングを行います。CrewAI は `manager_llm` 設定またはデフォルトからマネージャーを生成します。マネージャーは各ラウンドで次のタスクを選び、拒否や再ルーティングもできます。4人以上のスペシャリストがいて、順序が前の出力に本当に依存する場合に使用します。
- **Consensus.** 計画中で、現在のパブリック API には実装されていません。ドキュメントは将来の投票ベース・プロセスのために名前を予約しています。今日は依存しないでください。

Hierarchical は専門家の呼び出しに加え、ラウンドごとに LLM 呼び出し（マネージャー）が増えます。5ステップの実行でトークンコストが3倍になることがあります。ルーティングが必要な場合にのみ支払ってください。

### Crews vs Flows

2026 年のドキュメントはこのフレーミングから始まります。

- **Crew.** LLM 駆動の自律性。フレームワークが実行時に形を選びます。適している用途: リサーチ、ブレインストーミング、初稿、答えがパスの一部になる場面。再現が難しい。テストが難しい。プロトタイプには安価。
- **Flow.** 自分が所有するイベント駆動グラフ。`@start` がエントリーポイントを示します。`@listen(topic)` は別のステップがそのトピックを発行したときに起動するステップを示します。各ステップは純粋な Python（内部で Crew を呼べます）。適している用途: 本番環境。観察可能。テスト可能。決定論的。

2026 年の公式本番推奨: Flow から始めてください。自律性がコストに見合う場合に、Flow のステップ内から `Crew.kickoff()` 呼び出しとして Crews を組み込みます。Flow が監査証跡を提供し、Crew が探索を提供します。選択ではなく、組み合わせてください。

### ツール統合

エージェントにツールを与える3つの方法。最もシンプルなものを選んでください。

1. **`@tool` デコレーター.** 純粋関数をツールに変換します。シグネチャがスキーマ、ドックストリングが LLM が見る説明です。ワンオフのヘルパーに最適。

   ```python
   from crewai.tools import tool

   @tool("Search the web")
   def search(query: str) -> str:
       """Return top results for the query."""
       return run_search(query)
   ```

2. **`BaseTool` サブクラス.** 明示的な引数スキーマ、非同期サポート、リトライを持つクラスベースのツール。ツールが状態（クライアント、キャッシュ）を持つか、構造化された引数が必要な場合に使用します。

   ```python
   from crewai.tools import BaseTool
   from pydantic import BaseModel

   class SearchArgs(BaseModel):
       query: str
       limit: int = 10

   class SearchTool(BaseTool):
       name = "web_search"
       description = "Search the web and return top results."
       args_schema = SearchArgs

       def _run(self, query: str, limit: int = 10) -> str:
           return self.client.search(query, limit=limit)
   ```

3. **組み込みツールキット.** CrewAI はファーストパーティのアダプターを同梱します: `SerperDevTool`、`FileReadTool`、`DirectoryReadTool`、`CodeInterpreterTool`、`RagTool`、`WebsiteSearchTool`。1つのインポートで接続できます。

構造化出力には Pydantic を使用します。Task に `output_pydantic=MyModel` を渡します。CrewAI は LLM レスポンスをモデルに対して検証し、強制またはリトライします。これを厳密な `expected_output` 文字列と組み合わせます。下書きには自由テキスト出力で十分。構造化出力は下流の Flows が消費できるものです。

### メモリフック

CrewAI はすぐに使えるメモリタイプを4種類搭載しています。組み合わせ可能：Crew は4種類すべてを同時に有効にできます。

> **検証:** CrewAI 0.86 (2026-05) で確認済み。最近のリリースではすべてを統合された `Memory` システムでラップしています。以下の概念モデルは引き続き有効ですが、新バージョンでは公開クラスのインターフェースが単一の `Memory` エントリーポイントに統合される可能性があります。現在の API は [CrewAI memory ドキュメント](https://docs.crewai.com/concepts/memory)で確認してください。

- **短期記憶.** 1回の実行内の会話バッファ。終了時にリセットされます。
- **長期記憶.** 実行をまたいで永続化されます。ベクター DB（デフォルトは Chroma、交換可能）に保存されます。現在のタスクへの類似度で検索されます。
- **エンティティ記憶.** エンティティごとの事実。「顧客 X はエンタープライズプランです。」エンティティをキーとし、類似度ではなくキーで検索。実行をまたいで保持されます。
- **コンテキスト記憶.** アセンブリ時の検索。エージェントが必要とするタイミングで関連するメモリを引き出します。プリロードではありません。

Crew で `memory=True` またはタイプ別の設定で有効にします。設定する埋め込みプロバイダーでバックアップされます（デフォルトは OpenAI、ローカルに交換可能）。メモリは CrewAI が薄いフレームワークに対して価値を発揮する場所の1つです。純粋な LangGraph ではこれらをそれぞれ自分で配線する必要があります。

### CrewAI が適している場面

- 名前付きロールと協調ワークフローを持つ3〜6エージェント。下書き、レビュー、計画、ブレインストーミング。
- LLM の次のステップに関する判断が価値の一部であるルーティング（Hierarchical）。
- チームがグラフ定義を読むよりも `role + goal + backstory` を読む方が楽な場面。

### CrewAI が適していない場面

- 厳格な順序を持つ決定論的 DAG。LangGraph（レッスン13）を使用してください。グラフ形状が正しい抽象化です。CrewAI のロールフレーミングは摩擦になります。
- サブ秒のレイテンシ要件。Hierarchical はラウンドトリップを追加します。Sequential でさえ、バックストーリーと前の出力を含むプロンプトをシリアライズします。
- シングルエージェントループ。フレームワークをスキップしてください。エージェントループ（レッスン1）とツールレジストリの方が短くなります。

レッスン17（エージェントフレームワークのトレードオフ）でこれをマトリクスで示しています。要約: CrewAI は「協調ロールベース」の角に位置します。

### 依存関係

LangChain から独立しています。Python 3.10〜3.13。`uv` を使用します。スター数: [crewAIInc/crewAI](https://github.com/crewAIInc/crewAI)（2026-05 時点のスナップショット）を参照。AWS Bedrock 統合はドキュメントに記載されています。ベンダーベンチマークでは QA ワークロードで LangGraph より大幅な高速化が報告されていますが、方法論（データセット、ハードウェア、評価指標）は公開されていないため、フレームワークベンダーの数値は参考程度に扱ってください。

### このパターンが失敗するケース

- **バックストーリーによるプロンプト肥大化.** エージェントあたり 2000 ワードのバックストーリーと5エージェントのクルーでは、最初のツール呼び出し前にコンテキスト予算を消費します。バックストーリーは 200 ワード以内に抑えてください。エージェント間でフレーズを再利用し、ハウススタイルを5回繰り返さないでください。
- **マネージャー LLM トークンコスト.** Hierarchical プロセスはすべての専門家呼び出しの前にマネージャー LLM 呼び出しを追加します。5タスクのクルーでは5回ではなく6回の LLM 呼び出しとなり、マネージャー呼び出しは全タスクリストと前の出力を保持します。ルーティングが出力に依存しない限り、Sequential に切り替えてください。
- **脆弱なハンドオフ.** タスク N の `expected_output` が「アウトライン」です。タスク N+1 はそれを `context` として読み込み、3つのセクションを解析しようとします。LLM は4つを生成しました。下流エージェントはアドリブします。タスク N に `output_pydantic` を追加してタスク N+1 が自由テキストではなく型付きオブジェクトを読めるようにして修正します。
- **クルーを本番に直接.** フローラッパーなしで自由形式のクルーを本番に出荷する。出力の変動が高く、再現が不可能で、オンコール担当は失敗した実行と正常な実行を比較できません。Flow でラップしてください。

## 実装する

`code/main.py` には両方の形式の標準ライブラリ版と3エージェントクルーが実装されています。

形状:

- CrewAI のインターフェースに合わせた `Agent`、`Task` データクラス。
- `SequentialCrew.kickoff(inputs)` はタスクを宣言順に実行し、出力を `context` としてスレッドします。
- `HierarchicalCrew.kickoff(topic)` はマネージャーエージェントを追加して各ラウンドで次の専門家を選び、"done" で停止します。
- `@start` と `@listen(topic)` デコレーター、小さなイベントループ、トレースを持つ `Flow`。
- CrewAI の `@tool` 形状を模倣した `tool(name)` デコレーター。
- numpy を使ったモック類似度を持つ `short_term`、`long_term`、`entity` ストアを持つ `Memory`。
- モック LLM レスポンスはロールと入力プレフィックスをキーとするハードコードされた文字列。ネットワーク不要。決定論的。

具体的なデモ: researcher, writer, editor クルーが「エージェントエンジニアリング 2026」についてのブリーフを生成します。Researcher が（モックの）ソースを収集します。Writer が下書きします。Editor が仕上げます。決定論的な形を示すために同じクルーを Flow で実行します。

実行:

```bash
python3 code/main.py
```

トレース内容: `context` を通じて出力をスレッドする Sequential クルー、マネージャーの選択を伴う Hierarchical クルー（researcher, writer, editor、その後 "done"）、明示的なトピック（`researched`、`drafted`、`edited`）で同じ3ステップを実行する Flow、`@tool` 経由でルーティングされるツール呼び出し、2回のキックオフをまたいで永続化される長期記憶。

クルーのトレースは流動的で、マネージャーが原理的に順序を変えられます。Flow のトレースは固定されています。その選択がこのレッスンの本質です。

## 使ってみる

- **CrewAI Flow** を本番用に。Flow が1ステップで `Crew.kickoff()` を呼ぶだけでも。Flow が監査の境界を提供します。
- **CrewAI Crew（Sequential）** は明確な順序を持つ協調作業、特に初稿とレビューループに。
- **CrewAI Crew（Hierarchical）** はルーティングが出力に依存し、4人以上の専門家がいる場合。
- **LangGraph**（レッスン13）は明示的なステートマシン、durable な再開、厳格な順序付けに。
- **AutoGen v0.4**（レッスン14）はアクターモデルの並行性とフォールト分離に。
- **OpenAI Agents SDK**（レッスン16）はハンドオフとガードレールを持つ OpenAI ファーストのプロダクトに。
- **Claude Agent SDK**（レッスン17）はサブエージェントとセッションストアを持つ Claude ファーストのプロダクトに。

## 成果物を出す

`outputs/skill-crew-or-flow.md` はタスクに対して Crew か Flow かを選択し、最小限の実装を足場として提供します。バックストーリーなしの Crew、明示的なトピックなしの Flow、3人未満のスペシャリストの Hierarchical は厳しく拒否します。

## 落とし穴

- **フレーバーとしてのバックストーリー.** これは出力を形成します。エージェントごとに3つのバリアントをテストしてください。変動は実際に存在します。1つを選んで固定してください。
- **`expected_output` のスキップ.** タスクごとのコントラクトがなければ、下流タスクは LLM が生成したものをそのまま受け取ります。クルーは動くかもしれませんが、監査は失敗します。
- **メモリの常時オン.** 長期記憶はすべての実行で書き込みます。ベクター DB が肥大化します。検索がノイジーになります。事実が永続的なタスクにのみ書き込みをスコープしてください。
- **マネージャーのプロンプトドリフト.** Hierarchical のマネージャープロンプトは暗黙的です。ルーティングがおかしくなったら、verbose モードでダンプして読んでください。
- **クルー内のツール副作用.** クルーは想定より多くの回数ツールを呼ぶことがあります。POST、DELETE、支払いは Flow のステップに属し、クルーのツールには絶対に属しません。

## 演習

1. Sequential クルーを Flow に変換します。変動が減る接点を数えてください。可読性が下がった箇所をメモしてください。
2. クルーにエンティティ記憶を追加します: 顧客に関する事実がキックオフをまたいで永続化されます。検索が正しいエンティティを引き出すことを確認します。
3. Writer の出力に少なくとも3段落含まれるまで Editor にルーティングしないようにマネージャーが拒否する Hierarchical プロセスを実装します。リトライをトレースします。
4. （モックの）Web 検索用の `BaseTool` サブクラスを接続します。`@tool` デコレーター版とトレース形状を比較します。
5. editor タスクに `output_pydantic=Brief`（`title`、`summary`、`sections` を持つ）を追加します。writer タスクに一度不正な JSON を出力させ、トレースで CrewAI のリトライ動作を確認します。
6. CrewAI のドキュメントのイントロを読みます。玩具実装を実際の `crewai` API に移植します。標準ライブラリ版はどの保証を省いていましたか？
7. AgentOps または Langfuse（レッスン24）を実際の実行に接続します。標準ライブラリ版で見逃したトレースはどれですか？

## キーワード

| 用語 | 一般的な言い方 | 実際の意味 |
|------|----------------|------------|
| Agent | "ペルソナ" | ロール + ゴール + バックストーリー + ツール |
| Task | "作業単位" | 説明 + 期待する出力 + 担当者 + オプションの構造化出力 |
| Crew | "エージェントチーム" | Agents + Tasks + Process のコンテナ |
| Process | "実行戦略" | Sequential / Hierarchical / Consensus（計画中） |
| Flow | "決定論的ワークフロー" | イベント駆動、コード所有、テスト可能 |
| Backstory | "ペルソナプロンプト" | エージェントのトーンと判断を形成するもの |
| `@tool` | "関数ツール" | 関数をエージェントが呼び出せるツールに変換するデコレーター |
| `BaseTool` | "クラスツール" | 引数スキーマ、リトライ、非同期サポートを持つクラスベースのツール |
| エンティティ記憶 | "エンティティごとの事実" | 顧客・アカウント・問題にスコープされたメモリ |
| 長期記憶 | "クロスラン記憶" | キックオフをまたいで永続化されるベクターバックのメモリ |
| コンテキスト記憶 | "ジャストインタイム検索" | エージェントが必要とするタイミングで引き出されるメモリ |
| Manager LLM | "ルーターエージェント" | Hierarchical プロセスで次のタスクを選ぶ追加の LLM |
| `expected_output` | "タスクコントラクト" | エージェント（と監査）に返す形を伝える文字列 |
