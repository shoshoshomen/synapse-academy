# オーケストレーションパターン: スーパーバイザー、スワーム、階層型

> 2026 年のフレームワーク全体で4つのオーケストレーションパターンが繰り返し登場します: スーパーバイザー-ワーカー、スワーム/ピアツーピア、階層型、ディベート。Anthropic のガイダンス: 「ニーズに合った正しいシステムを構築することが重要です。」シンプルから始めて、1つのエージェントと5つのワークフローパターンでは不十分になって初めてトポロジーを追加してください。


## 学習目標

- 4つの繰り返しオーケストレーションパターンとそれぞれが適した場面を説明できる。
- 2026 年の LangChain の推奨を説明できる: ツール呼び出しベースの管理 vs スーパーバイザーライブラリ。
- Anthropic の「適切なシステムを構築する」ルールとトポロジー選択をどのようにゲートするかを説明できる。
- 共通のスクリプト化された LLM に対して4つすべてを標準ライブラリで実装できる。

## 問題設定

チームは必要になる前に「マルチエージェント」に手を伸ばします。4つのパターンがフレームワーク全体で繰り返し登場します。それらに名前を付けられれば、正しいものを選ぶか — またはトポロジーを完全にスキップできます。

## コンセプト

### スーパーバイザー-ワーカー

- セントラルなルーティング LLM がスペシャリストエージェントにディスパッチします。
- 決定事項: 自身にループバック、スペシャリストにハンドオフ、終了。
- スペシャリストは互いに話しません。すべてのルーティングはスーパーバイザーを通過します。

フレームワーク: LangGraph `create_supervisor`、Anthropic オーケストレーター-ワーカー、CrewAI Hierarchical Process。

**2026 年の LangChain 推奨:** `create_supervisor` ではなく直接ツール呼び出しで監視を実装してください。より細かいコンテキストエンジニアリングのコントロールが得られます — 各スペシャリストが正確に何を見るかを決定できます。

### スワーム / ピアツーピア

- エージェントが共有ツールサーフェスを介して直接ハンドオフします。
- セントラルルーターなし。
- スーパーバイザーより低いレイテンシ（少ないホップ）。
- 推論が難しい（単一のコントロールポイントなし）。

フレームワーク: LangGraph スワームトポロジー、OpenAI Agents SDK のハンドオフ（すべてのエージェントがすべての他のエージェントにハンドオフできる場合）。

### 階層型

- サブスーパーバイザーを管理するスーパーバイザーがワーカーを管理します。
- LangGraph ではネストされたサブグラフとして実装。CrewAI ではネストされたクルーとして。
- 運用の複雑さのコストを払って大規模なエージェント集団にスケール。

必要な場面: 1つのスーパーバイザーのコンテキスト予算がすべてのスペシャリストの説明を保持できなくなったとき。

### ディベート

- 並列提案者 + 反復的なクロス批評（レッスン25）。
- 実際にはオーケストレーションではありません — より検証に近い — しかしフレームワークではトポロジーの選択として現れます。

### CrewAI Crew vs Flow

CrewAI は2つのデプロイメントモードを正式化します:

- **Flow** は決定論的なイベント駆動オートメーション（本番に推奨される出発点）。
- **Crew** は自律的なロールベース協調。

これは上記の4つのパターンとは直交しますが、トポロジーにマッピングされます: Flow は通常スーパーバイザーまたは階層型。Crew は通常 LLM ルーターを持つスーパーバイザー。

### Anthropic のガイダンス

「LLM 空間での成功は最も洗練されたシステムを構築することではありません。自分のニーズに合った正しいシステムを構築することです。」

決定の順序:

1. 1つのエージェント + ワークフローパターン（レッスン12）— ここから始めてください。
2. スーパーバイザー-ワーカー — 2〜4人のスペシャリストがいる場合。
3. スワーム — 推論の明確さよりレイテンシが重要な場合。
4. 階層型 — スーパーバイザーのコンテキスト予算が失敗する場合のみ。
5. ディベート — コストより精度が重要な場合。

### このパターンが失敗するケース

- **トポロジーファーストな思考.** マルチエージェントが解決する問題を特定する前に「マルチエージェントが必要」と言う。
- **スワームでのバウンスするハンドオフ.** A -> B -> A -> B。ホップカウンターを使用してください。
- **偽の階層.** 「エンタープライズ」だからという理由で3層に構成。実際のチームは2つ。折り畳んでください。

## 実装する

`code/main.py` はスクリプト化された LLM に対して4つすべてのパターンを標準ライブラリで実装しています:

- `Supervisor` — セントラルルーター。
- `Swarm` — 直接ハンドオフを持つピアツーピア。
- `Hierarchical` — スーパーバイザーのスーパーバイザー。
- `Debate` — 並列提案者 + 批評。

各パターンは同じ3つのインテントタスク（返金 / バグ / セールス）を処理します。トレース形状が異なります。

実行:

```
python3 code/main.py
```

出力: パターンごとのトレース + 操作数。スーパーバイザーが最もクリーン。スワームが最短。階層型が最も深い。ディベートが最もコスト高。

## 使ってみる

- **LangGraph** はスーパーバイザーと階層型に（ネストされたサブグラフ）。
- **OpenAI Agents SDK** はツールとしてのハンドオフ（スーパーバイザー形状）に。
- **CrewAI Flow** は本番の決定論的に。
- **カスタム** はディベートまたは正確なコントロールが必要な場合に。

## 成果物を出す

`outputs/skill-orchestration-picker.md` はトポロジーを選択して実装します。

## 演習

1. スーパーバイザー-ワーカーをスワームに変換します（ルーターを除去して）。何が壊れますか？何が改善されますか？
2. スワームにホップカウンターを追加します: 3回のハンドオフ後に拒否します。A->B->A のバウンスをキャッチしますか？
3. 12 人のスペシャリストドメインの2層の階層システムを構築します。ネストなしではコンテキスト予算はどこで失敗しますか？
4. 本番形状のワークロードで4つのパターンをプロファイリングします。どのパターンがどのメトリクス（レイテンシ、コスト、精度、デバッグ可能性）で勝ちますか？
5. Anthropic の「Building Effective Agents」投稿を読みます。自分の本番フローをそれぞれ4つのうちの1つにマッピングします。きれいにマッピングされないものはありますか？

## キーワード

| 用語 | 一般的な言い方 | 実際の意味 |
|------|----------------|------------|
| スーパーバイザー-ワーカー | "ルーター + スペシャリスト" | セントラル LLM がスペシャリストにディスパッチ。互いには話さない |
| スワーム | "ピアツーピア" | 共有ツールを介した直接ハンドオフ。セントラルルーターなし |
| 階層型 | "スーパーバイザーのスーパーバイザー" | 大規模な集団のためのネストされたサブグラフ |
| ディベート | "提案者 + 批評" | 並列提案者、クロス批評（レッスン25） |
| ツール呼び出しベースの監視 | "ライブラリなしのスーパーバイザー" | コンテキストコントロールのためにスーパーバイザーを直接ツール呼び出しとして実装 |
| Crew | "自律チーム" | CrewAI のロールベース協調モード |
| Flow | "決定論的ワークフロー" | CrewAI のイベント駆動本番モード |
