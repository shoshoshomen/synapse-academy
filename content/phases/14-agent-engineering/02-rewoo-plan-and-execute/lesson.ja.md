# ReWOOとPlan-and-Execute: 分離されたプランニング

> ReActは思考と行動を1つのストリームにインターリーブする。ReWOOはそれらを分離する: 最初に1つの大きなプランを作り、それから実行する。トークンを5倍削減し、HotpotQAで+4%の精度、そしてプランナーを7Bモデルに蒸留できる。Plan-and-Executeはそれを一般化し、Plan-and-Actはウェブナビゲーションにスケールした。


## 学習目標

- ReWOOのPlanner / Worker / Solver分割が、ReActのインターリーブループよりもトークンを節約しロバスト性を向上させる理由を説明できる。
- プランDAG、依存順エグゼキューター、ワーカー出力を合成するソルバーをすべてstdlibで実装できる。
- Anthropicの2026年「5つのワークフローパターン」のフレーミングを使って、タスクをplan-then-executeとインターリーブReActのどちらで実行すべきかを決定できる。
- 長期的なウェブまたはモバイルタスクにPlan-and-Actの合成プランデータが必要な場合を認識できる。

## 課題

ReActのインターリーブされたthought-action-observationループはシンプルで柔軟だが、各ツール呼び出しは以前のすべての思考を含む完全な先行コンテキストを運ぶ必要がある。トークン使用量は深さとともに二次的に増大する。さらに悪いことに: ループの途中でツールが失敗した場合、モデルはエラー観察からプラン全体を再導出しなければならない。

ReWOO（Xu et al.、arXiv:2305.18323、2023年5月）はこれに気づき、ベットをした: 全体を事前にプランし、証拠を並列に取得し、最後に答えを合成する。プランに1回のLLM呼び出し、証拠のためにN回のツール呼び出し（並列可能）、解決に1回のLLM呼び出し。トレードオフは柔軟性の低下（プランは静的）と、はるかに優れたトークン効率と明確な失敗モードだ。

## コンセプト

### 3つの役割

```
Planner:  user_question -> [plan_dag]
Workers:  [plan_dag]     -> [evidence]        (tool calls, possibly parallel)
Solver:   user_question, plan_dag, evidence -> final_answer
```

プランナーはDAGを生成する。各ノードはツール、その引数、および依存する以前のノード（`#E1`、`#E2` のような参照）に名前を付ける。ワーカーはトポロジカル順でノードを実行する。ソルバーはすべてをまとめる。

### トークンが5倍少ない理由

ReActはステップ数に比例してプロンプトの長さが増大する。ステップ10では、プロンプトには思考1、行動1、観察1、思考2、行動2、観察2、などが含まれる。各中間ステップにも元のプロンプトが冗長に含まれる。

ReWOOは1つのプランナープロンプト（大きい）、N個の小さなワーカープロンプト（各ツール呼び出し、チェーンなし）、1つのソルバープロンプトを支払う。HotpotQAでは、論文が+4絶対精度を出しながら約5倍のトークン削減を測定した。

### ロバスト性がより高い理由

ReACTでワーカー3が失敗した場合、ループはストリームの途中でエラーから推論しなければならない。ReWOOでは、ワーカー3はエラー文字列を返す。ソルバーは元のプランとともにコンテキストで見て、優雅にデグレードできる。失敗のローカライズはステップ単位ではなくノード単位だ。

### プランナーの蒸留

論文の2番目の結果: プランナーは観察を見ないため、175Bのティーチャーからのプランナー出力で7Bモデルをファインチューンできる。小さいモデルがプランニングを担当し、大きいモデルは推論時には不要になる。これは今や標準的だ—多くの2026年の本番エージェントは小さいプランナーと大きいエグゼキューター、またはその逆を使用する。

### Plan-and-Execute（LangChain、2023年）

LangChainチームの2023年8月の投稿はReWOOをパターン名に一般化した: Plan-and-Execute。事前のプランナーがステップリストを出力し、エグゼキューターが各ステップを実行し、オプションのリプランナーが結果を観察した後に修正できる。これはReWOOよりReActに近い（リプランナーが観察をプランニングに戻す）が、トークン削減を維持する。

### Plan-and-Act（Erdogan et al.、arXiv:2503.09572、ICML 2025）

Plan-and-Actは、長期的なウェブおよびモバイルエージェントにパターンをスケールする。主要な貢献は合成プランデータだ: ラベル付きトラジェクトリジェネレーターがプランが明示的なトレーニングデータを生成する。WebArena的なタスクで30〜50ステップを超えた後でも動作するプランナーモデルをファインチューンするために使用される。単一のReActトラジェクトリはここで一貫性を失う。

### どれを選ぶか

| パターン | いつ |
|---------|------|
| ReAct | 短いタスク、未知の環境、リアクティブな例外処理が必要 |
| ReWOO | 既知のツールを持つ構造化タスク、トークン敏感、並列化可能な証拠 |
| Plan-and-Execute | ReWOOに似ているが、部分実行後のリプランニングあり |
| Plan-and-Act | 長期（30ステップ超）、ウェブ/モバイル/computer-use |
| Tree of Thoughts | 検索にコストをかける価値がある場合（レッスン04） |

Anthropicの2024年12月のガイダンス: 最もシンプルなものから始める。タスクが1回のツール呼び出しとサマリーなら、ReWOOを構築するな。タスクが40ステップの研究課題なら、ReActだけでやるな。

## 実装する

`code/main.py` はトイReWOOを実装している:

- `Planner` — プロンプトからプランDAGを出力するスクリプト化ポリシー。
- `Worker` — レジストリ経由で各ノードのツール呼び出しをディスパッチする。
- `Solver` — 証拠を読んで最終回答を生成するスクリプト化合成。
- 依存関係解決 — `#E1` のような参照は以前のワーカー出力で置換される。

デモは「フランスの首都の人口を百万単位で四捨五入したものは？」に2ステップのプランで答える: (1) 首都を調べる、(2) 人口を調べる、そして解決する。

実行:

```
python3 code/main.py
```

トレースは最初に完全なプランを表示し、次にワーカー結果、そしてソルバーの合成を表示する。トークン数（大まかな文字数を印刷する）をReActスタイルのインターリーブ実行と比較する—ReWOOはこの種の構造化タスクで勝る。

## 使ってみる

LangGraphはPlan-and-ExecuteをレシピとしてShipする（ReActは`create_react_agent`、plan-executeはカスタムグラフ）。CrewAIのFlowsはパターンを直接エンコードする: タスクを事前に定義し、Flow DAGがそれらを実行する。Plan-and-Actの合成データアプローチはまだほとんど研究段階だ。ランタイムパターン（明示的なプランDAG）はLangGraphとCrewAI Flowsを通じて本番環境で使用されている。

## 成果物を出す

`outputs/skill-rewoo-planner.md` は、ツールカタログが与えられたユーザーリクエストからReWOOプランDAGを生成する。エグゼキューターに渡す前にプランを検証する（非循環、すべての参照が解決済み、すべてのツールが存在する）。

## 演習

1. 独立したプランノードのワーカー実行を並列化する。2つの並列グループを持つ6ノードDAGで何が得られるか？
2. ワーカーがエラーを返した場合に発火するリプランナーノードを追加する。ReWOOをPlan-and-Executeにする最小限の変更は何か？
3. `Planner` を小さいモデル（7Bクラス）に置き換え、`Solver` をフロンティアモデルに保つ。エンドツーエンドの品質を比較する—どこで分割が失敗するか？
4. ReWOO論文のセクション4のプランナー蒸留を読む。175B -> 7Bの結果を概念的に再現する: どのトレーニングデータが必要で、プラン品質をどのようにスコアリングするか？
5. トイをPlan-and-Actのトラジェクトリ形状にポートする: プランはDAGではなくシーケンス。どのトレードオフが変わるか？

## キーワード

| 用語 | よく聞く言い方 | 実際の意味 |
|------|----------------|------------|
| ReWOO | "観察なしの推論" | プラン、次に証拠を並列に取得、次に解決—プランニングプロンプトに観察なし |
| Plan-and-Execute | "LangChainのplan-executeパターン" | 実行後のオプションのリプランナーノードを持つReWOO |
| Plan-and-Act | "スケールされたplan-execute" | 長期タスク向けの合成プラントレーニングデータを持つ明示的なプランナー/エグゼキューター分割 |
| Evidence reference（証拠参照） | "#E1、#E2、..." | ディスパッチ時に以前のワーカー出力で置換されるプランノードのプレースホルダー |
| Planner distillation（プランナー蒸留） | "小さいプランナー、大きいエグゼキューター" | 大きいティーチャーのプランナートレースで小さいモデルをファインチューン |
| Token efficiency（トークン効率） | "ラウンドトリップの削減" | 論文でReActに対してHotpotQAで5倍少ないトークン |
| DAG executor（DAGエグゼキューター） | "トポロジカルディスパッチャー" | 依存関係順にプランノードを実行; 各レベルで並列 |
