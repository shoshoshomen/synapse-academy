# A2A——エージェント間プロトコル

> GoogleはA2Aを2025年4月に発表した；2026年4月時点でスペックはhttps://a2a-protocol.org/latest/specification/にあり、150以上の組織が支持している。A2AはMCP（レッスン13）の水平方向の補完だ：MCPが垂直（エージェント↔ツール）なのに対し、A2Aはピアツーピア（エージェント↔エージェント）だ。Agent Card（発見）、アーティファクトを伴うタスク（テキスト、構造化データ、ビデオ）、不透明なタスクライフサイクル、認証を定義する。本番システムではMCPとA2Aをペアにすることが増えている。Google CloudはVertex AI Agent BuilderにA2Aサポートを2025〜2026年に展開した。


## 問題

エージェントが別のシステムの別のエージェントを呼び出す必要がある。どうやって？HTTPエンドポイントを公開し、独自のJSONスキーマを定義し、相手がそれを理解することを祈れる。エージェントのすべてのペアがカスタムインテグレーションになる。

A2Aはその呼び出しのための汎用ワイヤープロトコルだ。標準的な発見、標準的なタスクモデル、標準的なトランスポート、標準的なアーティファクト。HTTP+RESTのようなものだが、エージェントをファーストクラスの市民として扱う。

## 概念

### 4つの要素

**Agent Card。** エージェントを説明するJSONドキュメントで`/.well-known/agent.json`に置く：名前、スキル、エンドポイント、対応するモダリティ、認証要件。カードを読むことで発見が行われる。

```
GET https://agent.example.com/.well-known/agent.json
→ {
    "name": "code-review-agent",
    "skills": ["review-python", "review-typescript"],
    "endpoints": {
      "tasks": "https://agent.example.com/tasks"
    },
    "auth": {"type": "bearer"},
    "modalities": ["text", "structured"]
  }
```

**タスク。** 作業の単位。ライフサイクルを持つ非同期でステートフルなオブジェクト：`submitted → working → completed / failed / canceled`。クライアントはタスクを送り、ポーリングまたはサブスクライブして更新を受け取る。

**アーティファクト。** タスクが生成する結果の型。テキスト、構造化JSON、画像、ビデオ、オーディオ。アーティファクトはタイプされているため、異なるモダリティがファーストクラスになる。

**不透明なライフサイクル。** A2Aはリモートエージェントがタスクを*どのように*解決するかを規定しない。クライアントは状態遷移とアーティファクトを見る；実装はどのフレームワークも自由に使える。

### MCP/A2Aの分割

- **MCP**（レッスン13）：エージェント↔ツール。エージェントはJSON-RPCでツールサーバーを読み書きする。デフォルトでステートレス。
- **A2A**：エージェント↔エージェント。ピアプロトコル；両側が独自の推論を持つエージェントだ。

本番のマルチエージェントシステムは両方を使う。A2Aピアは自分側でMCPツールを呼び出す。この分割により2つの関心事がきれいに分かれる。

### 発見フロー

```
Client                     Agent server
  ├──GET /.well-known/agent.json──>
  <──Agent Card JSON─────────────
  ├──POST /tasks {skill, input}──>
  <──201 task_id, state=submitted
  ├──GET /tasks/{id}──────────────>
  <──state=working, 42% done──────
  ├──GET /tasks/{id}──────────────>
  <──state=completed, artifacts──
```

またはストリーミング：プッシュ更新のための`/tasks/{id}/events`へのSSEサブスクリプション。

### 認証

A2Aは3つの一般的なパターンをサポートする：

- **Bearerトークン** — OAuth2または不透明。
- **mTLS** — 相互TLS；組織がお互いにアイデンティティを証明する。
- **署名付きリクエスト** — ペイロードへのHMAC。

認証はAgent Cardで宣言される；クライアントはそれを発見して従う。

### 2026年4月時点で150以上の組織

エンタープライズの採用がA2AのスケールをドライブしたA2AはエンタープライズエージェントシステムがトラスT境界を越える方法になった。Google CloudはVertex AI Agent BuilderにA2Aサポートを出荷した；Microsoft Agent Frameworkがそれをサポートする；ほとんどの主要なフレームワーク（LangGraph、CrewAI、AutoGen）がA2Aアダプターを出荷している。

### A2Aが勝つ場所

- **組織間の呼び出し。** 会社AのエージェントがBのエージェントを呼び出す。A2Aなしでは、すべてのペアが独自の契約だ。
- **異種フレームワーク。** LangGraphエージェントがCrewAIエージェントを呼び出し、CrewAIエージェントがカスタムPythonエージェントを呼び出す。A2Aが正規化する。
- **型付きアーティファクト。** ビデオ結果、構造化JSON、オーディオ——すべてファーストクラス。
- **長時間実行タスク。** 不透明なライフサイクル＋ポーリングにより、時間単位のタスクが簡単になる。

### A2Aが苦手な場所

- **レイテンシに敏感なマイクロ呼び出し。** A2Aのライフサイクルは非同期だ。サブミリ秒のエージェント間通信には適合しない；直接RPCを使う。
- **密結合のインプロセスエージェント。** 両方のエージェントが同じPythonプロセスで動く場合、A2AのHTTPラウンドトリップはオーバーキルだ。
- **小さなチーム。** スペックのオーバーヘッドは本物だ；内部専用エージェントにはこの形式は不要かもしれない。

### A2A対ACP、ANP、NLIP

2024〜2026年にいくつかの関連スペックが出現した：

- **ACP**（IBM/Linux Foundation）——A2Aの前身、より狭いスコープ。
- **ANP**（Agent Network Protocol）——ピア発見中心、分散ファースト。
- **NLIP**（Ecma自然言語インタラクションプロトコル、2025年12月標準化）——自然言語コンテンツタイプ。

A2Aは2026年4月時点で最も採用されているピアプロトコルだ。比較については arXiv:2505.02279（Liu et al.、「A Survey of Agent Interoperability Protocols」）を参照。

## 実装する

`code/main.py`は`http.server`とJSONを使って最小限のA2AサーバーとクライアントをH実装している。サーバー：

- `/.well-known/agent.json`を公開する、
- `POST /tasks`を受け付ける、
- タスクの状態を管理する、
- `GET /tasks/{id}`でアーティファクトを返す。

クライアント：

- Agent Cardを取得する、
- タスクを送信する、
- 完了するまでポーリングする、
- アーティファクトを読む。

実行：

```
python3 code/main.py
```

スクリプトはバックグラウンドスレッドでサーバーを起動し、その後クライアントを起動して実行する。完全なフローが見られる：発見、送信、ポーリング、アーティファクト。

## 使ってみる

`outputs/skill-a2a-integrator.md`はA2Aインテグレーションを設計する：Agent Cardの内容、タスクスキーマ、認証の選択、ストリーミング対ポーリング。

## 成果物を出す

チェックリスト：

- **スペックバージョンを固定する。** A2Aはまだ進化中；Agent CardはプロトコルバージョンをH宣言すべきだ。
- **冪等タスク作成。** 重複送信（ネットワーク再試行）は1つのタスクを生成すべきだ。
- **アーティファクトスキーマ。** エージェントが返すシェイプを宣言する；コンシューマーはバリデーションすべきだ。
- **レート制限＋認証。** A2Aはパブリックフェーシング；標準的なWebセキュリティを適用する。
- **失敗タスクのデッドレター。** 繰り返しの失敗タイプのために時間をかけてパターンを検査する。

## 演習

1. `code/main.py`を実行する。クライアントがサーバーを発見し、正しいアーティファクトを受け取ることを確認する。
2. サーバーに2番目のスキルを追加する（例：「要約」）。Agent Cardを更新する。タスクタイプに基づいてスキルを選ぶクライアントを書く。
3. SSEストリーミングエンドポイントを実装する：状態変更を発行する`/tasks/{id}/events`。クライアントは何を違う形でする必要があるか？
4. A2Aスペック（https://a2a-protocol.org/latest/specification/）を読む。このデモが実装していないスペックが義務付けている3つのことを特定する。
5. A2A（Agent Card発見）とMCP（`listTools`を介したサーバーサイドの機能リスト）を比較する。自己記述的なエージェントと機能プロービングのトレードオフは何か？

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| A2A | 「エージェント間」 | エージェントがシステム間で他のエージェントを呼び出すためのピアプロトコル。Google 2025年。 |
| Agent Card | 「エージェントの名刺」 | スキル、エンドポイント、認証を説明する`/.well-known/agent.json`のJSON。 |
| タスク | 「作業の単位」 | ライフサイクルを持つ非同期ステートフルオブジェクト；完了時にアーティファクトが生成される。 |
| アーティファクト | 「結果」 | 型付き出力：テキスト、構造化JSON、画像、ビデオ、オーディオ。ファーストクラスのメディア。 |
| 不透明なライフサイクル | 「どう解決するかはエージェント次第」 | クライアントは状態遷移を見る；サーバーはフレームワーク/ツールを自由に選べる。 |
| 発見 | 「エージェントを見つける」 | `GET /.well-known/agent.json`がカードを返す。 |
| MCP対A2A | 「ツール対ピア」 | MCP：垂直エージェント↔ツール。A2A：水平エージェント↔エージェント。 |
| ACP / ANP / NLIP | 「兄弟プロトコル」 | 隣接するスペック；A2Aは2026年で最も採用されている。 |
