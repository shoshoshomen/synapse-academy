# FIPA-ACLとスピーチアクトの遺産

> MCPの前、A2Aの前に、FIPA-ACLがあった。2000年にIEEEのFoundation for Intelligent Physical Agentsが、20のパフォーマティブ、2つのコンテンツ言語、一連のインタラクションプロトコル（コントラクトネット、サブスクライブ/ノティファイ、リクエストウェン）を持つエージェント通信言語を批准した。オントロジーのオーバーヘッドがウェブには重すぎたため業界から消えたが、LLMによるマルチエージェントシステムの復活は、形式的意味論なしに同じアイデアを静かに再実装している：JSONコントラクトがパフォーマティブの代わりになり、自然言語がオントロジーの代わりになる。このレッスンではFIPA-ACLを真剣に読み、2026年のプロトコル決定のどれが再発明で、どれが新しいものか、そして現在の波がすでに2000年代に解決済みの問題をどこで再発見するかを見極める。


## 問題

2026年のエージェントプロトコル状況は混雑している：ツール用MCP、エージェント用A2A、エンタープライズ監査用ACP、分散信頼用ANP、自然言語コンテンツ用NLIP、さらにCA-MCPと数十の研究提案。各仕様が自らを基盤的だと宣言している。

正直に読めば、ほとんどが非常に具体的な20年前の決定木を再発見している。Austin（1962）とSearle（1969）のスピーチアクト理論が「発話は行為である」を与えてくれた。KQML（1993）がそれをワイヤープロトコルにした。FIPA-ACL（2000年批准）が参照標準化を生み出した：20のパフォーマティブ、コンテンツ言語SL0/SL1、コントラクトネットとサブスクライブ・ノティファイのインタラクションプロトコル。JADEとJACKがJavaの参照プラットフォームだった。オントロジーのオーバーヘッドが重すぎ、ウェブが勝ったため、この取り組みは2010年頃に廃れた。

MCPの`tools/call`、A2Aのタスクライフサイクル、CA-MCPの共有コンテキストストアを見ると、FIPA決定のよりソフトでJSONネイティブな焼き直しを見ている。遺産を知ることで2つのことがわかる：どの新しい「革新」が実際には再発明か、そしてどの古い失敗モードを新仕様が再発見するか。

## 概念

### スピーチアクト、1段落で

Austinはいくつかの文は世界を記述しないことに気づいた——それらは世界を変える。「約束する」「要求する」「宣言する」。彼はこれらをパフォーマティブ発話と呼んだ。Searleは5つのカテゴリを形式化した：アサーティブ、ディレクティブ、コミッシブ、エクスプレッシブ、デクララティブ。KQML（Finin et al.、1993）はこれをソフトウェアエージェントのために実用化した：メッセージはパフォーマティブ（行為）とコンテンツ（行為が何についてか）から成る。FIPA-ACLはKQMLのギャップを整理し、20のパフォーマティブを中心に標準化した。

### 20のFIPAパフォーマティブ（一部）

| パフォーマティブ | 意図 |
|---|---|
| `inform` | 「PがtrueであることをあなたにI告げる」 |
| `request` | 「Xを行うよう頼む」 |
| `query-if` | 「Pはtrueか？」 |
| `query-ref` | 「Xの値は何か？」 |
| `propose` | 「Xを行うことを提案する」 |
| `accept-proposal` | 「提案を受け入れる」 |
| `reject-proposal` | 「提案を拒否する」 |
| `agree` | 「Xを行うことに同意する」 |
| `refuse` | 「Xを行うことを断る」 |
| `confirm` | 「Pがtrueであることを確認する」 |
| `disconfirm` | 「Pを否定する」 |
| `not-understood` | 「あなたのメッセージは解析できなかった」 |
| `cfp` | 「Xへの提案依頼」 |
| `subscribe` | 「Xが変化したら通知して」 |
| `cancel` | 「進行中のXをキャンセルする」 |
| `failure` | 「Xを試みたが失敗した」 |

完全なリストは`fipa00037.pdf`（FIPA ACLメッセージ構造）にある。これを暗記するのが目的ではない——LLMプロトコルが最終的に再追加するプリミティブがそれぞれに対応することを理解することが目的だ。

### 標準的なFIPA-ACLメッセージ

```
(inform
  :sender       agent1@platform
  :receiver     agent2@platform
  :content      "((price IBM 83))"
  :language     SL0
  :ontology     finance
  :protocol     fipa-request
  :conversation-id   conv-42
  :reply-with   msg-17
)
```

7つのフィールドがプロトコルエンベロープを運び、1つのフィールド（`content`）がペイロードを運ぶ。残りのフィールドは、JSONプロトコルにリトライ、スレッド、オントロジーを組み込むたびに再発明されるものだ。

### 2つのレガシープラットフォーム

**JADE**（Java Agent DEvelopment framework、1999年〜2020年代）は最も使用されたFIPA準拠のランタイムだった。エージェントはベースクラスを拡張し、ACLメッセージを交換し、コンテナ内で実行し、「ビヘイビア」を使って調整した。インタラクションプロトコルライブラリにはコントラクトネット、サブスクライブ・ノティファイ、リクエストウェン、プロポーズ・アクセプトが含まれていた。

**JACK**（Agent Oriented Software、商用）はFIPAメッセージの上にBDI（信念・欲求・意図）推論を重視した。より形式的で、採用は少なかった。

どちらもウェブスタックがマルチエージェントのユースケースを食べると廃れた。MCPとA2Aが2026年のランタイム「コンテナ」だ。

### FIPAが廃れた理由

- **オントロジーのオーバーヘッド。** FIPAは`content`を解析するために共有オントロジーが必要だった。オントロジーの合意は何年もかかる標準化プロセスだ。ウェブはただHTTP + JSONを使った。
- **誰も使わなかった形式的意味論。** SL（セマンティック言語）は厳密な真理条件を与えたが、ほとんどの本番システムはフリーフォームのコンテンツを使い、形式主義を無視した。
- **ツールのロックイン。** JADEはJavaのみ；JACKは商用。ポリグロットなチームは両方を迂回した。
- **インターネットがスタックを制した。** REST、次にJSON-RPC、次にgRPCがACLのトランスポートを置き換えた。

### LLMの復活はFIPA-Liteだ

FIPAの`request`とMCPの`tools/call`を比較する：

```
(request                                {
  :sender  agent1                         "jsonrpc": "2.0",
  :receiver tool-server                   "method":  "tools/call",
  :content "(lookup stock IBM)"           "params":  {"name":"lookup_stock",
  :ontology finance                                   "arguments":{"symbol":"IBM"}},
  :conversation-id c42                    "id": 42
)                                        }
```

同じエンベロープ、異なる構文。どちらも運ぶもの：誰が、誰に、意図、ペイロード、相関ID。どちらも革命ではない——同じ設計における異なるトレードオフだ。

Liu et al.の2025年調査（「A Survey of Agent Interoperability Protocols: MCP, ACP, A2A, ANP」、arXiv:2505.02279）はこの系譜を明示している：MCPはツール使用スピーチアクトに対応し、A2Aはエージェントピアスピーチアクトに対応し、ACPは監査証跡スピーチアクトに対応し、ANPは分散アイデンティティ拡張に対応する。新しい仕様はJSONシンタックスとより緩い意味論を持つACLの子孫だ。

### トレードオフを率直に述べると

**FIPAが与えたが現代仕様が捨てたもの：**

- 形式的意味論——`inform`が送信者がコンテンツを信じることを意味することを証明できる。
- パフォーマティブの標準カタログ——「`cancel`を持つべきか？」と再議論する必要がない。
- 既知の正しさの特性を持つ数十年のインタラクションプロトコルパターン——コントラクトネット、サブスクライブ・ノティファイ、プロポーズ・アクセプト。

**現代仕様が与えてFIPAが持たなかったもの：**

- すべての現代ツールと互換性のあるJSONネイティブペイロード。
- LLMが手作りのオントロジーなしに解釈できる自然言語コンテンツ。
- ウェブスタックのトランスポート（HTTP、SSE、WebSocket）。
- 自己記述型ドキュメントによるケイパビリティ発見（MCPの`listTools`、A2AエージェントCard）。

実装を容易にするための緩い意図意味論。それが正確なトレードだ。

### 移植する価値があるインタラクションプロトコル

FIPAは約15のインタラクションプロトコルを出荷した。3つはLLMマルチエージェントシステムに持ち込む価値がある：

1. **コントラクトネットプロトコル（CNP）。** マネージャーが`cfp`（提案依頼）を発行；入札者が`propose`で応答；マネージャーが受け入れ/拒否する。これが標準的なタスクマーケットパターンだ（フェーズ16・16交渉）。
2. **サブスクライブ/ノティファイ。** サブスクライバーが`subscribe`を送信；パブリッシャーがトピックが変化するたびに`inform`を送信する。これが2026年のすべてのイベントバスだ。
3. **リクエストウェン。** 「条件Yが成立したときにXを行え。」事前条件付きの遅延アクション。2026年のアナログは耐久性ワークフローエンジンの遅延タスクだ（フェーズ16・22本番スケーリング）。

それぞれが現代のメッセージキュー、HTTP + ポーリング、またはSSEストリーミングにきれいにマッピングできる。

### オントロジーを捨てると何が壊れるか

共有オントロジーなしでは、エージェントは自然言語コンテンツから意味を推論する。2026年に文書化されている失敗モードは**セマンティックドリフト**だ：2つのエージェントが同じ単語（「顧客」）を微妙に異なる概念に使用し、受信側エージェントが誤った解釈に基づいて動作し、スキーマバリデーターがそれを捕捉しない。FIPAのオントロジー要件は解析時にメッセージを拒否していただろう。

完全なオントロジーなしの緩和策：

- `content`のJSONスキーマ——構造エラーをワイアレベルで拒否する。
- 型付きアーティファクト（A2A）——誤ったモダリティを拒否する。
- エンベロープ内の明示的なパフォーマティブ——コンテンツが自然言語でも意図を明確にする。

### 2026年の仕様をスピーチアクトの遺産にマッピングする

| 現代仕様 | FIPAアナログ | 保持するもの | 捨てるもの |
|---|---|---|---|
| MCPの`tools/call` | `request` | 明示的な意図、相関ID | 形式的意味論、オントロジー |
| MCPの`resources/read` | `query-ref` | 明示的な意図、相関ID | 形式的意味論 |
| A2Aタスクライフサイクル | コントラクトネット + リクエストウェン | 非同期ライフサイクル、状態遷移 | 形式的完全性保証 |
| A2Aストリーミングイベント | サブスクライブ/ノティファイ | 非同期プッシュ | 型付き述語サブスクリプション |
| CA-MCP共有コンテキスト | ブラックボード（Hayes-Roth 1985） | マルチライター共有メモリ | 論理一貫性モデル |
| NLIP | 自然言語コンテンツ | LLMネイティブ | スキーマ |

テーブルを上から下に読むと、パターンが見える：構造的プリミティブを維持し、形式主義を捨て、LLMに曖昧さを糊塗させる。

## 実装する

`code/main.py`は純粋な標準ライブラリのFIPA-ACLトランスレーターを実装している。標準的なACLエンベロープをエンコード・デコードし、すべてのMCP／A2Aメッセージ形状がどのように同じ7フィールドに還元されるかを示す。デモは：

- 5つのMCPスタイルとA2Aスタイルのメッセージを FIPA-ACLとしてエンコードする。
- FIPA-ACLを現代の等価物にデコードする。
- 1人のマネージャーと3人の入札者の間で、`cfp`、`propose`、`accept-proposal`、`reject-proposal`を使ったおもちゃのコントラクトネット交渉を実行する。

実行：

```
python3 code/main.py
```

出力は、2026年のJSON形式とFIPA-ACL形式の両方で各現代メッセージを並べて表示するトレースと、コントラクトネット入札のラウンドトリップを示す。同じプロトコルプリミティブがラウンドトリップを乗り越えて生き残る；シンタックスだけが異なる。

## 使ってみる

`outputs/skill-fipa-mapper.md`は、任意のエージェントプロトコル仕様を読み取り、FIPA-ACLマッピングを生成するスキルだ。新しいプロトコルを採用する前にこれを使用し、「これは本当に新しいものか、それともJSONシンタックスを持つ`inform`か？」に答える。

## 成果物を出す

FIPA-ACLを復活させるな。そのチェックリストを復活させろ：

- 各メッセージの意図プリミティブ（パフォーマティブ）は何か？
- リクエスト・レスポンスとキャンセルのための相関IDはあるか？
- 明示的なコンテンツ言語（JSON-RPC、プレーンテキスト、構造化型アーティファクト）はあるか？
- インタラクションプロトコルはファーストクラスか、それともコントラクトネットをゼロから再実装しているか？
- 2つのエージェントがコンテンツの意味について意見が合わない場合はどうなるか（セマンティックドリフト）？

これら5つの質問を新しいプロトコルのために、本番環境にリリースする前に文書化すること。

## 演習

1. `code/main.py`を実行する。ラウンドトリップエンコーディングを観察する。`tools/call`、`resources/read`、A2Aタスク作成がどのFIPAパフォーマティブに対応するかを特定する。
2. マネージャーが入札中にタスクを撤回できる`cancel`パフォーマティブでコントラクトネットデモを拡張する。`cancel`が単独のリトライでは解決しない失敗ケースを解決するのはなぜか？
3. FIPA ACLメッセージ構造（http://www.fipa.org/specs/fipa00037/）のセクション4.1〜4.3を読む。このレッスンでカバーされていない1つのパフォーマティブを選び、その現代のJSON-RPCアナログを説明する。
4. Liu et al.、arXiv:2505.02279を読む。MCP、A2A、ACP、ANPそれぞれについて、保持するFIPAパフォーマティブファミリーと捨てるものをリストアップする。
5. 自分のシステムの`request`パフォーマティブの`content`フィールドのための最小限のJSONスキーマを設計する。そのスキーマが純粋な自然言語では得られないものをあなたに与えるものは何で、それにかかるコストは何か？

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| スピーチアクト | 「何かをする発話」 | Austin/Searle：行為としての発話。ACLの理論的親。 |
| FIPA | 「あの古いXMLのやつ」 | IEEE Foundation for Intelligent Physical Agents。2000年にACLを標準化した。 |
| ACL | 「エージェント通信言語」 | FIPAのエンベロープ形式：パフォーマティブ + コンテンツ + メタデータ。 |
| パフォーマティブ | 「動詞」 | メッセージの意図クラス：`inform`、`request`、`propose`、`cfp`など。 |
| KQML | 「FIPAの前身」 | Knowledge Query and Manipulation Language（1993年）。よりシンプルで範囲が狭い。 |
| オントロジー | 「共有語彙」 | コンテンツ言語が話す概念の形式的定義。 |
| SL0 / SL1 | 「FIPAコンテンツ言語」 | セマンティック言語レベル0と1——形式的コンテンツ言語ファミリー。 |
| コントラクトネット | 「タスクマーケット」 | マネージャーがcfpを発行；入札者がproposeする；マネージャーが受け入れる。標準的なインタラクションプロトコル。 |
| インタラクションプロトコル | 「メッセージのパターン」 | 既知の正しさを持つパフォーマティブのシーケンス：リクエストウェン、サブスクライブ・ノティファイなど。 |
