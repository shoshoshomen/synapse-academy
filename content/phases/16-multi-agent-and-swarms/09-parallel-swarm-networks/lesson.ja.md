# 並列／スワーム／ネットワーク型アーキテクチャ

> スーパーバイザーとの対比：中央の決定者なし。エージェントは共有イベントバスを読み、非同期で作業をピックアップし、結果を書き戻す。LangGraphは分散された動的な環境のための「スワームアーキテクチャ」を明示的にサポートしている。Matrix（arXiv:2511.21686）はオーケストレーターのボトルネックを排除するために、制御フローとデータフローの両方を分散キューを通じて送信されるシリアル化されたメッセージとして表現する。トレードオフは明示的だ：スケーラビリティのための決定論性とトレーサビリティ。スワームは多くの独立したサブ問題を持つタスクに適合する；単一の一貫したプランが必要なタスクには適合しない。


## 問題

スーパーバイザーは数体のワーカーにスケールする。数百はどうか？スーパーバイザー自体がボトルネックになる：誰が何をするかについてのすべての決定が1つのエージェントを通る。1つの遅い計画ステップがシステム全体を止める。

スワームアーキテクチャはこの設計をひっくり返す。中央プランナーが作業を配布する代わりに、ワーカーが共有キューから作業をピックアップする。「調整」はイベントバスのセマンティクスに焼き込まれている。オーケストレーターなし；キューがスケールするまでシステムはスケールする。

## 概念

### 形状

```
                ┌──── 共有キュー ────┐
                │                    │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     ワーカー ワーカー ワーカー   ワーカー
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            結果プール
```

オーケストレーターなし。各ワーカーが繰り返す：タスクをプル、処理、結果を書く（オプションでフォローアップをエンキュー）。

### スワームが適合する場合

- **多数の独立したタスク。** スクレイピング、変換、分類。タスクは互いに依存しない。
- **変動する処理時間の作業。** いくつかのタスクが100ミリ秒かかり、他が10秒かかる場合、スワームは自動的に負荷を分散する——速いワーカーが次のジョブをピックアップする。スーパーバイザーは処理時間を予測しなければならない。
- **決定論性よりスループット。** 総完了時間を気にするが、厳密な順序は気にしない。

### スワームが失敗する場合

- **順序付きワークフロー。** ステップ3がステップ2の出力を必要とする場合、スワームはステップ2が完了する前にステップ3が発火するリスクがある。
- **グローバルプランタスク。** 複雑なリサーチ質問はプランナーから恩恵を受ける。リサーチャーのスワームは独立した事実を生成し、一貫したレポートではない。
- **デバッグ。** 中央ログなしで非同期作業を行うと、バグを再現するコストが高い。

### Matrix（arXiv:2511.21686）

Matrixはスワームをその自然な結論に持っていく2025年の論文だ：制御フローとデータフローの両方が分散キューのシリアル化されたメッセージだ。中央コーディネーターなし。耐障害性はメッセージの耐久性から来る。スケーラビリティはシステムではなくメッセージブローカーの問題だ。

貢献：マルチエージェント調整が「スーパーバイザーが次を誰を選ぶか？」ではなく「このエージェントはどのメッセージトピックをサブスクライブするか？」であるプログラミングモデル。これによりシステムはpub/subイベントメッシュのように見える。

### LangGraphのスワームアーキテクチャ

LangGraph 2025年のドキュメントは「スワームアーキテクチャ」をマルチエージェントパターンの1つとして明示的に説明している：エージェントはノードだが、エッジはサイクルを持つ有向グラフを形成し、任意のノードがプールからアクティベートできる。ワーカーはスーパーバイザーの割り当てではなく条件によって利用可能な作業から選択する。

### 失敗モード：スタベーションとホットスポッティング

すべてのワーカーが最も速く利用可能なタスクをピックアップすると、長時間実行タスクは唯一残るものになるまで選ばれない。典型的なキュースタベーション。

緩和策：
- 待機時間で優先度を上げる明示的なエイジングを持つ優先度付きキュー。
- ワーカーの特化：一部のワーカーは「長い」タスクのみ取る。
- バックプレッシャー：速いタスクがキューに入る量を制限する。

### コンテンツベースルーティングとのリンク

スワームはコンテンツベースルーティング（レッスン22）と自然にペアになる。汎用キューの代わりに、メッセージタイプごとに1つのキューを持つ。スペシャリストワーカーは自分のタイプのみサブスクライブする。これが数千のエージェントにスケールするメッセージバスアーキテクチャの基礎だ。

## 実装する

`code/main.py`は共有`queue.Queue`からプルする4つのワーカースレッドのスワームを実装している。タスクは変動する処理時間を持つ（いくつか速い、いくつか遅い）。デモは対比する：

- **逐次ベースライン：** 1つのワーカーがすべてのタスクを直列に処理する。
- **固定割り当て：** 各タスクが特定のワーカーに事前割り当てされる（スーパーバイザースタイル）。
- **スワーム：** ワーカーが共有キューからプルする。

スワームは自動的に負荷を分散する；固定割り当ては割り当てられたタスクが遅い場合に速いワーカーをアイドル状態にする。

実行：

```
python3 code/main.py
```

出力はワーカーごとのタスク数（スワームは不均一だが最適に分散）とウォールクロック時間を示す。

## 使ってみる

`outputs/skill-swarm-fit.md`はタスクがスワームとスーパーバイザーのどちらを使うべきかを評価する。入力：タスクの独立性、処理時間の分散、順序要件、デバッグ可能性の必要性。

## 成果物を出す

チェックリスト：

- **エイジング付き優先度キュー。** 長時間タスクのスタベーションを防ぐ。
- **ワーカーの冪等性。** タスクはワーカーがクラッシュした場合に複数回プルされることがある。ワーカーは冪等でなければならない。
- **耐久性キュー。** 本番にはKafka、Redis Streams、またはデータベースバックキューを使う。`queue.Queue`はインメモリのみ。
- **タスクごとの観測可能性。** すべてのタスクにトレースID；すべてのワーカーはそれと共に開始/終了をログする。
- **バックプレッシャー。** キューがワーカーのドレインより速く増える場合、プロデューサーを遅くする。

## 演習

1. `code/main.py`を実行する。変動する処理時間のワークロードでスワームは逐次型より何倍速いか？固定割り当てより何倍速いか？
2. 優先度キューバリアント（`queue.PriorityQueue`を使う）を追加する。タスクの「重要度」フィールドで優先度を割り当てる。継続的な負荷の下で低優先度タスクがスタベーションになるかどうかを観察する。
3. ホットスポット検出器を実装する：任意のワーカーが最も遅いワーカーより3倍多くのタスクを処理する場合にログする。それはタスク処理時間の分布について何を示すか？
4. Matrixの論文（arXiv:2511.21686）の要旨とセクション3を読む。Matrixが受け入れる1つの具体的なトレードオフ（スケーラビリティの向上）と諦めるもの（トレーサビリティ、決定論性）を特定する。
5. スワームデモを(task_type, payload)タプルの`queue.Queue`を使うように変換し、ワーカーが特定のタイプのみサブスクライブする。タスクが異質な場合にどのルーティングルールが理にかなっているか？

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| スワームアーキテクチャ | 「分散エージェント」 | ワーカーが共有キューからプルする；中央オーケストレーターなし。 |
| イベントバス | 「エージェントがトピックをサブスクライブする」 | タイプまたはコンテンツでワーカーにタスクをルーティングするメッセージブローカー。 |
| スタベーション | 「タスクが実行されない」 | より高い優先度の作業が継続的に届くため低優先度タスクが選ばれない。 |
| ホットスポッティング | 「1つのワーカーが溺れる」 | 1つのワーカーがほとんどのタスクを取る負荷の不均衡。 |
| バックプレッシャー | 「プロデューサーを遅くする」 | キューがいっぱいになった時に上流に停止を通知するメカニズム。 |
| 冪等ワーカー | 「再実行しても安全」 | 2回処理されたタスクが同じ結果を生む。ワーカーがクラッシュするかもしれないため必要。 |
| 耐久性キュー | 「クラッシュを乗り越える」 | ディスクまたはレプリケートされたストレージにバックされたキュー；ワーカーがクラッシュしてもタスクが失われない。 |
| Matrixフレームワーク | 「完全なメッセージパッシングスワーム」 | データフローと制御フローの両方が分散キューのシリアル化されたメッセージ。 |
