# マルチエージェントのプリミティブモデル

> 2026年に登場するすべてのマルチエージェントフレームワーク——AutoGen、LangGraph、CrewAI、OpenAI Agents SDK、Microsoft Agent Framework——は4次元設計空間上の1点だ。4つのプリミティブ、それだけ：エージェント、ハンドオフ、共有状態、オーケストレーター。このレッスンではゼロからそれらを構築し、おもちゃシステムをすべての4つで実行し、次に主要なフレームワークすべてを同じ軸にマッピングして、新しいリリースを1段落で読めるようにする。


## 問題

6ヶ月ごとに新しいマルチエージェントフレームワークが登場する。2023年のAutoGen。2024年のCrewAI。2024年のLangGraphとOpenAI Swarm。2025年4月のGoogle ADK。2026年2月のMicrosoft Agent Framework RC。各プレスリリースが「正しい抽象化」だと主張する。

一つずつ学ぼうとすると燃え尽きてしまう。APIが違って見える。ドキュメントが「エージェント」とは何かについて意見が合わない。あるフレームワークは共有メモリを「ブラックボード」と呼び、別は「メッセージプール」と呼び、3番目は「StateGraph」と呼ぶ。分野がただ churningしているのではないかと疑い始める。

そうではない。マーケティングの下に、4つのプリミティブは安定している。一度学べば、すべての新しいフレームワークを1段落で読める。

## 概念

### 4つのプリミティブ

1. **エージェント** — システムプロンプト + ツールリスト。ステートレス；すべての実行はそのシステムプロンプトと現在のメッセージ履歴から始まる。
2. **ハンドオフ** — あるエージェントから別のエージェントへの制御の構造的な転送。メカニカルには、新しいエージェントを返すツール呼び出しか、条件に従うグラフエッジ。
3. **共有状態** — 複数のエージェントが読める（時に書ける）データ構造。メッセージプール、ブラックボード、キーバリューストア、ベクターメモリ。
4. **オーケストレーター** — 次に誰が話すかを決める者。選択肢：明示的グラフ（決定論的）、LLMスピーカーセレクター（ソフト）、最後のスピーカーのハンドオフ呼び出し（OpenAI Swarm）、またはキュー上のスケジューラー（スワームアーキテクチャ）。

それが設計空間のすべてだ。すべてのフレームワークが各軸のデフォルトを選択する；残りは表面的な構文だ。

### 2026年のすべてのフレームワークがどうマッピングされるか

| フレームワーク | エージェント | ハンドオフ | 共有状態 | オーケストレーター |
|-----------|-------|---------|--------------|--------------|
| OpenAI Swarm / Agents SDK | `Agent(instructions, tools)` | toolがAgentを返す | 呼び出し元の問題 | LLMの次のハンドオフ呼び出し |
| AutoGen v0.4 / AG2 | `ConversableAgent` | GroupChatのスピーカーセレクター | メッセージプール | セレクター関数（LLMまたはラウンドロビン） |
| CrewAI | `Agent(role, goal, backstory)` | `Process.Sequential / Hierarchical` | チェーン化されたタスク出力 | マネージャーLLMまたは静的順序 |
| LangGraph | ノード関数 | グラフエッジ + 条件 | `StateGraph`リデューサー | グラフ（決定論的） |
| Microsoft Agent Framework | エージェント + オーケストレーションパターン | パターン固有 | スレッド / コンテキスト | パターン固有 |
| Google ADK | エージェント + A2Aカード | A2Aタスク | A2Aアーティファクト | ホストが決定 |

表面的な違いは大きく見える。その下は：同じ4つのノブ。

### なぜこれが重要か

プリミティブを見れば、フレームワーク比較は短いチェックリストになる：

- オーケストレーターはルーティングをLLMに信頼するか（Swarm）、コードでルーティングを固定するか（LangGraph）？
- 共有状態は全履歴か（GroupChat）、それとも射影か（StateGraphリデューサー）？
- エージェントは互いのプロンプトを変更できるか（CrewAIマネージャー）、それともハンドオフのみか（Swarm）？

これら3つの質問が、どのフレームワークが特定の問題に合うかの80%に答える。「最高のマルチエージェントフレームワーク」を探すのをやめて、実際に気にする軸のために設計し始める。

### ステートレスの洞察

共有状態以外のすべてのプリミティブはステートレスだ。エージェントは（プロンプト、ツール）の関数。ハンドオフは関数呼び出し。オーケストレーターはスケジューラー。**システムで唯一のステートフルなものは共有状態だ。** そこにすべての興味深いバグがある：メモリポイズニング（レッスン15）、メッセージ順序、バージョン管理、書き込み競合。

共有状態を隠すフレームワーク（Swarm）は問題を呼び出し元に押しつける。共有状態を集中管理するフレームワーク（LangGraphチェックポインター、AutoGenプール）は検査可能にするが、共有状態の実装に調整コストをかけさせる。

### 1つのプリミティブの解剖

#### エージェント

```
Agent = (system_prompt, tools, model, optional_name)
```

メモリなし。状態なし。同じシステムプロンプトとツールを持つ2つのエージェントは交換可能だ。エージェントの状態に見えるものはすべて、実際には共有状態またはハンドオフプロトコルにある。

#### ハンドオフ

```
Handoff = (from_agent, to_agent, reason, payload)
```

3つの実装が主流：

- **関数の返り値** — ツールが次のエージェントを返す。これがOpenAI Swarmパターン。エージェントはツールスキーマにルーティングを持つ。
- **グラフエッジ** — LangGraph。エッジは宣言的。LLMが値を生成；条件が次のノードを選択する。
- **スピーカー選択** — AutoGen GroupChat。セレクター関数（時にそれ自体がLLM呼び出し）がプールを読んで次に話す者を選ぶ。

#### 共有状態

```
SharedState = { messages: [], artifacts: {}, context: {} }
```

最低限、メッセージのリスト。多くの場合もっと多く：構造化アーティファクト（CrewAIタスク出力）、型付きコンテキスト（LangGraphリデューサー）、外部メモリ（MCP、ベクターDB）。

2つのトポロジー：**フルプール**（すべてのエージェントがすべてのメッセージを見る）と**射影**（エージェントは役割スコープのビューを見る）。フルプールはシンプルでスケールが悪い。射影プールはスケールするがスキーマ設計が前もって必要。

#### オーケストレーター

```
Orchestrator = ({state, last_speaker}) -> next_agent
```

4つのフレーバー：

- **静的** — グラフはビルド時に固定（LangGraph決定論的、CrewAI Sequential）。
- **LLM選択** — LLMがプールを読んで次のスピーカーを選ぶ（AutoGen、CrewAI Hierarchical）。
- **ハンドオフ駆動** — 現在のエージェントがハンドオフツールを呼び出すことで決定する（Swarm）。
- **キュー駆動** — ワーカーが共有キューからプルする；明示的な次のスピーカーなし（スワームアーキテクチャ、Matrix）。

### フレームワーク間で変わること

プリミティブが固定されると、残りの設計決定は：

- **メモリ戦略** — 一時的 vs 耐久性チェックポインティング（LangGraphチェックポインター）。
- **安全境界** — 誰がハンドオフを承認できるか（ヒューマン・イン・ザ・ループ）。
- **コスト会計** — エージェントごとのトークンバジェット。
- **観測可能性** — ハンドオフのトレース、リプレイのための状態の永続化。

すべてプリミティブの上に実装可能。どれも新しいプリミティブではない。

## 実装する

`code/main.py`は標準ライブラリPythonで4つのプリミティブを約150行で実装している。本物のLLMなし——各エージェントはスクリプト化されたポリシーなので、焦点は調整構造に留まる。

ファイルはエクスポートする：

- `Agent` — 名前、システムプロンプト、ツール、ポリシー関数のデータクラス。
- `Handoff` — 新しいエージェントを返す関数。
- `SharedState` — スレッドセーフなメッセージプール。
- `Orchestrator` — 3つのバリアント：`StaticOrchestrator`、`HandoffOrchestrator`、`LLMSelectorOrchestrator`（シミュレート）。

デモは同じ3エージェントパイプライン（リサーチ → 執筆 → レビュー）を3つのオーケストレータータイプすべてで実行し、最後にメッセージプールを出力する。出力は*誰が次を選ぶか*だけが異なることがわかる；エージェントと共有状態はすべての実行で同一だ。

実行：

```
python3 code/main.py
```

期待される出力：3つのオーケストレーター実行、パターンごとに1つ。各実行は最終メッセージプールを出力する。ハンドオフ駆動の実行は、リサーチャーが早く終了したと判断した場合、より少ないエージェントに到達する——それがミニチュアのLLMルーティングトレードオフだ。

## 使ってみる

`outputs/skill-primitive-mapper.md`は、任意のマルチエージェントコードベースまたはフレームワークドキュメントを読み取り、4プリミティブマッピングを返すスキルだ。新しいフレームワークリリースで実行して、ドキュメントを深く読む前に1段落の理解を得る。

## 成果物を出す

新しいフレームワークを採用する前に、そのためのプリミティブマッピングを書く。できないなら、ドキュメントが不完全か、フレームワークが5番目のプリミティブを発明している（まれ——見たことない共有状態のフレーバーかどうか確認する）。

アーキテクチャドキュメントにマッピングをピン留めする。新チームメンバーが参加したら、APIドキュメントの前にマッピングを送る。フレームワークのバージョンが変わったら、変更履歴ではなくマッピングをdiffする。

## 演習

1. 異なるエージェントポリシーで`code/main.py`を3回実行する。オーケストレーターの選択がどのエージェントを実行するかをどのように変えるかを観察する。
2. 4番目のオーケストレータータイプを実装する：エージェントが作業のために共有状態をポーリングするキュー駆動型。どのようなデッドロックが起こり得るか、どうやって検出するか？
3. LangGraphのクイックスタート（https://docs.langchain.com/oss/python/langgraph/workflows-agents）を取り上げ、4プリミティブとして書き直す。LangGraphのどの抽象化が1対1でマッピングされ、どれがコンビニエンスラッパーか？
4. OpenAI Swarmのクックブック（https://developers.openai.com/cookbook/examples/orchestrating_agents）を読む。Swarmが4プリミティブのどれを最もエルゴノミックにし、どれを呼び出し元に押しつけるかを特定する。
5. このテーブルで共有状態を完全に隠すフレームワークを1つ見つける。エージェントが履歴を再読せずにハンドオフをまたいで調整する必要がある場合に何が壊れるかを説明する。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| エージェント | 「ツールを持つLLM」 | `(system_prompt, tools, model)`の3つ組。ステートレス。 |
| ハンドオフ | 「制御の転送」 | 次のエージェントとオプションのペイロードを名指しする構造化呼び出し。3つの実装：関数の返り値、グラフエッジ、スピーカー選択。 |
| 共有状態 | 「メモリ」「コンテキスト」 | マルチエージェントシステムの唯一のステートフル部分。メッセージプールまたはブラックボード。 |
| オーケストレーター | 「コーディネーター」 | 次に誰が実行するかを決める者。静的グラフ、LLMセレクター、ハンドオフ駆動、またはキュー駆動。 |
| プリミティブ | 「抽象化」 | すべてのフレームワークがパラメータ化する4つの軸の1つ。フレームワーク機能ではない。 |
| メッセージプール | 「共有チャット履歴」 | すべてのエージェントが読む全履歴共有状態。推論が簡単で、スケールが悪い。 |
| 射影された状態 | 「スコープされたビュー」 | 共有状態への役割固有のビュー。スケールするがスキーマ設計が必要。 |
| スピーカー選択 | 「次に話す者」 | 関数（多くの場合LLM）がグループから次のエージェントを選ぶオーケストレーターパターン。 |
