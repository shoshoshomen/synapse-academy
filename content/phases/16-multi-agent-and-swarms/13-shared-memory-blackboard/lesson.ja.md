# 共有メモリとブラックボードパターン

> 2026年のマルチエージェントシステムでは2つのアプローチが共存している：**メッセージプール**（AutoGen GroupChatやMetaGPTのように全員が全員のメッセージを見る）と**サブスクリプション付きブラックボード**（Context-Aware MCPやMatrixフレームワークのようにエージェントが関連イベントにサブスクライブする）。どちらもマルチエージェントシステムの唯一のステートフルな部分だ——つまりどちらも興味深いバグが住む場所だ。参照失敗モードは**メモリポイズニング**だ：1つのエージェントが「事実」を幻覚し、他のエージェントがそれを検証済みとして扱い、即座のクラッシュよりはるかにデバッグが難しい方法で精度が徐々に低下する。このレッスンでは標準ライブラリで両方の構造をビルドし、ポイズニング攻撃を注入し、本番で実際に機能する3つの緩和策を示す。


## 問題

マルチエージェントシステムにはエージェントが事実を共有する場所が必要だ。文字通りのオプションは「すべてをメッセージで渡す」——しかしそれは余分なコピーで共有状態を再発明する。別の選択肢は「全員にグローバルログを与える」——しかしグローバルログは無限に増え、簡単にポイズニングされる。3番目は「エージェントごとにビューを射影する」——スケーラブルだがスキーマが重い。

エージェントの1つが幻覚し、幻覚を共有状態に書き込んだ場合、その状態を読む下流のすべてのエージェントが幻覚を事実として採用する。人間が気づく頃には、推論チェーンは5ステップ深くなり、根本原因は書かれた3番目のメッセージだ。マルチエージェントの精度低下のデバッグはクラッシュのデバッグより難しい。

これがメモリポイズニングだ。これはMASTタクソノミー（Cemri et al.、arXiv:2503.13657）で2番目に多く記録された失敗ファミリーであり、構造的だ：出所と書き込み不可のベリファイアーなしの共有メモリ設計は最終的にそれを示す。

## 概念

### 2つの主要なトポロジー

**フルメッセージプール。** すべてのエージェントがすべてのメッセージを読む。AutoGen GroupChatとMetaGPTがこれを使う。シンプル、透明、検査可能だが、各エージェントのコンテキストが他のエージェントの作業で満たされるため、約10エージェントを超えるとスケールしない。

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**サブスクリプション付きブラックボード。** エージェントはトピックへの関心を宣言する；サブストレートは関連するメッセージのみをルーティングする。CA-MCP（arXiv:2601.11595）とMatrixの分散フレームワーク（arXiv:2511.21686）がこれを使う。さらにスケールするが、サブスクリプションを意味のあるものにするための事前スキーマ設計が必要だ。

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### それぞれが勝つ場合

- **フルプール**はエージェントが少数（10未満）、異種で、会話が短期間な場合に勝つ。誰が何を言ったかについての推論は全員がすべてを見る場合に簡単だ。
- **ブラックボード**はエージェントが多数で、役割上同質だが数が多く（スワーム）、会話が長時間実行される場合に勝つ。ルーティングによりトークンコストとコンテキスト汚染が削減される。

本番システムはしばしば混在する：上部（計画層）に小さなフルプール、下部（ワーカー層）にブラックボード。

### メモリポイズニング、1つのシナリオで

3つのエージェントがリサーチタスクに取り組む。エージェントAは検索エージェントだ。エージェントBはサマライザーだ。エージェントCはアナリストだ。

1. Aはページを取得し、共有状態にメッセージを書く：「研究は42%の精度向上を報告している。」
2. 取得したページは実際には「4.2%の向上」と書かれていた。Aは小数点を幻覚した。
3. Bは共有状態を読み、書く：「大きな42%の精度向上が報告されている（ソース：A）。」
4. Cは共有状態を読み、書く：「採用を推奨——42%のリフトは変革的だ。」
5. 最終レポートは存在しなかった42%の数字を引用する。

エージェントはクラッシュしなかった。テストは失敗しなかった。システムは「機能した」。幻覚は1つのエージェントのコンテキストから共有状態を介してすべての下流エージェントの推論に入り込んだ。

### これが構造的な理由

共有状態なしでは、エージェントAの幻覚はAのコンテキストに留まる。下流のエージェントは再取得または再導出して、エラーに気づくかもしれない。ナイーブな共有状態では、AのコンテキストはすべてのコンテキストHになり、幻覚は事実に洗浄される。

問題は共有状態それ自体ではなく——**出所と独立したベリファイアーなしの**共有状態だ。3つの緩和策がこれに対処する：

1. **すべての書き込みに出所を属性付けする。** 共有状態のすべてのエントリに、誰が、いつ、どのプロンプトで書いたか、（該当する場合）エージェントが引用したソースを記録する。下流のエージェントは出所に基づいて懐疑的に読む。
2. **書き込みをバージョン化し、追記専用として扱う。** 修正は古いエントリを上書きするのではなく、古いものを置き換える新しいエントリだ。監査証跡が保持される。
3. **共有状態に書き込めないエージェントを少なくとも1つ置く。** 読み取り専用のベリファイアーエージェントがエントリをサンプリングし、ソースを再取得し、不整合にフラグを立てる。プールに書き込めないため、プールによってポイズニングされない。

### ブラックボードの前例（Hayes-Roth、1985年）

ブラックボードパターンはLLMエージェントより40年先立つ。Hayes-Roth（1985年、"A Blackboard Architecture for Control"）はグローバルブラックボードを観察し、部分的な解決策を提供し、他のソースをトリガーするスペシャリストKnowledge Sourcesを記述した。2026年のブラックボード（CA-MCP、Matrix）はLLMエージェントをKnowledge Sourcesとして、JSONブロブを部分的な解決策として使う同じパターンだ。古い文献には書き込み競合、日和見的な制御、一貫性に関する文書化された解決策があり、現代のシステムが再発見している。

### 射影対フルビュー

純粋なブラックボードはすべてのサブスクライバーに同じ射影（トピックスコープ）を与える。より積極的な設計は**エージェントごとの射影**だ：各エージェントは役割に合わせてカスタマイズされたビューを得る。LangGraphの状態リデューサーは2026年の標準的な実装だ——リデューサー関数がグローバル状態を役割固有のスライスに折りたたむ。

エージェントごとの射影はさらにスケールするがスキーマが必要だ。なければ、すべてのエージェントのプロンプトでアドホックな射影を再ビルドすることになる。

### 書き込み競合パターン

複数のエージェントが同時に書き込むのは並行性の問題であり、LLMの問題だけではない。3つのパターンが機能する：

- **シングルライター（単一プロデューサー）。** すべての書き込みが1つのコーディネーターエージェントを通って直列化される。シンプルだが、ボトルネックだ。
- **バージョニング付き楽観的並行性。** 各エントリにバージョンがある；ライターはバージョンの不一致で失敗し再試行する。古典的なデータベース手法。
- **トピックパーティション。** 異なるエージェントが異なるトピックを所有する。クロストピックの競合なし。設計されたパーティション境界が必要。

2026年のほとんどのフレームワークはシングルライターをデフォルトにしている。LLM呼び出しは十分に遅いため競合はまれで、ボトルネックは痛くない。

### 書き込み不可のベリファイアー

最も重要な緩和策は読み取り専用のベリファイアーだ。実装ルール：

- ベリファイアーはチームと状態を共有する（ブラックボードまたはプールを読む）。
- ベリファイアーは共有状態への書き込みハンドルを持たない——別の検証チャンネルへのみ。
- ベリファイアーは書き込みで引用されたソースを独立して取得する。不一致にフラグを立てる。
- ベリファイアー自身の出力は人間または別の決定エージェントにルーティングされ、プールには戻されない。

この分離なしでは、ベリファイアーの出力はプールの新しいエントリになり、ポイズニングされたプールがベリファイアーをポイズニングし、その検証をポイズニングすることを意味する。

## 実装する

`code/main.py`は標準ライブラリPythonで両方のトポロジー、おもちゃのポイズニング攻撃、3つの緩和策を実装している。

- `MessagePool` — スレッドセーフな追記専用ログとフルリードアウト。
- `Blackboard` — エージェントごとのサブスクリプションを持つトピックキー付きpub/sub。
- `ProvenanceEntry` — すべての書き込みが(writer, timestamp, prompt_hash, source_uri)を記録する。
- `PoisoningScenario` — エージェントAが小数点を幻覚する3エージェントリサーチタスクを実行する。最終レポートを出力する。
- `Verifier` — ソースを再取得し不整合にフラグを立てる読み取り専用エージェント。ベリファイアーがいる場合の同じシナリオを実行する。

実行：

```
python3 code/main.py
```

期待される出力：
- 実行1（ベリファイアーなし）：幻覚の42%が最終レポートに伝播する。
- 実行2（ベリファイアーあり）：ベリファイアーが不整合にフラグを立て、プールに「フラグ付き」とラベルが付き、最終レポートに撤回が含まれる。

## 使ってみる

`outputs/skill-memory-auditor.md`は任意のマルチエージェントシステムの共有メモリ設計を出所、バージョニング、ベリファイアーの分離について監査するスキルだ。本番前に新しいマルチエージェントアーキテクチャで実行する。

## 成果物を出す

任意の共有メモリ設計について：

- すべての書き込みに出所を記録する：`(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`。
- ログを追記専用にする。修正は置き換えられたものを参照する新しいエントリだ。
- 独立したソースアクセスを持つ読み取り専用ベリファイアーエージェントを少なくとも1つデプロイする。
- ベリファイアーの出力を別チャンネルにルーティングし、共有プールには戻さない。
- 置き換えである書き込みの比率をログする——上昇する比率は幻覚パターンの早期証拠だ。

## 演習

1. `code/main.py`を実行する。実行1が幻覚を伝播し、実行2がそれを検出することを確認する。
2. 2番目の幻覚を追加する：エージェントBがデータセットサイズを作り上げる。ベリファイアーはどちらにも手動チューニングなしで両方を検出すべきだ。
3. フルプールをトピックパーティション（`prices`、`summaries`、`analyses`）を持つブラックボードに切り替える。トピックパーティショニングがどのポイズニングシナリオを難しくし、どれを助けないか？
4. Hayes-Roth（1985年、"A Blackboard Architecture for Control"）を読む。このレッスンで議論されていない、2026年のシステムが恩恵を受ける論文の2つの制御パターンを特定する。
5. CA-MCP（arXiv:2601.11595）を読む。そのShared Context Storeを`code/main.py`の`MessagePool`または`Blackboard`クラスにマッピングする。CA-MCPがその上に追加するプリミティブは何か？

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| メッセージプール | 「共有チャット履歴」 | すべてのエージェントが読む追記専用ログ。完全な透明性、スケールが悪い。 |
| ブラックボード | 「共有ワークスペース」 | トピックキー付きpub/sub。エージェントは関連トピックにサブスクライブする。さらにスケールする。 |
| 出所 | 「誰が何を書いたか」 | 各書き込みのメタデータ：ライター、タイムスタンプ、プロンプト、ソース。 |
| メモリポイズニング | 「幻覚の拡散」 | 1つのエージェントのエラーが共有状態に入り、下流のエージェントがそれを事実として採用する。 |
| 追記専用 | 「インプレース更新なし」 | 修正は置き換えを行う新しいエントリ。監査証跡を保持する。 |
| 書き込み不可のベリファイアー | 「独立した監査者」 | ソースを再取得し不整合にフラグを立てる読み取り専用エージェント。 |
| 射影 | 「スコープされたビュー」 | グローバル状態から計算されたエージェントごとのビュー。LangGraphリデューサーが標準的なケース。 |
| Knowledge Source | 「スペシャリストエージェント」 | Hayes-Rothの1985年のブラックボード参加者の用語。 |
