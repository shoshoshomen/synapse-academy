# スーパーバイザー／オーケストレーター・ワーカーパターン

> 1人のリードエージェントが計画と委任を担い、専門化されたワーカーが並列コンテキストで実行して報告する。これがAnthropicのResearchシステム（リードとしてClaude Opus 4、サブエージェントとしてSonnet 4）の背後にあるパターンで、内部リサーチ評価でシングルエージェントのOpus 4より+90.2%を達成した。Anthropicのエンジニアリング投稿は、BrowseCompの分散の80%がトークン使用量だけで説明できると報告している——マルチエージェントが勝つ主なメカニズムはサブエージェントごとのフレッシュなコンテキストウィンドウだ。このレッスンではプリミティブからスーパーバイザーパターンを構築し、本番デプロイメントからの2026年のエンジニアリング教訓をカバーする。


## 問題

リサーチは、シングルエージェントシステムが失敗する典型的なタスクだ。「2023年から2026年の間にマルチエージェントシステムで何が変わったか？」と尋ねる。シングルエージェントは5本の論文を順番に読み、コンテキストの半分をそのテキストで埋め、次にそれらすべてについて一緒に推論しなければならない。5番目に到達する頃には最初の論文を忘れている。並列化できない。

スーパーバイザーパターンがこれを解決する：1つのリードエージェントが検索を計画し、各サブ質問をワーカーに委任し、統合する。各ワーカーは狭い質問のために独自の20万トークンウィンドウを持つ。リードは生の論文を見ることなく——ワーカーのサマリーだけを見る。

Anthropicの本番リサーチシステムは、シングルのOpus 4に対して内部リサーチ評価で+90.2%を報告している。同じ投稿は、BrowseCompの分散の80%が*トークン使用量だけ*で説明できると述べている。サブエージェントごとのフレッシュなコンテキストが主なメカニズムだ。

## 概念

### パターン

```
                 ┌──────────────┐
                 │   リード      │  計画、分解、
                 │  (Opus 4)    │  統合
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ワーカー1 │  │ワーカー2 │  │ワーカー3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         フレッシュ   フレッシュ    フレッシュ
         コンテキスト コンテキスト  コンテキスト
```

リードは生の資料を読まない。ワーカーはリードが統合するまで互いの作業を見ない。各矢印は狭いアーティファクトを持つハンドオフだ。

### なぜ勝つか

3つのメカニズム：

1. **サブエージェントごとのフレッシュなコンテキスト。** 「FIPA-ACLの遺産」を探索するワーカーは、リードが計画に費やした4万トークンを持ち込まない。1つの質問のために20万トークンのウィンドウを持つ。
2. **プロンプトによる専門化。** リードのプロンプトは「分解して統合する」ことであり「リサーチ」ではない。各ワーカーのプロンプトは狭い：「Xで何が変わったかを見つける」。焦点を絞ったプロンプトが焦点を絞った出力を生む。
3. **並列性。** ワーカーは同時に実行される。ウォールクロック時間はおおよそ`max(ワーカー時間) + 計画 + 統合`で、`sum(ワーカー時間)`ではない。

### エンジニアリング教訓（Anthropic 2025）

Anthropicの投稿は2026年でも関連する本番教訓をいくつかリストしている：

- **クエリの複雑さに合わせて努力をスケールする。** シンプルなクエリ：1エージェント、3〜10のツール呼び出し。複雑なクエリ：10以上のエージェント。リードはこれを見積もる必要があり、呼び出し元ではない。
- **広く、それから狭く。** まず広いサブ質問に分解し、次に答えが深さを正当化する場合はサブ質問ごとにより多くのワーカーを生成する。
- **レインボーデプロイメント。** エージェントは長時間実行でステートフル。従来のブルーグリーンは機能しない。Anthropicはレインボーを使う：古いものがドレインしている間に新しいバージョンの段階的ロールアウト。
- **トークン使用量が支配する。** マルチエージェントはシングルエージェントのトークン数の約15倍。タスクの価値がコストを正当化する場合にのみ実行する。

### LangGraphの転換

LangGraphは元々`create_supervisor`ヘルパーを持つ`langgraph-supervisor`ライブラリを出荷した。2025年にLangChainは、ツール呼び出しが*スーパーバイザーが何を見るか*（コンテキストエンジニアリング）をより細かく制御できるため、ツール呼び出しを直接使ってスーパーバイザーパターンを実装することを推奨に変えた。ライブラリはまだ機能する；ドキュメントは今やツール呼び出し形式を推奨する。

### 失敗モード

- **リードが計画を幻覚する。** リードが本当の質問を分解しないサブ質問を生成すると、ワーカーは間違ったターゲットで正確なリサーチを行う。
- **ワーカーが過探索する。** 明示的なスコープ境界なしに、ワーカーは割り当てられたサブ質問を超えてドリフトし、統合ステップを汚染する。
- **統合の矛盾。** 2つのワーカーが矛盾する事実を返す。リードは再質問（ラウンドを追加）するか、意見の不一致を明示的に記述するかしなければならない。どちらか一方を静かに選ぶのが最悪の失敗だ：ユーザーは意見の不一致があったことを知らない。

### スーパーバイザーが間違っている場合

- **逐次タスク。** ステップ2がステップ1の出力を必要とする場合、並列性は何も買わない。パイプライン（CrewAI Sequential、LangGraph線形グラフ）を使う。
- **シンプルなクエリ。** シングルエージェントはより速く安価に処理する。ワーカーを生成する前にリードの「努力のスケール」チェックを使う。
- **厳密な決定論。** スーパーバイザーはLLM選択の委任を使う。監査/リプレイが適応性よりも重要な場合は静的グラフの方が良い。

## 実装する

`code/main.py`は`threading`を使って3つの並列ワーカーのスーパーバイザーを実装している。リードがクエリをサブ質問に分解し、ワーカーが各サブ質問で同時に実行し、リードが統合する。本物のLLMなし——ワーカーはフェッチアンドサマライズをシミュレートするようスクリプト化されている。

主要な構造：

- `Lead.plan(query)`がクエリを3つのサブ質問に分割する。
- `Worker.run(sub_q)`がフェイクサマリーを返す（本番では任意のツール使用エージェントにできる）。
- `Lead.run(query)`がスレッドでワーカーを起動し、待ち合わせ、統合する。

実行：

```
python3 code/main.py
```

出力はプラン、開始/終了タイムスタンプ付きの並列ワーカートレース、最終統合を示す。ウォールクロックの勝利を見ることができる：3つの0.3秒のワーカーが約0.35秒で実行され、0.9秒ではない。

## 使ってみる

`outputs/skill-supervisor-designer.md`はユーザークエリを取り、スーパーバイザーパターンの設計を生成する：リードシステムプロンプト、ワーカーの役割、サブ質問の分解ルール、統合テンプレート。新しいリサーチスタイルのエージェントシステムを構築する前にこれを使う。

## 成果物を出す

スーパーバイザーパターンをデプロイする前のチェックリスト：

- **モデルのペアリング。** 推論ティアモデル（Opusクラス、`o3`クラス）のリード。より速く安価なモデル（Sonnet、`o4-mini`）のワーカー。
- **ワーカータイムアウト。** 中央値ランタイムの2倍を超えるワーカーはキルされる；リードは狭いスコープで再生成するか、それなしで進む。
- **ワーカーごとのトークン上限。** ハードリミット（例：予想される統合入力の10倍）は暴走ワーカーが予算を吹き飛ばすのを防ぐ。
- **観測可能性。** リードのプラン、各ワーカーのツール呼び出し、統合をトレースする。これが事後デバッグの基礎だ。
- **レインボーロールアウト。** ステートフルな長時間実行エージェントはホットスワップではなく段階的なバージョン遷移が必要だ。

## 演習

1. `code/main.py`を実行し、次にリードが3つの代わりに5つのワーカーを生成するよう変更する。ウォールクロック効果を観察する。このデモで並列の節約をスポーンのオーバーヘッドが超えるのは何ワーカーの数か？
2. ワーカータイムアウトを実装する：0.5秒以上実行するワーカーをキルし、リードが残りの結果で統合するようにする。ワーカーがカットされたことを知るためにどのような観測可能性が必要か？
3. リードの統合に競合検出ステップを追加する：2つのワーカーが矛盾する答えを返した場合、リードは1つを選ぶのではなく意見の不一致を記述する。LLMを呼び出さずに矛盾をどう検出するか？
4. Anthropicのリサーチシステムのエンジニアリング投稿を読む。このおもちゃデモが本番で実行するために採用する必要がある3つの実践をリストアップする。
5. LangGraphの`create_supervisor`（レガシー）と新しいツール呼び出しの推奨を比較する。どちらがスーパーバイザーが何を見るかをより細かく制御できるか？Anthropicはなぜサブアンサーだけをパスし、生のワーカーコンテキストを統合に入れないのか？

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| スーパーバイザー | 「リードエージェント」 | 計画し、委任し、統合するオーケストレーターエージェント。作業自体は行わない。 |
| ワーカー | 「サブエージェント」 | スーパーバイザーが狭いスコープと独自のコンテキストウィンドウで呼び出す焦点を絞ったエージェント。 |
| オーケストレーター・ワーカー | 「スーパーバイザーパターン」 | 同じもの、異なる名前。2026年の文献は両方を使う。 |
| フレッシュなコンテキスト | 「クリーンなウィンドウ」 | ワーカーのコンテキストはシステムプロンプトと割り当てられた質問から始まり、リードの履歴ではない。 |
| レインボーデプロイメント | 「段階的ロールアウト」 | 長時間実行ステートフルエージェントはブルーグリーンではなく、バージョン管理されたドレインアンドリプレースが必要。 |
| トークン支配 | 「コンテキストが変数だ」 | Anthropicによると、リサーチ評価の分散の80%はモデルの選択ではなく使用されたトークン数の合計から来る。 |
| 努力のスケール | 「エージェント数を複雑さに合わせる」 | リードはクエリの難易度を推定し、1つ対10以上のワーカーを生成する。 |
| 統合の矛盾 | 「ワーカーが意見が合わない」 | 2つのワーカーが矛盾する事実を返す；リードは意見の不一致を表面化させなければならず、静かに1つを選んではならない。 |
