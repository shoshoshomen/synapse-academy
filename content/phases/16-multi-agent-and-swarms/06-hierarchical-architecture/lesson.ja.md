# 階層型アーキテクチャとその失敗モード

> 階層型はスーパーバイザーをネストしたものだ。サブマネージャーの上のマネージャーエージェント、ワーカーの上のサブマネージャー。CrewAIの`Process.hierarchical`はテキストブックバージョンだ：`manager_llm`がタスクを動的に委任して出力を検証する。LangGraphの等価物は`create_supervisor(create_supervisor(...))`だ。タスクが本物の組織図である場合の自然なパターンだ。また、マネジメントループに陥る可能性が最も高いパターンでもある——マネージャーエージェントが作業を不適切に割り当て、サブ出力を誤解し、コンセンサスに達しない。逐次型が多くの場合これを上回る。


## 問題

スーパーバイザーパターンが理解できると、自然な次のステップは「ワーカーがスーパーバイザーだったら？」だ。チームにはサブチームがある；会社には部門の部門がある。階層型アーキテクチャがそれを反映する。

問題は：LLMマネージャーは人間のマネージャーと同じではない。人間のマネージャーは部下が何を知っているかについて安定した事前知識を持っている。LLMマネージャーはコンテキストにある内容から毎ターン組織を再推論する。そのコンテキストにわずかなドリフトがあると、ツリー全体が作業を誤配分する。

## 概念

### 形状

```
                 マネージャー
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       サブMgr A         サブMgr B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

すべての内部ノードが計画し、委任し、統合する。リーフのみが作業を行う。

### 輝く場所

- **明確な組織マッピング。** 本当のタスクが部門的である場合（「法務がドキュメントをレビューし、財務がドキュメントをレビューし、エンジニアリングがドキュメントをレビューし、次にエグゼクティブ向けに要約する」）、階層は明示的だ。
- **ローカル要約。** 各サブマネージャーはトップマネージャーが見る前にチームの出力を統合する。トップマネージャーは15個のワーカー出力ではなく3つのサブマネージャーのサマリーを見る。

### 壊れる場所

2026年のポストモーテムが繰り返し発見する3つの失敗モード：

1. **タスク割り当てエラー。** マネージャーが目標を読み取り、分解を幻覚し、間違ったサブマネージャーに委任する。サブマネージャーが与えられたものを従順に作業するため、エラーはトップ統合でのみ表面化する——人間が検出できたであろう場所から1レベル離れている。
2. **出力の誤解。** サブマネージャーが「主張Xを検証できなかった」を返す。トップマネージャーが「主張Xは確認されなかった」として要約する。意味がすべてのレベルでドリフトする。
3. **コンセンサスループ。** 2つのサブマネージャーが意見が合わない；トップマネージャーが和解を求める；再び下に委任する；ワーカーが再実行する；サブマネージャーが若干異なる答えを返す；ループ。CrewAIの`Process.hierarchical`はステップ制限でこれを防ぐが、制限自体がハイパーパラメーターになる。

### 決定の質問

逐次（線形パイプライン）対階層：タスクに実際に独立したサブチームがあるか、それとも木に見せかけている1つの線形フローか？後者なら逐次型を使う。前者なら階層型を使うが、明示的な和解ルールを予算化する。

### CrewAIの実装

`Process.hierarchical`はマネージャーLLMをスペシャリストクルーの上に配線する。マネージャーは：

- トップレベルのタスクを受け取り、
- クルーにサブタスクを割り当て、
- クルーの出力を評価し、
- 受け入れ、再委任、または反復するかを決定する。

ドキュメント：https://docs.crewai.com/en/introduction（コアコンセプトの「Hierarchical Process」を参照）。

### LangGraphの実装

LangGraphはネストされた`create_supervisor`呼び出しを使う。内部スーパーバイザーは独自のグラフを持ち；外部スーパーバイザーは内部グラフを不透明なノードとして扱う。これはCrewAIよりデバッグがクリーン（各グラフを別々にステップ実行できる）だが、ツリーの動的な再形成を表現するのが難しい。

リファレンス：https://reference.langchain.com/python/langgraph-supervisor。

## 実装する

`code/main.py`は3レベルの階層を実行する：

- トップマネージャー：タスクを「エンジニアリング」と「法務」ブランチに分割する、
- エンジニアリングサブマネージャー：「フロントエンド」と「バックエンド」ワーカーに分割する、
- 法務サブマネージャー：1つのワーカー。

デモは幸せなパス（全員が同意）と**乱れたパス**を対比する。乱れたパスではトップマネージャーの分解が「法務」を「財務」と誤ラベルし、エラーのカスケードを見る——サブマネージャーが従順に財務作業を行い、トップシンセサイザーが財務の調査結果を報告し、元の法務の質問が答えられない。

実行：

```
python3 code/main.py
```

出力は「何が求められたか」対「何が提供されたか」を明確に並べて両方のパスを示す。

## 使ってみる

`outputs/skill-hierarchy-fitness.md`は与えられたタスクが階層型、逐次型、フラットなスーパーバイザーを使うべきかを評価する。入力：タスク説明、組織構造、和解予算。出力：防ぐべき具体的な失敗モードを含むパターンの推奨。

## 成果物を出す

階層型をデプロイする場合：

- **ツリーの深さを2に制限する。** 3レベルはすでにほとんどのエラーを観測可能性から隠す。
- **明示的な和解予算。** トップマネージャーがコミットしなければならない前の最大ラウンドを設定する。通常2。
- **すべての統合でプロベナンス。** 各ノードのサマリーはそれを生成したリーフ出力を引用しなければならない。
- **分解ドリフトのアラート。** ステップごとにマネージャーの分解をログする；ユーザークエリと比較してdiffする。分解がクエリをカバーしなくなったら、アラートを発火する。

## 演習

1. `code/main.py`を実行し、幸せなパスと乱れたパスを比較する。トップ出力がユーザーの質問から完全に乖離するまでに何レベルのマネージャーハンドオフが必要か？
2. 3番目のレベル（トップ → サブ → サブサブ → ワーカー）を追加する。深さが増すにつれて乱れたパスが自己修正する頻度と完全に乖離する頻度を測定する。
3. 各サブマネージャーに「カナリア」ワーカーを実装する。常に元のユーザー質問をそのままに尋ねられる。カナリアの答えを使って分解ドリフトを検出する。カナリアが統合された答えと意見が合わない場合、マネージャーはどう反応するべきか？
4. CrewAIの`Process.hierarchical`ドキュメントを読む。CrewAIが適用する1つの具体的なガードレール（ステップ制限、manager_llm制約）を特定し、それが対象とする失敗モードを説明する。
5. ネストされたLangGraphスーパーバイザーをCrewAI hierarchicalと比較する。どちらが和解ループを検出するコストが安いか？

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| 階層型 | 「組織図パターン」 | スーパーバイザーの上のスーパーバイザー；リーフのみが作業をする。 |
| マネージャーLLM | 「ボス」 | 内部ノードで分解し、割り当て、検証するLLM。 |
| 分解ドリフト | 「ボスが焦点を失った」 | トップマネージャーの分割が元の質問をカバーしなくなる。 |
| 和解ループ | 「終わりのない会議」 | サブマネージャーが意見が合わない；トップが再委任；ワーカーが再実行；予算が尽きるまでループ。 |
| 深さ2の上限 | 「2レベルより深くしないこと」 | 経験的なガードレール：3レベル以上は観測可能性が崩壊する。 |
| カナリア質問 | 「すべてのレベルでの基準真実」 | 常に元のクエリをそのままに尋ねられるワーカー。ドリフトを検出するため。 |
| プロベナンスチェーン | 「誰が何を言ったか」 | 各統合からそれを生成したリーフ出力までのトレース。 |
