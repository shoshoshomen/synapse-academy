# 役割特化——プランナー、クリティック、エグゼキューター、ベリファイアー

> 2026年で最も一般的なマルチエージェント分解：1つのエージェントが計画し、1つが実行し、1つが批評または検証する。MetaGPT（arXiv:2308.00352）はこれを役割プロンプトにエンコードされたSOP（標準作業手順書）として形式化している——プロダクトマネージャー、アーキテクト、プロジェクトマネージャー、エンジニア、QAエンジニア——`Code = SOP(Team)`に従う。ChatDev（arXiv:2307.07924）はデザイナー、プログラマー、レビュアー、テスターを「コミュニカティブ脱幻覚」（エージェントが欠落した詳細を明示的に要求する）を持つ「チャットチェーン」でつなぐ。ベリファイアーは重要だ：Cemri et al.（MAST、arXiv:2503.13657）はすべてのマルチエージェント失敗が欠落または破損した検証に起因することを示している。PwCはCrewAIの構造化検証ループから7倍の精度向上（10%→70%）を報告した。


## 問題

汎用マルチエージェントシステムは汎用的な出力を生む。グループチャットの3人のコーダーは同じ平凡なコードの3つのフレーバーを書く。エージェントを追加し、ラウンドを追加しても、品質の閾値を越えられない。

解決策はより多くのエージェントではなく、*異なる*エージェントだ。明確な役割を割り当てる。プランナーが持たないツールをクリティックに与える。ベリファイアーに客観的なテストスイートを与える。これでシステムは根拠のある修正を伴う内部的な意見の不一致を持つようになり、単なる並列の推測ではなくなる。

## 概念

### 4つの標準的な役割

**プランナー。** 目標を読み、ステップリストまたは仕様を生成する。ツール：知識検索、ドキュメント。出力：構造化されたプラン。

**エグゼキューター。** 1度に1つのプランステップを読み、アーティファクトを生成する。ツール：実際の作業ツール（コードコンパイラー、シェル、APIクライアント）。出力：アーティファクト。

**クリティック。** プランナーの意図に対してエグゼキューターの出力を読む。ツール：アーティファクトへの読み取り専用アクセス、静的解析。出力：理由付き受け入れ/拒否。

**ベリファイアー。** アーティファクトを読んで決定論的チェックを実行する。ツール：テストランナー、型チェッカー、スキーマバリデーター。出力：証拠付き合格/不合格。

クリティックは主観的で意見を持ち、LLMベースが多い。ベリファイアーは客観的で決定論的で、コードベースが多い。同じ役割ではない。

### MetaGPTのSOPパターン

MetaGPT（arXiv:2308.00352）はソフトウェアエンジニアリングのSOPを役割プロンプトとしてエンコードする：

- **プロダクトマネージャー**がPRDを書く。
- **アーキテクト**がシステム設計を生成する。
- **プロジェクトマネージャー**がタスクを分割する。
- **エンジニア**が実装する。
- **QAエンジニア**がテストを実行する。

各役割には厳密な入出力スキーマがある。役割プロンプトは役割が*何者か*と*何を生成しなければならないか*を示す。`Code = SOP(Team)`の形式化——決定論的SOPがLLMのチームを予測可能なパイプラインに変える。

### ChatDevのコミュニカティブ脱幻覚

ChatDevは重要な動きを追加する：エグゼキューターがプランにない特定の詳細を必要とする場合、続ける前にデザイナーに明示的に尋ねる。これにより、LLMが詳細を尤もらしく発明するという古典的な失敗を防ぐ。

実装：役割プロンプトに「与えられなかった特定の情報が必要な場合、出力を生成する前に名前で関連する役割に尋ねよ」を含める。

### ベリファイアーが最も重要な理由

Cemri et al.（MAST）は1642のマルチエージェント実行失敗を追跡した。21.3%が検証ギャップだった——誰もチェックしないまま答えが出荷された。残りの79%も多くが「バグを検出していれば通過しなかったチェックが静かに失敗するかまたは実行されなかった」に起因する。検証は重要な役割だ。

PwCは（CrewAIデプロイメント、2025年）構造化検証ループを追加することで精度が10%から70%に向上したと報告した。1つの役割から7倍の向上。

### クリティック対ベリファイアー

- クリティックは品質のためにアーティファクトをレビューするLLMだ。主観的。尤もらしい散文に騙されることがある。
- ベリファイアーはアーティファクトで実行される決定論的プログラムだ。客観的。証拠付きの合格/不合格を出す。

両方使う。クリティックはベリファイアーが言語化できない趣味の問題を検出する。ベリファイアーはクリティックが見られないバグを検出する。なぜなら実行時にのみ現れるからだ。

### アンチパターン

システムのすべての役割がLLMで、すべての役割の出力が「良さそうだ」。典型的なMASTの失敗モード。コードで合格/不合格が決定される少なくとも1つのベリファイアーを追加する。LLMではなく。

### フレームワークのマッピング

- **CrewAI** — `Agent(role, goal, backstory)`がテキストブックの特化サーフェス。
- **LangGraph** — ノードは特化されたプロンプトを持てる；エッジはパイプラインを強制する。
- **AutoGen** — GroupChatに1単語の名前を持つ役割特化ConversableAgents。
- **OpenAI Agents SDK** — 役割特化エージェント間のハンドオフツール。

## 実装する

`code/main.py`はシンプルなPython関数を構築する4役割パイプラインを実装している：

- **プランナー**が仕様を生成する。
- **エグゼキューター**がコード文字列を生成する。
- **クリティック**（LLMシミュレート）が明らかな問題にフラグを立てる。
- **ベリファイアー**がテストケースに対してサンドボックス（`exec`）で生成されたコードを実行する。

デモは2回実行される：エグゼキューターが正しいコードを生成する場合（クリティック + ベリファイアー両方が合格）と、エグゼキューターが仕様外のコードを生成する場合（クリティックはバグを見逃すが尤もらしく見え、ベリファイアーはテストが失敗するため検出する）。

実行：

```
python3 code/main.py
```

## 使ってみる

`outputs/skill-role-designer.md`はタスクを取り、役割のリスト（3〜5の役割）、役割ごとの入出力スキーマ、ベリファイアーチェックを生成する。エージェントをフレームワークに組み込む前にこれを使う。

## 成果物を出す

チェックリスト：

- **少なくとも1つの決定論的ベリファイアー。** 全部LLMにしてはならない。
- **役割ごとの明示的なI/Oスキーマ。** プランナーは散文ではなく仕様を返す；エグゼキューターはそのスキーマを読む。
- **コミュニカティブ脱幻覚。** エグゼキューターは情報が欠落している場合にプランナーに尋ねなければならない；発明してはならない。
- **クリティック/ベリファイアーの順序。** まずクリティックを実行する（安価、設計問題を検出）、次にベリファイアー（遅い、バグを検出）。
- **ループ予算。** 人間にエスカレーションする前のクリティック・エグゼキューター修正ラウンドの最大数は2。

## 演習

1. `code/main.py`を実行し、クリティックが見逃したバグをベリファイアーがどのように検出するかを観察する。追加のベリファイアーとして静的解析チェック（`return`の出現回数をカウント）を追加する。ランタイムテストが見逃すものを何を検出するか？
2. 5番目の役割を追加する：「要件アナリスト」がユーザーの願望をプランナー向けの仕様に変換する。どのコミュニカティブ脱幻覚リクエストが上に流れるべきか？
3. MetaGPTのセクション3（「Agents」）を読む。MetaGPTの5つの役割それぞれの入出力スキーマをリストアップする。
4. ChatDevのチャットチェーン図（arXiv:2307.07924の図3）を読む。コミュニカティブ脱幻覚が本来無限になるループをどこで破るかを特定する。
5. PwCの7倍の精度向上は検証ループから来た。ベリファイアーを追加しても助けにならない3つのタスクを仮説立てる——正しさの決定論的チェックが不可能または法外にコストがかかる場所。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| 役割特化 | 「異なるエージェント、異なる仕事」 | プランナー/エグゼキューター/クリティック/ベリファイアーの役割のために調整された明確なシステムプロンプト。 |
| SOPパターン | 「エンコードされた標準作業手順書」 | MetaGPTのフレーミング：役割ごとの厳密なI/Oスキーマがチームをパイプラインに変える。 |
| コミュニカティブ脱幻覚 | 「発明する前に尋ねる」 | ChatDevパターン：エグゼキューターが詳細が欠落している場合に作り上げるのではなくプランナーに尋ねる。 |
| クリティック | 「LLMレビュアー」 | 主観的で意見を持つレビュアー。趣味の問題を検出。尤もらしい散文に騙されることがある。 |
| ベリファイアー | 「決定論的チェック」 | コードベースの合格/不合格。テストランナー、型チェッカー、スキーマバリデーター。騙されない。 |
| 検証ギャップ | 「誰もチェックしなかった」 | MASTの失敗の21.3%。バグを検出していたであろうチェックなしに答えが出荷された。 |
| 修正ループ | 「クリティックが差し戻す」 | クリティックの拒否がフィードバック付きでエグゼキューターの再実行を引き起こす。予算が必要。 |
| 全LLMアンチパターン | 「良さそうだ」 | すべての役割がLLMで、決定論的チェックなし。典型的なMASTの失敗。 |
