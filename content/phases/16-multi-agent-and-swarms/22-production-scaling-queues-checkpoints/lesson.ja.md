# 本番スケーリング — キュー、チェックポイント、耐久性

> マルチエージェントシステムを数千の同時実行にスケールするには**耐久実行**が必要だ。LangGraphのランタイムは各スーパーステップの後に `thread_id` をキーとするチェックポイントを書き込む（デフォルトはPostgres）; ワーカーのクラッシュがリースを解放し、別のワーカーが再開する。エージェントは人間の入力を待って無期限にスリープできる。**MegaAgent**（arXiv:2408.09955）はエージェントごとのプロデューサーコンシューマーキューを3つの状態（Idle / Processing / Response）と2層調整（グループ内チャット + グループ間管理チャット）で実行した。**Fiber/async** はLLMストリーミングではスレッドごとのジョブに勝る: スレッドはトークンを待つ99%の時間アイドル状態で座っている。反論: Ashpreet Bediの「Scaling Agentic Software」は負荷が証明されるまで**FastAPI + Postgres + それ以外なし**を主張する—シンプルなアーキテクチャは予想以上に進む。このレッスンでは耐久チェックポイントログ、3つの状態遷移を持つエージェントごとのワークキュー、async対スレッドのデモを構築し、「シンプルに始める」という実用的なルールを定着させる。


## 問題

プロトタイプマルチエージェントシステムはインメモリイベントループで3つのエージェントを持つ1台のラップトップで動作する。本番に移行する:

- エージェントが時々数時間実行される（長い研究、人間が関与する待機）。
- ワーカープロセスがクラッシュする。再起動すると状態が失われる。
- ピーク負荷は平均の10倍; 水平スケーリングが必要だ。
- ユーザーはエージェント実行ごとに支払う; 請求のためにexactly-onceセマンティクスが必要だ。

インメモリイベントループはこれらを何もしない。その下に耐久実行層が必要だ。2026年の標準的なオプションは:

1. チェックポイント付きワークフローエンジン（Temporal、LangGraphランタイム）。
2. ステートストアを持つメッセージキュー（Postgres + SQS/RabbitMQ）。
3. アクターモデルフレームワーク（MegaAgentのエージェントごとのプロデューサーコンシューマー）。
4. 手作りFastAPI + Postgres（Bediの主張）。

このレッスンでは各のミニチュアを構築する。

## 概念

### 耐久実行、パターン

耐久実行エンジンは各「ステップ」（LangGraphの言葉でスーパーステップ）の後に完全なプログラム状態を永続化する。クラッシュ時:

```
ワーカーがステップ途中でクラッシュ
  -> リースタイムアウト
  -> 別のワーカーがthread_idを引き取る
  -> 最後のチェックポイントから再開
  -> 重複した副作用なし
```

これが機能するための要件:

- **シリアライズ可能な状態。** すべてのエージェント状態が永続化可能でなければならない。ライブデータベース接続を持つ関数クロージャは生き残らない。
- **決定論的再開。** 同じ状態と同じ入力を与えられた場合、エージェントは同じアクションを生成する（またはLLM呼び出しのために外部決定論的オラクルに委ねる）。
- **冪等な副作用。** 外部呼び出し（ツール呼び出し、支払い）は冪等か、重複排除キーを使用しなければならない。

LangGraphはスーパーステップごとにチェックポイントを書き込む; Temporalはアクティビティごとに書き込む; Restateはイベントソースされたジャーナルを使用する。3つすべてが同じパターンを実装する。

### LangGraphのランタイム

各エージェントには `thread_id` があり; 状態は型付き辞書; 各スーパーステップはチェックポイントテーブルに行を書く。再開時に、ランタイムは最初からではなく最後のチェックポイントから再生する。エージェントは人間の入力を待つために `interrupt()` できる; ランタイムが永続化してワーカーを解放する。入力が到着すると、どのワーカーでも再開できる。

これは2026年4月現在の参照本番設計だ。

### MegaAgentのエージェントごとのキュー

arXiv:2408.09955はスケール実験を説明する: 1つのクラスターに数千の同時エージェント。アーキテクチャ:

```
エージェント i:
  状態 ∈ {Idle, Processing, Response}
  in_queue   <- エージェント i 宛のメッセージ
  out_queue  -> 返信 + 副作用

コーディネーター:
  グループ内チャット  (同じグループのエージェント)
  グループ間管理チャット  (高レベルルーティング)
```

2層調整によりグループ内会話が密に行われる一方、グループ間は疎に保つ—数千のエージェントでコストを線形に保つために使用されるパターン。

### Async対スレッドごとのジョブ

LLM呼び出しはI/Oバウンドだ。次のトークンを待つスレッドは99%の時間アイドルだ。スレッドは各約1MB RAM; 1万の同時呼び出しでスタックだけで10GBだ。

ファイバー（Python `asyncio`、Goゴルーチン、Rust `tokio`）はI/Oで協調的にyieldする。同じ1万の呼び出しがプロセス内に快適に収まる。LLMエージェントスケールでasyncは最適化ではなく—アーキテクチャだ。

例外: CPU バウンドのポスト処理（埋め込み、トークナイザーのトリック）はまだスレッドまたはプロセスが欲しい。I/O層をCPU層から分離する。

### Bediの反論

「Scaling Agentic Software」（Ashpreet Bedi、2026）は、ほとんどのチームが負荷を測定する前に過度に設計すると主張する。実用的なデフォルト:

- FastAPI + Postgres。
- 各エージェント実行は行; 楽観的同時実行でインプレース状態更新。
- `pg_notify` または単純なCeleryワーカーを介したバックグラウンドジョブ。
- アプリケーションコードでのリトライポリシー。

管理可能なタスクで約100の同時エージェント実行を下回る負荷では、これが必要なすべてであることが多い。それが失敗するのを測定したらアップグレードする。

ルール: シンプルなアーキテクチャが解決できない具体的な問題に当たった時に耐久実行フレームワークを採用する。時期尚早な採用は見返りのない儀式に時間を浪費する。

### Exactly-once セマンティクス

有料のエージェント実行には「実効exactly-once」（at-least-once配信 + 冪等コンシューマー）が必要だ。エンジニアリングの動き:

- **実行ごとの重複排除キー。** すべての副作用呼び出しに含める。
- **アウトボックスパターン。** 副作用がまずテーブルに書き込む、次に別のプロセスがそれらを実行する。両ステップが冪等。
- **補償トランザクション。** 副作用が成功したがそのトラッキング書き込みが失敗した場合、補償をスケジュールする。

これらはデータベースエンジニアリングパターンであってLLM固有ではない。LLMの税はLLM呼び出しが遅いだけ; それ以外はすべて標準的な分散システムだ。

### レインボーデプロイ

Anthropicのマルチエージェント研究システムは「レインボーデプロイ」を使用する: エージェントランタイムの複数バージョンが同時に実行されるため、実行中のエージェントがすべてのコードデプロイで強制終了されない。トラフィックのスライスで新しいバージョンをカナリー; 古いバージョンはそれらのエージェントが終了したら廃止する。

これは長期実行ステートフルシステムでは標準; 2026年の適応は、エージェントが数時間生存できることであり、デプロイサイクルはそれに対応しなければならない。

### 標準的な本番チェックリスト

- 耐久状態（チェックポイント、スナップショット、またはアウトボックス + 再生可能ログ）。
- 冪等な副作用。
- LLM呼び出しのためのAsync I/O層。
- 重複排除を伴うat-least-once配信。
- ステートフルなワークロードのためのレインボー/カナリーデプロイ。
- 可観測性: エージェントごとのトレース、スーパーステップ監査、リトライカウンター。

## 実装する

`code/main.py` は以下を実装する:

- `CheckpointStore` — thread-idキーを持つSQLiteバックドチェックポイントログ。各スーパーステップが行を追記する。
- `run_with_checkpoint(agent, thread_id)` — 実行途中のクラッシュをシミュレートする; 2番目のワーカーが最後のチェックポイントから再開する。
- `AgentQueue` — 小さなワークキューを持つエージェントごとのIdle / Processing / Responseステートマシン。
- `demo_async_vs_threads()` — asyncioとスレッドを使用して500の同時シミュレートされた「LLM呼び出し」を実行; 壁時計とピークメモリを報告する（近似）。

実行:

```
python3 code/main.py
```

期待される出力: シミュレートされたクラッシュ後にチェックポイント再開が成功する; asyncバージョンが500の同時呼び出しを< 1秒で処理する; スレッドバージョンが数秒かかり、同時ユニットごとに桁違いに多くのメモリを使用する。

## 使ってみる

`outputs/skill-scaling-advisor.md` は耐久実行の選択についてアドバイスする: FastAPI + Postgres、LangGraphランタイム、Temporal、またはカスタム。負荷、状態保持ニーズ、デプロイ頻度によって較正される。

## 成果物を出す

標準的な本番ハードニング:

- **シンプルに始める（Bediのルール）。** FastAPI + Postgresが失敗するのを測定するまで。
- **最適化前にすべてをインストルメント化する。** 実行ごとのレイテンシヒストグラム、ステップごとの時間、リトライカウント、失敗の分類。
- **副作用のためのアウトボックスパターン。** 特に支払いと外部API呼び出し。
- **レインボーデプロイ。** デプロイ中に実行中のエージェント実行を強制終了しない。
- **耐久実行エンジン（Temporal / LangGraph / Restate）を採用するのは**特定の問題に当たった時: 時間単位の人間が関与する待機、クロスリージョン協調、複雑なリトライ/補償ポリシー。
- **I/O層のためのAsync。** スレッドはCPUバウンドのポスト処理のみ。

## 演習

1. `code/main.py` を実行する。チェックポイント再開が機能することを確認; async対スレッドの同時実行の差を測定する。
2. **アウトボックス**テーブルを実装する: すべてのツール呼び出しがまずアウトボックスに書き込み、次に別のゴルーチン/タスクが実行する。ツール呼び出しを2回実行して冪等性を検証する。
3. **レインボーデプロイ**をシミュレートする: 2つの同時ランタイムバージョン; 新しいthread_idの半分をそれぞれにルーティング; 古いバージョンの実行中のスレッドが中断されないことを確認する。
4. LangGraphのランタイムドキュメントを読む（以下にリンク）。ランタイムのどの機能を手作りのFastAPI + Postgresバージョンで複製するのに最も時間がかかるかを特定する。それは採用する理由か、それとも延期できるか？
5. MegaAgent（arXiv:2408.09955）セクション3を読む。2層調整（グループ内 + グループ間管理チャット）は明示的だ。これを2つのキューファミリーを持つメッセージキューにマッピングする方法をスケッチする。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| 耐久実行 | 「プログラム状態を永続化」 | エンジンが各スーパーステップ後に状態を書き込む; クラッシュ回復が決定論的。 |
| スーパーステップ | 「トランザクション境界」 | チェックポイント間の作業単位。LangGraphの用語。 |
| thread_id | 「エージェント実行識別子」 | チェックポイントと再開ロジックをバインドするキー。 |
| 冪等性 | 「再試行しても安全」 | 副作用を繰り返すと1回の試行と同じ結果が生じる。 |
| アウトボックスパターン | 「副作用を切り離す」 | 意図をテーブルに書き込む; 別の実行者が実行して完了とマークする。 |
| At-least-once配信 | 「重複の可能性」 | メッセージキューセマンティクス; 重複排除キーがコンシューマーを実効onceにする。 |
| レインボーデプロイ | 「重複するバージョン」 | 長期実行ワークロード中の複数のランタイムバージョンが同時進行。 |
| Asyncファイバー | 「協調的yielding」 | ユーザーモード同時実行; I/Oバウンド負荷でスレッドより安価。 |
| チェックポイント | 「状態スナップショット」 | スーパーステップ境界でのシリアライズされた状態; 再開のためのキー。 |
