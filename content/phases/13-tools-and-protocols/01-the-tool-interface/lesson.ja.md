# ツールインターフェース — エージェントに構造化I/Oが必要な理由

> 言語モデルはトークンを生成します。プログラムはアクションを実行します。この2つの間にあるギャップを埋めるのがツールインターフェースです。モデルがアクションを要求し、ホストがそれを実行するための契約です。2026年のあらゆるスタック — OpenAI・Anthropic・GeminiのFunction calling、MCPの`tools/call`、A2AのTask Parts — はすべて同じ4ステップのループの異なるエンコーディングです。このレッスンではそのループを定義し、それを動かすための最小限の機構を示します。


## 学習目標

- テキストしか生成できないLLMが、単独では現実世界に対してアクションを取れない理由を説明できる。
- 4ステップのツール呼び出しループ（記述→判断→実行→観察）を図示し、各ステップの担当者を述べられる。
- ツールの説明を3つの要素（名前、JSONスキーマ入力、確定的なエグゼキュータ関数）として記述できる。
- 純粋ツールと副作用ツールを区別し、その区別が安全性において重要な理由を述べられる。

## 問題

LLMは次のトークンに対する確率分布を出力します。これが出力の全てです。「今のベンガルールの天気は？」とチャットモデルに聞くと、もっともらしい文章を書けますが、天気APIを呼び出すことはできません。その文章は偶然正しいか、3日前のデータかもしれません。

このギャップを埋めることがツールインターフェースの目的です。ホストプログラム — エージェントランタイム、Claude Desktop、ChatGPT、Cursor、またはカスタムスクリプト — が呼び出し可能なツールのリストをモデルに提示します。モデルがアクションが必要と判断すると、ツール名と引数を指定した構造化ペイロードを出力します。ホストはそのペイロードを解析し、実際にツールを実行し、結果を返します。モデルがこれ以上の呼び出しが不要と判断するまでループが続きます。

この契約の最初のバージョンは2023年6月にOpenAIの「functions」パラメータとして登場しました。AnthropicはClaude 2.1で`tool_use`ブロックを追加し、Geminiも数ヶ月後に`functionDeclarations`を追加しました。現在すべてのプロバイダが同じ形式を提供しています：JSONスキーマ型のツールリストが入力され、JSONペイロードのツール呼び出しが出力されます。Model Context Protocol（2024年11月）はこの契約を汎用化し、1つのツールレジストリがあらゆるモデルに対応できるようにしました。A2A（2026年4月、v1.0）はエージェント間委任のために同じプリミティブをレイヤーとして追加しました。

4ステップのループはこれらすべての基礎にある不変のものです。Phase 13の残りは全てその詳細化です。

## 概念

### ステップ1：記述

ホストは各ツールを3つのフィールドで宣言します。

- **名前。** 安定した機械可読な識別子。`weather_thing`ではなく`get_weather`。
- **説明。** 1段落の自然言語の概要。「特定の都市の現在の状況をユーザーが尋ねた場合に使用。過去のデータには使用しない。」
- **入力スキーマ。** ツールの引数を記述するJSONスキーマオブジェクト（draft 2020-12）。

モデルはそのリストを受け取ります。現代のプロバイダはプロバイダ固有のテンプレートを使ってこれらの宣言をシステムプロンプトにシリアライズするため、呼び出し側は構造化された形式だけを扱えばよいです。

### ステップ2：判断

ユーザーのメッセージと利用可能なツールを元に、モデルは3つの動作のうち1つを選択します。

1. **テキストで直接回答する。** ツール呼び出しなし。
2. **1つ以上のツールを呼び出す。** 構造化された呼び出しオブジェクトを出力します。`parallel_tool_calls: true`（OpenAIとGeminiではデフォルト、Anthropicではオプトイン）の場合、モデルは1ターンで複数の呼び出しを出力できます。
3. **拒否する。** ストリクトモードの構造化出力では、呼び出しの代わりに型付きの`refusal`ブロックが生成されることがあります。

ツール呼び出しペイロードには3つの安定したフィールドがあります：呼び出しの`id`、ツールの`name`、JSON形式の`arguments`オブジェクト。idは並列呼び出しが順序どおりに返ってこない場合に、後の結果を特定の呼び出しと対応付けるために存在します。

### ステップ3：実行

ホストは呼び出しを受け取り、宣言されたスキーマに対して引数を検証し、エグゼキュータを実行します。無効な引数はモデルがフィールドを誤って生成したか、間違った型を使用したことを意味します — 弱いモデルで非常によくある障害モードです。本番環境のホストは無効な引数に対して3つの対処法のいずれかを行います：即座に失敗してエラーをモデルに通知する、制約付きパーサでJSONを修復する、または検証エラーをプロンプトに含めてモデルを再試行する。

エグゼキュータ自体は通常のコードです。Python、TypeScript、シェルコマンド、データベースクエリ。結果を生成しますが、通常は文字列ですが、任意のJSON値やMCPの構造化コンテンツブロック（テキスト、画像、リソース参照）であることもあります。結果はシリアライズ可能でなければなりません。

### ステップ4：観察

ホストはツールの結果を会話に追加し（一致する`id`を持つ`tool`ロールメッセージとして）、モデルを再起動します。モデルはコンテキスト内にツールの出力を持ち、最終的な回答を生成するか、さらに呼び出しを要求できます。これはモデルが呼び出しを停止するか、ホストがイテレーション数の安全上限に達するまで続きます。

### 信頼の分割

ツールには安全性の観点から重要な2種類があります。

- **純粋。** 読み取り専用、決定論的、副作用なし。`get_weather`、`search_docs`、`get_current_time`。投機的に呼び出しても安全。
- **結果的。** 状態を変更したり、お金を使ったり、ユーザーデータに触れたりする。`send_email`、`delete_file`、`execute_trade`。ゲートが必要。

Metaの2026年「2のルール」によれば、エージェントセキュリティのために1ターンに組み合わせてよいのは「信頼されていない入力、機密データ、結果的なアクション」のうち最大2つです。ツールインターフェースはそのルールを強制する場所です — 呼び出しを拒否、ユーザー確認を要求、またはスコープをエスカレートすることで。全セキュリティチャプターはPhase 13 · 15、エージェントレベルのパーミッションポリシーはPhase 14 · 09を参照してください。

### ループが存在する場所

| コンテキスト | 誰が記述 | 誰が判断 | 誰が実行 |
|---------|---------------|-------------|--------------|
| 単一ターンのFunction calling（OpenAI/Anthropic/Gemini） | アプリ開発者 | LLM | アプリ開発者 |
| MCP | MCPサーバー | LLMがMCPクライアント経由で | MCPサーバー |
| A2A | エージェントカードの公開者 | 呼び出し元エージェント | 呼び出し先エージェント |
| Webブラウザ（Function callingエージェント） | ブラウザ拡張機能 / WebMCP | LLM | ブラウザランタイム |

どこでも同じ4ステップです。列名が変わっても、構造は変わりません。

### なぜモデルにJSONを出力させるだけではダメなのか？

「モデルにJSONで返答させる」というのはFunction calling以前のパターンでした。フロンティアモデルでも約5〜15%の確率で失敗し、小さなモデルではさらに多く失敗します。失敗モードには、括弧の欠落、末尾のカンマ、誤って生成されたフィールド、間違った型などがあります。そのためJSON修復パス、再試行、または制約付きデコーダが必要になります。

ネイティブのFunction callingが優れている理由は3つあります。第一に、プロバイダはモデルを正確な呼び出し形式でエンドツーエンドでトレーニングするため、ストリクトモードでの有効JSON率は98〜99%に向上します。第二に、呼び出しペイロードは自由テキストの中ではなく独自のプロトコルスロットに入るため、ツール呼び出しがユーザーに見える応答に漏れることはありません。第三に、プロバイダは制約付きデコーディングでスキーマ準拠を強制します（OpenAIのストリクトモード、Anthropicの`tool_use`、Geminiの`responseSchema`）。出力は必ず検証に通ります。

Phase 13 · 02では3つのプロバイダAPIを並べて説明します。Phase 13 · 04では構造化出力を深く掘り下げます。

### サーキットブレーカー

ループはモデルが呼び出しを停止するか、ホストが最大ターン数に達したときに終了します。本番環境のホストはこれを5〜20ターンに設定します。それを超えると、ほぼ確実にモデルが抜け出せないループに入っています。Claude Codeのデフォルトは20、OpenAI Assistantsは10、CursorのエージェントモードはのデフォルトはOpenAI。

代替手段 — 無制限のループ — は「エージェントが一夜でAPI呼び出しに400ドル使った」という事後分析として半年ごとに話題になります。上限なしでは出荷しないでください。

Phase 14 · 12ではエラーリカバリとセルフヒーリングを詳しく説明します。Phase 17では本番環境のレート制限を説明します。

### Phase 13の進む方向

- レッスン02〜05はプロバイダレベルのツール呼び出し面を磨きます。
- レッスン06〜14はループをMCPに汎用化します。
- レッスン15〜18はループを悪意あるサーバー、敵対的なユーザー、未認証のリモート認証サーフェスから守ります。
- レッスン19〜22はパターンをエージェント間コラボレーション、可観測性、ルーティング、パッケージングに拡張します。
- レッスン23は全プリミティブを使った完全なエコシステムを出荷します。

残りのレッスンはすべてこの4ステップループの詳細化です。不変のものとして心に留めておいてください。

## 使ってみる

`code/main.py`はLLMを使わずに4ステップのループを実行します。偽の「決定者」関数がユーザーメッセージのパターンマッチングでモデルをシミュレートします。エグゼキュータ、スキーマバリデータ、観察ステップのハーネスは本物です。これを実行して、出力可能な中間状態で完全なリクエスト/レスポンスの振る舞いを確認してから、後のレッスンで偽の決定者を実際のプロバイダに置き換えてください。

確認すべき点：

- ツールレジストリはツールごとに3つのフィールドを持ちます：名前、説明、スキーマ、エグゼキュータ参照。
- バリデータは標準ライブラリのみで書かれた最小限のJSONスキーマサブセット（型、required、enum、min/max）です。Phase 13 · 04でより完全なものが提供されます。
- ループはイテレーション数を5に制限します。本番環境のエージェントにはまさにこの種のサーキットブレーカーが必要です。

## 成果物を出す

このレッスンは`outputs/skill-tool-interface-reviewer.md`を生成します。ドラフトのツール定義（名前＋説明＋スキーマ＋エグゼキュータの概要）を受け取り、そのスキルはループ適合性を監査します：名前が機械安定か、説明が完全な使用要件か、スキーマがJSON Schema 2020-12を正しく使用しているか、純粋/結果的の分類が明示されているか。

## 演習

1. `code/main.py`に`get_stock_price(ticker)`という4番目のツールを追加します。説明を「ユーザーがティッカーで現在の株価を尋ねた場合に使用。過去の価格や市場サマリーには使用しない。」と書きます。ハーネスを実行し、ティッカーを言及するクエリが新しいツールにルーティングされることを確認します。

2. スキーマバリデータを壊してみます。`arguments`オブジェクトに必須フィールドが欠けている呼び出しを渡して、ホストが実行前に拒否することを確認します。次に、未知のフィールドを含む呼び出しを渡します。ホストは拒否すべきか無視すべきか？安全性の観点から選択を正当化してください。

3. ハーネス内の各ツールを純粋か結果的かに分類します。それが必要なレジストリエントリに`consequential: true`フラグを追加し、結果的なツールが選択されるたびに「ユーザーに確認する」という行を出力するようにループを変更します。これが全ての本番ホストに必要な確認ゲートの形です。

4. 上記のプロバイダ列表を使って、お気に入りのクライアント（Claude Desktop、Cursor、ChatGPT、またはカスタムスタック）について紙に4ステップのループを書きます。Phase 13 · 06のMCP固有のバリアントと相互参照してください。

5. OpenAIのFunction callingガイドを最初から最後まで読みます。ここで示した4ステップのループにはないが、リクエストに存在する1つのフィールドを特定します。それが何を追加するか、そして本質的ではなく便利なものである理由を説明してください。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| ツール | 「モデルが呼び出せるもの」 | 名前＋JSONスキーマ型入力＋エグゼキュータ関数の3つ組 |
| Function calling | 「ネイティブツール使用」 | 散文の代わりに構造化されたツール呼び出しを出力するためのプロバイダレベルAPIサポート |
| ツール呼び出し | 「モデルのアクション要求」 | モデルが出力する`id`、`name`、`arguments`を持つJSONペイロード |
| ツール結果 | 「ツールが返したもの」 | 一致するidを持つ`tool`ロールメッセージにラップされたエグゼキュータの出力 |
| 並列ツール呼び出し | 「同時に複数呼び出す」 | 1ターンのモデルで複数の呼び出しオブジェクト、独立していてidで順序付け可能 |
| ストリクトモード | 「JSONを保証」 | モデルの出力を宣言されたスキーマに対して検証するように制約するデコーディング |
| 純粋ツール | 「読み取り専用ツール」 | 副作用なし、再実行安全 |
| 結果的ツール | 「アクションツール」 | 外部状態を変更する、ゲート/監査/ユーザー確認が必要 |
| 4ステップループ | 「ツール呼び出しサイクル」 | 記述→判断→実行→観察 |
| ホスト | 「エージェントランタイム」 | ツールレジストリを保持し、モデルを呼び出し、エグゼキュータを実行するプログラム |
