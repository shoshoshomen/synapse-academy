# A2A — エージェント間プロトコル

> MCPはエージェント対ツールだ。A2A（Agent2Agent）はエージェント対エージェント — 異なるフレームワークで構築された不透明なエージェントが協調できるオープンプロトコルだ。2025年4月にGoogleがリリースし、2025年6月にLinux Foundationに寄贈し、AWS、Cisco、Microsoft、Salesforce、SAP、ServiceNowを含む150以上のサポーター企業と共に2026年4月にv1.0に到達した。IBMのACPを吸収し、AP2の支払い拡張を追加した。このレッスンではエージェントカード、タスクライフサイクル、2つのトランスポートバインディングを説明する。


## 学習目標

- エージェント対ツール（MCP）とエージェント対エージェント（A2A）のユースケースを区別できる。
- スキルとエンドポイントメタデータを含むエージェントカードを `/.well-known/agent.json` に公開できる。
- タスクライフサイクルを把握できる（submitted → working → input-required → completed / failed / canceled / rejected）。
- テキスト、ファイル、データのPartsを含むメッセージとアーティファクトを出力として使用できる。

## 問題背景

カスタマーサービスエージェントがレポート作成を専門のライターエージェントに委任する必要がある。A2A以前の選択肢：

- カスタムREST API。機能するが、すべてのペアが個別の実装になる。
- 共有コードベース。2つのエージェントが同じフレームワークで動作する必要がある。
- MCP。合わない：MCPはツールを呼び出すためのものであり、2つのエージェントが各エージェントの不透明な内部推論を維持しながら協調するためではない。

A2Aがそのギャップを埋める。あるエージェントが別のエージェントにタスクを送信し、ライフサイクル、メッセージ、アーティファクトを持つインタラクションとしてモデル化する。呼び出されたエージェントの内部状態は不透明のまま — 呼び出し元はタスクの状態遷移と最終的な出力だけを見る。

A2Aは「フレームワークをまたいでエージェントが互いに話す」プロトコルだ。MCPを置き換えない；2つは補完的だ。

## コンセプト

### エージェントカード

すべてのA2A準拠エージェントが `/.well-known/agent.json` にカードを公開する：

```json
{
  "schemaVersion": "1.0",
  "name": "research-agent",
  "description": "学術論文を要約して引用を作成する。",
  "url": "https://research.example.com/a2a",
  "version": "1.2.0",
  "skills": [
    {
      "id": "summarize_paper",
      "name": "論文を要約する",
      "description": "論文のPDFを読み、3段落の要約を生成する。",
      "inputModes": ["text", "file"],
      "outputModes": ["text", "artifact"]
    }
  ],
  "capabilities": {"streaming": true, "pushNotifications": true}
}
```

発見はURLベース：カードを取得し、A2AエンドポイントのURLを確認し、スキルを列挙する。

### 署名付きエージェントカード（AP2）

AP2拡張（2025年9月）がエージェントカードに暗号署名を追加する。発行者がJWTでカードに署名し、消費者が検証する。なりすましを防ぐ。

### タスクライフサイクル

```
submitted -> working -> completed | failed | canceled | rejected
             -> input_required -> working (メッセージ経由のループ)
```

クライアントは `tasks/send` で開始する。呼び出されたエージェントが状態を遷移し、クライアントはSSE経由で状態更新をサブスクライブするかポーリングする。

### メッセージとパーツ

メッセージは1つ以上のPartsを含む：

- `text` — プレーンコンテンツ。
- `file` — mimeTypeを持つbase64ブロブ。
- `data` — 呼び出されたエージェントの構造化入力のための型付きJSONペイロード。

例：

```json
{
  "role": "user",
  "parts": [
    {"type": "text", "text": "この論文を要約してください。"},
    {"type": "file", "file": {"name": "paper.pdf", "mimeType": "application/pdf", "bytes": "..."}},
    {"type": "data", "data": {"targetLength": "3段落"}}
  ]
}
```

### アーティファクト

出力はアーティファクトであり、生の文字列ではない。アーティファクトは名前付きの型付き出力だ：

```json
{
  "name": "summary",
  "parts": [{"type": "text", "text": "..."}],
  "mimeType": "text/markdown"
}
```

アーティファクトはチャンクとしてストリーミングできる。呼び出し元が蓄積する。

### 2つのトランスポートバインディング

1. **JSON-RPC over HTTP。** `/a2a` エンドポイント、リクエストにはPOST、ストリーミングにはオプションのSSE。デフォルトのバインディング。
2. **gRPC。** gRPCがネイティブなエンタープライズ環境向け。

両方のバインディングが同じ論理的なメッセージ形状を運ぶ。

### 不透明性の保持

重要な設計原則：呼び出されたエージェントの内部状態は不透明だ。呼び出し元はタスクの状態とアーティファクトを見る。呼び出されたエージェントの思考の連鎖、ツール呼び出し、サブエージェントへの委任 — すべて見えない。これはツール呼び出しが透明なMCPとは異なる。

根拠：A2Aはライバルが内部を明かさずに協調できるようにする。「このカスタマーサービスエージェントを呼び出す」ことができ、呼び出し元がそのエージェントがどのようにサービスを実装しているかを知らなくてよい。

### MCPとの関係

| 次元 | MCP | A2A |
|-----------|-----|-----|
| ユースケース | エージェント対ツール | エージェント対エージェント |
| 不透明性 | 透明なツール呼び出し | 不透明な内部推論 |
| 典型的な呼び出し元 | エージェントランタイム | 別のエージェント |
| 状態 | ツール呼び出しの結果 | ライフサイクルを持つタスク |
| 認可 | OAuth 2.1（フェーズ13・16） | JWT署名付きエージェントカード（AP2） |
| トランスポート | stdio / Streamable HTTP | JSON-RPC over HTTP / gRPC |

特定のツールを呼び出したいときはMCPを使う。タスク全体を別のエージェントに委任したいときはA2Aを使う。多くの本番システムが両方を使用している：エージェントがツール層にMCPを使い、協調層にA2Aを使う。

## 使ってみる

`code/main.py` は最小限のA2Aハーネスを実装している：リサーチエージェントがカードを公開し、ライターエージェントがPDFとテキスト命令を含むPartsを持つ `tasks/send` を受け取り、working → input_required → working → completedと遷移し、テキストアーティファクトを返す。すべてstdlib；メッセージ形状に集中するためにインメモリトランスポートを使用。

確認すべきポイント：

- エージェントカードのJSON形状。
- タスクIDの割り当てと状態遷移。
- 混合型のPartsを持つメッセージ。
- タスクの途中でのinput-requiredブランチ。
- 完了時のアーティファクト返却。

## 成果物を出す

このレッスンでは `outputs/skill-a2a-agent-spec.md` を生成する。他のエージェントから呼び出し可能にすべき新しいエージェントが与えられると、このスキルはエージェントカードのJSON、スキルスキーマ、エンドポイントの設計図を生成する。

## 演習

1. `code/main.py` を実行する。呼び出されたエージェントが明確化を要求するinput-requiredの一時停止を含む完全なタスクライフサイクルをトレースする。

2. 署名付きエージェントカードを追加する。カードの正規JSONのHMACで署名する。バリデーターを書き、変更されたカードに対して失敗することを確認する。

3. タスクストリーミングを実装する：ライターエージェントがSSEで3つの増分アーティファクトチャンクを出力し、呼び出し元がそれらを蓄積する。

4. MCPサーバーをラップするA2Aエージェントを設計する。各MCPツールをA2Aスキルにマッピングする。トレードオフを確認する — どんな不透明性が失われるか？

5. A2A v1.0の発表を読み、2026年4月時点でどのフレームワークもまだ実装していない機能を1つ特定する。（ヒント：マルチホップのタスク委任に関係する。）

## キーワード

| 用語 | よく言われる表現 | 実際の意味 |
|------|----------------|------------------------|
| A2A | "エージェント間プロトコル" | 不透明なエージェント協調のためのオープンプロトコル |
| エージェントカード | "`.well-known/agent.json`" | エージェントのスキルとエンドポイントを記述した公開メタデータ |
| スキル | "呼び出し可能な単位" | エージェントがサポートする名前付き操作（MCPツールのアナログ） |
| タスク | "委任の単位" | ライフサイクルと最終アーティファクトを持つ作業アイテム |
| メッセージ | "タスク入力" | Parts（テキスト、ファイル、データ）を含む |
| Part | "型付きチャンク" | メッセージの `text` / `file` / `data` 要素 |
| アーティファクト | "タスク出力" | 完了時に返される名前付きの型付き出力 |
| AP2 | "エージェント決済プロトコル" | 信頼と決済のための署名付きエージェントカード拡張 |
| 不透明性 | "ブラックボックス協調" | 呼び出されたエージェントの内部が呼び出し元から隠される |
| Input-required | "タスクの一時停止" | エージェントが追加情報を必要とするライフサイクル状態 |
