# MCPゲートウェイとレジストリ — エンタープライズコントロールプレーン

> エンタープライズは開発者が勝手にランダムなMCPサーバーをインストールすることを許可できない。ゲートウェイは認証、RBAC、監査、レート制限、キャッシング、ツールポイズニング検出を一元化し、マージされたツールサーフェスを単一のMCPエンドポイントとして公開する。公式MCPレジストリ（Anthropic + GitHub + PulseMCP + Microsoft、ネームスペース検証済み）が正規のアップストリームだ。このレッスンではゲートウェイがどこに位置するか、最小限の実装を説明し、2026年のベンダー状況を概観する。


## 学習目標

- MCPゲートウェイの位置を説明できる（MCPクライアントと複数のバックエンドMCPサーバーの間）。
- 5つのゲートウェイの責務を実装できる：認証、RBAC、監査、レート制限、ポリシー。
- ゲートウェイ層でピン留めされたツールハッシュマニフェストを強制できる。
- 公式MCPレジストリとメタレジストリ（Glama、MCPMarket、MCP.so、Smithery、LobeHub）を区別できる。

## 問題背景

Fortune 500企業には30の承認済みMCPサーバー、5000人の開発者、コンプライアンスと監査の要件、そして集中管理されたポリシーを望むセキュリティチームがある。すべての開発者がIDEに任意のサーバーをインストールすることは許容できない。

ゲートウェイパターン：

1. ゲートウェイが開発者が接続する単一のStreamable HTTPエンドポイントとして動作する。
2. ゲートウェイが各バックエンドMCPサーバーの認証情報を保持する。
3. すべての開発者リクエストはゲートウェイ独自のOAuthで認証とスコープ付けがされる。
4. ゲートウェイはポリシーを適用しながら呼び出しをバックエンドサーバーにルーティングする。
5. すべての呼び出しが監査のためにログに記録される。

Cloudflare MCP Portals、Kong AI Gateway、IBM ContextForge、MintMCP、TrueFoundry、Envoy AI Gateway — これらはすべて2025〜2026年にゲートウェイまたはゲートウェイ機能を出荷した。

一方、公式MCPレジストリが正規のアップストリームとして立ち上がった：Anthropic、GitHub、PulseMCP、Microsoftが管理するキュレーションされたネームスペース検証済みの逆引きDNS命名サーバー。メタレジストリ（Glama、MCPMarket、MCP.so、Smithery、LobeHub）は複数のソースからサーバーを集約する。

## コンセプト

### 5つのゲートウェイの責務

1. **認証。** 開発者を識別するOAuth 2.1；ユーザーロールにマッピングする。
2. **RBAC。** ユーザーごとのポリシー：どのサーバー、どのツール、どのスコープ。
3. **監査。** すべての呼び出しを誰が、何を、いつ、結果を含めてログに記録する。
4. **レート制限。** 悪用を防ぐためのユーザーごと / ツールごと / サーバーごとの上限。
5. **ポリシー。** ポイズニングされた説明を拒否し、Rule of Twoを強制し、PIIを編集する。

### 単一エンドポイントとしてのゲートウェイ

開発者にとって、ゲートウェイは1つのMCPサーバーのように見える。内部ではNつのバックエンドにルーティングする。セッションID（フェーズ13・09）は境界で書き換えられる。

### クレデンシャルボールティング

開発者はバックエンドのトークンを見ない。ゲートウェイがそれらを保持する（またはそうするアイデンティティプロバイダーにプロキシする）。ゲートウェイで `notes:read` を持つ開発者は、ゲートウェイ独自のバックエンド認証情報でノートMCPサーバーに推移的にアクセスできるが、推移的アクセスをバインドするポリシーの下でのみだ。

### ゲートウェイでのツールハッシュピン留め

ゲートウェイは承認済みのツール説明（SHA256ハッシュ）のマニフェストを保持する。発見時に各バックエンドの `tools/list` を取得し、マニフェストとハッシュを比較し、説明が変更されたツールを削除する。これはフェーズ13・15のラグプル防御をゲートウェイ層で集中的に適用したものだ。

### コードとしてのポリシー

高度なゲートウェイはOPA/Rego、Kyverno、Styraでポリシーを表現する。「ユーザー `alice` は組織 `acme` のリポジトリのみで `github.open_pr` を呼べる」などのルールを宣言的にエンコードする。シンプルなゲートウェイは手書きのPythonを使う。両方の形が有効だ。

### セッション対応ルーティング

ユーザーのセッションにサーバーの組み合わせが含まれる場合、ゲートウェイは多重化する：開発者の単一MCPセッションはサーバーごとにNつのバックエンドセッションを保持する。どのバックエンドからの通知もゲートウェイを通じて開発者のセッションにルーティングされる。

### ネームスペースのマージ

ゲートウェイはすべてのバックエンドからのツールネームスペースをマージし、通常は衝突時にプレフィックスを付ける。`github.open_pr`、`notes.search`。これでルーティングが明確になる。

### レジストリ

- **公式MCPレジストリ（`registry.modelcontextprotocol.io`）。** Anthropic、GitHub、PulseMCP、Microsoftの管理下で立ち上がった。ネームスペース検証済み（逆引きDNS：`io.github.user/server`）。基本的な品質のための事前フィルタリングあり。
- **Glama。** 多くのソースを集約する検索中心のメタレジストリ。
- **MCPMarket。** ベンダーリスト付きの商業向けディレクトリ。
- **MCP.so。** コミュニティディレクトリ；オープンな投稿。
- **Smithery。** パッケージマネージャースタイルのインストールフロー。
- **LobeHub。** LobeHubアプリに統合されたUIのレジストリ。

エンタープライズゲートウェイはデフォルトで公式レジストリから取得し、管理者がキュレーションしたメタレジストリからの追加を許可し、ピン留めされていないものを拒否する。

### 逆引きDNS命名

公式レジストリはパブリックサーバーに逆引きDNS名を義務付ける：`io.github.alice/notes`。ネームスペースがスクワッティングを防ぎ、信頼の委任をより明確にする。

### ベンダー調査、2026年4月

## 使ってみる

`code/main.py` は約150行の最小限のゲートウェイを提供する：偽のBearerトークンでユーザーを認証し、ユーザーごとのRBACポリシーを保持し、リクエストを2つのバックエンドMCPサーバーにルーティングし、すべての呼び出しを監査ログに書き込み、レート制限を適用し、説明のハッシュがピン留めされたマニフェストと一致しないバックエンドのツールを拒否する。

確認すべきポイント：

- `RBAC` 辞書はユーザーIDをキーにし、許可された `server_tool` エントリを持つ。
- `AUDIT_LOG` は追記専用のイベントリスト。
- レート制限はユーザーごとのトークンバケットを使用。
- ピン留めされたマニフェストは `server::tool -> hash` の辞書。

## 成果物を出す

このレッスンでは `outputs/skill-gateway-bootstrap.md` を生成する。エンタープライズのMCPプラン（ユーザー、バックエンド、コンプライアンス）が与えられると、このスキルはゲートウェイ設定仕様を生成する。

## 演習

1. `code/main.py` を実行する。許可されたユーザーとして呼び出しを行い、次に許可されていないユーザーとして、最後にレート制限を超えるバーストを行う。3つのフローすべてを確認する。

2. 結果をクライアントに返す前にPIIを編集するポリシーを追加する。SSN形状の文字列に対してシンプルな正規表現パスを使用し、ギャップ（メール、電話番号）に注意する。

3. 監査ログをOpenTelemetry GenAIスパンを出力するように拡張する。フェーズ13・20で正確な属性を説明する。

4. 5つのバックエンド（ノート、GitHub、Postgres、Jira、Slack）を持つ50人の開発者チームのRBACポリシーを設計する。各バックエンドで誰が読み取り専用になるか？誰が書き込みを持つか？

5. Cloudflareのエンタープライズ向けMCP投稿を最初から最後まで読む。Cloudflareが出荷しているがこのstdlibゲートウェイが持っていない機能を1つ特定する。

## キーワード

| 用語 | よく言われる表現 | 実際の意味 |
|------|----------------|------------------------|
| ゲートウェイ | "MCPプロキシ" | クライアントとバックエンドの間を集中管理するサーバー |
| クレデンシャルボールティング | "バックエンドトークンはサーバー側に保持" | 開発者はアップストリームのトークンを見ない |
| セッション対応ルーティング | "マルチバックエンドセッション" | ゲートウェイが開発者セッションごとにNつのバックエンドセッションを多重化 |
| ツールハッシュピン留め | "承認済みマニフェスト" | すべての承認済みツール説明のSHA256；ラグプルを集中管理でブロック |
| RBAC | "ユーザーごとのポリシー" | ツールとサーバーのロールベースのアクセス制御 |
| コードとしてのポリシー | "宣言的ルール" | ゲートウェイで強制されるOPA/Rego、Kyverno、Styraポリシー |
| 監査ログ | "誰が、何を、いつ" | コンプライアンスのための追記専用イベントログ |
| レート制限 | "ユーザーごとのトークンバケット" | 悪用を防ぐための1分あたりの上限 |
| 公式MCPレジストリ | "正規のアップストリーム" | `registry.modelcontextprotocol.io`、ネームスペース検証済み |
| 逆引きDNS命名 | "レジストリネームスペース" | `io.github.user/server` の慣例 |
