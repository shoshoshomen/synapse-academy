# MCPトランスポート — stdio対Streamable HTTP対SSE移行

> stdioはローカルでのみ機能し、それ以外では使えません。Streamable HTTP（2025-03-26）がリモート標準です。古いHTTP+SSEトランスポートは廃止され、2026年半ばに削除されます。間違ったトランスポートを選ぶと移行コストがかかりますが、正しいものを選べばセッション継続性とDNSリバインディング保護を備えたリモートホスト可能なMCPサーバーが手に入ります。


## 学習目標

- デプロイメント形状（ローカル対リモート、シングルプロセス対フリート）に基づいてstdioとStreamable HTTPを選べる。
- Streamable HTTPシングルエンドポイントパターンを実装できる：リクエストはPOST、セッションストリームはGET。
- `Origin`検証とセッションIDセマンティクスを強制してDNSリバインディングを防御できる。
- 廃止期限（2026年半ば）までにレガシーHTTP+SSEサーバーをStreamable HTTPに移行できる。

## 問題

最初のMCPリモートトランスポート（2024年11月）はHTTP+SSEでした：クライアントのPOST用の1つのエンドポイントとサーバーからクライアントへのストリーム用のサーバー送信イベントチャンネル。機能しましたが、扱いにくい部分もありました：セッションごとに2つのエンドポイント、一部のCDNでのキャッシュ破損、一部のWAFが積極的に終了する長時間のSSE接続への強い依存。

2025-03-26仕様がStreamable HTTPに置き換えました：1つのエンドポイント、クライアントリクエストはPOST、セッションストリームの確立はGET、両方で`Mcp-Session-Id`ヘッダーを共有します。それ以来構築または移行されたすべてのサーバーがStreamable HTTPを使います。古いSSEモードは廃止されています — AtlassianのRovoは2026年6月30日に削除；Keboola は2026年4月1日；残りのほとんどのエンタープライズサーバーは2026年末までに。

そしてstdioは依然としてローカルサーバーに重要です。Claude Desktop、VS Code、すべてのIDE形状のクライアントはstdio経由でサーバーを起動します。正しいメンタルモデル：stdioは「このマシン」用、Streamable HTTPは「ネットワーク越し」用。クロスオーバーはなし。

## 概念

### stdio

- 子プロセストランスポート。クライアントがサーバーを起動し、stdin/stdoutで通信。
- 1行に1つのJSONオブジェクト。改行区切り。
- セッションIDなし；プロセスのアイデンティティがセッション。
- 認証不要（子プロセスは親の信頼境界を継承する）。
- リモートサーバーには使用しない — トンネリングにはSSHかsocatが必要になり、それならStreamable HTTPを使う方が良い。

### Streamable HTTP

単一エンドポイント`/mcp`（または任意のパス）。3つのHTTPメソッドをサポート：

- **POST /mcp。** クライアントがJSON-RPCメッセージを送ります。サーバーは単一のJSONレスポンス、またはSSEストリームの1つ以上のレスポンスで返答します（バッチレスポンスとそのリクエストに関連する通知に役立つ）。
- **GET /mcp。** クライアントが長時間のSSEチャンネルを開きます。サーバーはサーバーからクライアントへのリクエスト（sampling、通知、elicitation）のためにこれを使います。
- **DELETE /mcp。** クライアントがセッションを明示的に終了します。

セッションはサーバーが最初のレスポンスで設定し、クライアントがその後のすべてのリクエストで繰り返す`Mcp-Session-Id`ヘッダーで識別されます。セッションIDは暗号的にランダムでなければなりません（128ビット以上）；クライアントが選択したIDは安全上の理由で拒否されます。

### シングルエンドポイント対2エンドポイント

古い仕様の2エンドポイントモードは2026年でも呼び出せます — 仕様は「レガシー互換」と宣言しています。しかし、すべての新しいサーバーはシングルエンドポイントにすべきです。公式SDKはシングルエンドポイントを出力します；レガシーモードは移行されていないリモートと通信する場合のみ使います。

### `Origin`検証とDNSリバインディング

ブラウザは（今日は）MCPクライアントではありませんが、攻撃者はブラウザを誘って`localhost:1234/mcp`（ユーザーのローカルMCPサーバーがリスンする場所）にPOSTするウェブページを作成できます。サーバーが`Origin`を確認しない場合、`Origin: http://evil.com`はクロスオリジンで有効なため、ブラウザの同一オリジンポリシーは助けになりません。

2025-11-25仕様はサーバーが`Origin`が許可リストにないリクエストを拒否することを要求します。許可リストは通常MCPクライアントホスト（`https://claude.ai`、`vscode-webview://*`）とローカルUIのためのlocalhostバリアントを含みます。

### セッションIDライフサイクル

1. クライアントは`Mcp-Session-Id`なしで最初のリクエストを送ります。
2. サーバーはランダムなIDを割り当て、レスポンスヘッダーに`Mcp-Session-Id`を設定します。
3. クライアントはそのヘッダーを以降のすべてのリクエストとストリームの`GET /mcp`で繰り返します。
4. セッションはサーバーによって取り消すことができます；クライアントは次のリクエストで404を確認して再初期化しなければなりません。
5. クライアントはクリーンシャットダウンのためにセッションを明示的にDELETEできます。

### キープアライブと再接続

SSE接続は切断されます。クライアントは同じ`Mcp-Session-Id`で再GETすることで再確立します。サーバーは停止中に見逃したイベントをキューに入れ（合理的なウィンドウまで）、クライアントが繰り返す`last-event-id`ヘッダーでリプレイしなければなりません。

Phase 13 · 13では、完全なセッション再接続でも長時間実行される作業が生存できるTasksを説明します。

### 後方互換性プローブ

新旧両方のサーバーをサポートしたいクライアント：

1. `/mcp`にPOSTする。
2. レスポンスが`200 OK`とJSONまたはSSEなら、これはStreamable HTTP。
3. レスポンスが`200 OK`と`Content-Type: text/event-stream`、かつセカンダリエンドポイントを指す`Location`ヘッダーがあれば、これはレガシーHTTP+SSE；`Location`に従います。

### Cloudflare、ngrok、ホスティング

2026年の本番リモートMCPサーバーはCloudflare Workers（MCP Agents SDKあり）、Vercel Functions、またはコンテナ化されたNode/Pythonで動きます。重要：ホスティングはSSE GETのために長時間のHTTP接続をサポートしなければなりません。Vercelの無料層は10秒の上限があり、不適切です。Cloudflare Workersは無期限のストリームをサポートします。

### ゲートウェイの構成

複数のMCPサーバーをゲートウェイ（Phase 13 · 17）でフロントにする場合、ゲートウェイはセッションIDを書き換えてアップストリームを多重化する単一のStreamable HTTPエンドポイントです。ツールはゲートウェイレイヤーでマージされます；クライアントは単一の論理サーバーを見ます。

### トランスポート障害モード

- **stdio SIGPIPE。** 書き込み中の子プロセス死亡でSIGPIPEが発生；サーバーはクリーンに終了すべきです。クライアントはEOFを検出してセッションを死んだものとしてマークすべきです。
- **HTTP 502 / 504。** Cloudflare、nginx、および他のプロキシがアップストリーム障害でこれらを出力します。Streamable HTTPクライアントは短いバックオフの後に1回再試行すべきです。
- **SSE接続の切断。** TCP RST、プロキシタイムアウト、またはクライアントのネットワーク変更がストリームを閉じます。クライアントは`Mcp-Session-Id`とオプションの`last-event-id`で再接続して再開します。
- **セッションの取り消し。** サーバーがセッションIDを無効化；クライアントは次のリクエストで404を確認します。クライアントは再ハンドシェイクしなければなりません。
- **クロックスキュー。** クライアントのリソースTTL計算がサーバーから乖離します。クライアントはサーバーのタイムスタンプを権威として扱うべきです。

### Streamable HTTPをバイパスすべき場合

一部のエンタープライズは自社ネットワーク内でgRPCまたはメッセージキュートランスポートの背後にMCPサーバーをデプロイします。これは非標準です — MCPの仕様はこれらを正式に定義していません。ゲートウェイはMCPクライアントにStreamable HTTPサーフェスを公開しながら内部的にgRPCを使うことができます。外部サーフェスを仕様準拠に保ちます；ゲートウェイが変換を所有します。

## 使ってみる

`code/main.py`は`http.server`（標準ライブラリ）を使って最小限のStreamable HTTPエンドポイントを実装します。`/mcp`でPOST、GET、DELETEを処理し、最初のレスポンスで`Mcp-Session-Id`を設定し、`Origin`を検証し、許可リストにないオリジンのリクエストを拒否します。ハンドラはLesson 07のノートサーバーのディスパッチロジックを再利用します。

確認すべき点：

- POSTハンドラはJSON-RPCボディを読み取り、ディスパッチし、JSONレスポンスを書き込みます（単一レスポンスバリアント；SSEバリアントは構造的に類似）。
- `Origin`チェックはデフォルトの`http://evil.example`プローブを拒否しますが、`http://localhost`を受け入れます。
- セッションIDはランダムな128ビットの16進文字列；サーバーはメモリ内にセッションごとの状態を保持します。

## 成果物を出す

このレッスンは`outputs/skill-mcp-transport-migrator.md`を生成します。HTTP+SSE（レガシー）MCPサーバーを受け取り、セッションID継続性、Origin確認、後方互換プローブサポートを含むStreamable HTTPへの移行計画を生成します。

## 演習

1. `code/main.py`を実行します。`curl`から`initialize`をPOSTして`Mcp-Session-Id`レスポンスヘッダーを観察します。ヘッダーを繰り返した2番目のリクエストをPOSTしてセッション継続性を確認します。

2. SSEストリームを開くGETハンドラを追加します。5秒ごとに`notifications/progress`イベントを1つ送ります。同じセッションIDで再GETして再接続し、サーバーがそれを受け入れることを確認します。

3. `last-event-id`リプレイロジックを実装します。再接続時に、そのIDから生成されたイベントをリプレイします。

4. `Origin`検証を拡張してワイルドカードパターン（`https://*.example.com`）をサポートし、`https://app.example.com`を受け入れるが`https://evil.example.com.attacker.net`を拒否することを確認します。

5. 公式レジストリからレガシーHTTP+SSEサーバーを取り（いくつかあります）、移行をスケッチします：エンドポイント処理、セッションID生成、ヘッダーセマンティクスで何が変わりますか。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| stdioトランスポート | 「ローカル子プロセス」 | stdin/stdout経由のJSON-RPC、改行区切り |
| Streamable HTTP | 「リモートトランスポート」 | シングルエンドポイントのPOST + GET + オプションSSE、2025-03-26仕様 |
| HTTP+SSE | 「レガシー」 | 2026年半ばに削除される2エンドポイントモデル |
| `Mcp-Session-Id` | 「セッションヘッダー」 | サーバーが割り当てるランダムIDで以降のリクエストで繰り返す |
| `Origin`許可リスト | 「DNSリバインディング防御」 | Originが承認されていないリクエストを拒否 |
| シングルエンドポイント | 「1つのURL」 | `/mcp`がすべてのセッション操作のPOST / GET / DELETEを処理 |
| `last-event-id` | 「SSEリプレイ」 | 切断されたストリームをイベントを見逃さずに再開するために使うヘッダー |
| 後方互換プローブ | 「旧対新の検出」 | トランスポートを自動選択するクライアントのレスポンス形状確認 |
| 長時間HTTP | 「SSEストリーミング」 | サーバーが1つのTCP接続で分/時間単位でイベントをプッシュ |
| セッションの取り消し | 「再初期化の強制」 | サーバーがセッションIDを無効化；クライアントは再ハンドシェイクしなければならない |
