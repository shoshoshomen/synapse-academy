# 構造化出力 — JSON Schema、Pydantic、Zod、制約付きデコーディング

> 「モデルにJSONを返すよう丁寧に頼む」方法はフロンティアモデルでも5〜15%の確率で失敗します。構造化出力は制約付きデコーディングでそのギャップを閉じます：モデルはスキーマに違反するトークンを文字通り出力できないようにされます。OpenAIのストリクトモード、Anthropicのスキーマ型ツール使用、Geminiの`responseSchema`、Pydantic AIの`output_type`、Zodの`.parse`は同じ考えの5つの表面形式です。このレッスンでは、あらゆる本番抽出パイプラインで使用するスキーマバリデータとストリクトモードの契約を構築します。


## 学習目標

- 適切な制約（enum、min/max、required、pattern）を使って抽出ターゲットのJSON Schema 2020-12を記述できる。
- ストリクトモードと制約付きデコーディングが「生成後に検証する」とは異なる保証を与える理由を説明できる。
- 3つの失敗モード（パースエラー、スキーマ違反、モデルの拒否）を区別できる。
- 型付き修復と型付き拒否処理を持つ抽出パイプラインを出荷できる。

## 問題

発注書メールを読むエージェントは自由テキストを`{customer, line_items, total_usd}`に変換する必要があります。3つのアプローチを示します。

**アプローチ1：JSONを促す。** 「customer、line_items、total_usdフィールドを持つJSONで返答せよ。」フロンティアモデルで85〜95%の確率で機能します。6つの方法で失敗します：括弧の欠落、末尾のカンマ、間違った型、誤って生成されたフィールド、トークン制限での切り捨て、「こちらがJSONです：」のような漏れた散文。

**アプローチ2：生成後に検証。** 自由に生成し、パースし、スキーマに対して検証し、失敗したら再試行します。信頼性は高いですが高コスト — 毎回の再試行でコストが発生し、切り捨てバグは1回の発生ごとに追加のターンを消費します。

**アプローチ3：制約付きデコーディング。** プロバイダがデコード時にスキーマを強制します。無効なトークンはサンプリング分布からマスクされます。出力はパースが保証され、検証が保証されます。失敗は1つのモードに絞られます：拒否（モデルが入力がスキーマに合わないと判断）。

2026年のすべてのフロンティアプロバイダはアプローチ3の何らかの形を提供します。

- **OpenAI。** `response_format: {type: "json_schema", strict: true}`に加えて、モデルが拒否する場合はレスポンスに`refusal`。
- **Anthropic。** `tool_use`入力のスキーマ強制；`stop_reason: "refusal"`は存在しませんが、ツール呼び出しのない`end_turn`がシグナルです。
- **Gemini。** リクエストレベルの`responseSchema`；2026年のGeminiは選択された型に対してトークンレベルの文法制約を提供します。
- **Pydantic AI。** `output_type=InvoiceModel`は`InvoiceModel`に型付けされた構造化`RunResult`を出力します。
- **Zod（TypeScript）。** プロバイダ出力をZodスキーマに対して検証するランタイムパーサ；OpenAIの`beta.chat.completions.parse`と組み合わせます。

共通スレッド：スキーマを一度宣言し、エンドツーエンドで強制します。

## 概念

### JSON Schema 2020-12 — 共通言語

すべてのプロバイダがJSON Schema 2020-12を受け入れます。最もよく使う構造：

- `type`：`object`、`array`、`string`、`number`、`integer`、`boolean`、`null`のいずれか。
- `properties`：フィールド名からサブスキーマへのマップ。
- `required`：存在しなければならないフィールド名のリスト。
- `enum`：許可される値の閉じた集合。
- `minimum` / `maximum`（数値）、`minLength` / `maxLength` / `pattern`（文字列）。
- `items`：すべての配列要素に適用されるサブスキーマ。
- `additionalProperties`：`false`は余分なフィールドを禁止（モードによってデフォルトが異なる）。

OpenAIのストリクトモードは3つの要件を追加します：すべてのプロパティが`required`に列挙されていること、あらゆる場所で`additionalProperties: false`、解決されていない`$ref`なし。これらに違反すると、APIはリクエスト時に400を返します。

### Pydantic、Pythonバインディング

Pydantic v2はデータクラス形式のモデルから`model_json_schema()`でJSON Schemaを生成します。Pydantic AIはこれをラップするため、次のように書けます：

```python
class Invoice(BaseModel):
    customer: str
    line_items: list[LineItem]
    total_usd: Decimal
```

エージェントフレームワークはエッジでスキーマをOpenAIストリクトモード、Anthropicの`input_schema`、またはGeminiの`responseSchema`に変換します。モデルの出力は型付きの`Invoice`インスタンスとして返ってきます。検証エラーは型付きエラーパスで`ValidationError`を発生させます。

### Zod、TypeScriptバインディング

Zod（`z.object({customer: z.string(), ...)}`）はTSの同等品です。OpenAIのNode SDKは`zodResponseFormat(Invoice)`を公開し、これをAPIのJSONスキーマペイロードに変換します。

### 拒否

ストリクトモードはモデルに回答を強制できません。入力がスキーマに合わない場合（「メールが詩で、請求書ではなかった」）、モデルは理由を含む`refusal`フィールドを出力します。あなたのコードはこれを失敗ではなく一級の結果として処理しなければなりません。拒否は安全シグナルとしても役立ちます：保護されたコンテンツのメールからクレジットカード番号を抽出するよう依頼されたモデルは、安全の理由が添付された拒否を返します。

### オープンウェイツでの制約付きデコーディング

オープンウェイツの実装は3つの技法を使います。

1. **文法ベースデコーディング**（`outlines`、`guidance`、`lm-format-enforcer`）：スキーマから確定有限オートマトンを構築；ステップごとにFSMに違反するトークンのロジットをマスク。
2. **JSONパーサを使ったロジットマスキング**：ストリーミングJSONパーサをモデルとロックステップで実行；ステップごとに有効な次のトークンセットを計算。
3. **ベリファイア付き投機的デコーディング**：安価なドラフトモデルがトークンを提案し、ベリファイアがスキーマを強制。

商用プロバイダはこれらのうち1つを内部で選びます。2026年の最先端は短い構造化出力では通常の生成より速く、長いものではほぼ同じ速さです。

### 3つの失敗モード

1. **パースエラー。** 出力が有効なJSONではない。ストリクトモードでは起こり得ない。非ストリクトプロバイダでは依然として起こる可能性がある。
2. **スキーマ違反。** 出力はパースされるがスキーマに違反する。ストリクトモードでは起こり得ない。ストリクト以外では一般的。
3. **拒否。** モデルが拒否する。型付き結果として処理しなければならない。

### 再試行戦略

ストリクトモードの外（AnthropicのツールUse、非ストリクトのOpenAI、古いGemini）の場合の回復パターン：

```
generate -> parse -> validate -> if fail, inject error and retry, max 3x
```

通常1回の再試行で十分です。3回の再試行は弱いモデルのフレークをキャッチします。3回を超えるのは悪いスキーマのサインです：モデルは一部の入力でそれを満たすことができず、プロンプトまたはスキーマを修正する必要があります。

### 小型モデルのサポート

制約付きデコーディングは小型モデルで機能します。文法強制ありの30億パラメータのオープンモデルは、構造化タスクでは生の促しありの700億パラメータモデルよりも優れています。これが本番で構造化出力が重要な主な理由です：信頼性をモデルサイズから切り離します。

## 使ってみる

`code/main.py`には標準ライブラリで書かれた最小限のJSON Schema 2020-12バリデータ（型、required、enum、min/max、pattern、items、additionalProperties）が付属しています。`Invoice`スキーマをラップし、偽のLLM出力をバリデータに通して、パースエラー、スキーマ違反、拒否パスを示します。本番では偽の出力をプロバイダの実際のレスポンスに置き換えます。

確認すべき点：

- バリデータはパスとメッセージを持つ型付き`[ValidationError]`リストを返します。それが再試行プロンプトに表示したい形です。
- 拒否ブランチは再試行しません。ログに記録して型付き拒否を返します。Phase 14 · 09は拒否を安全シグナルとして使います。
- `additionalProperties: false`チェックが敵対的なテスト入力で発火し、ストリクトモードが誤って生成されたフィールドへの扉を閉じることを示します。

## 成果物を出す

このレッスンは`outputs/skill-structured-output-designer.md`を生成します。自由テキスト抽出ターゲット（請求書、サポートチケット、履歴書など）を受け取り、ストリクトモード互換のJSON Schema 2020-12と、型付き拒否および再試行処理をスタブ化したそれをミラーするPydanticモデルを生成します。

## 演習

1. `code/main.py`を実行します。`total_usd`が負の数の4番目のテストケースを追加します。バリデータが`minimum`制約パスで拒否することを確認します。

2. バリデータを拡張して識別子付きの`oneOf`をサポートします。一般的なケース：`line_item`は`kind`でタグ付けされた製品またはサービスのいずれかです。ストリクトモードにはここで微妙なルールがあります；OpenAIの構造化出力ガイドを確認してください。

3. 同じInvoiceスキーマをPydantic BaseModelとして書き、`model_json_schema()`の出力を手作りのスキーマと比較します。Pydanticがデフォルトで設定する、手作りバージョンが省略している1つのフィールドを特定します。

4. 拒否率を測定します。抽出できないはずの10の入力（歌の歌詞、数学の証明、空のメール）を構築し、ストリクトモードで実際のプロバイダに通します。拒否対ハルシネーション出力をカウントします。これが拒否を考慮した再試行のグランドトゥルースです。

5. OpenAIの構造化出力ガイドを最初から最後まで読みます。ストリクトモードで明示的に禁止している、普通のJSON Schemaが許可している1つの構造を特定します。次にその禁止された構造を本質的でない形で使うスキーマを設計し、ストリクト互換にリファクタリングします。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| JSON Schema 2020-12 | 「スキーマ仕様」 | 現代のプロバイダが使うIETFドラフトスキーマ仕様 |
| ストリクトモード | 「スキーマ保証」 | 制約付きデコーディングでスキーマを強制するOpenAIフラグ |
| 制約付きデコーディング | 「ロジットマスキング」 | 無効な次のトークンをマスクするデコード時強制 |
| Refusal | 「モデルの拒否」 | 入力がスキーマに合わない場合の型付き結果 |
| パースエラー | 「無効JSON」 | 出力がJSONとしてパースできなかった；ストリクトでは不可能 |
| スキーマ違反 | 「形式が違う」 | パースされたが型/required/enum/範囲に違反 |
| `additionalProperties: false` | 「余分なフィールド禁止」 | 未知のフィールドを禁止；OpenAIストリクトで必須 |
| Pydantic BaseModel | 「型付き出力」 | JSON Schemaを出力して検証するPythonクラス |
| Zodスキーマ | 「TypeScriptの出力型」 | プロバイダ出力検証のためのTSランタイムスキーマ |
| 文法強制 | 「オープンウェイツ制約デコード」 | outlines / guidanceのようなFSMベースのロジットマスキング |
