# MCPクライアントの構築 — 発見、呼び出し、セッション管理

> MCPコンテンツのほとんどはサーバーのチュートリアルを出荷して、クライアントについては軽く触れるだけです。難しいオーケストレーションはクライアントコードにあります：プロセス起動、ケイパビリティネゴシエーション、複数サーバーをまたいだツールリストのマージ、samplingコールバック、再接続、名前空間の衝突解決。このレッスンでは、3つの異なるMCPサーバーをモデルのための1つのフラットなツール名前空間にリフトするマルチサーバークライアントを構築します。


## 学習目標

- MCPサーバーを子プロセスとして起動し、`initialize`を完了し、`notifications/initialized`を送れる。
- サーバーごとのセッション状態（ケイパビリティ、ツールリスト、最後に見た通知ID）を維持できる。
- 複数のサーバーのツールリストを衝突処理付きで1つの名前空間にマージできる。
- ツール呼び出しをそれを所有するサーバーにルーティングし、レスポンスを再組み立てできる。

## 問題

実際のエージェントホスト（Claude Desktop、Cursor、Goose、Gemini CLI）は複数のMCPサーバーを同時にロードします。ユーザーはファイルシステムサーバー、Postgresサーバー、GitHubサーバーを同時に実行しているかもしれません。クライアントの仕事：

1. 各サーバーを起動する。
2. 各々に独立してハンドシェイクする。
3. 各々に`tools/list`を呼び出して結果をフラット化する。
4. モデルが`notes_search`を出力したら、マージされた名前空間でそれを検索し、正しいサーバーにルーティングする。
5. 通知を任意のサーバーから（`tools/list_changed`）ブロッキングなしに処理する。
6. トランスポート障害時に再接続する。

これらすべてを手作りすることが「おもちゃ」と「使えるもの」を分けます。公式SDKはこれをラップしていますが、メンタルモデルはあなた自身のものでなければなりません。

## 概念

### 子プロセスの起動

`stdin=PIPE, stdout=PIPE, stderr=PIPE`を使った`subprocess.Popen`。行ごとの読み取りには`bufsize=1`を設定してテキストモードを使います。各サーバーが1つのプロセスです；クライアントはサーバーごとに1つの`Popen`ハンドルを保持します。

### サーバーごとのセッション状態

サーバーごとの`Session`オブジェクトには以下が含まれます：

- `process` — Popenハンドル。
- `capabilities` — サーバーが`initialize`で宣言したもの。
- `tools` — 最後の`tools/list`の結果。
- `pending` — レスポンスを待つプロミス/フューチャーへのリクエストIDのマップ。

リクエストは本質的に非同期です；サーバーAに送った`tools/call`は、サーバーBが呼び出し中であってもブロックしてはなりません。スレッドとキューを使うか、asyncioを使います。

### マージされた名前空間

クライアントが集計ツールリストを確認するとき、名前が衝突することがあります。2つのサーバーが両方とも`search`を公開するかもしれません。クライアントには3つの選択肢があります：

1. **サーバー名でプレフィクス。** `notes/search`、`files/search`。明確だが見た目が悪い。
2. **先着順で上書き。** 後のサーバーの`search`が前のものを上書きします。危険；衝突を隠す。
3. **衝突の拒否。** 2番目のサーバーのロードを拒否し、ユーザーに通知します。セキュリティに敏感なホストには最も安全。

Claude Desktopはサーバー名プレフィクスを使います。Cursorは明確なエラーで衝突を拒否します。VS CodeのMCPもサーバー名プレフィクスを採用しています。

### ルーティング

マージ後、ディスパッチテーブルが`tool_name -> session`にマップします。モデルは名前で呼び出しを出力；クライアントはセッションを見つけ、そのサーバーのstdinに`tools/call`メッセージを書き込み、レスポンスを待ちます。

### samplingコールバック

サーバーが`initialize`で`sampling`ケイパビリティを宣言していれば、`sampling/createMessage`を送ってクライアントにLLMを実行するよう要求することができます。クライアントは：

1. サンプルが解決するまでそのサーバーへの追加リクエストをブロックします、またはその実装が並行性をサポートしていればパイプライン処理します。
2. LLMプロバイダを呼び出します。
3. サーバーにレスポンスを送り返します。

レッスン11ではsamplingをエンドツーエンドで説明します。このレッスンは完全性のためにスタブ化します。

### 通知処理

`notifications/tools/list_changed`は`tools/list`を再呼び出しすることを意味します。`notifications/resources/updated`は使用中のリソースを再読み取りすることを意味します。通知にレスポンスしてはいけません — ackしようとしないでください。

よくあるクライアントのバグ：ストリームに通知が積まれている間に`tools/call`で読み取りループをブロックする。すべてのメッセージをキューにプッシュするバックグラウンド読み取りスレッドを使います；メインスレッドはデキューしてディスパッチします。

### 再接続

トランスポートは失敗することがあります：サーバーがクラッシュした、OSがプロセスを終了させた、stdioパイプが壊れた。クライアントはstdoutのEOFを検出し、そのセッションを死んだものとして扱います。選択肢：

- サーバーをサイレントに再起動して再ハンドシェイクします。読み取り専用サーバーには適しています。
- ユーザーに失敗を通知します。ユーザーに見えるセッションを持つステートフルサーバーには適しています。

Phase 13 · 09ではStreamable HTTPの再接続セマンティクスを説明します；stdioはよりシンプルです。

### キープアライブとセッションID

Streamable HTTPは`Mcp-Session-Id`ヘッダーを使います。stdioにはセッションIDがありません — プロセスのアイデンティティがセッションです。キープアライブpingはオプションです；stdioパイプは非アクティブ状態では壊れません。

## 使ってみる

`code/main.py`はサブプロセスとして3つのシミュレートされたMCPサーバーを起動し、各々にハンドシェイクし、ツールリストをマージし、ツール呼び出しを正しいものにルーティングします。「サーバー」は実際にはおもちゃのレスポンダを実行する他のPythonプロセスです（実際のLLMはありません）。実行して確認します：

- 独自のケイパビリティセットを持つ3つの初期化。
- 7ツールの名前空間にマージされた3つの`tools/list`の結果。
- ツール名に基づくルーティング決定。
- 名前空間プレフィクスで防がれた衝突。

確認すべき点：

- `Session`データクラスはサーバーごとの状態をクリーンに保持します。
- バックグラウンド読み取りスレッドはメインスレッドをブロックせずにstdoutのすべての行をデキューします。
- ディスパッチテーブルはシンプルな`dict[str, Session]`です。
- 衝突処理は明示的です：2つのサーバーが同じ名前を宣言すると、後のものはプレフィクスで名前が変更されます。

## 演習

1. `code/main.py`を実行してサーバー起動ログを確認します。SIGTERMでシミュレートされたサーバープロセスの1つを終了し、クライアントがどのようにEOFを検出してそのセッションを死んだものとしてマークするかを観察します。

2. 名前空間プレフィクスを実装します。2つのサーバーが`search`を公開する場合、2番目を`<server>/search`に名前変更します。ディスパッチテーブルを更新し、ツール呼び出しが正しくルーティングされることを確認します。

3. サーバー再起動のための接続プールスタイルのバックオフを追加します：連続した失敗に対する指数バックオフ、30秒の上限、3回の失敗後にユーザーへの通知を出力します。

4. 100の並列MCPサーバーをサポートするクライアントをスケッチします。単純なディスパッチ辞書を何に置き換えますか？（ヒント：プレフィクス名前空間用のトライ、プラスサーバーごとのツール数メトリクス。）

5. クライアントを公式MCP Python SDKに移植します。SDKは`stdio_client`と`ClientSession`をラップします。コードはマルチサーバールーティングを維持しながら〜200行から〜40行に縮小すべきです。

## キーワード

| 用語 | よく言われること | 実際の意味 |
|------|----------------|------------------------|
| MCPクライアント | 「エージェントホスト」 | サーバーを起動してツール呼び出しをオーケストレートするプロセス |
| セッション | 「サーバーごとの状態」 | ケイパビリティ、ツールリスト、保留中リクエストのブックキーピング |
| マージされた名前空間 | 「1つのツールリスト」 | すべてのアクティブサーバーをまたいだツール名のフラットセット |
| 名前空間の衝突 | 「2つのサーバーが同じツール」 | クライアントはプレフィクス、拒否、または先着順にしなければならない |
| ルーティング | 「誰がこの呼び出しを受け取る？」 | ツール名から所有サーバーへのディスパッチ |
| バックグラウンドリーダー | 「非ブロッキングstdout」 | サーバーstdoutをキューにドレインするスレッドまたはタスク |
| samplingコールバック | 「サービスとしてのLLM」 | サーバーからの`sampling/createMessage`のクライアントハンドラ |
| `notifications/*_changed` | 「プリミティブが変更された」 | クライアントが再発見または再読み取りしなければならないシグナル |
| 再接続ポリシー | 「サーバーが死んだとき」 | トランスポートが失敗した場合の再起動セマンティクス |
| stdioセッション | 「プロセス=セッション」 | セッションIDなし；子プロセスのライフタイムがセッション |
