# MCPセキュリティ II — OAuth 2.1、リソースインジケーター、インクリメンタルスコープ

> リモートMCPサーバーには認証だけでなく認可が必要だ。2025年11月25日の仕様はOAuth 2.1 + PKCE + リソースインジケーター（RFC 8707）+ 保護リソースメタデータ（RFC 9728）に対応している。SEP-835は403 WWW-Authenticateによるステップアップ認可でインクリメンタルなスコープ同意を追加した。このレッスンではステップアップフローをステートマシンとして実装し、すべてのホップを確認できるようにする。


## 学習目標

- リソースサーバーと認可サーバーの責任を区別できる。
- PKCEで保護されたOAuth 2.1認可コードフローを把握できる。
- Confused-deputy攻撃を防ぐために `resource`（RFC 8707）と保護リソースメタデータ（RFC 9728）を使用できる。
- ステップアップ認可を実装できる：サーバーが403とWWW-Authenticateで上位スコープを要求し、クライアントがユーザーの同意を再度求めてリトライする。

## 問題背景

初期のMCP（2025年以前）はアドホックなAPIキーや認証なしでリモートサーバーを出荷していた。2025年11月25日の仕様はOAuth 2.1プロファイルでこのギャップを埋めた。

3つの実際のニーズ：

- **通常のリモートサーバー。** ユーザーがNotion / GitHub / Gmailにアクセスするリモートサーバーをインストールする。OAuth 2.1とPKCEが適切な形だ。
- **スコープエスカレーション。** `notes:read` が付与されたノートサーバーが特定のアクションで `notes:write` が必要になる場合がある。フロー全体をやり直す代わりに、ステップアップ（SEP-835）で追加スコープを要求する。
- **Confused deputy防止。** クライアントがサーバーAのトークンを持っている。サーバーAが悪意を持ち、そのトークンをサーバーBに提示しようとする。リソースインジケーター（RFC 8707）がトークンを対象オーディエンスにピン留めする。

OAuth 2.1は新しくない。新しいのはMCPのプロファイル：特定の必須フロー（認可コード + PKCEのみ；暗黙なし、クライアントクレデンシャルはデフォルトなし）、すべてのトークンリクエストでリソースインジケーターが必須、クライアントが認証先を知るための保護リソースメタデータの公開だ。

## コンセプト

### ロール

- **クライアント。** MCPクライアント（Claude Desktop、Cursorなど）。
- **リソースサーバー。** MCPサーバー（ノート、GitHub、Postgresなど）。
- **認可サーバー。** トークンを発行する。リソースサーバーと同じサービスでも別のIdP（Auth0、Keycloak、Cognito）でもよい。

MCPのプロファイルでは、リソースと認可サーバーは同じホストでもよいが、URLで区別すべきだ。

### 認可コード + PKCE

フロー：

1. クライアントが `code_verifier`（ランダム）と `code_challenge`（SHA256）を生成する。
2. クライアントがユーザーを `/authorize?response_type=code&client_id=...&redirect_uri=...&scope=notes:read&code_challenge=...&resource=https://notes.example.com` にリダイレクトする。
3. ユーザーが同意する。認可サーバーが `redirect_uri?code=...` にリダイレクトする。
4. クライアントが `/token?grant_type=authorization_code&code=...&code_verifier=...&resource=...` にPOSTする。
5. 認可サーバーがベリファイアのハッシュを保存されたチャレンジと照合し、アクセストークンを発行する。
6. クライアントがトークンを使用：リソースサーバーへのすべてのリクエストに `Authorization: Bearer ...` を付ける。

PKCEが認可コードの傍受攻撃を防ぐ。リソースインジケーターがトークンが他の場所で有効にならないようにする。

### 保護リソースメタデータ（RFC 9728）

リソースサーバーが `.well-known/oauth-protected-resource` ドキュメントを公開する：

```json
{
  "resource": "https://notes.example.com",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["notes:read", "notes:write", "notes:delete"]
}
```

クライアントがリソースサーバーから認可サーバーを発見する。設定が減る — クライアントはリソースURLだけ知ればよい。

### リソースインジケーター（RFC 8707）

トークンリクエストの `resource` パラメーターがトークンの対象オーディエンスをピン留めする。発行されたトークンには `aud: "https://notes.example.com"` が含まれる。このトークンを受け取った別のMCPサーバーは `aud` を確認して拒否する。

### スコープモデル

スコープはスペース区切りの文字列だ。一般的なMCPの慣例：

- `notes:read`、`notes:write`、`notes:delete`
- `admin:*`（管理機能用、控えめに使用）
- `profile:read`（アイデンティティ用）

スコープの選択は最小権限であるべき：今必要なものをリクエストし、必要になったらステップアップする。

### ステップアップ認可（SEP-835）

ユーザーが `notes:read` を付与する。後でエージェントにノートの削除を依頼する。サーバーが応答する：

```
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
    scope="notes:delete", resource="https://notes.example.com"
```

クライアントが insufficient_scope エラーを確認し、追加スコープの同意ダイアログをユーザーに表示し、そのためのミニOAuthフローを実行し、新しいトークンでリクエストをリトライする。

### トークンオーディエンス検証

すべてのリクエストで：サーバーが `token.aud == self.resource_url` を確認する。不一致 = 401。これがクロスサーバーのトークン再利用を防ぐ。

### 短命トークンとローテーション

アクセストークンは短命であるべきだ（デフォルト1時間）。リフレッシュトークンはすべてのリフレッシュ時にローテーションされる。クライアントがバックグラウンドでサイレントリフレッシュを処理する。

### トークンパススルーなし

サンプリングサーバー（フェーズ13・11）はクライアントのトークンを他のサービスにパススルーしてはならない。サンプリングリクエストが境界となる。

### Confused deputy防止

トークンが `aud` にバインドされる。クライアントが `client_id` にバインドされる。すべてのリクエストが両方に対して検証される。仕様はMCP以前のリモートツールエコシステムで一般的だった古い「トークンパス」パターンを明示的に禁止している。

### クライアントID発見

各MCPクライアントが固定URLにメタデータを公開する。認可サーバーはリダイレクトURIと連絡先情報を発見するためにクライアントのメタデータドキュメントを取得できる。手動のクライアント登録が不要になる。

### ゲートウェイとOAuth

フェーズ13・17では企業ゲートウェイがOAuthを処理する方法を示す：ゲートウェイがアップストリームサーバーの認証情報を保持し、クライアントへのトークンはゲートウェイが発行し、アップストリームのトークンはゲートウェイの外に出ない。信頼モデルが逆転する — ユーザーはゲートウェイで一度認証し、ゲートウェイがN個のサーバー認可を処理する。

## 使ってみる

`code/main.py` はOAuth 2.1のステップアップフロー全体をステートマシンとしてシミュレートする。以下を実装している：

- PKCEのコードベリファイア / チャレンジ生成。
- リソースインジケーター付きの認可コードフロー。
- 保護リソースメタデータエンドポイント。
- オーディエンスチェック付きのトークン検証。
- `insufficient_scope` 時のステップアップ。

このレッスンではHTTPサーバーなし；ステートマシンはメモリ内で動作するので、すべてのホップをトレースできる。フェーズ13・17のゲートウェイレッスンで実際のトランスポートに接続する。

## 成果物を出す

このレッスンでは `outputs/skill-oauth-scope-planner.md` を生成する。ツールを持つリモートMCPサーバーが与えられると、このスキルはスコープセット、ピンのルール、ステップアップポリシーを設計する。

## 演習

1. `code/main.py` を実行する。2スコープのステップアップフローをトレースする。ステップアップ時にどのホップが繰り返されるかを確認する。

2. リフレッシュトークンのローテーションを追加する：すべてのリフレッシュで新しいリフレッシュトークンを発行し、古いものを無効にする。ローテーション後に盗まれたリフレッシュトークンが使われた場合をシミュレートし、失敗することを確認する。

3. 保護リソースメタデータエンドポイントをstdlib http.serverを使って実際のHTTPレスポンスとして実装する。Lesson 09の/mcpエンドポイントを参考に。

4. GitHubのMCPサーバーのスコープ階層を設計する：リポジトリ読み取り、PRの書き込み、PRの承認、PRのマージ、管理。各レベル間でステップアップを使用する。

5. RFC 8707とRFC 9728を読む。MCPが9728のRFC例とは異なる方法で使用しているフィールドを1つ特定する。（ヒント：`scopes_supported` に関係する。）

## キーワード

| 用語 | よく言われる表現 | 実際の意味 |
|------|----------------|------------------------|
| OAuth 2.1 | "モダンOAuth" | PKCEを義務付けて暗黙フローを禁止した統合RFC |
| PKCE | "所有証明" | 認可コード傍受を防ぐコードベリファイア + チャレンジ |
| リソースインジケーター | "トークンオーディエンス" | トークンを1つのサーバーにピン留めするRFC 8707 `resource` パラメーター |
| 保護リソースメタデータ | "ディスカバリードキュメント" | RFC 9728 `.well-known/oauth-protected-resource` |
| ステップアップ認可 | "インクリメンタルな同意" | オンデマンドでスコープを追加するSEP-835フロー |
| `insufficient_scope` | "WWW-Authenticateを含む403" | より大きなスコープに再同意するためのサーバーシグナル |
| Confused deputy | "サービスをまたいだトークン再利用" | 信頼された保持者が不適切にトークンを転送する攻撃 |
| 短命トークン | "アクセストークンのTTL" | すぐに期限切れになるベアラー；リフレッシュトークンで更新 |
| スコープ階層 | "最小権限スタック" | レベル間のステップアップを持つ段階的なスコープセット |
| クライアントIDメタデータ | "クライアントディスカバリードキュメント" | クライアントが自身のOAuthメタデータを公開するURL |
