# 非同期とHogwild!推論

> 投機的デコーディング（Phase 10・15）は1つのシーケンス内でトークンを並列化する。マルチエージェントフレームワークはシーケンス全体にわたって並列化するが、明示的な調整（投票、サブタスク分割）を強制する。Hogwild!推論（Rodionov et al.、arXiv:2504.06261）は別のことをする：同じLLMのN個のインスタンスを**共有**キーバリューキャッシュに対して並列で実行する。各ワーカーは他のワーカーが生成したトークンを即座に見ることができる。現代の推論モデル——QwQ、DeepSeek-R1——は任意の微調整なしにその共有キャッシュを通じて自己調整できる。このアプローチは実験的だが、投機的デコーディングと直交する推論並列処理の全く新しい軸を開く。このレッスンはstdlib Pythonで2ワーカーのHogwild!シミュレーターを実装し、なぜ共有キャッシュの協調が既存モデルの推論能力から自然発生するかを説明する。


## 学習目標

- 3つの一般的な並列LLMトポロジー（投票、サブタスク、Hogwild!）を説明し、それぞれがどの問題をターゲットとするかを挙げる。
- コアのHogwild!セットアップを述べる：複数のワーカー、1つの共有KVキャッシュ、自己プロンプティングを通じた自然発生的な調整。
- ワーカー数`N`、タスクレベルの並列性`p`、調整オーバーヘッド`c`の関数としてHogwild!の実行時間スピードアップを計算する。
- おもちゃの問題で2ワーカーのHogwild!シミュレーターを実装し、自然発生的なタスク分担を観察する。

## 課題

現代のLLMは長い推論チェーンを生成して難しい問題を解く——5000トークンのステップバイステップのロジックは一般的で、深い数学の問題では数万トークンになる。70Bモデルでの35トークン/秒のデコードでは、50kトークンは24分になる。とてもインタラクティブとは言えない。

投機的デコーディング（Phase 10・15）は3〜5倍のスピードアップを与えてシーケンス内を並列化する。その先では自己回帰デコーディングの逐次依存性が難しい上限だ。各新しいトークンはすべての前のトークンに依存する。

明白な質問：シーケンスを並列化できるか？同じモデルの複数のコピーを同じ問題で実行し、協力させ、仕事を分担させることができるか？

先行研究：投票アンサンブル（Nモデルを実行し、多数決で答えを選ぶ）、思考のツリー（推論パスを分岐して再結合する）、マルチエージェントフレームワーク（各エージェントにサブタスクを割り当て、コーディネーターを使用する）。これらはすべて特定のタスクドメインで役立つ。またすべて明示的な調整機構を導入する——投票ルール、分岐と剪定のロジック、エージェント間のメッセージングプロトコル。

Hogwild!推論は異なるアプローチを取る。Nワーカーが単一のKVキャッシュを共有する。各ワーカーは他のワーカーが生成したトークンを、まるで自分のコンテキストであるかのように即座に見る。ワーカーたちは——任意の学習や微調整なしに——仕事を分担する方法を見つける。現代の推論モデル（QwQ、DeepSeek-R1、Claudeファミリーの推論モード）は共有キャッシュを読んで「ワーカー2がすでにベースケースを処理したので、私は帰納法のステップを担当する」などと言える。

スピードアップはワークロードに依存し、2026年4月時点では実験的だ。しかしこのアイデアは推論並列処理の新しい軸を開くため知っておく価値がある。

## コンセプト

### セットアップ

N個のワーカープロセスを初期化し、すべてが同じLLMを実行する。ワーカーごとのKVキャッシュの代わりに、1つの共有キャッシュを維持する。ワーカー`i`がトークン`t_j`を生成すると、トークンは次の位置で共有キャッシュに書き込まれる。ワーカー`k`が次のステップを取ると、現在の状態のキャッシュを読む（すべてのNワーカーがこれまでに生成したすべてを含む）。

ステップ時間では、ワーカーはトークンを書き込むために競走する。ワーカーごとの位置インデックスはない——キャッシュは単一の成長するシーケンスだ。順序は書き込みの到着時間によって決まる。

### なぜ調整が自然発生するのか

ワーカーはプロンプトを共有する。通常は「あなたはこの問題に取り組むN個のインスタンスのうちの1つです。各インスタンスは共有メモリを読み、他のインスタンスが書いたものを見ることができます。冗長な作業を避けてください」のようなもの。プロンプトと共有キャッシュで十分だ。推論モデルはキャッシュを読み、問題のどの部分がすでに試みられているかに気づき、（常にではないが多くの場合）未探索の部分に転換する。

Hogwild!の論文（Rodionov et al.、2025）は以下のような観察を報告する：

- ワーカーが計画を立案し、キャッシュを通じて他のワーカーに伝達する。
- ワーカーが他のワーカーの推論の誤りに気づいてそれを指摘する。
- 計画が失敗すると適応して代替案を提案する。
- 冗長性をチェックするよう促されると、ワーカーはそれを検出して転換する。

これらはすべて微調整を必要としない。自然発生的な動作はモデルがすでに持っている推論能力から来る。

### 命名

論文の名前はHogwild! SGD（Recht et al.、2011）をもじったものだ。類比：SGDの非同期ワーカーはすべて共有パラメータベクトルに書き込む；Hogwild!推論のワーカーはすべて共有KVキャッシュに書き込む。両方とも同期の保証ではなく経験的な収束に依存する。

### RoPEがこれを実行可能にする

Rotary Position Embeddings（RoPE、Su et al. 2021）は回転によってQとKベクトルに位置情報をエンコードする。位置は回転であり組み込みのオフセットではないため、トークンの位置はKVキャッシュエントリを再計算することなく変えられる。ワーカー`i`が位置`p`で共有キャッシュに書き込むと、その位置を読む他のワーカーはキャッシュされたエントリを直接使用できる——再回転不要。

学習済み位置または絶対位置モデルでは、Hogwild!はすべての並行書き込みでキャッシュの無効化が必要になる。RoPEはキャッシュを安定させる。

### 実行時間の数学

`T_serial`を1ワーカーが単独で問題を解く時間とする。`p`をタスクレベルの並列化可能な割合とする。`c`をステップあたりの調整オーバーヘッド（拡張されたキャッシュの読み込み、何を書き込むかの決定）とする。

シングルワーカー時間：`T_serial`。
調整が無料のN-ワーカーのHogwild!時間：`T_serial * ((1 - p) + p / N)`。古典的なAmdahl。
調整オーバーヘッドあり：`T_serial * ((1 - p) + p / N) + c * steps_per_worker`。

ワーカーが生産的であるためには、`c`がステップあたりのデコード時間に対して小さくなければならない。5k以上のトークンを生成する推論モデルでは、ワーカーは数百トークンの調整オーバーヘッドを許容してまだ先に進める。短いチャットタスクでは、調整が支配してHogwild!はシリアルより悪い。

### 具体的な例

推論問題：10kトークンの思考の連鎖。問題に`p = 0.7`の並列化可能な内容（異なる証明戦略、異なるケース分析）と、ワーカーあたり`c = 200`トークンの調整オーバーヘッドがあるとする。`N = 4`ワーカーの場合：

- シリアル時間：10000デコードステップ。
- Hogwild!時間：10000 * (0.3 + 0.7 / 4) + 200 * 4 = 10000 * 0.475 + 800 = 5550デコードステップ。
- スピードアップ：10000 / 5550 = 1.8倍。

控えめだ。しかし長い推論問題（50kトークン）では、調整オーバーヘッドが償却されてスピードアップは2.5〜3倍まで高まる。Hogwild!は自然にマルチスレッドのコードを書ける言語でのスレッドレベルの並列処理と推論の等価物だ。

### Hogwild!を使うべき場面

- 独立したサブゴールにわたってタスクを並列化できる長い推論問題（数千トークン）。
- ステップバイステップで考えるよう学習された推論モデル。非推論モデルは自己調整がうまくできない。
- 共有キャッシュとNワーカープロセスを保持するのに十分なVRAMを持つシングルノードデプロイメント。キャッシュは共有されるが、各ワーカーは独自のアクティベーションメモリを持つ。

### 使うべきでない場面

- 短いインタラクティブチャット。調整オーバーヘッドが支配する。
- 並列化できないタスク（単一の線形証明、単一のコンパイル）。N=1が最大だ。
- 非推論モデル。調整が自然発生しない。
- マルチノードデプロイメント。共有キャッシュは非常に高速なクロスワーカー同期が必要だ。ノード内は問題ない；クロスノードはレイテンシの悪夢だ。

### 実験的な状況

2026年4月時点で、Hogwild!はオープンソースのPyTorch実装を持つ研究手法だ。本番採用はまだ起きていない。3つの障壁：

1. 並行プロセス間での共有KVキャッシュ管理は簡単ではないエンジニアリングだ。
2. 自然発生的な調整はタスク依存；ベンチマークはまだ構築中だ。
3. スピードアップは投機的デコーディングがすでに提供するものに比べて控えめで、2つを組み合わせることができるが、組み合わされたエンジニアリングはもう一つのレイヤーだ。

知っておく価値がある。実験する価値がある。まだプロダクトを賭ける価値はない。

## 実装する

`code/main.py`はおもちゃのHogwild!シミュレーターを実装する：

- 2つのワーカープロセス、それぞれが既知の確率でいくつかのトークンカテゴリ（ワークトークン、観察トークン、調整トークン）の1つを生成する決定論的な「LLM」。
- 両方のワーカーが読み書きする共有キャッシュ（単なるトークンのリスト）。
- シンプルな調整ロジック：ワーカーが他のワーカーがすでにあるカテゴリで十分なワークトークンを生成したことを見ると、異なるカテゴリを選ぶ。

シミュレーターは固定ステップバジェットで実行し、以下を報告する：

- 生成された総ワークトークン。
- 総実行時間（ワーカーステップ数）。
- シングルワーカーに対する有効なスピードアップ。
- どのワーカーがどのトークンを書いたかのトレース。

### ステップ1：共有キャッシュ

両方のワーカーが追加するリスト。実際の実装ではシンプルなロッキング（Python `threading.Lock`）；カウンターでシミュレートする。

### ステップ2：ワーカーループ

各ワーカーは各ステップで：

- 現在の共有キャッシュを読む。
- すでにそこにあるものに基づいてどのカテゴリのトークンを書くかを決定する。
- 1つのトークンを書く。

### ステップ3：調整ヒューリスティック

カテゴリXがキャッシュにすでにKトークンあり、ワーカーの意図するカテゴリがXの場合、ワーカーはカテゴリYに切り替える。これは「これはすでにカバーされている、他のことをする」という推論モデルの動作のおもちゃ版だ。

### ステップ4：測定されたスピードアップ

N=1ワーカーとN=2ワーカー、同じ総ステップバジェットでシミュレーターを実行する。生成されたワークトークンを数える。N=2は調整駆動のタスク分担のため、約1.5〜1.8倍多くのワークトークンを生成するはずだ。

### ステップ5：調整のストレスをかける

調整ヒューリスティックの感度を減らす。再実行する。良い調整なしでは、N=2が同じトークンを冗長に生成し、スピードアップが1を下回ることを観察する。これは論文の観察と一致する：トリックは、ワーカーが自己調整できる推論能力を持つ場合にのみ機能する。

## 使ってみる

2026年4月時点での本番でのHogwild!統合は研究グレードだ。Yandex/HSE/ISTからのリファレンス実装はPyTorachベースで、DeepSeek-R1とQwQモデルのシングルノードマルチプロセスセットアップをターゲットとする。

実践的な採用パス：

1. 推論タスクのワークロードをプロファイルする。探索的なトークン（複数の戦略、ケース分析、検索）と線形のトークンの割合を測定する。
2. 探索が支配する場合、2ワーカーのHogwild!実験を実行する。実行時間の改善を測定する。
3. 改善が1.3倍を下回る場合、調整支配のレジームにいる。シングルワーカーに戻す。
4. 改善が1.5倍を超える場合、N=4に押し上げてもう一度測定する。通常N=4〜8あたりで収益が逓減する。

投機的デコーディングと組み合わせる：各Hogwild!ワーカーは独立して投機的デコーディングを使用できる。2つのスピードアップは（大まかに）乗算され、3倍の投機的デコーディングと1.8倍のHogwild!はナイーブなシングルワーカーデコーディングに対して実効5.4倍になる。

## 成果物を出す

このレッスンは`outputs/skill-parallel-inference-router.md`を生成する。推論ワークロードプロファイル（トークン予算、タスク並列性プロファイル、モデルファミリー、デプロイメントターゲット）が与えられると、投票、思考のツリー、マルチエージェント、Hogwild!、投機的デコーディングの戦略間でルーティングする。

## 演習

1. デフォルト設定で`code/main.py`を実行する。N=2のHogwild!設定が同じ実行時間でN=1のベースラインより多くのワークトークンを生成することを確認する。

2. 調整ヒューリスティックの強さを下げる（`coordination_weight=0.1`を設定）。再実行する。スピードアップが崩壊することを示す。理由を説明する：調整できないとワーカーは重複した努力をする。

3. `p=0.8, c=500`、N=4ワーカーの50kトークン推論タスクの期待されるHogwild!スピードアップを計算する。`p=0.3, c=200`、N=4の1kトークンチャットタスクについて同様に計算する。なぜ一方が勝利でもう一方が損失なのか？

4. Hogwild!の論文のセクション4（予備的評価）を読む。著者が報告する2つの障害モードを特定する。より良い調整プロンプトが各障害モードをどのように軽減できるかを説明する。

5. Hogwild!をおもちゃで投機的デコーディングと組み合わせる：各ワーカーが内部的に2トークンの投機的デコーディングを使用する。乗算されたスピードアップを報告する。2つのワーカーが両方とも同じ共有キャッシュプレフィックスを拡張したいとき、どのようなブックキーピングの問題が生じるか？

## キーワード

| 用語 | 人々が言うこと | 実際の意味 |
|------|----------------|-----------|
| Hogwild! | 「並列ワーカー、共有キャッシュ」 | 1つの共有KVキャッシュで並行して実行する同じLLMのN個のインスタンス；自己プロンプティングを通じた自然発生的な調整 |
| 共有KVキャッシュ | 「調整の媒体」 | すべてのワーカーが読み書きする単一の成長するKVバッファ；ワーカー間でのトークンの即座の可視性を可能にする |
| 自然発生的な調整 | 「学習不要」 | 推論能力のあるLLMは共有キャッシュを読んで、任意の微調整や明示的なプロトコルなしに仕事を分担できる |
| 調整オーバーヘッド（c） | 「方向を定めるのに費やすトークン」 | 拡張されたキャッシュを読んで何をするかを決定するワーカーごとのコスト；総デコード時間に対して小さくなければならない |
| 並列化可能な割合（p） | 「並列で実行できるもの」 | タスクレベルの並列性：本質的に逐次でない総作業の割合 |
| RoPEがHogwild!を可能にする | 「回転位置はシフト不変」 | 位置が回転であるため、共有キャッシュへの書き込みは以前のトークンの再計算を必要としない |
| 投票アンサンブル | 「Nを実行し、多数決で選ぶ」 | 最もシンプルな並列推論トポロジー；分類には有用、長文推論には少ない |
| 思考のツリー | 「分岐と剪定」 | 複数のブランチを探索して剪定する推論戦略；明示的な調整ロジック |
| マルチエージェントフレームワーク | 「サブタスクを割り当てる」 | 各エージェントが役割を持ち；コーディネーターが調整する；重いプロトコルオーバーヘッド |
