# 音声生成

> 音声は16〜48kHzの1次元信号だ。5秒のクリップは8万〜24万サンプルだ。どのTransformerもそのシーケンスに直接アテンドしない。2026年のすべてのプロダクション音声モデルの解決策は同じだ：ニューラルコーデック（Encodec、SoundStream、DAC）が音声を50〜75Hzの離散トークンに圧縮し、TransformerまたはDiffusionモデルがトークンを生成する。


## 問題

3つの音声生成タスク：

1. **テキスト→音声。** テキストが与えられ、音声を生成する。クリーンな音声は狭帯域でフォネティック構造が強い——Transformer-over-tokensでうまく解決される。VALL-E（Microsoft）、NaturalSpeech 3、ElevenLabs、OpenAI TTS。
2. **音楽生成。** プロンプト（テキスト、メロディー、コード進行、ジャンル）が与えられ、音楽を生成する。分布がはるかに広い。MusicGen（Meta）、Stable Audio 2.5、Suno v4、Udio、Riffusion。
3. **音声エフェクト / サウンドデザイン。** プロンプトが与えられ、アンビエントサウンドまたはフォーリーを生成する。AudioGen、AudioLDM 2、Stable Audio Open。

3つはすべて同じ基盤で動く：ニューラル音声コーデック＋トークンARまたはDiffusionジェネレータ。

### ニューラル音声コーデック

Encodec（Meta、2022）、SoundStream（Google、2021）、Descript Audio Codec（DAC、2023）。畳み込みエンコーダが波形をタイムステップごとのベクトルに圧縮し；残差ベクトル量子化（RVQ）が各ベクトルをK個のコードブックインデックスのカスケードに変換する。デコーダが逆変換する。75Hzで8つのRVQコードブックを使用した24kHz音声の2kbps = 600トークン/秒。

```
waveform (16000 samples/sec)
    └─ encoder conv ─┐
                     ├─ RVQ layer 1 → indices at 75 Hz
                     ├─ RVQ layer 2 → indices at 75 Hz
                     ├─ ...
                     └─ RVQ layer 8
```

### 上に積み重ねる2つの生成パラダイム

**トークン自己回帰。** RVQトークンをシーケンスにフラット化し、デコーダのみのTransformerを実行する。MusicGenは「遅延並行」を使ってK個のコードブックストリームをストリームごとのオフセットで並列に出力する。VALL-Eはテキストプロンプト＋3秒の音声サンプルから音声トークンを生成する。

**潜在拡散。** コーデックトークンを連続的な潜在変数としてパックするか、カテゴリカル拡散でモデル化する。Stable Audio 2.5は連続的な音声潜在変数でフローマッチングを使用する。AudioLDM 2はテキスト→メル→音声拡散を使用する。

2024〜2026年のトレンド：フローマッチングは音楽で勝っている（より速い推論、よりクリーンなサンプル）一方、トークンARは自然に因果的でよくストリーミングするため音声では依然として主流だ。

## 実装する

`code/main.py` は中核的なアイデアをシミュレートする：「スタイル」が異なる2つの「音声トークン」シーケンス（スタイルAは低高トークンが交互、スタイルBは単調な傾斜）で小さな次トークンTransformerを訓練する。スタイルで条件付けしてサンプリングする。

### ステップ1：合成音声トークン

```python
def make_tokens(style, length, vocab_size, rng):
    if style == 0:  # "speech-like": alternating
        return [i % vocab_size for i in range(length)]
    # "music-like": ramp
    return [(i * 3) % vocab_size for i in range(length)]
```

### ステップ2：小さなトークン予測器を訓練する

スタイルで条件付けされたバイグラムスタイルの予測器。ポイントはパターン：コーデックトークン→クロスエントロピー訓練→自己回帰サンプリング。

### ステップ3：条件付きでサンプリングする

スタイルトークンと開始トークンが与えられ、予測分布から次のトークンをサンプリングする。20〜40トークンで続ける。

## 落とし穴

- **コーデック品質が出力品質の上限を決める。** コーデックが音を忠実に表現できなければ、ジェネレータの品質をいくら高めても無駄だ。DACが現在オープンで最高だ。
- **RVQエラーの蓄積。** 各RVQ層が前の層の残差をモデル化する。層1のエラーが伝播する。高い層で温度0でサンプリングすると役立つ。
- **音楽的構造。** 30秒のトークンは75Hzで2万以上のトークンだ。Transformerには難しい。MusicGenはスライディングウィンドウ＋プロンプト継続を使う；Stable Audioはより短いクリップ＋クロスフェーディングを使う。
- **境界でのアーティファクト。** 生成されたクリップ間のクロスフェーディングには慎重なオーバーラップ加算が必要だ。
- **クリーンデータへの飢え。** 音楽ジェネレータはライセンスされた音楽の数万時間が必要だ。Suno / UdioのRIAA訴訟（2024年）がこれを表面化させた。
- **音声クローニングの倫理。** 3秒のサンプルとテキストプロンプトでVALL-E / XTTS / ElevenLabsが声をクローンするのに十分だ。すべてのプロダクションモデルは乱用検出＋オプトアウトリストが必要だ。

## 演習

1. **易。** `code/main.py` を実行してスタイルを明示的に設定する。生成されたシーケンスがスタイルのパターンにマッチすることを確認する。
2. **中。** 遅延並行デコーディングを追加する：1ステップのオフセットを保持しなければならない2つのトークンストリームをシミュレートする。結合予測器を訓練する。
3. **難。** HuggingFace transformersを使ってローカルでMusicGen-smallを実行する。3つの異なるプロンプトで10秒クリップを生成する；スタイル順守のためA/Bテストする。

## プロダクションノート：音声はストリーミングの問題だ

音声は、ユーザーが全部一度にではなく*生成されながら*届くことを期待する唯一の出力モダリティだ。プロダクション用語でこれはTPOT（Output Tokenあたりの時間）が重要であることを意味する。ユーザーのリスニング速度が目標スループットだ——読むスピードでなく。Encodecを使って約75トークン/秒でトークン化された16kHz音声では、サーバーは再生をスムーズに保つためにユーザーごとに≥75トークン/秒を生成しなければならない。

2つのアーキテクチャ上の結果：

- **フローマッチング音声モデルは自明にはストリーミングできない。** Stable Audio 2.5とAudioCraft 2は1回のパスで固定クリップ長をレンダリングする。ストリーミングするには、クリップをチャンクし境界をオーバーラップする——スライディングウィンドウ拡散のような——コーデックARモデルと比べて100〜300msのレイテンシオーバーヘッドを追加する。

製品が「ライブ音声チャット」または「リアルタイム音楽継続」であれば、コーデックARパスを選ぶ。「送信時に30秒クリップをレンダリングする」であれば、フローマッチングが品質と総レイテンシで勝つ。
