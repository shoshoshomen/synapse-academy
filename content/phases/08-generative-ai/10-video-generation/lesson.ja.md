# 動画生成

> 画像は2次元テンソルだ。動画は3次元のものだ。理論は同じ；計算は10〜100倍困難だ。OpenAIのSora（2024年2月）は可能であることを証明した。2026年にはVeo 2、Kling 1.5、Runway Gen-3、Pika 2.0、WAN 2.2が1080pのプロダクション動画をテキストから出荷している——そしてオープンウェイトスタック（CogVideoX、HunyuanVideo、Mochi-1、WAN 2.2）は12ヶ月遅れだ。


## 問題

24fpsで10秒の1080p動画は240フレームの1920×1080×3ピクセルだ。それは1クリップあたり約1.5GBの生データだ。ピクセル空間拡散は不可能だ。必要なのは：

1. **時空間圧縮。** フレームではなく動画をエンコードして時空間パッチのシーケンスに変換するVAE。
2. **時間的コヒーレンス。** フレームは数秒間、コンテンツ、照明、オブジェクトのアイデンティティを共有する必要がある。ネットがモーションをモデル化しなければならない。
3. **計算予算。** 動画の訓練は同じモデルサイズの画像より10〜100倍コストが高い。
4. **条件付け。** テキスト、画像（最初のフレーム）、音声、または別の動画。ほとんどのプロダクションモデルは4つすべてを受け付ける。

これを解決したアーキテクチャが、大規模な（プロンプト、キャプション、動画）データセットで訓練された時空間パッチに適用された**Diffusion Transformer（DiT）**だ。同じ拡散損失（レッスン06）。

## 概念

![動画拡散：パッチ化、DiT、デコード](../assets/video-generation.svg)

### パッチ化

3D VAE（学習済み時空間圧縮）で動画をエンコードする。潜在変数の形状は `[T_latent, H_latent, W_latent, C_latent]`。`[t_p, h_p, w_p]` サイズのパッチに分割する。Soraスタイルのモデルでは `t_p = 1`（フレームごとのパッチ）または `t_p = 2`（2フレームごと）。10秒の1080p動画は約2万〜10万パッチに圧縮される。

### 時空間DiT

Transformerがパッチのフラットなシーケンスを処理する。各パッチは3D位置埋め込み（時間 + y + x）を持つ。アテンションは通常因子分解される：

- **空間アテンション**：各フレームのパッチ内で。
- **時間アテンション**：同じ空間位置の複数フレームにわたって。
- **フル3Dアテンション**：16〜100倍コストが高い；低解像度またはリサーチでのみ使用。

### テキスト条件付け

大きなテキストエンコーダとのクロスアテンション（SoraにはT5-XXL、CogVideoX-5BはT5-XXLを使用）。長いプロンプトが重要——Soraの訓練セットにはクリップあたり平均200トークンのGPT生成の密なキャプションがあった。

### 訓練

時空間潜在変数上での標準拡散損失（εまたはv予測）。データ：ウェブ動画 + 約1億の厳選クリップ + 合成テキストキャプション。計算：小さなリサーチランでも1万以上のGPU時間；Soraスケールは10万以上。

## 実装する

`code/main.py` は中核的な時空間DiTのアイデアをシミュレートする：小さな合成動画をパッチ化し、パッチごとの位置埋め込みを追加し、パッチにわたるTransformerスタイルのアテンションでシーケンス全体をデノイズする。numpyなし；純粋Python。隣接フレームのパッチがデノイザーと位置埋め込みを共有すると時間的コヒーレンスが1次元でも現れることを示す。

### ステップ1：合成1次元「動画」のパッチ化

```python
def make_video(T_frames=8, rng=None):
    # a "video" is a sequence of 1-D values following a smooth trajectory
    base = rng.gauss(0, 1)
    return [base + 0.3 * t + rng.gauss(0, 0.1) for t in range(T_frames)]
```

### ステップ2：フレームごとの位置埋め込み

```python
def pos_embed(t, dim):
    return sinusoidal(t, dim)
```

### ステップ3：デノイザーがシーケンス全体を見る

各フレームを独立してデノイズする代わりに、おもちゃのネットはすべてのフレームの値＋位置埋め込みを連結し、すべてのフレームに対してノイズを予測する。

### ステップ4：時間的コヒーレンステスト

訓練後、動画をサンプリングする。フレーム間のデルタを測定する。モデルが時間的構造を学習していれば、デルタは各フレームを独立してサンプリングするよりも小さく保たれる。

## 落とし穴

- **フレームごとの独立サンプリング = フリッカー。** 各フレームに対して独立して画像拡散を実行すると、各フレームのノイズが独立しているためフリッカーが発生する。動画拡散はアテンションまたは共有ノイズを通じてフレームを結合することでこれを修正する。
- **ナイーブな3Dアテンション = OOM。** 10秒の1080pの潜在変数上でのフル3Dアテンションは数千億の演算だ。空間＋時間に因子分解する。
- **データキャプションはサイズよりも重要だ。** SoraのQ先作業に対する主なアップグレードは、より詳細なキャプション（GPT-4が再ラベリングしたクリップ）で訓練したことだった。OpenAIの技術レポートはこれを明示している。
- **最初のフレーム条件付け。** ほとんどのプロダクションモデルは最初のフレームとして画像も受け付ける。これは「画像→動画」モード；訓練にはこのバリアントが含まれる。
- **物理的ドリフト。** 長いクリップ（>10秒）は微妙な不整合が蓄積する。スライディングウィンドウ生成＋キーフレームアンカリングが役立つ。

## プロダクションノート：動画潜在変数はメモリ帯域幅の問題だ

24fpsで10秒の1080pクリップは240フレーム × 1920 × 1080 × 3 ≈ 1.5GBの生ピクセルだ。4倍の動画VAE圧縮後（`2 × 空間 × 2 × 時間`）、潜在変数はリクエストあたり約100MBだ。これをバッチ1で30ステップ時空間DiTで実行すると、ステップごとにHBMを通じて約3GBを移動する——FLOPsではなくメモリ帯域幅がボトルネックだ。

3つのプロダクションノブ、プロダクション推論文献からそのまま：

- **DiT全体のTP。** テキスト→動画モデルは通常≥10Bパラメータ。4つのH100でTP=4が標準；405Bクラスモデルには PP=2 × TP=2。ステップごとのレイテンシはall-reduce wallまでTPと共にほぼ線形に低下する。
- **フレームバッチング = 連続バッチング。** 生成時に、動画はアテンションで結合されたフレームのバッチだと概念的に考えられる。連続バッチング（インフライトスケジューリング）が適用される：アーキテクチャが許す場合、フレーム `t-1` が返される間にフレーム `t+1` のレンダリングを開始する。
- **クリップレベルのプリフィルキャッシュ。** 画像→動画では、最初のフレーム条件付けはLLMのプロンプトプリフィルに類似している：一度計算し、時間的デコーダパス全体で再利用する。これは実質的に動画用のKVキャッシュだ。
